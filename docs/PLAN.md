# DB Studio — 개발 계획

DB 관리용 단일 바이너리 웹 앱. Go + Fiber + SQLite(메타 저장소), 프레임워크 없는 프론트엔드.

---

## 1. 기술 스택 결정

| 영역 | 선택 | 근거 |
|---|---|---|
| 웹 프레임워크 | Fiber v2 | 요구사항 |
| 메타 DB | SQLite via `modernc.org/sqlite` (Pure Go) | CGO 없이 크로스 컴파일 → 진짜 단일 바이너리 |
| 프론트엔드 | 네이티브 ES Module + 직접 작성 CSS, 번들러 없음 | 요구사항. `go:embed`로 바이너리에 포함 |
| 실시간 | `gofiber/websocket/v2` | ERD 동시 편집, 채팅, 모니터링 푸시 |
| 비밀번호 | argon2id (`golang.org/x/crypto`) | |
| 자격증명 암호화 | AES-256-GCM, 마스터 키는 env 또는 키파일 | DB 접속 정보 평문 저장 금지 |
| 세션 | 서버 사이드 세션 + HttpOnly/SameSite 쿠키 | JWT보다 즉시 무효화가 쉬움 (계정 관리 요구사항) |

### 대상 DB 드라이버 (전부 Pure Go)

| DB | 드라이버 | 상태 |
|---|---|---|
| MySQL/MariaDB | `go-sql-driver/mysql` | OK |
| PostgreSQL | `jackc/pgx/v5` | OK |
| MS-SQL | `microsoft/go-mssqldb` | OK |
| Oracle | `sijms/go-ora/v2` | OK (Oracle Instant Client 불필요) |
| SQLite | `modernc.org/sqlite` | OK |
| MongoDB | `mongodb/mongo-go-driver` | OK |
| Redis | `redis/go-redis/v9` | OK |
| **H2** | 없음 → **지원하지 않음 (결정됨)** | ⚠️ 아래 참조 |

> **H2 결정**: H2는 자체 TCP 프로토콜/JDBC만 지원하며 Pure Go 드라이버가 존재하지 않습니다.
> **지원하지 않습니다.** `kind` enum과 UI 종류 목록에서 제거했습니다 — 고를 수 없는 항목을
> 목록에 남겨두면 "왜 안 되는가"를 매번 설명해야 합니다. 향후 필요 시 옵션 JVM 사이드카로
> 추가하되, 그 경우 사이드카 없이도 앱 본체는 단독 동작하도록 유지합니다.

```
  store/        메타 SQLite: 스키마 마이그레이션, 리포지토리
    migrations/ 내장 .sql 파일
  model/        엔티티 정의
  auth/         로그인, 세션, RBAC 미들웨어, 감사로그
  api/          Fiber 라우팅 + 핸들러 (버전: /api/v1)
  dbx/          대상 DB 추상화 레이어
    adapter.go  Adapter 인터페이스

  erd/          ERD 문서, op-log, 실시간 허브, 채팅
  monitor/      폴러, 메트릭 시계열, 룰 평가, 이벤트
  dblog/        DB 로그 수집·검색·분석
  migrate/      마이그레이션 계획/승인/실행/롤백, 드리프트 감지
  vcs/          GitHub / GitLab / Bitbucket 클라이언트
  ai/           프로바이더, 툴 레지스트리, 채팅 세션
web/            embed 대상 프론트엔드
  index.html  css/  js/{core,pages,erd}

```

> 이것은 계획 단계의 구조다. 실제 구현은 몇 군데 달라졌다: `dbx`는 종류별 하위 패키지 대신
> 한 패키지 안에서 파일로 나뉘고(`introspect_*.go`, `metrics_*.go`, `logs_*.go`, `explore_*.go`),
> 순환 의존을 끊기 위해 `metric`·`dblog` 타입 패키지가 추가되었고, ERD 실시간 허브는
> `erdhub`로 분리되었다. 최종 구조는 [architecture.md](architecture.md)를 보라.

## 3. 핵심 도메인 설계

### 3.1 권한 모델

두 축으로 분리합니다.

**시스템 역할** (`users.role`): `superadmin` | `admin` | `member`
- `superadmin`: 사용자 CRUD, 모든 설정, 최초 부트스트랩 계정
- `admin`: 커넥션 등록/승인 가능, 사용자 관리 불가
- `member`: 부여된 범위만

**커넥션 접근** (`user_db_access`)
```
mode: all | allowlist | denylist
+ connection_id 리스트
```
- `all`: 전체 허용
- `allowlist`: 선택한 DB만
- `denylist`: 특정 DB만 차단, 나머지 허용

**커넥션별 능력** (`user_db_capability`, connection 또는 environment 단위로 부여)
```
level: none < monitor < erd < migrate
```
- `monitor`: 상태/부하/로그 조회
- `erd`: ERD 설계·초안 저장·리뷰 요청
- `migrate`: 승인된 마이그레이션 실행·롤백

권한 판정은 단일 함수 `auth.Can(user, connID, needed)` 로 집중 → 모든 핸들러·WS·AI 툴이 동일 경로 사용.

### 3.2 커넥션

```
connections: id, name, kind(mysql|postgres|...), environment(dev|prod),
             host, port, database, options(json), tags, created_by, ...
connection_secrets: connection_id, username, password_enc, extra_enc
```
`environment=prod` 커넥션은 마이그레이션 실행 시 2차 승인 + 확인 문구 요구.

### 3.3 스키마 IR (전체 기능의 중심)

ERD, introspect, diff, 마이그레이션, 버전 관리가 모두 하나의 중간 표현을 공유합니다.

```
Schema { Tables[], Enums[], Sequences[], Views[] }
Table  { Name, Columns[], PK, Indexes[], FKs[], Checks[], Comment }
Column { Name, Type(논리타입 + raw), Nullable, Default, Identity, Comment }
```
- `Introspect(conn) → Schema` : DB별 어댑터가 구현
- `Diff(from, to) → []Change` : 방향성 있는 변경 목록
- `Render(changes, dialect) → up SQL[], down SQL[]` : dialect별 DDL 생성
- MongoDB/Redis는 테이블 개념이 없으므로 `collection/keyspace` 프로파일링 결과를 IR의 축약 형태로 매핑 (ERD는 컬렉션 문서 스키마 추론 기반)

### 3.4 ERD 동시 편집

**동기화 방식**: 서버 권위(server-authoritative) op-log + 필드 단위 LWW.
CRDT는 이 도메인(도형/필드 편집)에 과합니다.

- 클라이언트 → `{docId, baseSeq, ops[]}` 전송
- 서버: 검증 → seq 부여 → `erd_ops` 저장 → 모든 구독자 브로드캐스트
- 클라이언트: 자신의 op는 낙관적 적용, 서버 seq 도착 시 정합
- op 종류: `table.add/move/rename/delete`, `column.*`, `fk.*`, `note.*`
- 주기적으로 스냅샷 압축(`erd_documents.snapshot`) → 재접속 시 스냅샷 + 이후 op만 전송
- 프레즌스: 커서 위치, 선택 중 객체, 참여자 목록 (메모리, 비영속)
- 채팅: 문서별 `erd_chat_messages` 영속 + 실시간 브로드캐스트

⚠️ 단일 바이너리·단일 인스턴스 전제. 수평 확장 시 허브 공유(Redis pub/sub) 필요 — 인터페이스만 분리해 둡니다.

### 3.5 버전 관리 & 마이그레이션 워크플로

```
초안(ERD draft) → 리뷰 요청 → 승인 → 마이그레이션 계획 생성 → 실행 → 버전 확정
```

```
schema_versions: id, connection_id, version_no, schema_json(IR), source, author, note
   source: migration | external_edit | initial_import
migrations: id, from_version, to_version, up_sql, down_sql, status, plan_json
   status: draft | in_review | approved | rejected | applied | rolled_back | failed
migration_reviews: migration_id, reviewer_id, decision, comment
```
- 실행 전 프리체크: 대상 DB 현재 스키마를 재-introspect → `from_version`과 일치하는지 검증 (불일치 시 차단)
- 파괴적 변경(DROP/타입 축소) 표시 및 prod 별도 확인
- 롤백: 저장된 `down_sql` 실행 + 역방향 버전 등록
- **외부 편집 감지**: 모니터 폴러가 주기적으로 스키마 핑거프린트 비교 → 불일치 시 `EXTERNAL_SCHEMA_DRIFT` 이벤트 + "외부 편집으로 버전 등록" 원클릭 액션(현재 스키마를 새 버전으로 커밋 + diff 표시)

### 3.6 모니터링 / 이벤트

- 커넥션별 폴러 goroutine (interval 설정 가능), 컨텍스트로 취소
- 수집 지표(어댑터별):
  - RDBMS 공통: 연결 수, 활성 세션, QPS, 슬로우쿼리 수, 락 대기, 복제 지연, 디스크/테이블 크기
  - PG: `pg_stat_activity`, `pg_stat_statements`, bloat, vacuum
  - MySQL: `SHOW GLOBAL STATUS`, `performance_schema`, InnoDB 버퍼풀
  - MSSQL: `sys.dm_os_performance_counters`, `dm_exec_requests`
  - Oracle: `v$sysstat`, `v$session`, `v$sql`
  - Mongo: `serverStatus`, `currentOp`, profiler
  - Redis: `INFO`, `SLOWLOG`, keyspace
- 저장: `metric_samples(conn_id, metric, ts, value)` + 자동 롤업(1m→5m→1h) + 보존기간
- 룰: `monitor_rules(metric, op, threshold, duration, severity)` → 위반 시 `events` 기록, WS로 실시간 알림
- 대시보드: 커넥션 상태 그리드, 시계열 차트(직접 구현 SVG), 이벤트 타임라인

### 3.7 DB 로그 탐색

- 소스 어댑터: MySQL slow_log 테이블 / PG `pg_stat_statements` + 로그파일 / MSSQL 에러로그 DMV / Oracle `v$diag_alert_ext` / Mongo profiler / Redis SLOWLOG
- 통합 검색 UI: 시간 범위, 심각도, 텍스트/정규식, 커넥션 필터
- 분석: 쿼리 정규화(리터럴 → `?`) 후 그룹 집계 → Top-N 느린/빈번한 쿼리, 시간대별 분포

### 3.8 Git 연동

- `vcs_integrations`: provider, base_url(self-hosted 지원), token_enc, repo, default_branch, path_template
- 액션: 브랜치 생성 → 마이그레이션 파일 커밋(`migrations/{ts}_{name}.up.sql` / `.down.sql` + ERD 스냅샷 json) → PR/MR 생성
- 3사 공통 인터페이스 `vcs.Provider{ EnsureBranch, PutFiles, OpenPR }`

### 3.9 AI 어시스턴트

- `ai_providers`: provider, api_key_enc, base_url, default_model, enabled
- **프로바이더 범위 (결정됨)**: 어댑터 2종 — ① Anthropic 네이티브(Messages API, 1차 구현), ② OpenAI 호환 엔드포인트(OpenAI 본체·로컬 LLM·게이트웨이 공통). `base_url`을 사용자가 지정할 수 있으므로 호환 엔드포인트 하나로 다수 서비스를 커버합니다. 키는 여러 개 등록 후 세션별 전환 가능.
- `ai_sessions` / `ai_messages`: 세션 목록, 대화 영속, 스트리밍 응답(SSE)
- **툴 레지스트리**: 앱의 모든 기능을 tool로 노출. 각 툴은 호출자 권한으로 실행 → AI가 권한을 우회할 수 없음
  - 예: `list_connections`, `get_metrics`, `search_logs`, `introspect_schema`, `propose_erd_change`, `diff_schema`, `create_migration`, `request_review`, `apply_migration`(승인 필요), `create_mr`, `manage_user`(superadmin 전용)
- 쓰기·파괴적 툴은 UI 확인 단계를 강제(툴이 "제안"을 반환하고 사용자가 승인 버튼을 눌러 실행)

## 4. 부트스트랩 동작

1. 메타 DB 열기 → 내장 마이그레이션 적용 (WAL 모드)
2. 마스터 암호화 키: `DBSTUDIO_MASTER_KEY` env → 없으면 데이터 디렉터리의 `master.key` 생성(0600) 후 사용, 경고 출력
3. `SELECT count(*) FROM users` == 0 이면:
   - `superadmin` 계정 생성, 24바이트 랜덤 → base58 비밀번호
   - 터미널에 박스로 강조 출력 (1회만, 최초 로그인 시 변경 강제)
4. 커넥션별 모니터 폴러 시작, Fiber 리스닝

## 5. 프론트엔드 설계 (프레임워크 없음)

- `core/router.js` — history API 기반 해시리스 라우터
- `core/api.js` — fetch 래퍼(에러/401 처리), `core/ws.js` — 자동 재연결 WS
- `core/dom.js` — 태그드 템플릿 기반 초경량 렌더 헬퍼 (h/ render / 이벤트 델리게이션)
- `core/store.js` — 이벤트 기반 상태 저장소
- 페이지: 로그인, 대시보드, 사용자 관리, 커넥션 관리, 모니터링, 로그 탐색, ERD 목록/에디터, 마이그레이션/버전, 설정(Git·AI 키), AI 채팅
- ERD 에디터: SVG 캔버스 직접 구현 — 팬/줌, 테이블 노드 드래그, 컬럼 인라인 편집, FK 라인 라우팅(직교 경로), 다중 선택, undo/redo(로컬 op 스택), 원격 커서 오버레이, 사이드 채팅 패널
- 차트: 의존성 없는 SVG 라인/영역 차트 컴포넌트
- 디자인: shadcn/ui의 토큰·컴포넌트 규약을 CSS로 옮긴다 (아래)

빌드 스텝 없음 → `go:embed web/*` 로 그대로 서빙. 개발 시 `-dev` 플래그로 디스크에서 직접 서빙.

### 디자인 시스템 (shadcn/ui 참고)

Tailwind와 React 없이 shadcn/ui의 **규약만** 옮겼다. 정확히 세 가지다.

1. **색은 HSL 3요소로 저장한다.** `--h-primary: 240 5.9% 10%` 처럼 적어 두고
   `hsl(var(--h-primary) / 0.1)`로 조합한다. hover·선택·비활성처럼 배경 위에 얹는 상태를
   색을 새로 정의하지 않고 만들 수 있다. 이 방식이 아니면 상태마다 팔레트가 늘어난다.
2. **컨트롤은 무채색, 색은 의미가 있을 때만.** 버튼·입력·탭은 zinc 계열이고, 색은
   파괴적 동작·상태(정상/경고/오류)·차트에만 쓴다. 관리 도구는 화면에 요소가 많아서
   색을 장식으로 쓰면 정작 위험한 동작이 눈에 띄지 않는다.
3. **변형은 이름으로 고정한다.** 기본 버튼 = outline(테두리), 주 동작 = solid primary,
   파괴적 동작 = solid destructive(대화상자) 또는 ghost destructive(목록).
   목록에서 카드마다 solid 버튼이 반복되면 "지금 눌러야 하는 것"이 사라진다.

테마는 `data-theme` 속성 하나로 결정된다. 기본값은 OS 설정(`prefers-color-scheme`)이고,
사용자가 고른 값이 그것을 덮는다. 첫 페인트가 반대 팔레트로 깜빡이지 않도록
`js/theme-init.js`를 `<head>`에서 동기로 읽는다. 인라인 스크립트는 CSP(`script-src 'self'`)가
막고, 모듈 스크립트는 defer와 같아 파싱 후에 실행되므로 둘 다 쓸 수 없다.

이 문제는 브라우저 검사가 잡지 못했다. CDP의 Runtime 도메인은 `console.*` 호출과 예외만
보고하고, CSP 위반 같은 브라우저 수준 차단은 Log 도메인으로만 온다. 검사 하네스에
`Log.enable`을 추가하고, 인라인 스크립트를 일부러 되살려 실패하는 것을 확인한 뒤 되돌렸다.

**테스트가 찾아낸 실제 버그 7건**

1. MySQL `information_schema.CHECK_CONSTRAINTS`에 `TABLE_NAME`이 없어 체크제약을 못 읽음 → `TABLE_CONSTRAINTS` 조인
2. Oracle `all_tab_cols.data_default`는 LONG 타입이라 `NVL()` 적용 시 ORA-00932 → 직접 선택 + NullString
3. SQLite `AUTOINCREMENT`를 독립 컬럼 제약으로 생성 → 문법 오류. `INTEGER PRIMARY KEY AUTOINCREMENT` 인라인으로 수정
4. SQLite는 ALTER로 FK/체크제약 추가 불가 → CREATE TABLE에 인라인하도록 수정 (신규 테이블은 제약이 통째로 누락되고 있었음)
5. MS-SQL 주석 DDL 미구현 → `sp_addextendedproperty`/`sp_updateextendedproperty` 분기 생성 (ERD→MSSQL 마이그레이션 시 주석이 사라지던 문제)
6. MS-SQL introspect가 `master`의 시스템 객체(`spt_values` 등)를 사용자 객체로 취급 → `is_ms_shipped=0` 필터
7. FK 참조가 네임스페이스 없이 생성되어 세션 기본 스키마로 해석 → 소유 테이블의 네임스페이스로 명시적 보완

또한 스키마 API의 권한 거부가 403 대신 500을 반환하는 버그를 발견해 수정했습니다
(응답을 직접 쓰는 `fail()` 헬퍼의 반환값 `nil`을 다중 반환 함수에서 에러 신호로 오용).

**누적 카운터는 초당 변화율로 변환한다.** 절대값은 서버 재시작 시 초기화되어 의미가 약하다.
첫 관측은 비교 대상이 없어 저장하지 않고, 카운터가 감소하면(재시작) 그 구간을 건너뛴다 —
음수 변화율을 저장하면 차트에 스파이크가 생기고 룰이 오발동한다.

**지속 시간 조건.** 위반이 `duration_sec` 이상 연속될 때만 이벤트를 만든다.
순간 스파이크마다 알림이 쏟아지면 알림 자체가 무의미해진다. 이 상태는 메모리에만 두는데,
앱이 재시작되면 관측이 끊겼으므로 처음부터 다시 세는 것이 옳기 때문이다.

**이벤트 중복 억제.** 같은 원인은 새 행을 만들지 않고 `occurrences`를 올린다.
30초 주기로 위반하면 하루 2880건이 쌓여 타임라인이 무의미해진다.
심각도는 올라가기만 한다 — 잠깐 완화됐다고 낮추면 최악의 상태를 놓친다.

**스키마 드리프트 감지.** P3의 구조 지문을 재사용해 앱 외부 변경을 잡는다.
첫 확인은 기준선만 저장하고(커넥션 등록마다 경고가 뜨면 안 된다), 변경이 없으면
스냅샷을 쌓지 않고, 파괴적 변경이 섞이면 심각도를 올린다. 드리프트는 변경마다
새 이벤트를 만든다(누적하면 어떤 변경이 언제 있었는지 뭉개진다).

  기간 전환, 이벤트 필터/확인, 룰 생성·삭제·토글. 콘솔 에러 0건

**테스트가 찾아낸 실제 버그 6건**

1. **시간 문자열 정렬 버그(심각)** — `RFC3339Nano`는 소수점 뒤 0을 제거해 자리수가 가변이다.
   정확히 정초인 `"…:40Z"`와 `"…:40.5Z"`를 비교하면 `'Z'`(0x5A) > `'.'`(0x2E)라서
   사전순과 시간순이 뒤집힌다. SQLite는 시간을 문자열로 비교하므로 모든 범위 조건과
   `ORDER BY`가 조용히 틀렸다. 소수점 9자리 고정 폭 형식으로 교체
2. **룰 삭제 시 이벤트가 영구히 열린 채로 남음** — `events.rule_id`가 `ON DELETE SET NULL`이라
   룰을 먼저 지우면 `rule_id`가 NULL이 되어 해소 UPDATE가 대상을 못 찾았다. 순서를 뒤집고 트랜잭션으로 묶음
3. **PostgreSQL 세션 지표 전부 누락** — `MAX(expr FILTER (...))`는 문법 오류.
   `FILTER`는 집계 함수 호출 뒤에 와야 한다. 12개 중 6개만 수집되고 있었음
4. **MongoDB 지표 절반이 조용히 누락** — 드라이버가 중첩 문서를 `bson.D`로 디코딩하는데
   `bson.M`으로 타입 단정해 실패했고, 노트조차 남지 않았다. 같은 패턴이 인덱스 introspect에도 있었음
5. **MS-SQL 최장 실행 쿼리 오탐** — `session_id > 50` 필터로는 시스템 태스크를 못 걸러
   "1.9시간 실행 중" 같은 거짓 경고가 계속 발생. `dm_exec_sessions.is_user_process`로 교체
6. **`monitor_rules.op` CHECK 제약이 빈 문자열 거부** — connectivity/drift 룰은 비교 연산자가
   없는데 제약이 이를 허용하지 않아 기본 룰 시딩이 실패

**테스트 하네스에서 걷어낸 거짓 음성**: PowerShell → `docker exec` → mysql 경로의 stdin 전달이
파이프라인 문맥에 따라 조용히 실패해, 드리프트 테스트가 "감지 실패"로 보고했으나 실제 기능은
정상이었다. 외부 DDL 조작이 필요한 검증은 Go 통합 테스트로 옮겼다.

- `Entry` — 시간순 항목. "언제 무슨 일이 있었나"를 본다 (슬로우 쿼리, 서버 오류, 실행 중 쿼리)
- `QueryStat` — 다이제스트 단위 누적 통계. "무엇을 개선하면 효과가 큰가"를 본다

이 둘을 한 목록에 섞으면 둘 다 쓸모없어진다. 누적 통계에는 발생 시각이 없고,
시간순 항목에는 호출 횟수가 없다. UI도 탭 두 개로 나눴다.

**SQL 정규화가 분석의 전제.** 리터럴만 다른 쿼리를 따로 세면 Top-N이 무의미해진다.
`internal/dblog/normalize.go`의 7단계 파이프라인: 주석 제거 → 문자열 리터럴 `?` →
숫자 리터럴 `?`(16진수·지수 표기 포함) → `IN (?,?,?)` → `IN (?)` →
다중 VALUES 목록 축약 → 공백 정규화 → 키워드 대문자화. 그 결과의 SHA-256 앞 8바이트가
다이제스트다. 중요한 판단 두 가지:

- **단일 인용부호만 문자열이다.** 백틱(MySQL)과 이중 인용부호(PostgreSQL/표준)는 식별자이므로
  보존한다. 이를 리터럴로 바꾸면 `SELECT "user_id"`가 `SELECT ?`가 되어 쿼리가 뭉개진다
- **키워드만 대문자화한다.** 식별자를 대문자로 바꾸면 대소문자를 구분하는 PostgreSQL에서
  다른 테이블이 된다

**소스별 가용성을 먼저 알려준다.** 로그 소스는 DB 설정에 의존한다 —
MySQL 슬로우 로그는 `slow_query_log=ON` + `log_output=TABLE`이 필요하고,
PostgreSQL 통계는 `pg_stat_statements` 확장이, MongoDB 프로파일러는 `setProfilingLevel`이 필요하다.
비어 있는 화면만 보여주면 기능이 고장난 것으로 오해하므로, 각 소스마다
`available` + `hint`(활성화 방법)를 반환하고 UI가 칩으로 노출한다.

| DB | 시간순 소스 | 통계 소스 |
|---|---|---|
| MySQL | `mysql.slow_log`, `processlist` | `performance_schema.events_statements_summary_by_digest` (DB 자체 다이제스트 사용) |
| PostgreSQL | `pg_stat_activity`, `pg_read_file(pg_current_logfile())` | `pg_stat_statements` (버전별 컬럼명 분기 + 폴백) |
| MS-SQL | `dm_exec_requests`, `sp_readerrorlog` | `dm_exec_query_stats` (`query_hash`를 다이제스트로) |
| Oracle | `v$session`, `v$diag_alert_ext` | `v$sql` (`sql_id`를 다이제스트로) |
| MongoDB | `system.profile`, `getLog`, `currentOp` | 프로파일 항목을 쿼리 형태(shape)로 집계 |
| Redis | `SLOWLOG GET` | 명령 형태(`GET ?×1`)로 집계 |
| SQLite | 없음 (Capabilities로 400 반환) | 없음 |

### P6 완료 기록 (2026-08-13)

**op-log는 이력이 아니라 의도의 기록이다.** diff는 스키마 두 장만 보고 이름 변경을
추론하지 않는다(잘못 짚으면 데이터가 사라진다). 그래서 P3에서 rename을 삭제+생성으로
표현했고, 그 의도를 어디선가 전달해야 했다. `erd_ops`의 `table.update{name}`이 그
자리다 — P7의 마이그레이션은 op-log를 읽어 "DROP+CREATE"가 아니라 "RENAME"임을 안다.

**충돌 해결은 필드 단위 LWW이고, 그래서 갱신 op는 패치여야 한다.** 두 사람이 같은
컬럼의 서로 다른 속성(한 명은 타입, 한 명은 주석)을 동시에 고칠 때 전체 교체 방식이면
나중 op가 앞의 편집을 되돌린다. 없는 필드는 "변경 없음"이고, 빈 문자열은 "제거"다 —
이 둘을 구분하지 못하면 기본값 삭제를 표현할 방법이 없다.

`payload` 디코딩은 `DisallowUnknownFields`로 엄격하게 한다. 관대한 디코더는 `nullible`
같은 오타를 조용히 버리고 "변경 없음"으로 처리하는데, 사용자 입장에서는 편집이 아무
오류 없이 사라진다. 프론트엔드가 바이너리에 함께 담기므로 버전 불일치가 없어 손해가 없다.

**클라이언트는 op 적용 로직을 다시 구현하지 않는다.** 구조를 바꾼 op는 브로드캐스트에
적용 결과(문서 전체)를 함께 담는다. 검증·제약 정리·이름 변경 전파를 JavaScript로 또
구현하면 두 구현이 어긋나는 순간 사용자마다 다른 스키마를 보게 된다. 구조 편집은 사람의
속도(분당 몇 번)로 일어나므로 문서를 다시 보내는 비용이 싸다. 반대로 이동·메모 op는 초당
수십 번인데 좌표 대입은 틀릴 여지가 없어 그 둘만 op 자체를 보내고 클라이언트가 반영한다.

**좌표는 스키마 IR에 넣지 않는다.** IR의 지문이 드리프트 감지와 버전 비교의 기준이므로,
좌표가 IR에 들어가면 테이블을 옮기기만 해도 "스키마가 바뀌었다"가 된다.
레이아웃과 메모는 `erd_documents`의 별도 컬럼이다.

**거부(reject)에는 최신 상태를 함께 보낸다.** 낙관적으로 적용한 클라이언트는 거부 시점에
틀린 상태를 보고 있다. op별 역연산을 만드는 방법은 op 종류마다 필요하고 틀리기 쉬운데,
문서는 작아서 통째로 받는 쪽이 싸고 항상 정확하다.

**WebSocket의 CSRF 방어는 Origin 검사다.** 브라우저의 WebSocket API는 커스텀 헤더를 붙일
수 없어 `X-Requested-With` 검사를 쓸 수 없다. 대신 핸드셰이크에 반드시 실리는 Origin을
Host와 비교한다. Origin이 아예 없으면(브라우저가 아닌 클라이언트) 쿠키 자동 전송이라는
CSRF의 전제가 성립하지 않으므로 허용한다.

**스냅샷 + 잔여 op.** 매 op마다 문서를 통째로 다시 쓰면 큰 스키마에서 쓰기 비용이 op 수에
비례하고, op만 쌓으면 로딩이 무한히 느려진다. 100개 op마다(그리고 마지막 참여자가 나갈 때)
스냅샷을 굳히고 최근 200개 op만 남긴다.

### P7 완료 기록 (2026-08-13)

**워크플로.** `초안(ERD) → 계획 생성 → 리뷰 요청 → 승인 → 사전 검사 → 실행 → 버전 확정`.
상태 전이 규칙은 `store.allowedTransitions` 한 표에 모았다. 전이 검사가 핸들러마다
흩어지면 새 경로를 추가할 때 한 곳을 빠뜨리게 되고, 그러면 "승인 없이 실행" 같은 구멍이
생긴다. 실행/롤백은 전용 엔드포인트에서만 일어나며, 상태 변경 API로는 `in_review`와
`draft`로만 바꿀 수 있다 — 상태만 고쳐 "적용됨"으로 만들 수 있으면 실행 기록 없는 적용이
생긴다.

**DDL 트랜잭션 지원 여부가 안전성의 핵심이다.**

| DB | DDL 트랜잭션 | 실패 시 |
|---|---|---|
| PostgreSQL · MS-SQL · SQLite | 지원 | 전부 되돌아감 (부분 적용 없음) |
| MySQL · Oracle | 미지원 (암묵적 커밋) | 앞의 문장은 적용된 채 남음 |

그래서 실행 기록을 **문장 단위**로 남긴다. MySQL에서 중간에 실패하면 "어디까지
적용됐는가"가 복구의 유일한 출발점이다. 자동 복구는 하지 않는다 — up 문장과 down 문장이
1:1로 대응하지 않아(되돌릴 수 없는 변경은 down이 없다) 기계적 짝짓기는 틀리기 쉽다.
대신 적용된 문장을 정확히 보여주고, "오류를 무시하고 계속" 옵션이 있는 롤백으로 정리하게
한다(이미 없는 것을 지우려는 문장이 섞여 있어 첫 실패에서 멈추면 나머지를 정리할 수 없다).

**프리체크가 오래된 계획을 막는다.** 계획을 만든 시점의 구조 지문을 저장하고, 실행 직전에
대상 DB를 다시 읽어 비교한다. 다르면 차단하고 무엇이 달라졌는지 보여준다. 이 검사가 없으면
남이 먼저 바꾼 스키마 위에 낡은 계획을 실행해 그 변경을 덮어쓴다.

**운영 DB 안전장치** (사용자와 합의한 "실행 계획 + 롤백 SQL 사전 검토 + 2차 승인"):

- 승인 2명 필요 (운영 DB, 또는 파괴적 변경이 있는 개발 DB). 승인은 **사람 단위**로 센다 —
  같은 사람이 여러 번 승인해도 검토자는 한 명이다.
- 본인이 만든 계획은 승인할 수 없다. 2차 승인이 "다른 사람이 한 번 더 봤다"를 뜻해야
  실질적인 장치가 된다.
- 실행 시 커넥션 이름을 입력하는 확인 문구 (운영 또는 파괴적 변경).
- 백업 훅은 외부 명령(`-backup-cmd`)으로 지정한다. 앱이 DB별 백업을 직접 구현하지 않는
  이유는 도구와 정책이 조직마다 다르고 잘못 만든 백업이 없는 것보다 위험하기 때문이다.
  명령은 **플래그로만** 지정할 수 있다 — API로 지정하게 하면 앱이 임의 명령 실행 통로가
  된다. 셸을 거치지 않고 실행하며, 커넥션 이름 같은 사용자 지정 값이 명령으로 해석되지
  않게 인자 치환만 한다. 운영 DB에서 백업이 실패하면 마이그레이션을 중단한다.

**버전은 의도가 아니라 관측된 실제 스키마를 기록한다.** 실행 후 다시 introspect한 결과를
버전으로 등록하고, 목표와의 차이가 남으면 경고한다. 목표를 등록하면 생성기의 미묘한 차이가
이력에 영원히 숨는다. 롤백도 새 버전으로 남긴다 — 되돌린 것도 이력이다.

**외부 편집 등록.** 드리프트 이벤트 화면에서 한 번에 현재 상태를 `external_edit` 버전으로
확정할 수 있다. 이전 버전과의 차이를 요약으로 남기며, 구조가 같으면 새 버전을 만들지 않는다
(같은 구조를 반복 등록하면 이력이 의미를 잃는다). 마이그레이션 실행/롤백 직후에는 드리프트
기준선을 자동으로 갱신한다 — 우리가 방금 한 변경이 "외부 편집"으로 감지되면 알림이
무의미해진다.

**검증 결과**

- 단위 테스트: 상태 전이 15조합, 승인 수 규칙 4케이스
- 통합 테스트 (실제 DB): MySQL·PostgreSQL·SQLite에 대해
  **적용 → 실제 구조 확인 → 롤백 → 지문이 원본과 일치**를 검증. 그 외:
  드리프트 차단, 승인 게이트(초안·리뷰중·반려 각각), 파괴적 변경의 2인 승인,
  같은 사람 반복 승인이 1명으로 계산됨, dialect별 실패 동작(트랜잭션 DB는 전부 되돌아가고
  비트랜잭션 DB는 부분 적용이 기록됨 + 정리 롤백으로 원복), 문장별 실행 기록,
  버전 번호 부여와 중복 방지, 대상 DB가 표현할 수 없는 변경(SQLite 주석) 보고
- API 스모크 전 항목 통과: 기준선 등록, 중복 방지, 버전 diff, 초안→계획 생성,
  승인 전 실행 차단(409 + 차단 사유 목록), 상태 API로 승인/적용 불가(400),
  반려 → 초안 복귀 시 리뷰 초기화, 실행, 실행 기록, 적용된 마이그레이션 삭제 불가(409),
  롤백, 롤백 후 재실행 불가, 드리프트 차단, 외부 편집 등록,
  운영 DB의 2인 승인·본인 승인 거부(403)·확인 문구(400), 멤버 권한 범위, 감사 로그
- 브라우저 전 항목 통과: 버전 타임라인(출처 배지·통계), 버전 diff, 초안에서 계획 생성,
  계획 상세(변경 목록·up/down SQL·경고), 승인 전 실행 버튼 없음, 리뷰 대화상자,
  사전 검사(트랜잭션 지원 여부·경고), 실행 → 결과 요약 → 실행 기록, 롤백,
  상태 필터, 드리프트 이벤트의 버전 등록 버튼. 콘솔 에러 0건

**테스트가 찾아낸 실제 문제 2건**

1. **표현할 수 없는 변경이 조용히 사라짐** — SQLite에는 테이블 주석을 저장할 곳이 없어
   ERD에서 주석을 달면 그 차이가 영원히 수렴하지 않는다. 계획 단계에서 이미 경고를 내고
   있었지만, 실행 후 "생성된 DDL이 의도를 재현하지 못했다"는 별개의 경고가 또 나와
   새로운 문제가 생긴 것처럼 보였다 → 두 메시지를 연결해 "이 DB 종류가 표현할 수 없는
   변경"임을 한 번에 설명하도록 수정
2. **패키지 간 테스트 간섭 (P4와 같은 함정)** — `go test ./...`는 패키지를 병렬 실행한다.
   `migrate` 통합 테스트가 `dbx` 통합 테스트와 같은 MySQL `appdb`를 쓰자 상대의 테이블이
   introspect 결과에 섞여 "적용 후 목표와 다르다"는 거짓 실패가 났다 →
   전용 데이터베이스(`dbstudio_migrate`)를 만들어 격리하고, 두 번 연속 실행해 결정성 확인

**테스트 하네스에서 걷어낸 거짓 신호 3건**: (1) mysql 클라이언트는 비밀번호 경고를
stderr로 내는데 `$ErrorActionPreference='Stop'` + `2>&1` 조합에서 그 경고가 오류 레코드가
되어 스크립트를 중단시켰다 → docker 호출을 헬퍼로 감싸 종료 코드로만 판단.
(2) `admin` 역할은 커넥션을 관리할 수 있을 뿐이고 개별 DB 접근은 접근 정책이 정한다 —
검토자에게 등급을 부여하지 않아 리뷰가 403으로 막혔다(제품 동작은 올바름).
(3) 스모크 테스트가 공유 DB에서 컬럼을 지운 채로 남겨, 그 컬럼을 참조하는 시드된 뷰가
깨져 다른 패키지의 통합 테스트가 실패했다 → 전용 프로브 컬럼을 쓰고 마지막에 원상 복구,
그리고 뷰가 여전히 유효한지 확인하는 단계 추가

### P8 완료 기록 (2026-08-13)

**세 서비스의 API는 "여러 파일을 한 커밋으로 올리는 방법"에서 크게 갈린다.**

| 서비스 | 방식 | 호출 수 |
|---|---|---|
| GitLab | 커밋 API 하나가 파일 액션 배열을 받는다 | 1 (+ 파일별 존재 확인) |
| Bitbucket | `/src`에 multipart/form-data — 파일 경로가 폼 필드 이름 | 1 |
| GitHub | Contents API는 파일당 커밋을 만든다 → 트리 → 커밋 → ref 갱신을 직접 | 5 |

그래도 한 커밋으로 묶는다: up.sql과 down.sql이 다른 커밋에 흩어지면 리뷰어가 반쪽만
보게 되고, 되돌릴 때도 커밋 하나로 처리할 수 없다. GitHub 경로에서 `base_tree`를
빠뜨리면 나머지 파일이 전부 삭제된 트리가 만들어지므로 그 지점을 테스트로 고정했다.

**브랜치 이름 인코딩이 서비스마다 반대다.** 이 차이는 문서를 읽지 않으면 알 수 없고,
틀리면 404가 나는데 원인을 찾기 어렵다.

- GitLab — 브랜치 이름을 하나의 경로 요소로 보므로 슬래시까지 `%2F`로 인코딩해야 한다
- GitHub — `/git/ref/heads/` 뒤의 나머지 전체를 ref로 해석한다. 슬래시를 그대로 둬야 한다
- Bitbucket — `refs/branches/{name}`에서 슬래시를 그대로 받는다

인증 방식도 다르다: GitHub `Authorization: Bearer`, GitLab `PRIVATE-TOKEN`,
Bitbucket은 앱 비밀번호면 Basic(사용자 이름 필요)·액세스 토큰이면 Bearer.

**토큰 보호.** 커넥션 비밀번호와 같은 방식(AES-256-GCM)으로 봉인하고,
`Token` 필드에 `json:"-"`를 달아 API 응답에 실릴 수 없게 했다. 화면에는 "설정됨" 여부만
보여준다. 조회 함수는 `withToken` 인자를 요구해, 목록·표시 경로에서 실수로 복호화하는
일을 구조적으로 막는다. 수정 시 토큰을 비워 두면 "지우기"가 아니라 "유지"다 —
이름만 고치려던 사용자의 연동이 망가지면 안 된다.

HTTP 클라이언트는 **리다이렉트를 따르지 않는다**. `Authorization` 헤더가 다른 호스트로
전달되면 그것은 자격증명 유출이며, Git 서비스의 정상 API 경로는 리다이렉트를 요구하지 않는다.

**self-hosted 주소는 https를 기본으로 강제하되 사설망 주소에만 http를 허용한다.**
사내망 인스턴스나 로컬 환경에 TLS가 없는 경우는 현실에 존재하므로, 그 둘을 구분하면
안전한 기본값과 실용성을 함께 얻는다. SSRF를 완전히 막지는 못한다(DNS는 나중에 바뀔 수
있다) — 연동 설정은 어드민만 할 수 있고 그들은 이미 DB 자격증명을 다루므로,
이 지점의 신뢰 경계는 "어드민을 신뢰한다"이며 [design/permissions.md](design/permissions.md)에 그렇게 적었다.

**PR 설명에 판단 근거를 담는다.** 저장소의 리뷰어는 이 앱을 보지 않는다. 그래서 PR 본문에
대상 커넥션·기준 버전·변경 목록·파괴적 변경의 사유·되돌릴 수 없는 항목·계획 경고·앱 내
검토 의견·커밋된 파일 목록을 적는다. PR 화면만 보고 판단할 수 있어야 리뷰가 실제로 이뤄진다.

**같은 브랜치의 열린 PR이 있으면 재사용한다.** 다시 만들려 하면 GitHub은 422로 거부하는데,
사용자에게 정답은 "이미 열려 있다"다. 브랜치도 이미 있으면 그 위에 커밋한다 —
같은 마이그레이션을 다시 올리는 것은 정상적인 일이다. ref 갱신에 force를 쓰지 않는 이유는
그 사이 누군가 브랜치에 커밋했다면 실패해야 하기 때문이다.

**검증 결과**

- 단위 테스트 23건 (`httptest` 기반): 3사의 요청 경로·헤더·본문 형식·호출 순서를 고정.
  GitHub의 5단계 호출 순서와 `base_tree`, GitLab의 create/update 액션 선택과 iid 사용,
  Bitbucket의 multipart 필드와 parents, 오류 메시지 추출(GitHub `errors` 배열 ·
  GitLab `{message:{base:[...]}}`), API 접두사 중복 방지, Slugify(Git 참조 금지 문자),
  base URL 검증, 리다이렉트 시 토큰 미전달
- API 스모크 전 항목 통과 (가짜 Git 서버 대상): 3사 연동 등록·확인, 토큰 미노출,
  단일 커밋에 3개 파일(up/down/schema.json)과 본문 검증, PR 본문 내용,
  재푸시 시 브랜치·PR 재사용, PR 없이 커밋, 사용자 지정 브랜치,
  **단계별 실패 보고(브랜치/커밋/PR)**, 푸시 이력, 커넥션 전용 연동의 범위 제한,
  비활성 연동 거부, 토큰 유지 편집, 권한(멤버 403), 감사 로그에 토큰 없음
- 브라우저 전 항목 통과: 연동 목록·서비스별 입력 힌트·Bitbucket 사용자 이름 칸 노출,
  연결 확인 결과 모달, 서버 검증 메시지, 마이그레이션에서 푸시 → 결과 요약과 PR 링크,
  푸시 이력, 실패 단계 표시, 차단 사유 목록 렌더링. 콘솔 에러 0건

**테스트가 찾아낸 실제 버그 3건**

1. **브랜치 이름 인코딩을 세 서비스에 똑같이 적용했다** — 처음에는 모두 `%2F`로
   인코딩했다. GitLab에는 맞지만 GitHub·Bitbucket에서는 ref를 찾지 못한다.
   `httptest` 테스트가 경로를 정확히 단정해 즉시 드러났다 → 서비스별로 분리
2. **오류 본문의 추가 정보를 클라이언트가 버렸다** — `ApiError`가 `status/code/message/detail`만
   보관해서, 서버가 애써 보낸 실패 단계(`stage`)와 차단 사유 목록(`blockers`)이 화면에
   도달하지 못했다. 마이그레이션 차단(P7)에도 같은 문제가 잠재해 있었다 →
   오류 본문 전체를 `payload`로 보관하고, 드리프트 차단 화면까지 브라우저로 검증
3. **PR 본문에 파일 목록이 없었다** — 리뷰어가 어느 파일에 SQL이 있는지 diff에서 찾아야
   했다. PR에 다른 커밋이 섞이면 특히 불편하다 → 커밋한 파일 경로를 본문에 나열

**테스트 하네스**: 실제 GitHub/GitLab/Bitbucket에 붙을 수 없으므로 Node로 가짜 Git 서비스를
만들어 세 API 경로를 모두 처리하게 했다. 받은 요청과 커밋 내용을 `GET /__state`로 노출해,
스모크 테스트가 **커밋된 파일 본문과 PR 설명까지** 단정할 수 있다. `POST /__fail`로
특정 경로·메서드의 응답을 강제 실패시켜 단계별 오류 경로를 검증한다.
걷어낸 거짓 신호: 실패 주입을 경로만으로 필터하자 PR 생성 검증에서 앞선
`GET /pulls`(기존 PR 확인)가 실패를 먹어버렸다 → 메서드까지 지정하도록 수정.

### P9 완료 기록 (2026-08-13)

**AI는 앱의 권한을 우회하는 통로가 되어서는 안 된다.** 이것이 이 단계의 유일한 설계 제약이고
나머지는 여기서 파생됐다.

- 툴은 **호출한 사용자의 권한으로** 실행된다. 모든 커넥션 접근은 P2의 `authz.Can`을 통과하고,
  목록형 툴은 접근 가능한 것만 반환한다. 같은 질문("어떤 DB가 있나요?")에 사용자마다
  다른 답이 나오는 것이 정상이다
- **쓰기 툴은 실행하지 않고 제안만 만든다.** 모델이 `create_migration`을 부르면 만들어지는 것은
  제안(pending action)이고, 사용자가 승인 버튼을 눌러야 실행된다. 승인 후에도 P7의 안전장치
  (검토자 승인 수, 사전 검사, 운영 DB 확인 문구)는 전부 그대로 적용된다 — AI 경로는
  `migrate.Runner.Apply`를 그대로 호출하므로 우회할 지점이 없다
- 조회 12종 / 변경 6종. 변경 툴은 `Propose`(아무것도 바꾸지 않고 미리보기만 만든다)와
  `Apply`(승인 후 호출) 두 함수로 나뉜다
- 세션은 소유자만 읽을 수 있다. 대화에는 그 사람의 권한으로 조회한 결과가 담기므로,
  세션을 공유하면 권한 모델에 구멍이 난다

**프로바이더는 두 종류로 충분하다.** Anthropic 네이티브와 OpenAI 호환. 후자는 base URL을
사용자가 지정할 수 있어 OpenAI 본체·로컬 LLM(Ollama, vLLM)·호환 게이트웨이를 하나로 덮는다.
두 규약의 차이는 어댑터 안에 갇혀 있다:

| | Anthropic | OpenAI 호환 |
|---|---|---|
| 시스템 프롬프트 | 최상위 `system` 필드 | `messages[0]`에 `role=system` |
| 툴 결과 | user 메시지 안의 `tool_result` 블록 | 결과마다 `role=tool` 메시지 하나 |
| 툴 인자 스트리밍 | `input_json_delta`를 블록 index별로 조립 | `tool_calls[i].function.arguments` 조각을 index별로 조립 |
| 인자 타입 | JSON 객체 | JSON **문자열** |

로컬 LLM 대응으로 OpenAI 쪽은 `finish_reason`이 오지 않고 스트림이 끝나는 경우에도
누적된 툴 호출을 방출한다. SSE 줄 버퍼는 4MB로 올렸다 — 기본 64KB는 큰 툴 인자에서 터진다.

**POST + SSE.** `EventSource`는 GET만 지원해서 질문을 URL에 넣어야 하는데, 길면 길이 제한에
걸리고 서버 로그에 대화 내용이 남는다. 그래서 클라이언트는 `fetch` + `ReadableStream`으로
직접 프레임을 파싱한다. 서버 쪽 제약이 하나 있다: fasthttp의 스트림 라이터는 **핸들러가
반환한 뒤** 실행되므로 그 안에서 `*fiber.Ctx`를 만지면 안 된다. 필요한 값(사용자, IP, 세션,
프로바이더 설정, 툴 목록)은 전부 핸들러에서 복사해 넘긴다.

**루프 상한 8회.** 무한 루프는 토큰과 DB 부하를 태우기만 한다. 상한에 걸리면 조용히 끊지 않고
"툴 호출이 8회를 넘어 중단했습니다"를 이벤트로 보낸다 — 응답이 멈춘 이유를 사용자가 알아야 한다.
새 사용자 메시지가 오면 이전 제안은 만료시킨다. 그대로 두면 문맥을 잃은 승인 버튼이 남아
한참 뒤에 예상하지 못한 시점에 실행될 수 있다.

**검증 결과**

- 단위 테스트 20건: 두 프로바이더의 요청 본문 형식·스트림 조립·툴 인자 재구성·오류 추출·
  취소 처리, 에러 뒤에 `Done`이 오지 않는 것, base URL 검증
- API 스모크 60여 항목 전부 통과 (가짜 AI 서버 대상): 키 검증·오류 보고·키 미노출,
  세션 소유권 격리, 청크 단위 스트리밍, 자동 제목, 토큰 집계, 시스템 프롬프트/툴 스키마 전달,
  읽기 툴 루프와 결과 되먹임, **권한 범위 차이(같은 툴, 다른 결과)**, 금지된 커넥션 유도 차단 +
  감사 기록, 없는 툴 거부, 쓰기 제안이 실행되지 않음, 타인 제안 승인 차단,
  **중복 승인 차단(409, 두 번 실행되지 않음)**, 거부, 만료, 루프 상한, 프로바이더 오류 전달,
  OpenAI 경로 동등성, 비활성 프로바이더 안내, 키 유지 편집, CSRF, 감사 로그 8종
- 브라우저 전 항목 통과: 새 대화 생성, 스트리밍 커서, 청크 누적 렌더, 툴 호출 칩과 접힌 결과,
  승인 카드(요약·미리보기·안전장치 안내)와 승인/거부 실행 결과, 프로바이더 관리 모달,
  키 미노출, 멤버 권한 분기, 새로고침 후 대화 복원, 480px 레이아웃. 콘솔 에러 0건

**테스트가 찾아낸 실제 버그 2건**

1. **오류 뒤에 성공 이벤트가 따라왔다** — 스트림 중 오류가 나면 `error` 이벤트를 보낸 뒤에도
   `Done`을 보내고 있었다. 마지막 이벤트만 보는 소비자에게는 성공으로 보인다 →
   두 어댑터에 `failed` 플래그를 두고 오류 뒤에는 `Done`을 보내지 않는다
2. **실패한 툴 호출이 화면에서 사라졌다** — 없는 툴 이름이나 권한 거부는 모델에게만
   결과가 가고 사용자 화면에는 아무것도 남지 않았다. 그러면 모델이 왜 갑자기 "할 수 없다"고
   답하는지 알 수 없다 → 호출 사실을 먼저 알리고 실패도 이벤트로 보낸다. 저장된 대화에서도
   실패는 접지 않고 그대로 보여준다(성공 결과만 접는다)

**테스트 하네스**: Node로 가짜 AI 서버를 만들어 Anthropic·OpenAI 두 규약을 모두 흉내낸다.
`POST /__script`로 응답 순서(텍스트/툴 호출/실패)를 주입하면 그 뒤 요청부터 그대로 재생하므로,
LLM 없이 툴 루프·승인·오류 경로를 **결정적으로** 재현할 수 있다. 텍스트는 4자씩 쪼개고 툴 인자는
반씩 나눠 보내 조립 로직을 강제로 태운다. `GET /__state`로 받은 요청(시스템 프롬프트 길이,
툴 이름, 메시지 역할·블록 종류)을 노출해 프로토콜 변환까지 단정한다.
걷어낸 거짓 신호 3건: PowerShell 5.1에서 단일 요소 결과가 스칼라로 풀려 `.Count`가 비는 문제
(`,$array`로 방지), 로그인에 쓴 `WebRequestSession`이 CSRF 헤더를 기억해 헤더 없는 요청 검증이
통과한 문제, 실패 라운드가 폴링 간격보다 빨라 스트리밍 중 상태를 놓친 문제(MutationObserver로 대체).

### P10 완료 기록 (2026-08-14)

**MongoDB·Redis를 스키마 화면에 계속 밀어넣지 않았다.** 두 DB는 P3부터 스키마 IR로 읽히지만
(컬렉션→테이블, 필드→컬럼, 키 접두사 그룹→테이블), 그것은 다른 DB와 나란히 비교하기 위한
최소 공통 표현이다. 실제 운영에서 필요한 것은 다른 데 있다:

| 필요한 정보 | 스키마 IR에 담을 수 있나 |
|---|---|
| 컬렉션별 저장 크기·평균 문서 크기 | 없음 |
| 인덱스가 실제로 쓰이는지 (`$indexStats`) | 없음 |
| 뷰/시계열 컬렉션 구분 | 없음 |
| Redis 메모리 정책·지속성 상태 | 없음 |
| TTL이 없는 키 그룹, 큰 키 | 없음 |
| 명령별 호출 분포 | 없음 |

그래서 전용 화면(`/nosql`)과 전용 조회 경로를 만들었다. **Adapter 인터페이스는 키우지 않았다** —
`DocumentExplorer`/`KeyspaceExplorer`를 선택적 인터페이스로 두고 타입 단정으로 분기한다.
관계형 어댑터 5종은 이 코드를 알 필요가 없고, 지원 여부는 `Capabilities.explore` 하나로
화면·AI 툴·API 게이트가 모두 같은 판단을 한다.

**구조와 통계만 반환한다.** 문서 내용과 키 값은 응답에 담지 않는다. 이 앱의 권한 모델은
"모니터링 < ERD < 마이그레이션"이고 데이터 열람은 그 안에 없는 개념이다. 감사 로그에도
규모(컬렉션 수, 스캔한 키 수)만 남기고 키 이름·필드 이름은 남기지 않는다 —
감사 로그가 데이터 유출 경로가 되면 안 된다.

**전체를 훑지 않는다.** Redis는 `SCAN` 표본(최대 2만)만 보고, 타입·TTL·메모리는 그중 앞쪽
2천 개만 파이프라인으로 조사한다. `KEYS`는 서버를 멈추고, 키마다 세 번 왕복하면 1천 개에
3천 번이 된다. 화면에는 표본 크기와 상한 도달 여부를 함께 보여준다 — 근사값을 정확한 값처럼
보여주면 잘못된 결정을 만든다.

**"확인 불가"와 "0"을 구분한다.** `$indexStats` 권한이 없으면 사용 횟수는 nil이고, 화면은
"확인 불가"로 표시한다. 0회로 보여주면 멀쩡한 인덱스를 지우게 된다. 반대로 정말 0회인 인덱스는
경고로 끌어올려 삭제 후보로 제시하되, "서버 재시작 시 초기화된다"는 전제를 함께 적었다.

**릴리스**: 버전을 `internal/buildinfo`에 ldflags로 주입하고, `-version` 플래그와
`/api/v1/health`(인증 불필요)에서 확인할 수 있게 했다. health를 인증 뒤에 두면 배포 검증
스크립트가 쓸 수 없다. `scripts/release.sh`(bash) / `release.ps1`(Windows)이 5개 플랫폼
바이너리와 `SHA256SUMS`를 만든다. `-trimpath -ldflags "-s -w"` 적용으로 50MB → 37~39MB.

**검증 결과**

- 통합 테스트 2건 추가 (Docker MongoDB/Redis 대상): 컬렉션 통계, 인덱스 unique/sparse/TTL과
  크기, 복합 인덱스의 키 순서·방향, 뷰 구분, 필드 존재 비율(6/10 → 0.6), Redis INFO 섹션 파싱,
  접두사 그룹의 타입·TTL 집계, 큰 키 정렬, keyspace(db별 키 수) 해석
- 단위 테스트 4건: keyspace/commandstats 문자열 파싱, 부분 실패 판별, 미지원 종류 거부
- API 스모크 전 항목 통과: capability 게이팅(관계형은 400 + 안내), MongoDB 통계·인덱스·뷰,
  Redis 메모리·지속성·그룹·큰 키·명령 통계, **응답에 문서 값/키 값이 없음**, 권한 없는 사용자 403,
  감사 로그가 규모만 남김, AI `explore_nosql` 툴의 동작과 권한 거부, health의 빌드 정보
- 브라우저 전 항목 통과: 내비게이션·커넥션 카드의 조건부 링크(Mongo/Redis만), 컬렉션 카드와
  상세(저장 통계·필드 존재 비율 바·혼합 타입 강조·인덱스 속성·0회 배지), 컬렉션 검색,
  Redis 통계 타일·패널·정책 안내·선택된 DB 강조·그룹 표(ID 세그먼트 `*` 묶음, TTL 비율,
  혼합 타입)·큰 키·명령 통계, 스키마 화면의 상호 링크, 480px 레이아웃. 콘솔 에러 0건

**테스트가 찾아낸 실제 버그 2건**

1. **TTL이 없는 키가 분석에서 전부 빠졌다** — Redis는 "만료 없음"을 -1로 답하는데, go-redis는
   양수만 초 단위로 변환하고 이 센티널은 `time.Duration(-1)`(=-1ns)로 그대로 돌려준다.
   `-1 * time.Second`와 비교했으므로 조건이 어긋나 "사라진 키"로 분류되어 타입·TTL·크기 집계에서
   제외됐다. 그 결과 TTL 없는 키(정확히 화면이 찾아내려는 대상)가 하나도 보이지 않았다 →
   두 표기를 모두 받도록 수정. 통합 테스트가 "가장 큰 키가 blob이 아니다"로 드러냈다
2. **MongoDB 내부 컬렉션이 사용자 데이터처럼 보였다** — `system.profile`이 목록에 섞여
   문서 553개·필드 131개로 집계되고, `system.views`는 권한 오류 메시지만 남겼다. 컬렉션 수와
   전체 크기가 실제와 달라 보인다 → `system.*` 제외 + 제외 사실을 노트로 남김.
   같은 기준을 P3 introspect에도 적용해 두 화면이 다른 목록을 보여주지 않게 했다
   (P5의 PostgreSQL 확장 소유 객체 제외와 같은 원리)

**걷어낸 거짓 신호**: 접두사 그룹은 숫자·UUID 세그먼트를 `*`로 치환해 묶는다(P3에서 만든 규칙).
`session:a` 같은 비숫자 키로 테스트를 작성해 "그룹이 없다"는 실패를 만들었고, 원인은 코드가 아니라
테스트 데이터였다. 또 `redis-cli`는 stdin으로 넘긴 여러 줄을 실행하지 않아 시드가 조용히 누락됐다 —
명령마다 호출하도록 고쳤다.

### 로깅 보강 (2026-08-14)

**"서버가 이유 없이 꺼진다"는 보고에서 출발했다.** 조사해 보면 이유는 대개 기록돼 있었지만,
그 기록이 **사라지는 곳**에 있었다.

- stderr만 썼다 → 터미널을 닫거나 서비스로 띄우면 아무것도 남지 않는다
- 시작 실패(포트 충돌 등)는 stderr로만 나갔다
- 백그라운드 goroutine 패닉은 프로세스를 죽이면서 흔적을 남기지 않았다

고친 것:

| 문제 | 조치 |
|---|---|
| 기록이 사라진다 | stderr + `<data>/dbstudio.log` 동시 기록, 20MB 단위 로테이션(보관본 1개) |
| 런타임 크래시에 흔적이 없다 | `debug.SetCrashOutput`으로 `dbstudio.log.crash`에 스택 저장 |
| 왜 멈췄는지 모른다 | 신호 이름·정리 시작/완료·uptime을 각각 기록. 줄이 없으면 강제 종료라는 뜻 |
| 시작 실패 원인이 모호하다 | 실패 유형별 `hint`(포트 충돌 / 키 / 데이터 디렉터리) 추가 |
| goroutine 패닉이 프로세스를 죽인다 | 폴러·WS 펌프·SSE 라이터를 `applog.Recover`로 감싸 해당 작업만 중단 |
| 패닉이 조용히 500이 된다 | Fiber recover에 스택 로깅 연결 |
| 5xx·느린 요청을 알 수 없다 | 5xx는 ERROR, 5초 초과는 WARN, 나머지는 debug에서만 |

**설계에서 가장 중요한 판단**: 파일을 열지 못해도 서버는 뜬다. 로그를 못 쓴다고
서비스가 중단되면 그것이 더 큰 장애다. 대신 stderr에 경고를 남기고 stderr 전용으로 진행한다.

**검증 과정에서 찾은 실제 버그 3건** (모두 테스트가 먼저 드러냈다)

1. **시작 실패 이유가 파일에 남지 않았다** — 실패 로그를 `main()`에서 남겼는데,
   그 시점에는 `run()`의 defer가 이미 로그 파일을 닫아 놓았다. MultiWriter의 stderr 쪽만
   성공해서 화면에는 보이고 파일에는 없었다. 가장 중요한 한 줄이 빠진 것이다 →
   로거가 살아 있는 `run()` 안에서 기록하고, `main()`은 종료 코드만 정하도록 분리
2. **로테이션이 Windows에서 실패했다** — 크래시 출력을 로그 파일과 같은 파일로 보냈더니
   런타임이 그 핸들을 쥐고 있어 이름을 바꿀 수 없었다(Go는 `FILE_SHARE_DELETE` 없이 파일을 연다).
   조용히 실패하고 파일이 무한히 커진다 → 크래시 출력을 `.crash` 별도 파일로 분리
3. **로테이션 후 파일 핸들이 샜다** — `Close()`가 로테이션 이전의 핸들을 닫고 있었다.
   Windows에서는 그 파일을 지울 수도 없다 → 로테이터가 현재 핸들을 소유하고 Close에서 닫는다.
   `SetCrashOutput`은 파일을 복제해 런타임이 따로 들고 있으므로 Close에서 `nil`로 해제한다

**검증**: `applog` 단위 테스트 9건(파일 기록·레벨 필터·JSON·로테이션·핸들 해제·크래시 파일 분리·
열기 실패 시 동작·패닉 기록), 그리고 Windows에서 CTRL_BREAK를 보내 정상 종료 경로를 태우는
하네스로 "신호 → 정리 → 종료" 순서와 강제 종료 시 줄이 없는 것까지 확인했다.

### 비정상 종료 감지 (2026-08-14)

**"서버가 가만히 있다가 에러도 없이 꺼진다"는 두 번째 보고에서 나왔다.** 조사 결과 원인은
앱이 아니었다: 개발 중 쓰던 정리 명령(`Get-Process dbstudio | Stop-Process -Force`)이
**이름으로** 프로세스를 찾아, 리포지토리와 무관한 사용자 인스턴스까지 함께 종료시켰다.
강제 종료(TerminateProcess)는 프로세스에 아무 기회도 주지 않으므로 로그도 크래시 리포트도
남지 않는다 — 증상이 정확히 "이유 없이 꺼짐"이었다.

원인을 찾는 데 쓴 증거는 **로그가 아니라 파일 수정 시각**이었다(로그 마지막 줄 02:05,
WAL 마지막 쓰기 02:24 → 그 사이 살아 있었고 02:25에 내 명령이 실행됨). 이것이 문제였다:
앱이 스스로 말해 줄 수 있어야 한다.

**실행 중 표식**(`<data>/dbstudio.running`)을 도입했다.

| 상황 | 표식 | 다음 시작의 반응 |
|---|---|---|
| 정상 종료 | 지운다 | 조용하다 |
| 강제 종료·전원 차단 | 남는다 | "이전 실행이 종료 기록을 남기지 않았습니다" + pid·시작·**마지막 생존 시각** |
| 런타임 크래시 | 남는다 + `.crash`에 스택 | 위와 같지만 "런타임 크래시로 보입니다" + 스택 앞부분 |
| 다른 인스턴스가 실행 중 | 남아 있고 주인이 살아 있다 | "같은 데이터 디렉터리를 다른 인스턴스가 쓰고 있습니다" (표식을 건드리지 않는다) |

1분마다 갱신하는 이유는 "몇 시까지 살아 있었는가"를 말하기 위해서다. 표식의 존재만으로는
비정상 종료라는 사실만 알 수 있고, 언제 죽었는지는 알 수 없다.

**검증 과정에서 찾은 실제 버그 2건** (둘 다 테스트가 먼저 드러냈다)

1. **살아 있는 인스턴스를 크래시로 오해했다** — 표식이 있으면 무조건 "비정상 종료"로
   보고하고 표식을 덮어썼다. 같은 데이터 디렉터리를 쓰는 두 번째 인스턴스가 첫 번째의
   표식을 가져가고, 자기가 끝날 때 지워버린다 → 살아 있는 쪽의 비정상 종료를 영구히
   감지할 수 없게 된다. 표식 주인의 생존을 확인하고, 살아 있으면 손대지 않도록 고쳤다
2. **Windows에서 죽은 PID를 살아 있다고 판단했다** — `os.FindProcess`는 최신 Go의
   Windows 구현에서 종료된 PID에도 성공을 돌려준다. 그 결과 강제 종료 직후 재시작하면
   "다른 인스턴스가 있다"는 엉뚱한 안내가 나왔다(가장 흔한 시나리오에서 정확히 틀린 답이다)
   → `OpenProcess` + `WaitForSingleObject(0)`로 종료 여부를 직접 확인한다.
   `GetExitCodeProcess`의 `STILL_ACTIVE(259)`를 보는 방법은 종료 코드가 259인 프로세스와
   구분되지 않아 쓰지 않았다. PID 재사용 대비로 심장박동 신선도(3분)를 함께 본다

**개발 도구도 고쳤다.** 이름이 아니라 **실행 파일 경로**로 대상을 고르는 종료 스크립트를
쓴다. 다른 경로에서 도는 인스턴스는 종료하지 않고 "건드리지 않음"으로 표시만 한다.
같은 사고를 두 번 낼 수 없게 만드는 것이 사과보다 낫다.

**검증**: `runstate` 단위 테스트 9건(표식 생성·삭제, 없는 파일=정상, 깨진 파일도 사실 유지,
현재 프로세스=살아 있음, 오래된 심장박동=죽음, **종료된 실제 PID=죽음**, 심장박동 갱신,
컨텍스트 취소, JSON 형식), 그리고 실제 프로세스를 강제 종료·정상 종료·이중 실행시켜
네 시나리오를 확인하는 하네스(13항목).

## 7. 계획 단계의 열린 결정 사항 — 결론

1. **H2 지원** → **제외.** Pure Go 드라이버가 존재하지 않는다(자체 TCP 프로토콜/JDBC 전용).
   지원하려면 JVM 사이드카가 필요해 단일 바이너리 원칙과 정면으로 충돌한다.
   `kind` enum과 UI 종류 목록에서 제거했다.
2. **Oracle·MSSQL 검증 환경** → **확보했다.** Docker로 Oracle Free 23과 MS-SQL 2022를 띄워
   introspect·지표·로그·DDL 라운드트립을 실제로 검증했다. 문서 기반 추측으로 남은 쿼리는 없다.
3. **prod DB 쓰기 안전장치** → **실행 계획 + 롤백 SQL 사전 검토 + 2차 승인**으로 확정(사용자 동의).
   여기에 구조 지문 비교(사전 검사), 커넥션 이름 확인 문구, 문장 단위 실행 기록을 더했다.
   백업은 외부 커맨드(`-backup-cmd`) 훅으로만 제공한다 — 도구와 정책이 조직마다 다르고,
   잘못 만든 백업은 없는 것보다 위험하다.
4. **수평 확장** → **단일 인스턴스 전제를 유지한다.** 세션과 ERD 허브가 프로세스 메모리를 쓴다.
   `erdhub`가 전송 계층을 모르는 구조로 분리되어 있어 공유 계층(Redis pub/sub 등)을 끼울 수는
   있지만, 지금 넣으면 검증할 수 없는 복잡성만 늘어난다.
5. **DB별 기능 차이** → **`Capabilities()`로 처리했다.** introspect·monitor·logs·migrate·erd·explore
   여섯 플래그를 어댑터가 노출하고, 화면·API 게이트·AI 툴이 모두 같은 값을 본다. 미지원 기능은
   화면에서 비활성화되고 API는 "지원하지 않는다"를 명시적으로 답한다.

### MongoDB 인증 방식 설정 (2026-08-14)

사용자 요청: "MongoDB의 경우 authMechanism을 세팅할 수 있게 수정해주세요."

기존 약속대로 옵션이 붙지 않는다.

### P11 완료 기록 (2026-08-14) — 데이터 열람·수정, 매크로, 프로필 이미지

P10 시점에 남겨 두었던 "데이터 열람" 질문에 답하면서 시작했다. 그 답이 나머지 두 기능의
설계를 결정했다.

**등급을 하나 더 만들지 않았다.** 원래 계획은 `monitor < erd < migrate` 사다리에 칸을 더하는
것이었는데, 어느 자리에 넣어도 틀린다. `migrate` 위에 넣으면 "데이터를 보려면 마이그레이션
권한이 있어야 한다"가 되고, `monitor` 아래에 넣으면 "지표를 보려면 고객 데이터를 볼 수 있어야
한다"가 된다. 문제는 자리가 아니라 **한 줄로 세운 것 자체**였다.

그래서 데이터 능력을 **독립적인 축**으로 분리했다(`data.read` / `data.write` / `sql.run`).
등급과 마찬가지로 커넥션 단위이며, 서로를 함의하지 않는다. 예외 하나는 `data.write`가
`data.read`를 요구하는 것뿐이다 — 보이지 않는 행은 고를 수 없다.

전역 권한(`macro` / `script.run`)은 세 번째 자리다. 커넥션에 매이지 않는 것들이므로
커넥션별로 부여하면 "어느 커넥션의 권한으로 셸을 실행하는가"라는 답할 수 없는 질문이 생긴다.

**데이터 접근 계층의 규칙 두 가지.**

- *식별자는 사용자 입력에서 오지 않는다.* 테이블·컬럼·정렬 기준은 요청에 담겨 오지만,
  쿼리에 넣기 전에 DB에서 읽은 실제 목록과 대조해 그 목록의 문자열로 치환한다. 값은 파라미터로만
  보낸다. 인용만으로 막으려 하면 언젠가 인용을 빠뜨린 경로가 생긴다.
- *수정은 기본키로만 한다.* 기본키가 없는 테이블은 편집 불가로 표시하고, 복합키의 일부만 오면
  거부한다. 한 행을 고치려던 UPDATE가 여러 행을 바꾸는 것이 이 기능에서 가장 흔한 사고다.

컬럼 메타데이터는 방언별 카탈로그 쿼리 대신 `SELECT * FROM t WHERE 1=0`의 결과 메타데이터로
얻는다. 다섯 벌의 쿼리를 쓰지 않아도 되고, 뷰나 권한으로 컬럼이 숨겨진 경우에도 실제 결과와
어긋나지 않는다. 기본키만 방언별 쿼리 한 줄이 필요하다.

문장 분리는 직접 만들었다. `strings.Split(s, ";")`으로는 문자열 리터럴·주석·PostgreSQL
달러 인용 안의 세미콜론에서 문장이 조각나고, 사용자는 자기 SQL이 틀렸다고 오해한다.

**매크로는 "저장된 것만, 실행자의 권한으로"**가 전부다. `Engine.Start`가 그래프를 인자로 받지
않고 매크로 ID와 버전만 받는 것이 그 약속의 구현이다 — 편집 중인 내용을 실행할 방법이 없어야
"무엇이 실행됐는지"가 버전 하나로 특정된다. 버전은 추가만 되고 롤백도 새 버전을 만든다.
포인터만 옮기면 그 뒤의 버전들이 미래에 남아 이력이 시간순으로 읽히지 않는다.

실행 모델은 **제어 흐름 + 변수 가방**이다. 진짜 데이터플로우(데이터 포트를 선으로 잇는 방식)를
쓰지 않은 이유는, DB 자동화에서 노드가 만드는 것은 대개 "행 목록" 하나인데 그것을 쓰는 쪽은
세 노드 뒤의 조건식이거나 Lua 스크립트 안이기 때문이다. 선으로 표현하면 화면이 선으로 덮이고
정작 알고 싶은 실행 순서가 묻힌다. 반복은 되돌아오는 간선 대신 반복 노드가 몸통을 소유한다
(`body` / `done` 포트) — 되돌아오는 간선은 종료 조건이 어디 있는지 보이지 않는다.

무엇을 내장 노드로 만들고 무엇을 Lua에 맡길지는 **권한이 걸린 동작인가**로 갈랐다.
DB 접속·셸 실행·매크로 호출은 실행자 권한을 확인해야 하므로 내장이고, 값을 만지는 일은 전부 Lua다.
후자를 노드로 만들기 시작하면 "문자열 자르기 노드"가 생기고 결국 그림으로 프로그램을 쓰게 된다.

Lua 샌드박스는 화이트리스트다(`base`·`table`·`string`·`math`만). 블랙리스트는 언젠가 하나를
빠뜨리고, 빠뜨렸다는 사실은 사고가 난 뒤에 알게 된다. 무한 루프는 컨텍스트 타임아웃으로 멈춘다 —
GopherLua에는 명령 수 훅이 없고, 있더라도 "몇 개가 정상인가"는 답할 수 없는 질문이다.

셸은 **이중 게이트**다(`-allow-shell` + `script.run`). 권한은 클릭 몇 번으로 바뀌지만 이 기능이
켜지면 앱은 원격 셸이 되므로, 그 결정은 프로세스를 띄우는 사람이 해야 한다.

**프로필 이미지는 이전 결정을 뒤집었다.** P1에서 "업로드를 받지 않는다"고 적었고 그 이유
(저장·상한·디코딩·삭제 정책이 딸려 온다)는 지금도 사실이다. 달라진 것은 비용을 어디에 두느냐다:
바이트를 메타 DB에 넣으면 백업·삭제·권한이 나머지 데이터와 같은 규칙을 따르고, 사용자당 한 장에
상한이 있으므로 비용이 작다. 형식은 확장자가 아니라 **바이트를 디코딩해** 확인하고, SVG는 받지
않는다(스크립트를 품을 수 있는 문서 형식이다). URI는 서버가 한 번 내려받아 저장한다 — URL을 그대로
두면 CSP를 외부까지 열어야 하고 링크가 깨지면 아바타가 사라진다. 대신 SSRF를 막기 위해 사설망·
루프백을 기본 차단하고 리다이렉트 대상도 같은 검사를 거친다.

### P12 완료 기록 (2026-08-14) — 백업·복구, 버전 롤백, 구문 강조

**백업: 층을 나눴다.** 이 앱에는 이미 `-backup-cmd` 훅이 있었다(P7). 그래서 첫 질문은
"또 만들 필요가 있는가"였고, 답은 **층이 다르다**였다. 훅은 마이그레이션 직전에 조직의 도구를
부르는 안전망이고, 여기서 만드는 논리 덤프는 **옮기고 재현하기 위한 것**이다(운영 데이터를
개발 DB에 부어 문제를 재현하는 것이 가장 흔한 용도다). 물리 백업·PITR은 여전히 하지 않는다 —
DB마다 절차가 다르고 잘못 만든 물리 백업은 없는 것보다 위험하다.

덤프 생성에서 가장 조심한 것은 **값의 왕복**이다. 데이터 화면(P11)이 이미 행을 읽고 있었지만
그 값을 쓸 수 없었다. 화면은 보여주기 위해 값을 가공하기 때문이다 — 바이너리를 16진 문자열로
바꾸고 긴 문자열을 자른다. 그것으로 덤프를 만들면 복구했을 때 다른 데이터가 들어간다.
그래서 원본 값을 그대로 흘려보내는 경로(`StreamRows`)와 방언별 리터럴 인코더(`SQLLiteral`)를
따로 만들었다. 이 인코더가 이 기능에서 가장 조용히 틀릴 수 있는 자리라 테스트를 가장 두껍게 썼다
(작은따옴표, MySQL만 필요한 백슬래시 이스케이프, 방언별 바이너리 표기 5종, Oracle의 시각 형식,
NaN, NUL).

읽기는 커서 하나로 한다. 페이지(LIMIT/OFFSET)로 읽으면 뒤로 갈수록 앞의 행을 다시 세므로
큰 테이블에서 전체 시간이 행 수의 제곱에 가까워진다.

상한을 넘긴 덤프는 **자르지 않고 실패**시킨다. 잘린 백업은 복구할 수 있다고 믿게 만들므로
없는 백업보다 위험하다. 상한은 압축 전 크기로 잰다 — 압축률이 데이터에 따라 열 배씩 달라져서
압축 후로 재면 사용자가 예측할 수 없다.

**복구는 이 앱이 만든 백업만 받는다.** 외부 .sql 업로드를 넣지 않은 이유는 그것이 결국
"임의의 SQL을 파일로 실행하는 기능"이고, 그 통로가 이미 SQL 콘솔(`sql.run`)에 있기 때문이다.
두 경로가 같은 능력을 가리키면 어느 쪽이 진짜 관문인지 흐려진다. 복구 권한은 `migrate` 등급과
`data.write`를 **둘 다** 요구한다 — 구조를 바꾸면서 데이터를 덮어쓰는 동작이므로 한쪽만으로
허용하면 그 권한 하나로는 못 하는 일을 하게 된다.

**버전 롤백은 마이그레이션이 된다.** "v3으로 되돌린다"는 현재 구조에서 v3 구조로 가는
마이그레이션이므로, 전용 실행 경로를 만들지 않고 기존 흐름(리뷰 → 승인 → 프리체크 → 실행)을
그대로 탔다. 전용 경로를 만들면 승인 없이 구조를 바꾸는 길이 하나 더 생기고, 그것이 P7부터
막으려던 상황이다. "되돌리기니까 안전하다"는 직관도 틀렸다 — 그 버전 이후에 만들어진 테이블은
되돌리면 삭제된다. 그래서 대화상자가 누르기 전에 변경 목록·파괴적 변경 수·실행될 SQL을 보여준다.
적용 후 등록되는 버전의 출처는 `rollback`이다(그 상수는 P7에 이미 있었고 마이그레이션 롤백에만
쓰이고 있었다).

**구문 강조는 직접 만들었다.** 번들러가 없고 CSP가 `script-src 'self'`라 CDN은 불가능하며,
highlight.js를 통째로 넣으면 바이너리에 수백 KB가 붙는다. 필요한 것은 네 언어의 토큰을 나누는
것뿐이라 스캐너 하나와 규칙 표로 끝났다. 두 가지를 지켰다: **innerHTML을 쓰지 않고**(강조 대상은
사용자가 쓴 SQL이다 — 문자열을 이어 붙이는 순간 저장형 XSS의 자리가 생긴다),
**토큰을 다시 이으면 원본과 같아야 한다**(규칙에 걸리지 않는 문자는 한 글자씩 평문으로 흘려서
어떤 입력에도 누락이 없게 했다).

편집기는 투명한 textarea를 강조된 pre 위에 겹치는 고전적인 방법이다. contenteditable을 쓰면
커서 위치·되돌리기·IME·붙여넣기를 직접 다뤄야 하고 그중 하나만 틀려도 한글 입력이 깨진다.

**검증 결과**

- 단위 테스트: `dbx` 8건(리터럴 인코딩 — 따옴표·백슬래시 방언별·불리언·바이너리 5종·
  Oracle 상한·시각 형식·NaN·NUL), `backup` 11건(범위·형식 판정, 경로 탈출 6케이스,
  대상 매칭, 취소와 실패 구분, Redis 명령 생성·따옴표 처리·점수 분리, 크기 상한 초과 시 실패)

- 실서버 스모크: SQLite 전체 덤프 → 파일 내용 확인 → **다른 커넥션에 복구 → 값 비교**.

  모두 원본과 일치. 미리보기·다운로드·삭제 동작 확인
- 버전 롤백 스모크: 기준선 v1 → 외부 변경(테이블 추가 + 컬럼 추가) v2 → 롤백 미리보기
  (파괴적 2건, SQL 2문장) → 계획 생성(`rollbackToNo: 1`, 승인 2명 필요) → 초안 상태 실행 차단(400)
  → 본인 승인 거부(403) → 두 명 승인 → 확인 문구 요구(`confirm_required`) → 실행 →
  **v3이 `source=rollback`으로 등록**되고 스키마가 v1로 복원됨
- 권한 게이트 실측: `migrate` 등급 + 데이터 능력 없음 → 구조만 백업 202 / 전체 백업 403 /
  내려받기 403 / 복구 403. `data.read`+`data.write` 추가 → 전체 백업 202 / 내려받기 200.

**설계하며 되돌린 것 하나**: 백업 진행 상황을 매크로처럼 SSE로 스트리밍하려다 폴링으로 바꿨다.
매크로 로그는 줄이 쌓이고 순서가 의미를 갖지만, 백업이 만드는 정보는 "지금 어느 테이블의 몇
번째 행"이라는 **덮어쓰면 되는 값 하나**다. 놓쳐도 잃을 것이 없는 값에 스트림 배관을 놓는 것은
코드만 늘린다. 대신 화면이 1.2초마다 다시 읽고, 진행 중인 작업이 없으면 폴링을 멈춘다.

**구현 중 잡은 것**: 백업 목록 화면의 폴링 타이머가 새는 경로가 있었다. 화면을 다시 그리는 것이
라우터만이 아니라 타이머 자신이기도 해서(스스로를 다시 부른다), 라우터가 붙잡은 정리 함수는 첫
타이머만 알고 그 뒤로 이어진 타이머는 아무도 모르는 상태가 된다 — 화면을 떠나도 목록이 계속
되살아난다. 타이머를 모듈에 하나만 두어 누가 다시 그렸든 하나만 살아 있게 했다.

### P13 완료 기록 (2026-08-14) — MCP 서버와 API 토큰

**툴 레지스트리를 나누지 않았다.** 첫 갈림길은 "MCP용 툴을 따로 만들 것인가"였고 답은 분명했다.
두 벌을 만들면 어느 한쪽에만 있는 툴이 생기고, 더 나쁘게는 **권한 검사가 한쪽에만 들어간다.**
그래서 P9의 레지스트리를 그대로 쓰고 P11~P12의 새 기능 툴(데이터·SQL·매크로·백업·롤백) 12종을
거기에 더했다. 결과적으로 앱 안의 어시스턴트도 같은 툴을 함께 얻었다.

패키지는 나눴다. `internal/mcp`는 프로토콜(JSON-RPC 타입, 판 협상)만 알고 앱을 모른다.
툴 실행은 `internal/api/mcp_handlers.go`가 기존 경로로 넘긴다. 이렇게 하면 프로토콜을 그 자체로
시험할 수 있고(스토어도 커넥션도 필요 없다), 반대로 툴은 어느 전송을 타는지 몰라도 된다.

**전송은 Streamable HTTP만.** stdio를 넣지 않은 이유는 그것이 같은 SQLite 파일을 여는 두 번째
프로세스를 뜻하기 때문이다 — 이 앱은 P6부터 단일 인스턴스를 전제해 왔고, 그 전제를 MCP 때문에
깨는 것은 순서가 뒤바뀐 일이다.

**인증에서 가장 오래 고민한 것은 쿠키를 받을 것인가였다.** 받으면 브라우저에서 바로 붙일 수 있어
편하지만, 브라우저가 쿠키를 자동으로 실어 보내므로 다른 사이트가 이 엔드포인트를 부를 수 있게 된다.
`/api/v1`은 `X-Requested-With` 검사로 그것을 막고 있는데, MCP 클라이언트에 커스텀 헤더를 요구하는
것은 규약 밖의 요구다. 그래서 **쿠키를 아예 받지 않기로** 했다 — Bearer 토큰만 받으면 CSRF의
전제(자동 전송)가 성립하지 않는다.

토큰은 세션과 다른 것으로 만들었다. 세션 TTL을 늘려 겸용하면 브라우저 세션까지 길어진다.
저장은 세션과 같은 규칙(해시만), 발급은 자기 것만(슈퍼 어드민도 남의 토큰을 만들 수 없다),
폐기는 행을 남긴다("언제까지 살아 있었는가"가 사고 조사에 필요하다).

**쓰기를 어떻게 다룰 것인가**가 두 번째 갈림길이었다. 앱 안에서는 AI가 제안을 만들고 사용자가
화면에서 승인 버튼을 누른다. MCP에는 그 화면이 없다. 세 가지를 고려했다.

- *제안만 만들고 웹에서 승인받게 한다* — 안전하지만 MCP로 무언가를 하려면 매번 브라우저로
  건너가야 해서 기능이 사실상 죽는다.
- *그냥 실행한다* — 클라이언트가 도구 호출 전에 사람에게 묻는다는 것에 기대는 셈인데,
  그것은 우리가 검증할 수 없는 남의 동작이다.
- *토큰 범위로 가른다* ← 골랐다.

발급할 때 쓰기 허용 여부를 명시적으로 고르게 하고, 읽기 토큰에는 변경 툴이 **목록에도 나오지
않게** 했다(보이는데 부르면 거부되는 툴은 모델이 계속 시도한다). 여기에 툴 주석
(`readOnlyHint`/`destructiveHint`)을 붙여 클라이언트가 사람에게 확인을 받도록 유도한다.
그리고 무엇보다 **서버 쪽 게이트는 그대로다** — 능력 판정, 승인 수, 확인 문구가 전부 살아 있고,
확인 문구가 필요한 동작(운영 DB 복구 등)은 MCP로는 아예 실행되지 않는다.

쓰기 툴을 실행할 때 Propose를 먼저 부르는 것도 그 연장이다. 화면에서는 그 결과를 사용자에게
보여주지만 여기서는 **검증 단계**로 쓴다 — Propose는 아무것도 바꾸지 않으면서 인자와 권한을
확인하므로, 건너뛰면 Apply 안에서만 잡히는 실수가 생긴다.

**검증 결과**

- 단위 테스트: `mcp` 8건(판 협상, 알림 판정 — `id:0`이 알림으로 새는 흔한 실수 포함,
  배치·공백·빈 본문 파싱, isError 직렬화, 응답에 result/error가 함께 나오지 않는지,
  안내문의 범위 표기, 툴 주석 직렬화), `store` 7건(해시만 저장되는지 원문으로 직접 조회해 확인,
  조회, 폐기 후에도 기록이 남는지, 남의 토큰 폐기·삭제 차단, 만료 판정, 사용자 삭제 시 CASCADE,
  모르는 범위가 read로 떨어지는지)
- 실서버 스모크: 인증 없음/잘못된 토큰/폐기된 토큰 → 401. initialize 협상 성공.
  `tools/list`가 읽기 토큰에 19종·쓰기 토큰에 31종(변경 12종)을 반환.
  `query_data`·`list_connections` 실행, `run_sql`의 읽기 전용 강제(UPDATE 거부),

  목록에서 제외됨(23종). 감사 로그에 `mcp.tool.call`·`mcp.auth.denied`·`token.created`·
  `token.revoked`가 남는 것 확인

### P14 완료 기록 (2026-08-14) — 매크로 자동 실행과 외부 API 호출

**"누구의 권한으로 도는가"에 답했다.** P13까지 이것은 미결로 남아 있었고(§8에 적혀 있었다),
스케줄링을 넣으려면 먼저 답해야 하는 질문이었다. 세 가지를 놓고 골랐다.

- *서비스 계정을 만들어 그 권한으로 돌린다* — 흔한 방식이지만 "툴은 호출자의 권한으로 실행된다"는
  앱 전체의 규칙이 자동 실행에서만 무너진다. 트리거를 만들 수 있는 사람은 누구나 서비스 계정의
  권한을 빌려 쓸 수 있게 되므로, 권한 상승 통로가 하나 생기는 셈이다.
- *마지막으로 수정한 사람의 권한으로 돌린다* — 남의 트리거를 고치는 순간 그 책임이 조용히 옮겨온다.
- *만든 사람(소유자)의 권한으로 돌린다* ← 골랐다.

소유자는 만들 때 고정되고 수정으로도 바뀌지 않는다(바꿀 수 있으면 남의 권한으로 도는 자동 실행을
만들 수 있다). 발화할 때마다 소유자를 다시 읽어 권한을 판정하므로, **권한이 회수되면 자동 실행도 멈춘다.**
그것이 옳은 동작이다 — 사람이 못 하게 된 일을 그 사람이 만든 자동화가 계속하고 있으면 안 된다.

이 결정의 부산물로 **권한 판정이 한 곳으로 모였다.** 그전에는 같은 계산이 세 벌 있었다(화면이 실행
버튼을 막을 때, MCP/AI 툴이 계획을 세울 때, 그리고 이제 스케줄러). 셋이 각자 계산하면 언젠가 답이
갈라지는데, 갈라진 쪽이 자동 실행이면 아무도 알아채지 못한다. `macro.Engine.Blockers`로 뽑아
세 곳이 같은 함수를 부른다.

**두 종류를 한 테이블에 뒀다.** 정기(schedule)와 조건(event)은 조건 필드만 다를 뿐 목록·활성화·
소유자·실행 이력이 전부 같다. 나누면 화면도 API도 두 벌이 되는데 정작 다른 것은 몇 개 컬럼뿐이다.
사용자가 답하려는 질문도 하나다 — "이 매크로가 언제 저절로 도는가".

**cron은 직접 구현했다.** 필요한 것은 표준 5필드고, 그것은 표 다섯 개와 "다음 시각 찾기" 한 함수로
끝난다. 라이브러리를 들이면 초 필드·`@every`·자체 스케줄러 고루틴처럼 쓰지 않는 것들이 함께 들어오고,
그중 하나가 우리 실행 모델(소유자 권한·중복 방지·놓친 실행)과 어긋나기 시작한다.
다음 시각은 1분씩 늘려가며 찾는다 — 영리한 방법도 있지만 "2월 30일"처럼 영원히 오지 않는 식을
다루려면 어차피 상한이 필요하고, 그 상한(4년) 안에서는 단순한 쪽이 틀릴 여지가 없다.
`time/tzdata`를 `internal/macro`에서 넣는다(main이 아니라). 시간대를 필요로 하는 것이 그 파일이고,
main에 두면 스케줄러를 쓰는 다른 바이너리와 테스트가 조용히 tzdata 없이 돈다.

**놓친 실행은 따라잡지 않는다**(유예 1시간). 새벽 3시 정리를 오전 9시에 실행하는 것은 대개 틀린
일이고, 밤새 꺼져 있었다면 여덟 번을 몰아 실행하게 된다. 같은 이유로 이벤트 디바운스 상태는
메모리에만 둔다 — 재시작 뒤 첫 이벤트는 억제하지 않는 편이 안전하다.

**이벤트는 "새로 열릴 때"만 받는다.** 모니터가 occurrences만 올리는 경우까지 받으면 지표가 임계치
근처에서 흔들릴 때마다 매크로가 시작된다. 그 위에 트리거별 최소 간격을 둔다. 모니터 쪽에는
`EventSink` 인터페이스 하나만 추가했다 — 모니터가 매크로를 알 필요는 없다.

**HTTP는 셸과 다른 게이트를 골랐다.** 셸은 `-allow-shell`(서버) + `script.run`(사용자) 이중
게이트인데, HTTP에는 서버 플래그를 두지 않았다. 셸은 켜지는 순간 앱이 원격 셸이 되지만 HTTP는
이 앱이 이미 하고 있는 일(Git 연동, AI 프로바이더, 프로필 이미지 가져오기)과 같은 종류다.
게이트를 하나 더 두면 실제로 막는 것 없이 설정만 늘어난다.
그래도 권한을 따로 둔 것은 이것이 **데이터 반출 통로**이기 때문이다 — 조회 권한과 결합하면
DB에서 읽은 값을 임의의 주소로 보낼 수 있다. 링크로컬은 허용 목록에 적어도 막고(클라우드 메타데이터),
리다이렉트는 매 홉마다 다시 검사한다.

**구현 중에 드러난 것 하나.** 스모크 도중 멤버 계정의 전역 권한이 전혀 먹지 않는 것을 발견했다 —
`LookupSession`이 `u.perms`를 SELECT하지 않아 모든 인증 요청이 "권한 없음"으로 보였다.
증상이 고약한 종류다: 권한을 주는 화면에서는 값이 제대로 보이고(`GetUser`는 읽는다),
슈퍼 어드민은 역할로 통과하므로 관리자가 직접 눌러 보면 잘 된다. 즉 **멤버에게만** 나타난다.
P11에서 `perms`를 추가할 때 세션 조회 경로를 빠뜨린 것으로, 아바타에서 같은 실수를 한 적이 있어
그때 남긴 테스트(`TestAvatarRoundTrip`)와 같은 모양의 회귀 테스트를 붙였다.

### P15 완료 기록 (2026-08-14) — 서버 하나에 DB 여러 개

**갈림길은 "커넥션을 무엇으로 볼 것인가"였다.** 요구는 "커넥션 하나로 여러 DB를 관리"였고,
그대로 읽으면 커넥션이 DB 목록을 갖고 화면마다 DB 선택기가 붙는 모양이 된다. 그렇게 하지 않았다.

`connection_id`는 이 앱에서 **18개 테이블의 기준 단위**다(접근 권한·능력 등급·지표·이벤트·드리프트·
ERD 문서·스키마 버전·마이그레이션·백업·트리거). 커넥션 하나가 DB 여러 개를 뜻하게 되면 그 18개
전부에 database 차원을 더해야 하고, 더 나쁜 것은 **권한이 조용히 넓어진다는 점**이다 — 권한이
커넥션 단위이므로 "이 DB만 허용"을 표현할 방법 자체가 사라진다.

그래서 반대 방향으로 갔다. 커넥션을 쪼개는 대신 **접속 정보를 서버로 위에 뽑았다.**
`model.Connection`이 접속 정보를 서버에서 조인해 채우므로 다운스트림은 서버가 생긴 것을 모른다.
사용자가 얻는 것은 같다 — 자격증명 한 벌, DB 여러 개, 한 번에 등록.

**환경만은 DB에 남겼다.** 서버 속성처럼 보이지만 이 값이 뜻하는 것은 "이 대상을 얼마나 조심히
다룰 것인가"이고(운영이면 승인 수와 확인 문구가 붙는다), 한 서버에 실운영 DB와 임시 DB가 함께 사는
일은 흔하다. 마침 SQLite가 CHECK 제약이 걸린 컬럼을 지우지 못해 기술적으로도 그 편이 맞았다.

**이관은 자동으로 묶지 않는다.** 커넥션 하나당 서버 하나를 만든다. `(종류, 호스트, 포트)`가 같으면
같은 서버처럼 보이지만 자격증명이 다를 수 있고, 봉인된 비밀번호는 SQL로 같은지 비교할 수조차 없다.
잘못 묶으면 한쪽 자격증명이 조용히 사라지고 그 사실은 다음 접속 실패로만 드러난다. 대신 화면에
**서버 병합**을 두어, 값을 확인할 수 있는 사람이 명시적으로 합치게 했다.

**권한은 서버로 주고 DB로 뺀다.** DB 열 개짜리 서버에서 체크박스를 열 번 누르게 하면 결국
"그냥 전체 허용"으로 이어져 권한 모델이 무력해진다. 그래서 서버 단위 일괄 부여를 얹되 판정은
**좁은 쪽이 이긴다**(DB > 서버 > 기본값). 반대로 두면 예외를 적을 수 없다.

**DB 목록은 서버에 직접 물어본다.** 이름을 손으로 적게 하면 오타가 나고, 오타는 접속 실패로만
드러나는데 그것은 자격증명 문제와 구분되지 않아 엉뚱한 곳을 뒤지게 된다. PostgreSQL·MySQL·MS-SQL·
MongoDB·Redis는 목록을 읽어 온다. Oracle은 서비스/PDB 나열에 CDB 권한이 필요하고, SQLite는 파일
하나가 곧 DB라서 둘 다 직접 입력한다 — 이 경우 서버만 먼저 만드는 것도 막고("대상이 곧 접속 정보의
일부입니다") 커넥션 등록으로 안내한다.

**검증 과정에서 드러난 것 둘.**

첫째는 테스트가 찾았다. DB 하나만 등급을 "없음"으로 내려도 서버에서 물려받은 데이터 능력이 남아
그 DB가 여전히 열려 있었다. 권한 화면에는 "없음"으로 보이므로 **화면이 거짓말을 하는** 상태였다.
DB 단위 none은 "예외를 빼겠다"는 뜻이므로 물려받은 능력도 함께 지우도록 고쳤다(그 DB에 능력을 따로
지정했다면 의도한 것이므로 남긴다).

둘째는 실서버 스모크가 찾았다. DB 이름만 고치는 요청에는 접속 정보가 들어 있지 않은데,
"빈 호스트 = 호스트를 지우려 한다"로 읽어 서버 수정 경로로 새고, 종류가 비어 있어 400이 났다 —
화면에서는 "저장이 안 된다"로만 보였을 것이다. 빈 값을 "바꾸지 않겠다"로 읽도록 고쳤다.
접속 정보를 실제로 지우는 일은 없으므로(호스트 없는 서버는 접속할 수 없다) 잃는 것이 없다.

**검증 결과**

### P15 추가 — MCP·어시스턴트 툴 (2026-08-14)

P14·P15에서 만든 기능을 툴 레지스트리에 더했다. 레지스트리는 한 벌이므로 MCP와 앱 안의
어시스턴트가 함께 얻는다(P13의 결정). 31종 → **38종**(조회 22, 변경 16).

- 서버: `list_servers`, `list_server_databases`(서버에 실제로 접속해 읽는다), `register_databases`
- 자동 실행: `list_macro_triggers`, `create_macro_trigger`,
  `set_macro_trigger_enabled`, `delete_macro_trigger`

**넣지 않은 것과 그 이유가 이 작업의 실질이다.**

*서버 등록·비밀번호 변경*은 자격증명을 인자로 받아야 한다. 그러면 비밀번호가 대화 기록에 남고
AI 프로바이더로 전송된다 — 툴 하나 편하자고 감수할 일이 아니다. *서버 삭제·병합*은 DB 여러 개와
그 지표·이벤트·버전·ERD를 함께 지우거나 "두 자격증명 중 무엇이 맞는가"라는 사람의 판단을 요구한다.
되돌릴 수 없는 쪽으로 크게 움직이는 동작은 승인 절차가 아니라 화면에 둔다.
반면 `register_databases`는 이미 등록된 서버의 자격증명을 그대로 쓰므로 새 비밀을 받지 않고,
잘못 넣어도 관리 목록에서 빼면 그만이라 넣었다.

**노출 게이트를 하나 늘렸다.** 기존에는 `SuperadminOnly`뿐이었는데 서버·DB 등록은 어드민의 일이다.
둘을 합치면 어드민이 자기 일을 툴로 할 수 없게 되므로 `ConnManagerOnly`를 따로 두었다.

**트리거 생성은 매크로 실행 권한을 먼저 확인한다.** 트리거는 만든 사람의 권한으로 돌기 때문에,
지금 실행할 수 없는 매크로에 자동 실행을 걸면 반드시 나중에 실패한다. 그 실패는 아무도 보고 있지
않은 시각에 일어나므로, 만드는 시점에 막는 편이 낫다. 검증은 화면과 같은 함수(`triggerParams`)를
쓴다 — 규칙이 두 벌이 되면 툴로 만든 트리거만 화면에서 열리지 않는 식으로 어긋난다.

**검증 결과**

- 단위 테스트 4건: 레지스트리 정합성(쓰기 툴에 Propose/Apply가 모두 있는지, 쓰기 툴에 Run이
  없는지 — 있으면 모델이 승인 없이 실행한다), 새 툴 등록 여부, 권한별 노출(멤버에게 서버 관리 툴이
  보이지 않고 매크로 권한 없는 어드민에게 트리거 툴이 보이지 않는지), **어떤 툴도 비밀번호류를
  인자로 받지 않는지**(나중에 편의를 위해 되살리는 것을 막는다)
- MCP 실측: `tools/list` 38종, 새 툴의 주석(readOnlyHint/destructiveHint) 확인,
  `list_servers`·`list_server_databases`(실제 MySQL에서 6개 DB를 읽고 registered/system 표시),
  `register_databases`(등록 성공 → 중복 재등록 거부), 트리거 생성(잘못된 cron 거부, 정기·조건 둘 다)·
  목록·켜기끄기(이미 꺼진 것을 또 끄면 거부)·삭제

- 어시스턴트: 같은 38종이 조회/변경 구분과 함께 노출됨

### P16 완료 기록 (2026-08-14) — 설계를 시작하는 자리와, 있는 것을 읽는 자리

**세 갈래의 요구가 하나의 축으로 모였다: "SQL과 ERD 사이를 오갈 수 있는가."**

**1. 대상 DB 없는 초안.** 지금까지 모든 초안은 커넥션을 하나 정해야 만들 수 있었다. 그 제약에는
근거가 있었다 — dialect와 편집 권한이 커넥션에서 나온다. 하지만 설계는 DB를 만들기 전에 시작되는
일이 더 많고, "어디에 적용할지"는 나중에 정해도 되는 것이었다.

`erd_documents.connection_id`를 NULL 허용으로 바꿨다. SQLite는 NOT NULL을 없앨 수 없어 테이블을
새로 만들어 옮겨야 하는데, **외래키 검사가 켜진 채로 옛 테이블을 DROP 하면 `erd_ops`와
`erd_chat_messages`가 CASCADE로 함께 사라진다.** `PRAGMA foreign_keys`는 트랜잭션 안에서 바뀌지
않으므로, 마이그레이션 러너에 `-- +no-foreign-keys` 표시를 읽어 커넥션을 붙잡고 처리하는 경로를
더했다. 적용 뒤 `PRAGMA foreign_key_check`로 결과를 확인한다.

권한은 계정으로 판정한다: **열람과 편집은 로그인한 사람 전원, 삭제와 설정 변경은 만든 사람과
어드민.** 설계는 함께 하는 일이고 이 문서는 어떤 데이터베이스도 가리키지 않으므로 편집을 막을
근거가 없다. 반대로 되돌릴 수 없는 동작(삭제)까지 같은 문턱에 두면, 협업을 열어 준 대가로 사고가
따라온다.

**2. SQL 불러오기는 op 하나다.** 파싱 결과를 `table.add`/`column.add` 수십 개로 쪼개 보내지
않았다. 쪼개면 열 번째 op가 거부되는 순간 초안이 "절반만 불러온" 상태로 남고 되돌릴 방법이 없다.
또 편집 이력이 "테이블 추가" 40줄로 채워지는 것보다 "SQL 불러오기 — 테이블 12개" 한 줄이 나중에
훨씬 쓸모 있다.

payload에는 **파싱된 결과**를 담는다. 원본 SQL을 담고 재생할 때 다시 파싱하면 파서가 바뀐 뒤
같은 op가 다른 결과를 낳고, 그러면 op 로그 재생으로 복원한 문서가 사람들이 보던 것과 달라진다 —
이 동기화 방식의 전제가 무너진다.

파서(`internal/sqlimport`)는 완전하지 않고, 완전할 필요도 없다. 필요한 것은 ERD로 그릴 수 있는
것뿐이다. 그래서 규칙을 하나 세웠다: **모르는 것은 조용히 버리지 않는다.** 해석하지 못한 문장은
화면에 그대로 나열된다. 조용히 넘기면 사용자는 불러오기가 끝난 뒤에야 빠진 것을 발견한다.

같은 이유로, 정의가 스크립트에 없는 테이블을 `ALTER` 하는 문장은 반영하지 않는다. 빈 테이블을
만들어 붙이면 초안의 기존 테이블이 컬럼 하나짜리로 덮어써진다 — 불러오기가 데이터를 지우는 셈이다.

**3. 구조 화면은 ERD 설계의 반대편이다.** 캔버스를 공유하되(`web/js/core/erdcanvas.js`로 추출)
목적이 반대다. 저쪽은 만들고 싶은 것을 그리고, 이쪽은 있는 것을 읽는다.

그래서 스키마는 편집할 수 없고, 편집할 수 있는 것은 **읽는 사람의 정리**(위치·메모·묶음)뿐이며
그것은 **계정별로 저장된다**. 결제를 보는 사람과 배송을 보는 사람은 같은 스키마를 다르게 늘어놓아야
하고, 한 사람의 정리가 다른 사람의 것을 덮어쓰면 둘 다 쓸 수 없게 된다. 함께 그리는 그림은
ERD 설계 문서가 맡는다.

`erd_documents`를 재사용하지 않은 이유: 저 문서는 "만들고 싶은 것"이고 이것은 "있는 것"이다.
같은 표에 두면 목록에 초안 아닌 것이 섞이고, 마이그레이션 대상을 고를 때 실제로는 적용할 수 없는
항목이 후보로 뜬다.

**4. 구문 검사는 Prepare다.** EXPLAIN을 쓰지 않았다. DB마다 문법이 다르고 DDL에는 붙일 수 없으며,
무엇보다 **문장 앞에 무언가를 덧붙이는 순간 사용자가 쓴 것과 다른 문장을 검사하게 된다.**
Prepare는 문장을 그대로 보내면서 파싱과 이름 해석까지 하고 실행은 하지 않는다 — `DELETE FROM t`를
검사해도 한 행도 지워지지 않는다(시험으로 확인한다).

여기서 갈린 것은 **"틀렸다"와 "확인할 수 없다"를 구분한 것**이다. `USE`·트랜잭션 제어는 준비만으로는
효과가 나타나지 않고, MySQL은 일부 문장을 프리페어드 프로토콜에서 지원하지 않는다. 그것을 오류와
같은 색으로 보여주면 사람은 멀쩡한 문장을 고치기 시작한다.

**5. 줄 번호를 켜면 자동 줄바꿈이 꺼진다.** 논리적인 한 줄이 화면에서 여러 줄을 차지하면 번호가
어긋나고, 어긋난 번호는 오류 메시지의 "3행"을 찾는 데 쓸 수 없다 — 없느니만 못하다. 긴 줄은
가로 스크롤로 본다.

### P17 완료 기록 (2026-08-15) — REST API: 세 번째 문

MCP 클라이언트가 아닌 것들(셸 스크립트, CI 잡, 사내 대시보드, 다른 언어의 서비스)이 같은 툴을
쓸 길을 열었다. 그들에게 JSON-RPC 봉투와 `initialize` 협상을 요구할 이유가 없다.

**기존 `/api/v1`을 토큰으로 열지 않았다.** 가장 쉬운 길이었고, 그래서 먼저 검토했다. 문제는 그쪽이
**화면의 필요에 맞춰 바뀌는 내부 계약**이라는 점이다. 응답 한 칸을 화면 편의로 바꾸는 순간 외부
스크립트가 깨지고, 그때부터 화면을 고칠 때마다 "밖에서 쓰고 있을지 모른다"를 걱정해야 한다.
툴 레지스트리는 정반대다 — 이름과 인자 스키마가 곧 계약이고, 어시스턴트와 MCP가 이미 그 계약에
의존하고 있어 함부로 바뀌지 않는다. 그래서 REST API도 **툴 단위**로 열었다.

**공통 관문을 먼저 뽑았다**(`internal/api/tokenapi.go`). MCP 핸들러 안에 있던 세 가지 —
Bearer 인증, 토큰 범위에 따른 툴 노출 판정, 쓰기 툴의 Propose→Apply 실행 — 를 꺼내 두 문이
같은 함수를 쓰게 했다. 순서가 중요했다: REST를 먼저 만들고 나중에 합치려 했으면 그 사이에
판정이 두 벌이 되고, 두 벌이 된 판정은 어느 한쪽에만 검사가 빠져도 아무도 모른다. P13에서
"툴 레지스트리를 나누지 않았다"고 결정한 것과 같은 이유이며, 그 결정을 관문까지 밀어붙인 것이다.
결과적으로 `mcp_handlers.go`는 프로토콜을 입히는 일만 남았고 309줄에서 224줄로 줄었다.

**오류를 상태 코드로 답한다 — MCP와 다른 유일한 판단이다.** MCP는 툴 오류를 `isError` 텍스트로
돌려준다. 그래야 모델이 읽고 스스로 고쳐 다시 부른다(P13 기록 참고). REST를 부르는 것은 모델이
아니라 프로그램이고, 그것은 `if res.ok`로 분기한다. 200 안에 오류를 숨기면 그 분기가 조용히 틀린다.
그래서 401/403/404/400/422로 갈랐고, 그중 하나는 따로 코드를 두었다: 읽기 토큰으로 변경 툴을 부른
경우는 `read_only_token`이다. `forbidden`과 합치면 클라이언트는 "쓰기 범위로 다시 발급하면 된다"는
사실을 알 수 없다.

**툴이 거절한 것에 422를 쓴 이유.** 요청 형식은 맞았으므로 400이 아니고, 서버가 고장 난 것도
아니므로 500이 아니다. "그 커넥션에는 접근할 수 없다", "그런 테이블이 없다"는 요청 **내용**의
문제이며 그것이 422다.

**결과는 파싱해서 준다.** 툴 결과는 대부분 JSON 문자열이므로(`asJSON`) 문자열째로 넘기면
클라이언트가 한 번 더 파싱한다. 다만 결과가 24KB 상한을 넘으면 잘리면서 안내 문장이 붙어 더 이상
JSON이 아니다 — 그때는 `result` 대신 `text`에 원문을 담는다. 잘린 JSON을 억지로 고쳐 넘기면
클라이언트는 그것이 결과 전부라고 믿는다.

**미들웨어를 `/api` 전체에 걸지 않았다.** 그러면 뒤에 등록되는 `/api/*` 폴백까지 토큰을 요구하게
되고, 오타 난 프론트엔드 요청이 404 대신 401을 받는다. 화면은 401을 세션 만료로 읽어 로그아웃한다.
경로 네 개에 각각 붙이는 편이 지루하지만 정확하다.

**검증 결과**

- 단위 테스트 12건(`rest_handlers_test.go`): 토큰 없는 요청·잘못된 토큰·폐기된 토큰 401,
  **세션 쿠키로는 통하지 않음**(CSRF 방어의 핵심), 읽기 토큰 목록에 변경 툴 없음,
  이름을 직접 적어 부른 변경 툴 403 `read_only_token`(목록에서 감추는 것은 편의이고 관문은
  호출 시점 판정이라는 것), 없는 툴 404 + 목록 경로 안내, 빈 본문 허용, 배열·문자열 본문 400,
  툴 거절 422, 결과가 파싱된 JSON으로 오는지, `/api/me`의 주인·범위·툴 수,
  **정의되지 않은 `/api` 경로가 여전히 404인지**(미들웨어 범위 실수를 잡는 시험)
- 기존 MCP 시험 전부 통과 — 관문을 공유로 바꾼 뒤에도 판정이 그대로임을 확인한다

### P18 완료 기록 (2026-08-15) — 모델 선택과 사고 서명

두 가지를 함께 했다. 하나는 요청받은 기능(어떤 모델을 쓸 수 있게 할지 정하는 설정)이고,
하나는 그 과정에서 드러난 버그(Gemini로 툴을 부르면 대화가 죽는 것)다.

**모델은 두 층으로 나눴다.** 지금까지 프로바이더에는 기본 모델 하나뿐이었고, 그것으로는
"같은 키로 빠른 모델과 좋은 모델을 나눠 쓰는" 흔한 사용법을 담을 수 없었다(프로바이더를
여러 개 등록해 흉내내야 했다). 그렇다고 아무 모델이나 쓰게 두면 키를 등록한 사람이 비용을
통제할 수 없다 — 모델마다 열 배씩 차이 난다. 그래서 **관리자는 범위를 정하고 사용자는 그 안에서
고른다.** 빈 목록을 "제한 없음"으로 둔 것이 이 설계의 핵심이다: 기본값이 "아무것도 못 쓴다"가
되면 이미 돌고 있는 설치가 업데이트만으로 멈춘다.

판정은 `modelAllowed` 한 함수를 지난다. 저장할 때, 세션이 모델을 고를 때, 실제 호출 직전에
모두 같은 것을 쓴다. 세 번째가 특히 중요하다 — 세션을 만든 뒤에 관리자가 목록에서 모델을
뺄 수 있고, 그때 조용히 다른 모델로 바꿔 부르면 비용도 답도 달라진 이유를 아무도 모른다.
막고 이유를 말한다.

**모델 목록은 저장 전에 부를 수 있어야 했다.** 허용 모델을 고르는 일은 키를 등록하는 화면
안에서 일어난다. 먼저 저장하고 다시 열어 고르게 하면 그 사이에 기본 모델이 비어 있는
프로바이더가 존재하고, 사용자는 두 단계를 오간다. 그래서 `POST /ai/providers/models`는
아직 저장되지 않은 입력값으로도 조회한다(수정 중이면 id만 보내 저장된 키를 쓴다).

**그리고 사고 서명(thought_signature).** 사용자가 Gemini를 붙였더니 툴을 한 번 부른 뒤
400으로 죽었다. Gemini는 툴 호출마다 사고 과정의 서명을 붙여 보내고 다음 요청에 그대로
돌려주기를 요구하는데, 그 칸이 OpenAI 규약에 없어서(`extra_content.google.thought_signature`)
우리 어댑터가 응답을 정규화하며 버리고 있었다.

고친 방법은 "해석하지 않고 나른다"이다. `ai.ToolCall.Signature`는 프로바이더 중립인 불투명한
값이고, 하는 일은 스트림에서 읽고 → 대화 이력에 함께 저장하고 → 다음 요청의 같은 자리에
싣는 것뿐이다. **저장이 이 수정의 절반**이다: 그것을 빠뜨리면 같은 요청 안에서는 되고
새로고침 뒤에 이어지는 대화만 죽는다 — 원인을 찾기 가장 나쁜 형태다.

서명이 없는 호출에는 `extra_content` 칸 자체를 만들지 않는다. 이 필드를 모르는 서버에
빈 객체를 보내면 거부당할 수 있고, 그러면 Gemini를 고치려다 로컬 LLM을 깨뜨리게 된다.

덤으로 Google의 호환 엔드포인트는 루트가 `/v1beta/openai`라 우리가 붙이던 `/v1` 때문에
404가 났다. 접미사 규칙("openai로 끝나면 붙이지 않는다")으로 가르려 했지만 Groq의 루트가
`/openai/v1`이라 같은 규칙이 반대로 작용한다 — 그래서 호스트를 보고 판단한다.

**검증 결과**

- 단위 시험: 어댑터 2건(스트림에서 서명을 줍는지, 다음 요청에 같은 자리로 실려 나가는지 —
  서명 없는 호출에 빈 칸이 붙지 않는 것까지), 루트 경로 3건(Google·Groq·기존 동작),
  이력 왕복 1건(**저장 → 재조립에서 서명이 살아남는지**), 모델 게이트 5건(정리·판정·
  기본 모델 제약·세션 선택·목록에서 빠진 모델로 호출 시도)
- **실측**: Gemini를 흉내내되 서명이 없으면 실제와 같은 400을 내는 가짜 서버를 세우고
  전 구간을 돌렸다 — 저장 전 모델 목록 조회, 허용 목록 밖 기본 모델 거부, 세션 생성 시
  모델 게이트, 툴 호출이 포함된 대화(첫 턴 + **DB에서 이력을 다시 조립하는 둘째 턴**),
  대화 중 모델 변경, 허용 목록에서 모델을 뺀 뒤의 거부 메시지까지 확인.
  가짜 서버 로그에 `OK: 서명 확인`이 남는 것으로 왕복을 확인했다.

### P18 후속 (2026-08-15) — index를 보내지 않는 스트림

Gemini를 붙인 사용자가 두 가지 오류를 함께 봤다.

```
인자를 해석할 수 없습니다: invalid character '{' after top-level value
HTTP 400: [{ "error": { "code": 400, "message": "Request contains an invalid argument." } }]
```

**뿌리는 하나였다.** OpenAI 규약은 스트리밍 툴 호출을 `index`로 가르라고 하는데 Gemini의
호환 계층은 그 필드를 보내지 않는다. 우리는 `index`를 `int`로 받고 있었으므로 "없음"이 0이 되어,
한 턴에 툴을 두 개 부른 응답이 전부 0번 슬롯에 겹쳤다. 두 호출의 인자 JSON이 이어 붙어
`{...}{...}`가 되었고 — 첫 번째 오류가 그것이다.

두 번째 오류는 그 결과다. 깨진 인자가 담긴 assistant 메시지는 직렬화에 실패해 저장되지 못하고,
그 뒤에 저장되는 툴 결과만 대화에 남는다. 그러면 이력에 **호출 없는 결과**가 생기고,
프로바이더는 그것을 요청 전체의 거부 사유로 삼는다. 이력은 새 질문마다 그대로 다시 실려
나가므로 그 대화는 지우기 전까지 회복되지 않는다.

그래서 세 겹으로 고쳤다. 하나만으로는 부족하다고 본 이유가 각각 다르다.

1. **원인**: `index`를 `*int`로 받아 존재 여부를 구분하고, 조각을 index → id → 직전 슬롯
   순으로 가른다. 규약을 지키는 서버에서는 예전과 똑같이 동작한다.
2. **문법 방어선**: 완결된 JSON 뒤에 다시 `{`가 오면 이어짐일 수 없으므로 새 호출로 가른다.
   id마저 재사용하거나 아예 주지 않는 구현을 위한 것이다. 다만 같은 이름·같은 인자의
   되풀이는 가르지 않는다 — 그러면 같은 툴이 두 번 실행된다.
3. **오염 차단**: 툴 인자는 어떤 경로로 나가든 유효한 JSON임을 보장한다(`NormalizeToolArgs`).
   저장되는 값이기 때문이다. 그리고 이력을 조립할 때 짝 없는 호출·결과를 걷어내
   **이미 깨진 대화가 스스로 회복되게** 했다. 이것이 없으면 사용자는 대화를 지워야 한다.

**검증 결과**

- 단위 시험 9건: index 없는 병렬 호출이 둘로 갈리고 서명도 각자에게 붙는지, index·id가
  모두 없을 때 문법으로 갈리는지, 되풀이 조각이 중복 실행을 만들지 않으면서 서명은 흡수하는지,
  이력의 깨진 인자가 복구되는지, `NormalizeToolArgs` 8가지 입력, 짝 없는 호출·결과 정리 3건
- 실측: 가짜 Gemini가 **index 없이 툴 두 개**를 부르고, 되돌아온 요청의 인자가 유효한 JSON이
  아니거나 서명이 없으면 실제와 같은 400을 내도록 했다. 두 툴이 각자의 인자로 실행되고
  (`list_connections{}`, `list_migrations{"limit":5}`), 서명 두 개가 각자 붙어 돌아갔으며,
  DB에서 이력을 재조립하는 둘째 질문도 통과했다.

### P18 후속 — 어시스턴트 화면 다듬기 (2026-08-15)

실제로 쓰면서 나온 지적 다섯 가지를 고쳤다. 넷은 화면이고 하나는 동작이다.

**마크다운 렌더러를 만들었다**(`web/js/core/markdown.js`). 모델은 제목·목록·표를 섞어 답하는데
그것을 글자 그대로 보여주고 있었다. 라이브러리를 넣지 않은 이유는 구문 강조기 때와 같다 —
번들러가 없고 CSP가 외부 스크립트를 막으므로 통째로 벤더링해야 한다.

여기서 가장 중요한 결정은 **innerHTML을 쓰지 않는 것**이다. 이 문자열은 LLM이 만들었고 그 안에는
사용자가 조회한 DB 값이 섞여 있다. 문자열로 HTML을 조립하면 그 순간 저장형 XSS 통로가 된다.
링크도 스킴을 허용 목록으로 막되, 막힌 주소는 지우지 않고 글자로 남긴다(조용히 지우면 원문에
무엇이 있었는지 알 수 없다).

한국어와 이 앱의 데이터 때문에 갈린 규칙이 하나 있다. 밑줄 강조(`_x_`)는 낱말 안에서 무시하고
별표 강조(`*x*`)는 그렇게 하지 않는다. 컬럼 이름은 대개 snake_case라 `app_order_item`의 가운데가
기울임이 되면 이름이 달라 보이지만, `*중요*합니다` 처럼 조사가 바로 붙는 것은 한국어에서 정상이기
때문이다. 두 문자에 같은 규칙을 적용하면 둘 중 하나가 반드시 깨진다.

**화면을 한 화면에 가뒀다.** 대화 로그가 `max-height: 62vh`여서 아래로 300px쯤 남았다. 다른
화면에서는 여백이지만 여기서는 손해다 — 남긴 만큼 대화가 보이는 창이 좁아진다. 본문 여백을 CSS
변수로 빼고 `height: calc(100vh - 여백)`으로 고정했다. 두 곳에 같은 숫자를 적으면 언젠가 어긋난다.

**대화 머리에서 이름과 대상 DB를 바꾸게 했다.** 모델 선택과 같은 이유다: 이야기하다 보면 옆 DB를
같이 봐야 하는데, 그때 대화를 새로 시작하면 지금까지의 문맥을 버리게 된다. 설정을 바꿔도 쓰던
질문은 지킨다 — 사라지면 사용자는 그 칸을 다시 건드리지 않는다.

**그리고 동작 하나.** 대상 DB를 고른 대화인데 모델이 "어느 DB를 볼까요?"라고 되물었다. 화면
머리에는 DB 이름이 떠 있으니 사용자 입장에서는 이미 고른 것을 다시 묻는 셈이고, 앱이 고장 난
것으로 보인다. 원인은 단순했다 — 시스템 프롬프트가 상수였고 세션의 대상 DB가 거기 실리지 않았다.
이름만이 아니라 종류와 환경까지 넣었다: 모델이 방언과 위험도(운영이면 파괴적 변경을 먼저
경고해야 한다)를 판단할 근거가 된다.

**검증 결과**

- 마크다운 렌더러: node에서 최소 DOM을 흉내내 22가지 입력을 확인했다(제목·중첩 목록·번호
  이어받기·코드 블록·표·인용·링크·구분선, 그리고 **`<script>`와 `javascript:`가 코드가 되지
  않는지**, snake_case가 기울임으로 바뀌지 않는지, 재귀가 정규식 진행 위치를 망가뜨리지 않는지).
  이 저장소에는 JS 시험 도구가 없으므로(node 의존을 들이지 않는다는 결정) 하네스는 남기지 않았다.
- 시스템 프롬프트: 단위 시험 3건 + 가짜 프로바이더가 받은 요청에서 `이 대화의 대상 데이터베이스는
  "운영 MySQL" 입니다 (종류: mysql, 환경: 운영)` 줄을 실측으로 확인
- 세션 이름 변경·대상 DB 변경·해제를 HTTP로 확인

### P18 후속 — ERD 인스펙터가 비어 있던 이유 (2026-08-15)

테이블 카드를 눌러도 오른쪽 패널이 그대로였다. 원인은 한 줄이었다: `erdeditor.js`가
`truncate`를 부르는데 그 모듈에 정의도 import도 없었다(`erdcanvas.js`가 export하고 있다).

증상이 "아무 일도 일어나지 않음"이었던 것이 이 버그의 성격을 말해 준다. 패널을 그리는
첫 줄에서 `ReferenceError`가 나고 그 자리에서 함수가 끝나므로, **이전에 그려 둔 빈 안내가
그대로 남는다.** 선택은 됐고(카드 테두리가 바뀐다) 패널만 안 바뀌니, 화면만 봐서는
"선택이 안 되는 건가"로 읽힌다.

**확인 방법이 이번 작업의 절반이었다.** 정적으로 원인을 찾은 뒤, 실제 브라우저에서
A/B로 확인했다: dev 모드(`-dev`)로 디스크의 web/을 서빙하고, import 한 줄을 뺀 채
새로고침 → 카드를 눌러도 패널은 빈 안내 그대로(접근성 트리 146줄), 한 줄을 되돌리고
새로고침 → 제목·이름·주석·표시·컬럼 5개·인덱스·외래키·삭제까지 전부 렌더(252줄).
두 테이블 모두 확인했다.

**그리고 같은 부류를 다시 놓치지 않도록 정적 검사를 넣었다**(`assets_test.go`).
번들러도 타입 검사기도 없다는 결정의 대가가 이것이다 — 부르는데 없는 이름이 조용히 남고,
그 코드가 도는 순간에만 터진다. 그 한 줄을 잡자고 node 도구 사슬을 들여올 이유는 없어서,
필요한 검사만 Go 시험으로 한다: 모듈이 부르는 이름이 그 모듈 안에 있거나 import되어 있는가.

만들면서 두 번 다듬었다. 처음에는 주석·문자열을 정규식으로 지웠는데 거짓 경보가 27건 나왔다 —
문자열 안의 `//`(`'https?://…'`)가 주석으로 먹히면서 그 뒤가 통째로 망가졌기 때문이다.
한 글자씩 훑는 스캐너로 바꾸고, 구조 분해로 콜백을 받는 서명(`function openModal({ body })`)의
매개변수까지 걷자 0건이 되었다. **거짓 경보가 하나라도 남으면 이 시험은 곧 무시된다**는 것이
기준이었다. 마지막으로 import 한 줄을 다시 빼서 시험이 실제로 그 버그를 잡는지 확인했다.

### P19 (2026-08-16) — 사용 피드백 반영 1차

실제로 쓰면서 나온 35건을 받아 **버그와 작은 항목 14건**, 그리고 **데이터 화면 5건**을 먼저
끝냈다. 남은 것은 아래 "8. 남은 것"에 목록으로 옮겼다.

**전역·메뉴**

바깥을 눌러도 모달이 닫히지 않는다. 이 앱의 모달은 대부분 무언가를 고치는 자리이고,
긴 폼을 채우다 여백을 한 번 잘못 누르면 입력이 통째로 사라진다. `dismissible` 옵션 자체를

사용자가 외울 이유가 없다.

메뉴는 일의 단계로 묶었다(개요·관측·데이터·설계/변경·운영·관리·도구). 화면 이름이 아니라
목적으로 묶은 것이 요점이다 — "스키마"와 "데이터"는 둘 다 DB를 보는 화면이지만 찾는 사람의
머릿속에서는 다른 서랍에 있다.

**ERD 버그 셋의 원인이 서로 달랐다**

- *컬럼 추가·삭제가 인스펙터에 안 나타남*: 다시 그리기를 막는 조건이 "패널 안에 포커스가
  있으면"이었다. 지키려던 것은 타이핑 중인 글자인데, 버튼을 누른 직후도 그 조건에 걸린다.
  판정 대상을 글자를 받는 칸으로 좁혔다.
- *아이콘·색 변경이 안 먹힘*: 클라이언트의 `applyLightOp`이 `table.move` op에서 icon을
  베끼지 않았다. 서버는 저장하고 있었으므로 새로고침하면 나타났다 — 그래서 "가끔 되는"
  버그로 보였다.
- *노드를 옮겨도 간선이 안 따라옴*: 드래그 중에는 카드의 transform만 바꾸고 있었다.
  관계선은 두 카드의 좌표에서 계산되므로 레이아웃을 먼저 갱신하고 선 레이어만 다시 그린다
  (카드까지 다시 그리면 지금 쥐고 있는 요소가 버려져 드래그가 끊긴다).

**이름은 확정 전에도 화면을 따라온다.** commitOn에 preview를 더해, 서버로 가는 것은 확정할
때 한 번이되 캔버스는 글자마다 따라가게 했다. 글자마다 op를 보내면 `use`, `user`, `users`가
모두 편집 이력에 남는다.

**백업 노드에 "전체 DB"를 더했다.** "매일 새벽에 전부 백업"은 흔한 요구인데, DB를 하나 늘릴
때마다 노드를 하나씩 붙이게 하면 언젠가 빠뜨린다 — 그 사실은 복구가 필요한 날에 드러난다.
권한은 커넥션마다 확인하고(건너뛴 수만 알린다), 하나가 실패해도 나머지를 진행한 뒤 모아서
알린다. SQL 실행·데이터 수정에는 같은 옵션을 주지 않았다: 문장 하나가 모든 DB에 도는 것은
되돌릴 수 없는 쪽으로 너무 크게 움직인다.

### P19-2 — 데이터 화면: 모아 두었다가 한 번에 적용

가장 큰 변화는 **수정을 바로 보내지 않는 것**이다. 한 줄씩 저장하면 "무엇을 바꾸고 있는지"를
전체로 볼 기회가 없는데, 데이터 수정은 되돌릴 수 없다. 그래서 화면에서 고친 것은 적용 대기에
쌓이고, "적용하기"에서 실행될 문장을 확인한 뒤 한 번에 나간다.

그 흐름이 값어치를 가지려면 두 가지가 지켜져야 한다.

1. **미리보기가 실제와 같아야 한다.** 화면에서 SQL을 조립해 보여주면 그것은 추측이고,
   방언과 인용 규칙이 다른 순간 미리보기와 실행이 갈라진다. 그래서 서버에 dryRun으로 물어
   **실제 적용과 같은 코드**(`buildMutation`)가 만든 문장을 받아 온다. 이를 위해 어댑터의
   문장 조립과 실행을 분리했다.
2. **전부 되거나 전부 안 되어야 한다.** 한 트랜잭션으로 돈다. 절반만 반영되면 사용자는
   무엇이 남았는지 알 수 없다. 트랜잭션이 없는 종류(Mongo·Redis)는 이 흐름을 켜지 않고
   지금처럼 바로 반영한다 — `DataCapabilities.Preview`가 그 갈림길이다.

나머지 넷은 표를 읽고 고르는 방식의 문제였다. 행 왼쪽의 아이콘 세 개를 없애고 **행 자체를
상세의 입구**로 삼았다(그 자리는 어느 표에서나 폭을 먹고 값을 오른쪽으로 민다). 대신 체크박스를
두어 여러 행을 고르고 일괄 편집·삭제할 수 있게 했다. 컬럼 설명은 값 위에 머무를 때 popover로
뜬다 — 브라우저 기본 툴팁을 쓰지 않은 이유는 뜨기까지 1초 가까이 걸리고, 그 자리는 이미
"전체 값"이 쓰고 있기 때문이다.

정렬은 **이미 있었다.** 다만 눌러 보기 전에는 알 수 없었다(활성 컬럼에만 화살표가 있었다).
호버 시 흐린 화살표와 "무엇이 일어날지" 툴팁을 더했다.

**검증 결과**

- 단위 시험 6건: 백업 노드의 전체 DB 옵션 2건, 일괄 적용 4건(미리보기가 아무것도 바꾸지
  않는지, 셋을 적용하는지, **두 번째에서 실패하면 첫 번째도 남지 않는지**, 미리보기를
  지원하지 않는 종류에서 dryRun이 거절되는지). SQLite로 돌려 컨테이너 없이 `go test`에 얹었다.
- 브라우저 실측(격리한 Chrome + 접근성 트리): 메뉴 묶음과 이름, 매크로 탭에서 커스텀 노드
  만들기, **모달 배경 클릭이 닫지 않는 것**, ERD 컬럼 추가·삭제가 즉시 인스펙터에 반영되는 것,
  아이콘·색이 저장되는 것, 테이블 이름 타이핑이 캔버스에 바로 반영되는 것,
  그리고 데이터 화면의 전 과정(체크 → 선택 막대 → 선택 삭제 → 적용 대기 → SQL 미리보기 →
  적용 → DB에서 사라짐)을 확인했다.
- HTTP 실측: dryRun이 데이터를 바꾸지 않는 것, 적용이 반영되는 것, 실패한 묶음이 통째로
  취소되는 것.
- 간선 따라오기는 node에서 확인했다(드래그는 좌표 조작이라 브라우저 자동화로 재현이 어렵다).
  카드 좌표를 옮긴 뒤 선의 `d`가 실제로 달라지고 레이어가 다시 그려지는지 확인했다.

### P19-3 (2026-08-16) — Git 계정 개인화, ERD 편집 기능

**Git 연동에 주인이 생겼다.** 여기 담기는 것은 개인의 Git 계정 토큰인데 지금까지는 커넥션
관리자가 등록해 모두가 함께 썼다. 그러면 원격 저장소의 PR이 전부 토큰 주인 이름으로 열려
"누가 이 스키마를 바꿨는가"가 Git 쪽 기록에서 사라진다. 이 앱은 어시스턴트·MCP·매크로·자동
실행에서 "누구의 권한으로 실행되는가"를 지켜 왔는데 이 경로만 예외였다.

판정을 **질의에 넣은 것**이 이번 작업의 핵심이다. "찾은 뒤에 주인을 비교한다"로 두면
호출부마다 그 한 줄을 반복해야 하고, 한 곳이라도 빠지면 그것이 통로가 된다.
`GetVCSIntegration(ctx, id, ownerID, ...)`처럼 주인을 인자로 받아 `WHERE`에 넣으면
빠뜨릴 자리 자체가 없어진다. 슈퍼 어드민도 예외가 아니며, 없는 것과 남의 것은 똑같이
404다 — 존재 여부도 알려줄 이유가 없다.

기존 공유 연동은 **지웠다**(사용자 결정). 공유 연동에는 "이것이 누구의 계정인가"가
기록되어 있지 않다. 표를 다시 만들어야 하는 마이그레이션이라(SQLite는 열 제약을 바꿀 수
없다) 행이 없는 그 시점이 유일한 기회이기도 했다.

**ERD 편집 기능 다섯.** 선택이 이제 종류를 갖는다(`{kind, id}`) — 예전에는 테이블 키
문자열 하나였는데, 간선·메모·그룹까지 같은 인스펙터에서 고치게 되면서 그것으로는 "무엇을
고른 상태인가"를 표현할 수 없게 되었다.

- **간선 클릭 → FK 편집**: 보이는 선은 1.4px이라 마우스로 맞히기 어렵다. 같은 경로를
  투명한 12px 선으로 한 겹 더 깔아 그것으로 받는다(보이는 선을 굵게 하면 그림이 지저분해진다).
  이름은 바꿀 수 없게 두었다 — 서버의 `fk.update`가 이름으로 대상을 찾으므로 이름 변경은
  사실상 지우고 새로 만드는 일이고, 그 둘을 한 칸에 숨기면 되돌릴 수 없는 동작이 이름
  수정처럼 보인다.
- **메모·그룹 인스펙터**: 더블클릭 모달을 없애고 인스펙터로 옮겼다. 편집기가 두 벌이면
  한쪽만 고치게 된다.
- **사이드바 접기**: 접으면 캔버스가 340px 넓어진다. 테이블이 스무 개를 넘으면 그 폭이
  "한 화면에 다 보이는가"를 가른다.
- **도구 막대 아이콘화**: 이름을 글자로 늘어놓으면 막대가 두 줄이 되고 캔버스가 그만큼
  낮아진다. 이름은 CSS popover로 띄운다 — 브라우저 기본 툴팁은 1초 가까이 기다려야 하고,
  도구 막대에서는 그 사이에 이미 다른 버튼을 찾고 있다.
- **문서 설정 모달**: 이름과 메모. 자주 바뀌지 않는 값을 막대에 펼쳐 두면 자주 쓰는 도구가
  밀린다.

작업 중에 **P17에서 넣어 둔 프론트엔드 정적 검사가 내가 방금 쓴 코드를 잡았다** —
설정 모달에서 `toastError`를 부르는데 import를 빠뜨렸다. 그 코드는 저장이 실패할 때만
도는 경로라, 시험이 없었다면 한참 뒤에 "저장이 안 되는데 아무 말도 없다"로 나타났을 것이다.

**검증 결과**

- 단위 시험 6건(Git): 주인만 읽는지, 슈퍼 어드민이 읽지 못하는지, 남이 수정·삭제할 수
  없는지, 이름이 사람마다 따로 세는지, 계정 삭제가 연동을 함께 지우는지, 주인 없이는
  만들 수 없는지. 그리고 **마이그레이션 시험**: 옛 스키마(v24)에서 시작해 공유 연동과 푸시
  이력을 넣고 마이그레이션을 돌려, 표를 다시 만드는 과정이 실제로 도는지 확인했다.
- HTTP 실측(Git): 멤버가 자기 계정을 등록하고, 슈퍼 어드민의 목록에는 0건이 보이며,
  남의 연동에 대한 수정·삭제·연결 확인이 모두 404, 계정을 지우니 연동도 사라졌다.
- 브라우저 실측(ERD): 도구 막대가 아이콘 12개로 바뀌고 이름이 접근성 이름으로 남는 것,
  관계선을 눌러 FK 인스펙터가 열리고 ON DELETE 변경이 서버에 반영되는 것, 사이드바 접기,
  문서 설정 저장과 재조회, 메모 추가 → 캔버스에서 클릭 → 인스펙터에서 색 변경까지.

### P19-4 (2026-08-16) — ERD 화면 안의 AI, 그리고 다른 사람의 화면

**초안을 고치는 AI.** 어시스턴트 화면의 대화와 같은 엔드포인트를 쓰되 **툴 상자를 바꿔
끼웠다**. 앱 전체의 툴(커넥션 목록·질의 실행·마이그레이션…)을 그대로 주면 모델이 "어느
DB를 볼까"부터 정하려 들고, 이 대화의 맥락(초안 하나)을 벗어난 일을 한다. `ai_sessions`에
`erd_document_id`가 붙어 있으면 초안 툴 8개만 넘어간다.

승인 단계를 두지 않았다. 판단의 근거는 셋이다. (1) 이것은 초안이고 실제 DB는 바뀌지
않는다 — 위험한 것은 마이그레이션 실행이지 그림이 아니다. (2) 바뀐 결과가 캔버스에 즉시
보이고, op-log에 누가 언제 했는지 남는다. (3) 테이블 하나를 만들려면 툴이 대여섯 번
불리는데 그때마다 승인을 물으면 쓸 수 없다. 대신 **지우는 툴은 넣지 않았다** — 되돌리기가
생기기 전까지는 잘못 지운 것을 복구할 방법이 없다.

권한은 실행 시점에 다시 본다(`erdCanEdit`). 대화는 며칠 뒤에 이어질 수 있고 그 사이에
권한이 회수될 수 있는데, 그때도 예전 대화창에서 툴이 도는 것은 곤란하다.

**대화 패널이 둘을 나눠 쓴다.** 전체 대화(방 채팅)와 AI 세션을 콤보 상자 하나로 고른다.
AI 세션은 나만 본다 — 여러 사람의 지시가 한 줄로 섞이면 누가 무엇을 요청했는지 읽을 수
없다. 대신 **쓸 만한 답만 골라 전체 대화로 옮긴다**(`[AI] ` 접두어). 자동으로 흘리지 않는
이유는 AI와의 대화에는 시행착오와 되묻기가 섞여 있어서, 그것을 전부 방에 보내면 사람들의
대화가 묻히기 때문이다. 공유된 줄은 방 채팅에서도 마크다운으로 그린다 — 모델이 쓴 글에는
`**강조**`가 들어 있고, 사람이 친 `*`는 그대로 별표로 둔다.

SSE 파싱은 `web/js/core/aistream.js`로 뺐다. 어시스턴트 화면과 ERD 화면이 같은 형식을
읽는데 파서가 두 벌이면, 서버가 이벤트를 하나 추가할 때 한쪽만 고쳐지고 증상은 "어떤
화면에서는 툴 실행이 안 보인다"가 된다.

**남의 화면 따라가기와 채팅 알림.** 참여자 아이콘이 버튼이 되었다. 누르면 그 사람의 커서를
따라 캔버스가 움직이고, 그 사람이 나가거나 내가 캔버스를 직접 끌면 풀린다(따라가는 중에
내 조작이 화면을 되돌리면 그 다음 커서 이벤트가 다시 끌고 가서 싸운다). 채팅은 대화 탭을
보고 있지 않을 때만 캔버스 위에 카드로 뜬다 — 보고 있는 것을 또 알릴 이유가 없다.

**작업 중 발견한 것**: `GET /ai/sessions`(어시스턴트 목록)가 초안 대화까지 함께 돌려주고
있었다. 시험이 잡았다. 그대로 두면 어시스턴트 화면에서 초안 대화를 열어 "이 DB의 테이블을
보여줘"라고 물었을 때 모델이 가진 툴은 초안 편집 툴뿐인 상황이 된다. 목록 질의에
`erd_document_id IS NULL`을 넣어 막았다.

**검증 결과**

- Go 시험 4건: 세션이 문서에 매이는지, 남의 AI 세션이 보이지 않는지, 어시스턴트 목록에
  섞이지 않는지, 툴 스키마와 구현이 짝을 이루는지, 툴이 실제로 문서를 바꾸는지(이름 중복과
  없는 테이블 참조는 거절되는지). 그리고 **가짜 프로바이더를 세워 왕복 전체**를 확인했다 —
  질문 → 툴 호출 → 문서 변경 → 마무리 응답이 한 줄로 이어지는지, 모델에게 넘어간 툴 목록에
  실제 DB를 건드리는 툴이 섞이지 않았는지.
- 브라우저 실측: 가짜 LLM(로컬 SSE 서버)을 붙여 ERD 화면에서 "orders 테이블을 만들어 줘"를
  보냈다. 스트리밍 중 마크다운이 그려지고, `add_table` 호출 줄이 뜨고, **캔버스에 orders
  카드가 나타났으며**, "전체 대화로 공유"를 누르니 방 채팅에 마크다운으로 렌더된 줄이 남았다.
- 두 사람이 필요한 것(채팅 알림 카드, 마우스 팔로우)은 브라우저 두 개를 띄우는 데 실패해
  코드 수준까지만 확인했다 — 두 번째 창의 접근성 트리가 노출되지 않았다.

### P19-5 (2026-08-16) — 되돌리기: 역연산을 쓰지 않고 만드는 법

되돌리기의 어려운 부분은 UI가 아니라 **역연산**이다. op가 24종이고, 그중 몇은
단순하지 않다 — 테이블 삭제는 컬럼·인덱스·외래키·제약을 함께 지우고 **다른 테이블의
외래키까지** 정리한다. 컬럼 삭제도 기본키·인덱스·외래키를 훑는다. 이 규칙을 역방향으로
한 벌 더 쓰면 두 구현이 생기고, 언젠가 한쪽만 고쳐진다. 그 증상은 "되돌렸는데 뭔가
사라져 있다" — 사용자가 되돌리기를 다시는 믿지 않게 되는 종류의 버그다.

그래서 **적용 전후를 비교해서** 되돌리는 op를 만든다(`erd.Diff`). 규칙은 여전히
`Apply` 한 곳에만 있다. 비교 결과는 `doc.restore` op 하나이며, 이 op를 다시 Diff에
넣으면 그 역이 나온다 — 그래서 **다시실행에 별도 규칙이 없다.** 비용은 편집마다
문서 크기에 비례하는 비교인데, 이미 op마다 문서를 통째로 복제하고 있으므로 같은 차수다.

**되돌리기는 사람마다 따로다.** 문서 하나를 여럿이 고치는 곳에서 "마지막 편집"을 문서
단위로 잡으면, 내가 Ctrl+Z를 눌렀을 때 남이 방금 한 일이 사라진다. 스택은 (문서,
사용자)마다 하나이고, 되돌리는 op는 **새 편집으로 기록된다** — op-log에서 과거를 지우면
그 사이에 남이 쌓아 올린 편집의 기준이 흔들린다.

**남의 편집을 덮어쓰지 않는다.** 복원은 테이블을 통째로 교체하므로, 내가 지운 테이블을
되살리는 사이에 다른 사람이 같은 이름으로 새 테이블을 만들었다면 그것이 조용히 사라진다.
그래서 복원 payload에 "지금 이것들이 이 모습이어야 한다"는 지문을 함께 싣고, 하나라도
다르면 거절하고 이유를 말한다(`... 은(는) 다른 사용자가 그 사이에 고쳤습니다`). 좌표에는
걸지 않는다 — 남이 카드를 조금 옮겼다고 되돌리기를 막으면 쓸 수 없다.

스택은 **방(room)보다 오래 산다.** 새로고침하면 마지막 참여자가 나간 것이 되어 방이
접히는데, 그때 되돌리기가 사라지면 혼자 편집하는 사람에게는 기능이 없는 것과 같다.
사람·문서마다 30단계, 30분 TTL로 허브가 들고 있다. SQL 불러오기만은 되돌릴 수 없어
스택을 비운다 — 그러지 않으면 다음 Ctrl+Z가 그 이전 편집을 되돌려, 사용자가 보기에는
엉뚱한 것이 사라진다.

AI가 만든 편집도 같은 경로(`SubmitOp`)를 지나므로 그대로 되돌릴 수 있다. ERD AI 툴에
삭제를 넣지 않은 이유가 "되돌리기가 없어서"였는데(P19-4), 그 전제가 이번에 사라졌다 —
다만 툴을 늘리는 것은 실제 사용을 보고 정한다.

**검증 결과**

- `internal/erd` 시험 20건: op 16종을 하나씩 적용하고 되돌려 문서가 **완전히** 같아지는지
  (JSON 전체 비교 — 컬럼 순서·좌표·남의 테이블의 외래키까지), cascade 삭제와 컬럼 삭제의
  복원, 다시실행이 되돌리기의 역인지, 참조가 끊기는 복원의 거절.
- `internal/erdhub` 시험 9건: 내 편집만 되돌아가는지(두 사람), 새 편집이 다시실행을
  비우는지, 빈 스택·권한 없음의 응답, 방이 접혔다 다시 열려도 스택이 남는지,
  **남의 편집을 덮어쓰는 되돌리기를 거절하는지**, 두 번 연속 되돌리기/다시실행의 순서.
- 브라우저 실측: 테이블 추가 → 되돌리기 → 다시실행을 도구 막대 버튼으로 확인했고,
  단축키는 Ctrl+Shift+Z(다시실행)와 Ctrl+Y(다시실행)가 동작했다. 맨 Ctrl+Z는 합성 입력이
  페이지까지 전달되지 않아(브라우저가 편집 명령으로 먹는다) 버튼 경로로만 확인했다 —
  같은 함수의 같은 분기이고 `session.undo()`는 버튼으로 검증되었다.

### P19-6 (2026-08-16) — 어시스턴트를 팝업으로

어시스턴트는 **다른 화면을 보면서** 쓰는 도구다. 스키마를 보다가 물어보고, 답을 보며
화면을 조작한다. 그런데 지금까지는 메뉴를 누르면 보고 있던 화면이 사라졌다 — 물어보려면
하던 일을 접어야 했고, 답을 받고 돌아오면 다시 찾아 들어가야 했다.

모달이 아니라 **떠 있는 패널**인 이유가 같다. 모달은 "지금 이것만 하라"는 뜻이라 뒤를
덮고 배경을 막는데, 여기서는 뒤가 보여야 한다. 그래서 옮기고 크기를 바꿀 수 있는 창으로
만들었다(`web/js/core/floatpanel.js`). 배치는 브라우저에 기억한다 — 넓은 모니터에서는
옆에 세워 두고 좁은 화면에서는 크게 펴는데, 매번 끌어다 놓게 하면 그 도구는 결국
쓰이지 않는다.

**화면을 한 벌만 유지한다.** 페이지(`/assistant`)와 팝업이 같은 `mountAssistant`를
쓴다. 둘의 차이는 "다른 대화로 옮겨 가는 방법" 하나뿐이라, 그것만 `nav`로 주입한다:
페이지에서는 주소를 바꾸고(뒤로 가기·새로고침·링크 공유가 성립한다), 팝업에서는 그
자리에서 내용만 바꾼다. 팝업이 주소를 바꾸면 뒤에서 보고 있던 화면이 사라지므로
목록도 링크가 아니라 버튼으로 그린다 — `href`가 있으면 가운데 버튼이나 새 탭으로
페이지가 통째로 바뀐다.

**배치는 CSS가 정한다.** 패널은 폭에 따라 `is-narrow`/`is-short` 표시만 붙이고, 대화
목록을 옆에 둘지 위에 눕힐지는 스타일이 결정한다. 자바스크립트로 폭을 재서 요소를
옮기면 규칙이 두 벌이 되고, 창 크기를 바꿀 때마다 둘이 어긋난다. 좁아졌다고 목록을
**숨기지는** 않는다 — 목록이 사라지면 다른 대화로 갈 방법이 없어져 팝업이 "지금 이
대화 하나"만 되는 반쪽 도구가 된다.

패널은 화면 밖으로 나가지 않는다. 걸쳐 두는 것을 허용하면 오른쪽 끝의 보내기 버튼이나
크기 손잡이에 닿을 수 없고, 그 상태가 저장되어 다음에 열 때도 그대로 나온다.

**검증 결과** (가짜 LLM을 붙인 브라우저 실측)

- 스키마 화면에서 메뉴를 눌러 팝업이 뜨고 **뒤 화면이 그대로 남는 것**, 팝업 안에서
  새 대화 만들기 → 질문 → 스트리밍 응답과 툴 호출 표시까지.
- 제목 줄을 끌어 옮기기, 모서리로 크기 바꾸기, 넓히면 목록이 왼쪽 사이드바로 돌아오고
  좁히면 위로 눕는 것.
- 새로고침 뒤 다시 열었을 때 **마지막 배치가 복원**되고, 화면을 넘던 크기가 안으로
  당겨지는 것.
- "전체 화면으로 열기"가 보고 있던 대화 그대로 `/assistant?s=…`로 옮겨 가고 팝업이
  닫히는 것. 페이지 쪽 목록은 여전히 링크(`<a href>`)인 것.

### P19-7 (2026-08-16) — 메뉴얼

설명서를 앱 안에 두는 이유는 하나다. 따로 배포하면 버전이 갈린다. 이 앱은 단일
바이너리이므로, 화면과 같은 바이너리에 들어 있는 문서만이 "지금 이 서버의" 설명서다.

사이드바에서 **새 탭으로** 연다(`target="_blank"`). 설명서를 보려고 하던 일을 접어야
하면 결국 읽지 않는다 — 어시스턴트를 팝업으로 만든 것과 같은 판단이다.

본문은 마크다운 문자열이고 기존 렌더러(`core/markdown.js`)로 그린다. DOM으로 직접 짜면
문장 하나를 고칠 때마다 `h()` 호출을 고쳐야 하고, 그러면 아무도 고치지 않는다.

**노드 목록은 서버에서 받아 그린다.** 매크로 노드는 앞으로도 늘어날 텐데, 손으로 적은
목록은 늘어난 다음부터 틀린 목록이 된다. `/macros/meta`가 팔레트에 주는 것과 같은
데이터를 표로 그린다. 권한이 없어 못 받으면 그 사실만 적는다.

담은 것: 앱의 원칙 네 가지, 시작하기(첫 로그인·2단계 인증), **권한 모델**(역할·등급·
데이터 능력·전역 권한), 커넥션, 관측, 스키마·데이터(스테이징 편집), SQL 콘솔, ERD 설계
(동시 편집·되돌리기·AI 세션), 마이그레이션·버전, 매크로(변수·트리거·사용자 노드),
노드 목록, **Lua 레퍼런스**, 백업, Git 연동, 어시스턴트·MCP·REST, 감사, 단축키.

Lua 레퍼런스는 코드에서 확인하며 적었다 — 열려 있는 표준 라이브러리 네 개, 제거된
로딩 함수들, `db`/`http`/`sh`/`macro`/`json`/`log`의 시그니처와 **필요한 권한**,
반환값과 포트 규약. 문서가 코드보다 관대하게 적히면 "된다고 적혀 있는데 안 된다"가
되고, 그것은 없는 문서보다 나쁘다.

작업 중 **시험 하나가 가끔 실패하는** 것을 발견해 함께 고쳤다. erdhub 시험의 사용자
캐시가 스토어 **포인터**를 키로 쓰고 있었는데, 앞 시험이 끝나 회수된 주소에 다음
스토어가 앉으면 없는 사용자 ID를 돌려주어 `erd_ops.actor_id` 외래키가 깨졌다. 증상이
"매번 다른 시험이 가끔 실패한다"라서 원인을 짚기 어려운 종류다. 시험이 끝날 때 그
스토어의 캐시를 지우도록 했다.

**검증 결과**: 브라우저에서 차례·본문·표·코드 블록이 그려지는 것, 차례의 앵커로 이동하는
것, 노드 목록이 서버 데이터로 채워지는 것(흐름/데이터베이스/DB Studio 기능/스크립트
묶음), 사이드바의 메뉴얼이 **새 탭**으로 열리는 것(탭 2개)을 확인했다.

### P19-8 (2026-08-16) — 아이콘·색이 "안 먹던" 이유 셋

사용 피드백: ERD 인스펙터의 **표시(아이콘·색)가 여전히 잘 안 된다.** 원인이 하나가
아니라 셋이었다.

**1. 테이블 색이 아예 그려지지 않았다.** JS는 `--card-accent`를 카드 **사각형**에
붙이는데, CSS 규칙은 `.erd-card-g[style*="--card-accent"] ...`처럼 **묶음(g)**에 있을
때만 걸리도록 쓰여 있었다. 사각형에 정의된 변수는 그 사각형에만 있으므로 머리띠
(형제 요소)에는 닿지도 않는다. 그룹(`--group-accent`)은 처음부터 묶음에 실려 있어
멀쩡했고, 그래서 "그룹 색은 되는데 테이블 색은 안 된다"였다. 변수를 묶음으로 옮겼다.

**2. 메모 색은 CSS가 아예 쓰지 않았다.** `--note-accent`를 심기만 하고 `.erd-note-bg`는
고정된 노란색을 칠하고 있었다. 색을 골라도 저장은 되는데 화면은 그대로다.

**3. 골라도 고르개가 그대로였다.** `table.move`는 구조 op가 아니라 서버가 op만
보내는데, 그때 인스펙터를 다시 그리지 않았다. 캔버스는 바뀌는데 아이콘 고르개에는
여전히 "없음"이 켜져 있으니, 사용자에게는 눌러도 안 먹는 것으로 보인다 — 실제로는
반영되어 있는데도. 지금 고른 대상을 건드리는 op일 때만 패널을 다시 그린다(남이 저쪽
끝에서 카드를 옮길 때마다 다시 그리면 입력하던 칸이 사라진다).

덤으로, 색·아이콘을 누를 때 보내는 **좌표를 누르는 순간 다시 읽도록** 했다. 패널을
그린 뒤에 카드가 움직였다면 옛 좌표가 함께 나가 카드가 되돌아간다 — 색만 골랐는데
카드가 움직이는 종류의 버그다.

**정적 검사 하나 추가**: 자바스크립트가 인라인으로 심는 CSS 변수는 스타일시트가
실제로 `var(...)`로 써야 한다(`TestInlineCSSVarsAreUsed`). 2번을 그대로 잡는 검사이고,
일부러 깨뜨려 잡히는 것을 확인했다. 1번(어느 요소에 붙였는가)까지 정적으로 따지려면
DOM 구조를 재현해야 해서 넣지 않았다 — 그 검사는 곧 실제 코드보다 자주 틀린다.

**검증 결과**(브라우저 실측): 테이블 색을 노랑 → 파랑으로 바꾸니 카드 테두리와 머리띠가
즉시 바뀌고 고르개의 표시도 따라 움직였다. 아이콘을 고르면 카드에 붙고 고르개가
그 아이콘을 켠다. 메모 색을 초록으로 바꾸니 쪽지가 초록이 되었다. 새로고침 뒤에도
그대로였다.

### P19-9 (2026-08-16) — 팝업이 손에서 튀던 이유

사용 피드백: 어시스턴트 팝업의 **이동과 크기 조절이 둘 다 이상하게 동작한다.**

원인은 한 줄이었다.

```js
const start = { x: e.clientX, y: e.clientY, ...state };
```

`state`에도 `x`·`y`(패널의 위치)가 있으므로, 뒤에 온 전개가 앞의 포인터 좌표를
덮어쓴다. 그래서 `dx = ev.clientX - start.x`는 "포인터가 움직인 거리"가 아니라
"포인터와 패널 왼쪽 끝 사이의 거리"가 되고, 끌기 시작하는 순간 패널이 그만큼
튀어 나갔다. 크기 조절도 같은 값을 쓰므로 함께 어긋났다.

문제는 문법이 아니라 **이름이 두 가지 뜻을 갖게 둔 것**이다. `x`가 포인터의 x인지
패널의 x인지 그 자리에서는 알 수 없다. 포인터 시작점(`px`,`py`)과 패널의 시작
배치(`x`,`y`,`w`,`h`)를 서로 다른 이름으로 나눴다.

함께 고친 것 둘.

- **저장은 손을 뗄 때 한 번.** 끌고 있는 동안 매 프레임 localStorage에 쓰고 있었다.
  긴 드래그에서 눈에 띄게 끊긴다. 그리기(`apply`)와 저장(`save`)을 나눴다.
- **pointercancel도 끝으로 본다.** 창 밖으로 나가거나 다른 제스처가 끼어들면
  pointerup이 오지 않아, 손을 뗐는데도 패널이 계속 따라다닌다.

**검증 결과**(브라우저 실측): 머리를 잡아 정확히 (+200, +157)만큼 끌었더니 패널이
(20,122) → (220,279)로, 요청한 만큼만 움직였다. 모서리를 끌어 줄인 크기도 요청과
일치했고, 화면 밖으로 끌면 가장자리에 붙어 멈춘다. 새로고침 뒤 배치도 그대로였다.

### P20 (2026-08-17) — 사용 피드백 2차 (35건)

화면 12곳에 걸친 요청을 한 번에 반영했다. 개별 항목보다, 같은 종류의 문제가 여러
화면에서 반복되고 있었다는 점이 이번 배치의 요점이다.

**커넥션 고르기가 화면마다 달랐다.** 로그·SQL 콘솔·구조는 커넥션을 평평한 목록으로
늘어놓고 있었다. 같은 서버의 DB가 이름만 다른 항목으로 반복되어, 커넥션이 늘수록
"어느 서버의 것인가"가 사라진다. 데이터·스키마가 쓰던 `serverDbPicker`를 그대로
붙였다 — 고르는 규칙은 앱 전체에 하나여야 한다.

**외래키를 따라갈 수 없었다.** 데이터 화면에서 `user_id = 481`을 보고 그것이 누구인지
알려면 표를 옮겨 다녀야 했다. 이제 행 상세에서 FK 컬럼을 누르면 **대상 행이 오른쪽에
펼쳐지고**, 거기서 또 따라가면 그 오른쪽으로 이어진다. 사슬이라 앞을 접으면 뒤도 함께
사라진다 — 남겨 두면 지금 보는 것이 어디서 뻗어 나온 것인지 알 수 없다. 서버는 이를
위해 컬럼마다 참조 대상(`fk: {namespace, table, column}`)을 함께 준다.

**EXPLAIN에 구멍이 있었다.** 실행 계획 버튼을 붙이면서 읽기 전용 판정을 다시 보니,
`EXPLAIN`으로 시작하는 문장을 전부 조회로 보고 있었다. `EXPLAIN ANALYZE DELETE …`는
**행을 실제로 지운다.** 읽기 전용이라는 표시가 거짓말이 되는 자리라, ANALYZE가 붙은
EXPLAIN은 안쪽 문장으로 판정하도록 고치고 시험을 붙였다.

**ERD 속성창이 조용히 아무 일도 하지 않았다.** 이름 칸은 글자마다 캔버스에 미리보기를
반영하는데(`previewCanvas`), 확정 비교를 그 **미리보기가 바뀐 객체**와 하고 있었다.
그래서 이름을 고쳐도 "값이 같다"가 되어 서버로 가지 않았고, 그 다음 편집(NULL 해제 등)은
서버가 모르는 이름을 향해 나가 오류가 났다. 서버가 아는 이름을 따로 들고, 타자를 멈추면
0.7초 뒤 보내도록 했다.

**끌던 카드가 손에서 빠졌다.** 고르지 않은 테이블을 끌면 간선만 따라오고 카드는 제자리에
있었다. 누르는 순간 잡아 둔 요소가 선택 변경에 따른 재렌더로 버려지는데, 관계선은 매번
새로 찾으므로 선만 움직인 것이다. 끌고 있는 요소를 **살아 있는 것으로 다시 찾도록** 했다.

그 밖에 화면별로: 데이터 행 상세의 버튼 크기·이름 정리, FK 아이콘 표시, SQL 콘솔의
최근 실행 접힘 방지·초기화 버튼·"포맷팅" 이름·실행 분석, 구조 화면의 선택 하이라이트와
메모·그룹 인스펙터(모달 제거), ERD의 사이드바 폭 조절·테이블 추가 아이콘 분리·표시
아이콘 26종·메모 크기 조절, 매크로의 그룹·메모 선택 표시, 버전 비교의 기준 버전 선택,
보안 설정 버튼 줄 정리, 감사 로그 상세 모달(키·값 표 + 전체 복사), 어시스턴트 팝업의
compact 배치(대화 목록·설정을 팝업 안 모달로)·이동 제한 완화·AI 아이콘, 메뉴얼을 같은
탭에서 열기, 그리고 좁은 화면의 표 처리.

**모바일에서 표가 세로로 뭉개지던 이유**: `.table-wrap`이 코드에는 있는데 **CSS에는
없었다.** 감싸는 통이 없으니 폭이 모자랄 때 브라우저가 칸을 글자 단위로 쪼갰고, 그래서
한 칸에 글자가 세로로 한 줄씩 쌓였다. 통을 정의하고, 좁은 화면에서는 표에 최소 폭을 주어
옆으로 밀어 보게 했다 — 읽는 순서(행)가 유지된다.

**검증 결과**

실제 SQLite DB(users·teams·orders, 외래키 3개)를 만들어 브라우저에서 확인했다.

- 데이터: FK 아이콘 표시, 행 상세에서 orders → users → teams **3단 사슬**이 펼쳐지는 것,
  펼친 컬럼 표시와 접기, 바닥 버튼(수정·삭제·닫기)의 높이가 맞는 것.
- SQL 콘솔: 구문 검사·포맷팅·실행 분석·초기화 네 버튼, "실행 분석"이 SQLite에서
  `EXPLAIN QUERY PLAN`으로 돌아 `SCAN o` / `SEARCH u USING INTEGER PRIMARY KEY` 계획을
  보여주는 것.
- 구조: 서버/DB/시점 고르개, 테이블 선택 시 파란 외곽선.
- ERD: **고르지 않은 카드를 끌어 카드가 따라오는 것**, 테이블 추가 아이콘이 확대(＋)와
  구분되는 것, 표시 아이콘 26종, 메모의 크기 손잡이, 컬럼 추가 → 이름 변경 → NULL 해제가
  **오류 없이 서버에 반영**되는 것(`customer_no`, nullable=false).
- 감사 로그: 줄을 눌러 상세 모달이 열리고 상세가 키·값 표로 그려지는 것, 전체 복사 버튼.
- 어시스턴트 팝업: AI 아이콘, 전체 화면 버튼 제거, [대화]·[설정] 두 버튼만 남은 머리글,
  대화 목록이 **팝업 안 모달**로 열리는 것.

모바일은 화면 폭 ~370 CSS px에서 구조만 확인했다(빈 상태·메뉴 서랍). 실제 기기에서의
확인은 하지 못했다.

### P20-1 (2026-08-17) — 아이디 저장

로그인 화면에 "아이디 저장"을 넣었다. 담는 것은 아이디 하나뿐이다 — **비밀번호는
저장하지 않는다.** 그 일은 브라우저의 비밀번호 관리자가 하도록 만들어진 물건이고,
앱이 흉내 내면 저장소를 읽을 수 있는 누구에게나 자격증명을 넘겨주는 셈이 된다.
(체크 옆에 그 사실을 한 줄로 적어 두었다가, 군더더기라는 지적을 받아 뺐다.)

세부 결정 둘.

- **저장은 로그인에 성공한 뒤에** 한다. 입력하는 대로 저장하면 오타가 기억되고,
  다음에도 그 오타로 시작하게 된다. 2단계 인증이 남은 경우에도 아이디는 맞았다는
  뜻이므로 그 자리에서 저장한다(코드 입력에 실패해 돌아와도 다시 치지 않아도 된다).
- **기억하고 있으면 비밀번호 칸부터** 시작한다. 이미 채워진 칸에 커서를 두면 사용자가
  한 번 더 탭을 눌러야 한다.

**검증 결과**(브라우저 실측): 체크하고 로그인 → 로그아웃하니 아이디가 채워지고 체크도
켜진 채로, 커서는 비밀번호 칸에 있었다. 체크를 끄고 로그인 → 로그아웃하니 아이디 칸이
비어 있었다.

### P20-2 (2026-08-17) — 팝업의 대화 목록

피드백: 팝업에서 연 대화 목록이 "너무 보기 힘들다". 실제로 항목 하나가 **85px**까지
줄어 제목도 시각도 읽을 수 없었다.

원인은 규칙 두 벌이 겹친 것이다. 좁은 팝업용으로 "목록을 가로로 눕힌다"는 규칙
(`.float-panel.is-narrow …`)을 만들어 두었는데, 그 뒤 목록을 **팝업 안 모달**로 옮기면서
모달용 규칙을 새로 썼다. 그런데 눕히는 쪽의 선택자가 더 구체적이라(클래스 3개 대 2개)
모달 안에서도 가로 배치가 이겼다.

고친 방법은 규칙을 이기게 만드는 것이 아니라 **없애는 것**이다. 목록은 이제 모달에서만
나타나므로 눕히는 규칙 자체가 갈 곳이 없다. 목록은 목록의 모양(세로)일 때만 목록이다 —
제목 한 줄과 시각·개수 한 줄이 보여야 어느 대화였는지 고를 수 있다.

**검증 결과**(브라우저 실측): 대화 4개가 세로로, 각각 전체 폭으로, 제목과 "방금 / 1분 전 /
1일 전 4개"까지 보이며 현재 대화가 강조된다.

### P20-3 (2026-08-17) — 설명서의 코드 강조·복사 버튼, 테이블 추가 아이콘

**설명서의 코드에 색을 입혔다.** 거기 실린 것은 그대로 복사해 쓰는 예제라, 문자열과
키워드가 구분되지 않으면 어디까지가 값인지 눈으로 세어야 한다.

강조기를 마크다운 렌더러 안에서 부르지 않고 **주입받게** 했다(`renderMarkdown(src,
{highlight})`). 이유가 둘이다. 마크다운을 그리는 일과 SQL·Lua를 아는 일은 다른
관심사이고, 스트리밍 중에는 강조를 끄는 편이 낫다 — 토큰이 도착할 때마다 전체를 다시
그리는데 거기에 토큰화까지 얹으면 긴 코드에서 눈에 띄게 느려진다. 그래서 설명서는 켜고
어시스턴트는 지금처럼 둔다.

**코드 블록마다 복사 버튼**을 우상단에 붙였다(마크다운 렌더러가 아니라 설명서 화면에서
붙인다 — 복사 버튼은 문법이 아니라 이 화면의 장치이고, 렌더러가 버튼을 만들기 시작하면
그것을 쓰는 다른 화면까지 원하지 않는 버튼을 얻는다). 평소에는 옅게 두었다가 블록에
마우스를 올리면 진해진다. 마우스가 없는 기기에서는 늘 보인다.

**테이블 추가 아이콘이 직관적이지 않다**는 피드백. 원래는 표 전체(24px)에 작은 십자를
얹었는데, 15px로 줄면 십자가 표의 칸선과 섞여 그냥 네모로 보였다. 표를 왼쪽에 작게 두고
더하기를 오른쪽 위에 크게 뒀다 — 두 뜻(무엇을 + 어떻게)이 겹치지 않아야 작은 크기에서도
읽힌다.

**검증 결과**(브라우저 실측): 설명서 Lua 절에서 `local`·`return`이 키워드 색으로,
`"SELECT * FROM users …"`가 문자열 색으로, `--` 주석이 기울임으로 그려진다. ERD 도구
막대에서 테이블 추가와 확대(＋)가 눈으로 구분된다.

**뒤늦게 드러난 것**: 위 "검증"은 처음에 틀렸다. 강조를 넣는 편집이 파일에 적용되지
않았는데(스크립트 치환이 조용히 실패했다) 화면에서 색이 보인다고 판단했다. 실제로는
캐시에 남은 옛 모듈이 그려지고 있었고, 사용자가 DOM(`<code data-lang="lua">` 안에
span이 없다)으로 그것을 잡아냈다. 편집을 다시 넣고 **새 프로필 브라우저**로 열어
확인했다 — 캐시가 남은 창에서는 하드 리로드가 전달되지 않아 계속 옛 화면을 보게 된다.
화면으로 확인할 때는 "무엇을 보고 있는지"(새 코드인지 캐시인지)부터 확인해야 한다.

### P21 (2026-08-17) — 서버 컴퓨터: 이 앱이 도는 기계를 함께 본다

**왜.** DB가 느릴 때 원인은 DB 안에만 있지 않다. 디스크가 차서 쓰기가 막히거나, 다른
프로세스가 CPU를 다 쓰거나, 네트워크가 포화된 것이 흔하다. 그런데 그것을 확인하려면
이 화면을 떠나 서버에 로그인해야 했다 — 장애 중에 가장 하고 싶지 않은 일이다.

**외부 라이브러리를 쓰지 않았다.** 필요한 것은 "몇 퍼센트인가" 정도이고, 그 값은 OS마다
파일 하나 또는 함수 하나에서 나온다. 리눅스는 `/proc/stat`·`/proc/meminfo`·`/proc/net/dev`와
`statfs`, 윈도우는 `GetSystemTimes`·`GlobalMemoryStatusEx`·`GetDiskFreeSpaceEx`·`GetIfTable`을
직접 부른다. 오래되고 안 바뀌는 API만 골랐다 — 최신 API(`MIB_IF_ROW2` 등)는 구조체에
열거형과 비트필드가 섞여 있어 한 칸만 어긋나도 **그럴듯한 숫자**가 나오고, 그런 오류는
화면에서 알아볼 수 없다.

**못 읽은 것은 못 읽었다고 말한다.** 0으로 채우면 화면이 "한가한 서버"라고 거짓말한다.
첫 표본의 CPU 사용률도 없다(비교 대상이 없으므로) — 여기서 0을 넣으면 "방금 켠 서버는
한가하다"는 거짓이 차트 맨 앞에 박히고 그 뒤의 모든 판단이 그 점에서 시작한다.

**윈도우 네트워크는 세 배로 세진다.** 같은 물리 어댑터가 필터 드라이버마다 한 줄씩
나온다(WFP Native MAC Layer, QoS Packet Scheduler …). 이름은 조금씩 다르지만 바이트 수가
정확히 같다 — 같은 트래픽을 세고 있기 때문이다. 누적값으로 한 번만 세고, 같은 값을 가진
줄 중에서는 **짧은 이름**을 남긴다(필터 줄은 "어댑터-필터이름-0000"처럼 길다).
한 바이트도 오간 적 없는 인터페이스는 버린다. 그러지 않으면 목록이 41개가 되어
진짜 랜카드를 찾을 수 없다(실측: 41개 → 4개).

**임계값은 플래그가 아니라 설정이다.** "디스크 몇 %에서 알릴 것인가"는 서버를 띄우는
순간이 아니라 운영하면서 정해진다. 플래그로만 받으면 숫자 하나를 고치려고 프로세스를
재시작해야 한다. 경고와 심각이 뒤집혀 저장되면 맞바꾼다(경고가 심각보다 높으면 심각
이벤트는 영원히 나오지 않는다).

**해소에는 히스테리시스를 뒀다.** 임계선 바로 위아래에서 값이 흔들리면 열고 닫기를
반복해 이벤트 목록이 같은 이야기로 가득 찬다. 경고선의 95% 아래로 내려올 때만 닫는다.
CPU·메모리에는 지속 시간 조건이 있고(기본 5분) 디스크에는 없다 — 사용률은 순간적으로
튀지 않고, 찼다면 그 순간부터 이미 문제다.

**"열려 있는가"를 기억한다.** 정상 범위일 때마다 해소 UPDATE를 날리면 아무 일도 없는
서버가 30초마다 SQLite에 쓰기 잠금을 건다. 그래서 열린 지표를 메모리에 들고 있고,
시작할 때 DB에서 한 번 읽어 맞춘다 — 그러지 않으면 재시작 직후에는 이미 열린 이벤트를
몰라 영원히 닫지 못한다.

**OS 이벤트.** 재부팅은 부팅 시각이 2분 이상 달라졌을 때만 본다(가동 시간에서 역산하므로
매번 조금씩 흔들린다). 첫 관측에는 이벤트를 만들지 않는다 — 그때는 "재부팅되었다"가
아니라 "이제 보기 시작했다"이고, 구분하지 않으면 기능을 켠 모든 서버가 재부팅했다고 말한다.
비정상 종료는 이미 있던 실행 표식(`internal/runstate`)을 이벤트로 승격했다: 로그는 서버에
들어갈 수 있는 사람만 보지만 "언제부터 앱이 안 돌고 있었는가"는 화면에서 답해야 한다.

**시스템 로그.** 리눅스는 syslog 파일을 위치(offset)를 기억하며 이어 읽고, 윈도우는
이벤트 로그의 "시스템" 채널을 옛 API(`ReadEventLog`)로 뒤에서부터 읽어 마지막 기록 번호
이후만 본다. 새 API(`EvtQuery`)는 XML을 여러 단계로 렌더링해야 하는데, 우리가 필요한 것
(언제·무엇이·어떤 오류)은 옛 구조체 하나에 다 있다. **처음 볼 때는 자리만 기억하고 아무것도
만들지 않는다** — 기능을 켠 순간 지난 몇 달의 오류가 쏟아지면 그 목록은 아무도 보지 않는다.
한 번에 최대 20줄을 한 이벤트로 묶는다(이벤트 표가 로그 사본이 되면 안 된다).

**권한.** 호스트 이벤트에는 커넥션이 없다. 이벤트 조회는 "볼 수 있는 커넥션 목록"으로
걸러 왔는데, 목록에 넣을 ID가 없다고 조건을 비우면 전체 공개가 된다. 그래서 범위 조건을
`ConnectionIDs`와 `IncludeSystem`으로 나누고, 시스템 이벤트는 **커넥션 관리 권한**에게만
보인다 — 컴퓨터 이름·디스크 경로·시스템 로그는 특정 DB의 열람 권한으로 판단할 수 없는
운영 정보다. 목록과 요약 배지가 같은 함수를 쓰게 했다(둘이 어긋나면 배지에는 숫자가
있는데 목록은 비어 있는 화면이 나오고, 그때 사람들은 알림 자체를 믿지 않는다).

**곁가지 하나.** 열린 이벤트의 임계값도 갱신하도록 고쳤다. 운영 중에 기준을 바꾸면
열려 있던 이벤트만 옛 숫자를 들고 남아, 본문("기준 85%")과 표의 임계값이 서로 다른 말을
했다(실측으로 발견했다).

**곁가지 둘.** 메뉴 강조가 접두사 일치였다. `/monitor/host` 에 들어가면 "모니터링"과
"서버 컴퓨터"가 함께 켜져 "지금 어디에 있는가"에 답이 두 개가 됐다. 가장 길게 맞는 항목
하나만 켜도록 바꿨다(경계까지 본다 — 문자열 접두사만 보면 `/macros` 가 `/macrosomething`
에도 맞는다). `/monitor/rules` 처럼 메뉴가 없는 하위 경로는 그대로 상위 메뉴가 켜진다.

**검증 결과**(브라우저 실측, 윈도우): `DESKTOP-MS327CL · windows/amd64 · CPU 22개`,
가동 14일, CPU 29%·메모리 87%(27.4/31.5GB)·디스크 C: 56.3%/G: 17.4%,
네트워크 수신 177KB/s·송신 17.6KB/s가 카드와 4개 차트에 그려진다. 임계값을 낮추자
CPU·메모리·디스크 이벤트가 열렸고 되돌리자 CPU·디스크가 자동 해소되었다(메모리는 87%로
히스테리시스 구간에 남았다 — 설계대로다). 앱을 강제 종료한 뒤 재시작하니
"이전 실행이 종료 기록을 남기지 않았습니다"가 경고로 열렸다.

### P21-1 (2026-08-18) — 이름을 바꾸면 카드가 튀던 이유

**증상**: ERD 편집에서 테이블 이름을 바꾸면 그 카드가 다이어그램의 엉뚱한 자리로 튀었다.

**원인**: 이 문서에서 테이블을 가리키는 것은 이름으로 만든 키(`namespace.name`)다.
배치(layout)와 그 테이블을 참조하는 외래키가 모두 그 키를 쓴다. 서버의 `table.update`는
이름을 바꿀 때 레이아웃 키와 참조를 함께 옮기지만(그 규칙은 시험도 있었다),
**화면의 미리보기**는 `tbl.name` 하나만 갈아 끼웠다. 그 순간 캔버스는 배치가 없는 카드를
기본 자리(80,80)에 그렸다 — 확정 전 몇 초 동안 카드가 튀어 보인 것이 이것이다.
같은 이유로 그 테이블을 가리키는 관계선도 함께 사라졌다.

**고친 것**: 미리보기를 한 함수(`previewTableName`)에 모으고, 서버가 하는 일과 같은
것을 문서 사본에 한다 — 레이아웃 키 이동, 참조하는 외래키의 대상 이름 갱신, 선택 키 이동.
"이름만 바꾸는 것은 이 문서에서 성립하지 않는다"가 이 버그의 교훈이고, 그래서 이름을
바꾸는 길을 하나로 만들었다.

**곁가지 셋**:
- **인스펙터 제목**이 옛 이름으로 남았다. 패널을 다시 그리면 입력 중인 칸의 포커스가
  사라지므로(그래서 `renderPanelIfIdle`이 있다), 제목 글자만 제자리에서 갈아 끼운다.
- **거부된 이름이 남의 테이블을 고르게 만들었다.** 이름 충돌로 거부되면 선택은 이미 새 키를
  가리키고 있고, 그 키는 **그 이름을 쓰던 다른 테이블**이라 `pruneSelection`이 "있는 대상"으로
  보고 그대로 두었다. 그 뒤의 편집은 조용히 다른 테이블에 갔다. 미리보기가 선택을 옮길 때
  원래 키를 기억해 두고, 거부(reject)와 오류(error) 양쪽에서 되돌린다.
  거부 메시지는 문서를 함께 보내므로 `onReject`가 문서를 갈아 끼우기 **전에** 되돌려야 한다.
- **개발 모드 캐시.** 응답에 `Cache-Control`이 없어 브라우저가 스스로 유효기간을 정하고
  있었다(휴리스틱 캐싱). 파일을 고쳐도 새로고침에 옛 모듈이 그려지는데, 이 저장소에서
  같은 함정에 두 번 빠졌다(P20-3의 "뒤늦게 드러난 것"). dev에서는 `no-store`,
  SPA 셸은 `no-cache`로 명시한다 — dev의 목적이 "새로고침만으로 반영"이므로 속도보다
  정확함이 맞다.

**검증 결과**(브라우저 실측): 카드를 (470, 356.8)에 두고 `orders` → `purchase_orders` →
`orders_v2` → `orders_v3` 로 세 번 바꿨다. 카드는 매번 제자리에 있었고 서버의 레이아웃도
같은 좌표를 유지했다. 이미 있는 이름(`customers`)으로 바꾸면 거부 메시지가 뜨고 선택·제목·
입력칸이 모두 `orders_v2`로 돌아왔다(예전에는 `customers`가 골라진 채 남았다).
서버 쪽 시험(`TestTableRenamePropagates`)에는 좌표가 그대로인지 보는 단정을 더했다.

### P21-2 (2026-08-18) — 인스펙터가 잡아 둔 객체는 곧 유령이 된다

**증상**: 이름을 처음 칠 때는 괜찮은데, **백스페이스로 고치면 카드가 다시 튀었다**.

**원인**: P21-1은 미리보기가 문서를 옳게 고치도록 했지만, **어느 문서를 고치는지**는
그대로였다. 구조 편집이 확정되면 서버가 문서 전체를 보내고 `this.doc`이 통째로 바뀐다.
인스펙터는 패널을 그릴 때 잡아 둔 테이블 객체를 계속 고치고 있었으므로, 확정 뒤의
한 글자부터는 **화면에 없는 유령 객체의 이름**이 바뀌고 배치 키만 살아 있는 문서에서
옮겨졌다. 배치를 잃은 카드는 다시 기본 자리로 갔다.

**고친 것**: 인스펙터가 객체 대신 **키를 들고 다니게** 했다(`tableRef`). 이름 미리보기,
컬럼 편집, 아이콘·색, 컬럼·인덱스·외래키·체크 제약 추가, 테이블 삭제가 모두 이 참조를
통해 "지금 문서에서 다시 찾은" 대상에 적용된다. 컬럼 줄도 같은 이유로 컬럼 객체를
잡아 두지 않는다.

**같은 원인의 다른 버그들**(테스트 중 발견, 함께 고침): 이름을 바꾼 **직후에는**
- 컬럼 이름·타입·NULL·기본값 수정, 컬럼 순서 이동·삭제, 기본키 토글이 옛 테이블 키로
  전송되어 조용히 거부되었다.
- 아이콘·색 고르개가 옛 키로 `table.move`를 보내 아무 일도 일어나지 않았다.
- 컬럼 추가, 인덱스·외래키·체크 제약 추가, 테이블 삭제도 마찬가지였다.
확정 뒤 패널을 다시 그리면 정상으로 돌아왔기 때문에 "가끔 안 먹는다"로만 보였다.

**빈 이름**(테스트 중 발견): 이름 칸을 다 지우면 캔버스에 **이름 없는 카드**가 남았다.
빈 이름은 서버로 보내지 않으므로(거부된다) 화면만 어긋난 상태였다. 미리보기는 빈 값을
반영하지 않고, 칸을 떠날 때(blur) 지금 이름으로 되돌린다 — 타자 도중에는 되돌리지 않는다.
지우고 새로 치는 중에 글자가 되살아나면 커서가 튀기 때문이다.

**검증 결과**(브라우저 실측, 실제 편집처럼): 이름 확정 → 백스페이스 3번 → 다시 타자 →
카드는 (470, 356.8) 그대로, 서버 배치도 같은 좌표. 이어서 같은 패널에서 컬럼 이름 변경,
컬럼 추가, 아이콘·색 지정, 인덱스 추가, 외래키 추가, 테이블 삭제가 모두 정상 동작했다.
이름 충돌로 거부되면 선택·제목·입력칸이 원래 테이블로 돌아오고, 참조하는 테이블의 이름을
바꾸는 동안 관계선이 끊기지 않았으며, 되돌리기도 좌표를 지킨 채 옛 이름으로 돌아갔다.

### P22 (2026-08-18) — 타입 고르개, 자동 증가, 도메인

**왜.** 컬럼 타입을 정하는 유일한 길이 "타입 문자열을 손으로 치는 것"이었다. 그러면
DB마다 다른 타입 이름을 사람이 외우고 있어야 하고(VARCHAR2? NVARCHAR? TIMESTAMPTZ?),
자동 증가는 켤 방법조차 없었다(값은 `AUTO` 배지로 보이기만 했다). 같은 뜻의 컬럼이
표마다 다른 타입으로 만들어지는 것도 손으로 치는 방식의 필연이었다.

**타입 목록은 서버가 쥔다**(`internal/schema/catalog.go`). 화면이 따로 들고 있으면 DB
종류가 늘 때마다 두 곳을 고쳐야 하고, 어긋나는 순간 화면에서 고른 타입을 서버가 모르는
상태가 된다. 파싱(ParseType)과 렌더링(RenderType)이 이미 그 파일 옆에 있으므로 고르는
목록도 같은 자리에 있는 것이 맞다. 5개 dialect에 200개가 넘는 타입을 담았고,
**시험이 목록의 모든 타입을 다시 파싱해 본다** — 목록에만 있고 파서가 모르는 타입은
고르는 순간 unknown이 되어 다른 DB로 옮길 때 그대로 문자열로 새어 나간다.
정규화하지 않기로 한 타입(range, hierarchyid, INTERVAL YEAR TO MONTH …)은 그 판단이
의도된 것임을 시험의 예외 목록으로 못 박았다.

**고르개는 타입이 요구하는 것만 묻는다.** 길이(VARCHAR), 자릿수(DECIMAL), 값 목록(ENUM),
초의 소수 자릿수(TIMESTAMP), UNSIGNED(MySQL 숫자형), 배열(PostgreSQL). 카탈로그의
`param`이 그 모양을 알려주고 화면은 그것만 그린다 — 모든 칸을 늘 보여주면 어느 칸이
이 타입에 쓰이는지 사람이 판단해야 한다. **직접 입력**을 그대로 남긴 이유: 아는 타입은
치는 편이 빠르고, 모르는 타입은 고르는 편이 빠르다. 둘 중 하나만 두면 언제나 한쪽이 불편하다.

**자동 증가**는 op에 이미 있던 `identity`를 화면에 연결한 것이다. 정수 계열이 아닌
컬럼에서는 잠근다 — 어느 DB도 문자열을 자동 증가시키지 않으므로, 켤 수 있게 두면
ERD에서는 멀쩡해 보이다가 마이그레이션에서 거부된다. 다만 **이미 켜져 있으면 끌 수는
있게** 두었다(SQL 불러오기로 들어온 이상한 상태를 화면에서 고칠 수 있어야 한다).
DB마다 다른 이름과 조건은 카탈로그가 함께 알려주고, 그 문구가 체크박스의 설명이 된다.

**도메인은 문서에 두고, 컬럼에는 결과를 남긴다.** IR(schema.Schema)에 넣지 않은 이유:
도메인은 설계의 어휘이지 대부분의 DB에 만들어지는 물건이 아니다. IR에 넣으면 지문이
바뀌어 "도메인을 정리했을 뿐인데 대상 DB와 구조가 다르다"가 된다. 컬럼에는 도메인 이름과
**그 결과인 구체 타입이 함께** 남는다 — 이름만 남기면 도메인을 지우는 순간 컬럼이 타입을
잃는다. 그래서 마이그레이션·비교·DDL 생성은 도메인을 몰라도 되고, 도메인을 지워도 설계는
그대로 성립한다.

도메인의 값어치는 "고치면 따라 바뀐다"에 있다. 정의를 고치면 그것을 쓰는 컬럼의 타입이
함께 바뀌고(이름을 바꾸면 연결도 따라간다), 컬럼에서 타입을 직접 고치면 그 컬럼은
도메인에서 **벗어난다** — 연결을 남겨 두면 다음에 도메인을 고칠 때 그 컬럼의 값이 이유
없이 되돌아간다. NULL 여부와 기본값은 도메인이 "정하지 않을" 수도 있게 했다(세 갈래):
같은 뜻의 컬럼이라도 표마다 필수/선택이 다르다.

**곁가지 하나**: `Document.Clone()`이 도메인을 얕게 복사하고 있었다. 되돌리기는 두 문서를
비교해 만들어지므로(Diff), 사본에서 정의를 고치면 원본까지 바뀌어 "바뀐 것이 없다"가
된다. 시험이 이것을 첫 실행에서 잡았다.

**검증 결과**(브라우저 실측): PostgreSQL 초안에서 도메인 `email`을 고르개로 만들고
(VARCHAR 선택 → 길이 칸이 나타나 320 입력 → 결과 `VARCHAR(320)`), 컬럼의 타입 창에서
그 도메인을 골라 적용했다. 컬럼은 `VARCHAR(320)`이 되고 줄에 `email` 표식이 붙었다.
도메인 정의를 `VARCHAR(254)`로 고치자 그 컬럼이 함께 바뀌었고, 사이드바에는
"1개 컬럼에서 사용"이 표시됐다. AUTO를 켜고 끄는 것도 서버 상태(identity)에 그대로
반영됐으며, VARCHAR 컬럼에서는 잠긴다.

### P23 (2026-08-18) — 이벤트를 메신저로 (Mattermost)

**왜.** 이벤트는 화면을 열어야 보인다. 디스크가 차거나 운영 DB가 응답을 멈춘 사실은
**보고 있지 않을 때** 일어나고, 그때 사람에게 닿지 않으면 이벤트 목록은 사후 기록일 뿐이다.
(P14의 "트리거 실패 알림"에서 "이메일이나 웹훅으로 알리려면 무엇을 어디로 보낼지
정해야 한다"고 미뤄 둔 결정이 여기서 정해졌다.)

**들어오는 웹훅을 쓴다.** 봇 토큰과 API를 쓰면 채널 목록 조회·권한 관리가 따라오는데,
우리가 필요한 것은 "정해진 채널에 글 한 줄"이다. 대신 그 주소는 **그것 하나가 곧 그
채널에 글을 쓸 권한**이므로 커넥션 비밀번호와 같은 급으로 다룬다: 암호화해 저장하고,
화면에는 호스트만 남기고 토큰을 가리며(`…/hooks/ab••••78`), 감사 로그에도 남기지 않는다
("켰는가/무엇을 보내는가"만 남긴다).

**보내기는 큐를 거친다.** 전송은 네트워크 왕복이고 폴러는 그 시간을 기다려서는 안 된다.
큐가 가득 차면 기다리지 않고 버리되 버렸다는 사실을 남긴다 — 메신저가 죽어 있을 때
메모리가 늘어나는 것보다 "그 사이 몇 건을 잃었다"고 말하는 편이 낫다. 실패는 몇 초
간격으로 세 번까지 다시 시도한다(메신저 재시작은 대개 그 안에 지나간다).

**해소도 보낸다.** "문제가 생겼다"만 오는 채널은 시간이 지나면 아무도 믿지 않는다.
그러려면 저장 계층이 "무엇이 닫혔는가"를 알려줘야 해서 `ResolveEvents`가 개수 대신
**닫힌 이벤트들**을 돌려주도록 바꿨다(닫기 전에 대상을 먼저 읽는다). 해소 메시지의
값은 "발생 당시 값"으로 이름을 달리했다 — 그냥 "값"이라고 적으면 이미 정상으로 돌아온
지표를 아직 넘은 것처럼 읽는다. 지속 시간도 함께 싣는다("5분 만에 끝났다"와 "이틀 동안
열려 있었다"는 전혀 다른 이야기다).

**드리프트는 예외다.** 스키마 변경 이벤트는 새 것으로 갈아 끼우려고 옛 것을 닫는다.
그 닫힘에 해소 알림을 보내면 채널에 "해소"와 "발생"이 나란히 찍혀 무엇이 실제로
정리되었는지 읽을 수 없다.

**수신자가 둘이 되었다.** 이벤트는 매크로 자동 실행을 깨우기도 하고 메신저로 나가기도
한다. 둘은 서로를 몰라야 하고(한쪽이 느려도 다른 쪽이 막히면 안 된다), 그 조합을 아는
것은 부팅 절차의 몫이다 — `monitor.FanOut`. 해소 알림은 선택적 인터페이스(`ResolveSink`)로
두었다: 매크로는 해소에 반응할 이유가 없으므로 빈 메서드를 강요하지 않는다.

**곁가지 하나**: 전송 상태의 시각을 `time.Time`으로 두었더니 한 번도 보내지 않은 서버가
"1-01-01에 실패"라고 표시했다(`omitempty`는 구조체에 걸리지 않는다). 포인터로 바꿔
"아직 보낸 알림이 없습니다"와 실패를 구분한다. 화면 실측에서 잡았다.

**검증 결과**(가짜 웹훅 수신기 + 브라우저 실측): 설정 저장 → 응답의 주소가
`http://127.0.0.1:8391/hooks/ab••••78`로 마스킹됨 → 테스트 전송이 채널 이름·보내는 이름·
색·"보낼 기준" 안내와 함께 도착. 디스크 임계값을 30%로 낮추자
`:warning: **[서버 컴퓨터 발생]** 디스크 사용률 (C:)이 58% 입니다 (기준 30%)`가
주황색으로, 임계값을 되돌리자 같은 이벤트가 초록색 **해소** 메시지로 왔다.

### P23-1 (2026-08-18) — Slack도 같은 자리에서

**왜 하나의 설정인가.** Mattermost의 들어오는 웹훅은 Slack 호환으로 만들어졌다. 본문
구조(`text`·`username`·`channel`·`attachments`의 색과 필드)가 같으므로, 저장 구조와 화면을
두 벌로 나눌 이유가 없다. 메신저를 고르는 값 하나를 더하고, **다른 곳만** 갈랐다.

**다른 것은 글자 문법뿐이다.** Slack의 mrkdwn은 굵게가 별표 **하나**이고 링크가
`<주소|글자>`다. Mattermost는 표준 마크다운을 쓴다. 그 차이를 함수 두 개(`bold`·`link`)에
가둬 두면 나머지 코드는 어느 메신저인지 몰라도 된다 — 틀리면 채널에 별표와 괄호가
그대로 찍히고, 알림이 오긴 오는데 읽기 싫어진다. 시험이 두 메신저의 본문을 나란히 비교해
"문법은 다르고 구조(색·필드)는 같다"를 못 박는다.

**옛 설정은 Mattermost다.** provider가 비어 있는 저장값을 "알 수 없는 메신저"로 보면
이미 쓰던 알림이 조용히 멈춘다. 빈 값은 mattermost로 읽고, 설정 키 이름(`notify.mattermost`)도
그대로 두었다 — 키를 바꾸면 저장된 설정이 사라진다. 이름의 정확함보다 쓰던 것이 그대로
있는 편이 낫다.

**화면이 미리 말해 준다.** 최신 Slack 앱 웹훅은 채널·보내는 이름 지정을 무시하고 웹훅을
만들 때 고른 채널로 보낸다. 그 사실을 모르면 "채널을 적었는데 다른 곳으로 간다"를 겪고
나서야 찾아보게 된다. 메신저를 고르면 안내문과 주소 예시, 그리고 채널·이름 칸의 설명이
함께 바뀐다.

**검증 결과**(가짜 웹훅 수신기): Slack으로 저장 후 테스트 전송이
`:white_check_mark: *DB Studio* 알림 연결을 확인했습니다.`로 도착(별표 하나).
디스크 임계값을 낮추자 `:warning: *[서버 컴퓨터 발생]* …`가 주황색으로,
되돌리자 초록색 해소 메시지가 `발생 당시 값`과 `지속 14초`를 달고 왔다.
링크는 `<http://127.0.0.1:8199/events|이벤트 화면에서 보기>` 형식이었다.

### P22-1 (2026-08-18) — 자동 증가는 타입 창 안으로

**왜 옮겼나.** 자동 증가는 독립된 속성이 아니라 **타입에 딸린 속성**이다. 정수 계열에만
붙고, 그 경계가 DB마다 다르다(MS-SQL은 소수 자릿수 0인 DECIMAL에도, SQLite는 INTEGER
하나뿐이다). 컬럼 줄에 체크박스로 떼어 두면 타입을 바꾼 뒤에도 그 값이 그대로 남아,
"varchar인데 자동 증가"처럼 말이 안 되는 상태를 사람이 직접 치워야 했다. 타입 창 안에
두면 타입이 바뀔 때 함께 정리된다 — 적용할 때 identity를 **늘 함께 보낸다**.

**칸이 아예 나타나지 않는다.** 예전에는 비활성 체크박스로 남겨 두고 툴팁으로 이유를
설명했다. 하지만 꺼진 체크박스는 "지금은 못 켠다"가 아니라 "왜 안 되지"를 만든다.
붙일 수 있는 타입을 골랐을 때만 칸이 나타나고, 그 옆에 그 DB의 문법 이름
(`GENERATED BY DEFAULT AS IDENTITY` 등)과 제약이 함께 적힌다.

**판단의 근거는 서버 카탈로그다.** `TypeDef.Identity`를 새로 두고 정수 계열 타입에
표시했다. 화면이 타입 이름을 보고 짐작하면 DB별 예외를 화면에서 다시 구현하게 되고,
두 곳이 어긋나면 "카탈로그에는 있는데 켤 수 없는" 타입이 생긴다. 다만 자릿수 조건
(MS-SQL·Oracle의 DECIMAL/NUMBER는 소수 자릿수 0일 때만)은 타입이 아니라 **인자**에
달린 것이라 표시로 나타낼 수 없어, 화면이 인자를 한 번 더 본다.

**PostgreSQL의 serial은 표시하지 않았다.** 그 자체가 자동 증가이므로 그 위에 IDENTITY를
또 얹는 것은 뜻이 겹친다. 대신 정수 타입의 설명에 "예전 방식인 serial을 골라도 같은
뜻이 된다"고 적어 둔다.

**켜져 있다는 사실은 여전히 컬럼 줄에서 보인다** — 읽기 전용일 때만 보이던 `AUTO`
배지를 늘 보이게 했다. 안 보이면 창을 하나하나 열어 확인하게 된다.

**검증 결과**(헤드리스 브라우저 + CDP로 실제 화면 조작): PostgreSQL 초안에서
BIGINT → 칸 보임, VARCHAR·TEXT·NUMERIC·SERIAL → 칸 사라짐, SMALLINT → 다시 보임.
BIGINT에서 켜고 적용하니 문서가 `rawType=BIGINT, identity=true`가 되고 컬럼 줄에 AUTO
배지가 붙었다. 자동 증가가 켜진 컬럼을 VARCHAR(255)로 바꾸자 `identity=false`로 함께
정리됐다.

### P24 (2026-08-18) — 클러스터: 여러 서버, 하나의 DB Studio

**요구**: 분산 서버에서 각각 DB Studio가 떴을 때 마스터의 DB를 슬레이브로 복제해 동기화하고,
어느 노드에서나 하나의 서버처럼 모든 기능과 DB를 다룰 수 있어야 한다.

**왜 마스터-리플리카인가.** 이 앱의 상태는 SQLite 파일 하나다. 여러 노드가 각자 쓰면 같은 행을
서로 다르게 고칠 수 있고, SQLite에는 그 충돌을 풀 방법이 없다. 쓰기를 한 곳으로 모으면 충돌 자체가
생기지 않는다. 대신 마스터가 멈추면 그동안 쓰기를 못 한다 — 그때 리플리카는 **읽기 전용으로 계속
동작한다**(화면이 열리고 지표·이력·설계가 그대로 보인다). 자동 승격은 하지 않는다: 노드가 서로를
못 보는 동안 각자 자신을 마스터로 올리면 진실이 둘이 되고, 그 둘은 합칠 방법이 없다.

**복제는 행 단위다.** 마스터의 모든 표에 트리거를 달아 변경을 `repl_log`에 적고, 리플리카가 그 로그를
순서대로 적용한다. SQL 문장을 재실행하지 않는 이유는 `now()`·`random()`이 노드마다 다른 값을 만들어
두 DB가 **조용히** 갈라지기 때문이다. 행을 식별하는 키는 rowid로 통일했다 — 이 앱의 표는 기본키가
제각각(TEXT id, 복합키, 없음)인데 rowid는 모든 표에 있다.

**REPLACE는 쓸 수 없었다.** 처음 구현은 `INSERT OR REPLACE`로 행을 맞췄다. REPLACE는 충돌 행을
**지우고 다시 넣기** 때문에 `ON DELETE CASCADE`가 깨어난다. 그래서 사용자 행이 복제될 때마다 그
사람의 세션이 통째로 사라졌고, 증상은 "리플리카에서만 로그인이 풀린다"였다. 오류도 경고도 남지
않는 종류의 실패다. 지금은 있으면 고치고 없으면 넣는다(`TestReplicationKeepsChildRows`가 지킨다).

**새 노드는 스냅샷으로 시작한다.** 변경 로그에는 트리거를 단 뒤의 것만 있다. 이미 쓰고 있던 마스터에
새 노드가 붙으면 그 전의 데이터(계정·커넥션·이력 전부)는 로그 어디에도 없으므로, 첫 동기화는 반드시
스냅샷(`VACUUM INTO`)이다. 파일을 바꿔치기하지 않고 표 단위로 비우고 채운다 — 지금 이 프로세스가
그 파일을 열고 있기 때문이다.

**쓰기 전달과 "방금 한 일".** 리플리카는 상태 변경 요청을 마스터로 넘긴다(세션 쿠키를 그대로 실어
권한 판정은 언제나 마스터에서 그 사람의 자격으로 한다). 그리고 마스터가 응답 헤더에 실어 준 복제
지점까지 따라잡은 뒤에 답한다. 그러지 않으면 저장 직후 화면이 목록을 다시 읽을 때 방금 만든 것이
없다 — 사용자에게는 저장이 실패한 것으로 보인다.

**리플리카가 쓰지 않도록 막은 곳**: 지표 폴러·매크로 스케줄러(마스터만 실행), 호스트 지표 저장
(관측만 하고 하트비트로 보고), 세션 마지막 접속 시각, 접속 테스트 결과. 감사 기록만은 예외로
마스터에 **전달**한다 — 기록이 조용히 사라지는 것은 감사 로그에서 가장 나쁜 실패다.

**ERD 실시간 편집은 중계한다.** 편집 방은 메모리에 있고 확정된 op는 DB에 적힌다. 리플리카가 그 일을
하면 순서가 갈리고 op가 사라진다. 그래서 리플리카는 브라우저의 소켓을 마스터로 이어 준다 — 모든
편집자가 마스터의 방 하나에 모이므로, 접속한 노드가 달라도 서로의 커서가 보인다.

**특정 노드에서만 닿는 DB.** 커넥션에 담당 노드를 지정하면 그 DB에 접속하는 요청은 어느 노드로
들어오든 그 노드에서 실행된다. 넘기는 경로는 **허용 목록**이다: 기본값이 "넘긴다"이면 메타 DB에
행을 남기는 새 경로가 리플리카에서 실행되어 그 기록이 사라진다. 백업 생성·버전 캡처·마이그레이션
적용처럼 메타 DB에 쓰는 작업은 마스터에서 처리한다.

**노드 전용 API의 접두어를 나눈 이유**(`/api/v1/node/*`): Fiber의 그룹 미들웨어는 그 접두어로 시작하는
모든 경로에 걸린다. 사람이 보는 `/api/v1/cluster/` 와 같은 접두어를 쓰자 화면 조회까지 공용 비밀을
요구했고, 증상은 "슈퍼 어드민인데 클러스터 화면이 401"이었다.

**검증**: 실제로 두 프로세스를 띄워(seoul=마스터, busan=리플리카) 확인했다 —
리플리카에서 로그인·비밀번호 변경·서버 등록이 마스터에 저장되고 두 노드에서 같은 목록이 보였다.
담당 노드를 busan으로 지정한 SQLite DB의 스키마를 **마스터에서** 조회하자 응답에
`X-Cluster-Node: busan`이 붙어 왔다(그 노드가 실행했다는 뜻이다). 마스터를 내린 뒤에는 조회가
200으로 계속되고 변경만 503 `master_unreachable`로 거절됐다. 클러스터 화면은 두 노드의 복제 지연과
각 서버의 CPU·메모리·디스크를 함께 보여준다.

**남은 것**: 자동 승격(합의 프로토콜이 필요하다), 리플리카의 호스트 지표 시계열(지금은 최신 스냅샷만
노드 목록에 남는다), 노드 사이 TLS 상호 인증(지금은 공용 비밀 하나다).

### P25 (2026-08-18) — 하둡·Ceph 관리

**요구**: 하둡과 Ceph를 관리할 수 있게 한다.

**어디에 붙일 것인가.** 이 둘은 데이터베이스가 아니다. 테이블도 스키마도 SQL도 없고, 대신
파일·풀·OSD·용량이 있다. dbx의 인터페이스(Introspect/ExecDDL/Logs)에 억지로 끼우면 절반이
"미지원"인 어댑터가 되고, 화면은 그 절반을 숨기는 조건문으로 채워진다. 그래서 접점을 둘로
나눴다 — **접속 확인과 지표 수집은 어댑터로**(그래야 권한·자격증명·임계값·이벤트·알림·클러스터가
이미 하던 일을 그대로 한다), **목록·탐색·조작은 별도 패키지와 전용 화면으로**.

**능력으로 화면을 가른다.** `Capabilities.Storage`를 새로 두고 스키마·SQL·마이그레이션·ERD는
전부 껐다. 화면이 종류 이름을 비교하는 대신 이 값을 보므로, 종류가 늘어도 화면을 고칠 일이 없다.
모니터링 화면의 "스키마 변경 확인"과 스냅샷 카드도 같은 값으로 감춘다 — 버튼만 남겨 두면
눌렀을 때 "지원하지 않습니다"가 돌아오고, 그 순간 사용자는 자기가 뭘 잘못했는지 찾기 시작한다.

**REST만 쓴다.** HDFS RPC는 하둡 클라이언트 라이브러리를, librados는 C 라이브러리를 요구한다.
둘 다 단일 바이너리 원칙과 충돌한다. 필요한 것은 WebHDFS(탐색·조작), NameNode JMX(용량·블록),
YARN REST(애플리케이션), Ceph 대시보드 API(상태·풀·OSD·버킷)로 전부 된다.

**지표 이름을 종류 너머로 공유한다.** 하둡의 데이터노드와 Ceph의 OSD는 둘 다 "데이터를 들고
있는 구성원"이므로 `storage.nodes.up/down` 하나로 본다. 상태도 `storage.health`(0/1/2)라는 같은
눈금에 올려 Ceph의 HEALTH_*와 HDFS의 손실 블록·세이프모드를 함께 판정한다. 그 덕에 기본 룰
다섯 개(용량 85/95%, 노드 이탈, 상태 위험, 손실 블록)가 두 종류에 함께 걸린다.

**Ceph는 조회 전용으로 정했다.** 풀 삭제·OSD out·CRUSH 변경은 되돌릴 수 없고 클러스터 전체의
데이터 배치를 바꾼다. 그 판단을 이 앱의 버튼 하나로 옮기는 것은 위험을 옮기는 것일 뿐이다.
하둡의 디렉터리 조작은 지원하되, 재귀 삭제는 **먼저 세어 보여준다**(파일·디렉터리·용량) —
휴지통이 꺼져 있으면 되돌릴 방법이 없고, 그 사실은 지운 뒤에야 드러난다. 루트는 어떤 경우에도
지우지 않는다.

**오류를 번역한다.** WebHDFS는 `AccessControlException: Permission denied: user=dr.who…`를
돌려주고, 그 줄을 그대로 보여주면 사용자는 무엇을 고쳐야 할지 알 수 없다. 원문은 남기되 앞에
"HDFS 권한이 없습니다. 커넥션의 계정이…"를 붙인다. 계정을 비워 두면 서버 기본 사용자로
접속된다는 사실도 인증 실패 메시지에 적는다 — 그것이 가장 흔한 원인이다.

**구현 중 걸린 것**: `fail()`은 응답을 쓰고 **nil을 돌려준다**(Fiber 관례). 그것을 헬퍼에서
그대로 반환하고 호출부에서 `err != nil`로 검사하자, 권한을 거절해 놓고도 핸들러가 계속 실행됐다.
헬퍼는 `fiber.NewError`를 돌려주도록 고쳤다.

**검증**: 실제 응답 모양을 흉내 낸 서버(WebHDFS/JMX/YARN, Ceph 대시보드)로 20개 시험을 돌리고,
가짜 클러스터 둘을 띄운 개발 서버에서 화면까지 확인했다 — 하둡은 용량 75%·죽은 노드 1대·복제
부족 27블록과 경로 탐색·YARN 앱 3건이, Ceph는 HEALTH_WARN·OSD 24개 중 23 up·풀 3개·버킷 3개가
보였다. 지표는 자동으로 수집되어(`storage.*`, `hdfs.*`, `ceph.*`) 두 클러스터 모두 "비정상 노드"
임계 이벤트가 열렸고, HDFS 디렉터리 생성은 감사 로그에 남았다.

**남은 것**: Kerberos(SPNEGO) 인증, HDFS 파일 내용 미리보기·업로드, Ceph 쓰기 조작(정책적으로
보류), 하둡 3.x 미만의 JMX 이름 차이.

### P26 (2026-08-31) — 프로젝트: 자원의 울타리

**요구**: 왼쪽 메뉴에서 프로젝트를 고르면 그 프로젝트의 자원만 보이게 한다. 모든 자원은
프로젝트 산하에서 관리하고(없으면 만들고 그 안에서 커넥션·ERD·마이그레이션·버전을
만든다), 사용자 접근 권한에도 프로젝트를 넣는다.

**결정**

- **컬럼은 두 개만 늘렸다.** 커넥션·독립 ERD 초안·용어 사전만 `project_id`를 갖는다.
  마이그레이션·버전·스냅샷·백업·구조 문서는 커넥션을 따라 저절로 딸려 오므로, 표마다
  프로젝트를 적으면 같은 사실이 여러 곳에 적히고 그중 하나가 어긋나는 날이 온다.
- **서버 컴퓨터·매크로·클러스터·사용자·알림은 프로젝트 밖.** 한 대의 서버가 여러
  프로젝트의 DB를 담고 매크로 하나가 두 프로젝트를 오갈 수 있다. 프로젝트에 매면
  "어느 프로젝트의 권한으로 도는가"라는 답 없는 물음이 생긴다.
- **참여는 등급을 대신하지 않고 그 앞에 선다.** `auth.resolveWithPolicy`의 첫 줄이
  참여 검사다 — 한 곳에 두었으므로 HTTP·WebSocket·AI 툴이 모두 같은 판정을 지난다.
  합쳤다면 "프로젝트에는 있지만 운영 DB만 못 본다"를 적을 수 없게 된다.
- **프로젝트를 알 수 없는 대상도 막는다.** 확인할 수 없는 것을 통과시키면 관문이
  아니다. 같은 이유로 `Resolve`는 커넥션 조회 실패에 이제 거부로 답한다(전에는 서버
  없이 판정을 이어 갔다 — 그때는 실패가 권한을 넓히지 않았고 지금은 넓힌다).
- **커넥션 목록의 관리자 예외에도 관문을 걸었다.** 목록은 관리 편의로 등급 없는 DB도
  보여주는데, 그 예외가 프로젝트를 넘으면 참여하지 않은 팀의 DB 이름이 그대로 뜬다.
- **없는 프로젝트와 남의 프로젝트에 같은 404.** 403은 그 자리에 무언가 있다는 사실을
  알려 주는데, 이름 자체가 알려서는 안 되는 것일 수 있다.
- **커넥션 이름의 유일성을 프로젝트 안으로 좁혔다.** 앱 전체에서 유일하면 보이지도
  않는 남의 이름 때문에 등록이 막히고, 그 실패는 원인을 짚을 방법이 없다. 이것 때문에
  `connections` 표를 새로 만들어 옮겼다(0037, `-- +no-foreign-keys`).
- **빈 프로젝트만 지운다.** 안에 든 것을 함께 지우는 단추는 무엇을 지우는지 말할 수
  없는 단추다. 커넥션 하나를 지우는 것도 무엇이 함께 사라지는지 세어 보여 준 뒤에 하는
  일이다(ConnectionImpact).
- **올리는 순간 권한을 빼앗지 않는다.** 옮길 자원이 있는 앱에만 기본 프로젝트를 만들고
  있던 사용자를 전원 참여자로 넣는다. 빈 앱에는 만들지 않는다 — 그래야 처음 켠 사람이
  이 층이 있다는 것을 알게 된다.
- **고르는 자리는 사이드바 하나.** 화면마다 고르게 하면 같은 사람이 같은 시간에 서로
  다른 프로젝트를 보게 된다. 목록 요청은 모두 `withProject`를 지난다.
- **용어 사전도 프로젝트마다.** 팀이 다르면 약속도 다르다("주문"이 한쪽에서는 결제 전
  장바구니, 다른 쪽에서는 배송 지시서). 앱 하나에 사전이 하나뿐이면 둘 중 하나는
  사전에 적지 못한 채로 쓰게 된다.

**확인**: 30번까지만 적용한 옛 DB로 시작하는 기존 시험이 0037의 무손실 이관과 기본
프로젝트 참여자 백필을 함께 확인한다. 실제 데이터가 든 개발 DB(커넥션 1·ERD 40·용어 5)
에서도 이관 후 `PRAGMA foreign_key_check`가 비어 있었다. 브라우저에서는 프로젝트를
바꿀 때 ERD·마이그레이션·스키마·사전이 모두 따라오는 것을 확인했다(기본 39/3/7/5 →
새 프로젝트 0/0/2/0).

**남은 것**: 서버나 커넥션을 다른 프로젝트로 **옮기는** 길은 아직 없다(만들 때 정하고
그대로 둔다). 옮기면 그것을 쓰던 사람들이 소리 없이 잃게 되므로, "무엇이 함께 옮겨지고
누가 잃는가"를 보여 준 뒤에 하는 일이어야 한다.

### P26-1 (2026-08-31) — 서버도 프로젝트 안으로

**요구**: 프로젝트마다 서버를 별개로 등록하므로 DB뿐 아니라 서버도 프로젝트별로
관리되어야 한다.

**무엇이 틀렸었나**: P26에서 서버를 프로젝트 밖에 두었다. 한 대의 물리 서버가 여러
팀의 DB를 담는 경우를 생각했기 때문이다. 그러나 실제 쓰임은 다르다 — 접속 정보와
자격증명이 서버에 붙어 있어서, 같은 호스트라도 팀이 다르면 계정이 다르고 그래서
등록도 따로 한다. 그 결과 프로젝트를 바꿔도 서버 목록은 그대로여서, DB 커넥션
화면에는 남의 팀 서버가 호스트 이름까지 그대로 떠 있었다.

**결정**

- 계층은 셋이 되었다: **프로젝트 → 서버 → DB.**
- **DB의 프로젝트는 그 서버의 프로젝트다.** 저장 계층이 쓸 때마다 서버 쪽 값을 넣고,
  다른 프로젝트를 적어 넣으면 ErrProjectMismatch로 막는다. 조용히 고치면 사람이 고른
  것과 저장된 것이 달라지고, 그 사실은 목록에서 사라진 형태로만 드러난다. 커넥션에
  컬럼을 남겨 두는 것은 판정과 목록이 조인 없이 읽기 위해서일 뿐이다.
- 서버 이름의 유일성도 프로젝트 안으로 좁혔다(표 재생성, 0038).
- 서버 병합은 같은 프로젝트 안에서만 된다. 옮겨진 DB는 대상 서버의 프로젝트로 딸려
  가는데, 그러면 원래 프로젝트의 사람들이 그 DB를 소리 없이 잃는다.
- 프로젝트 삭제 조건에 서버를 더했다. 서버에는 접속 정보와 자격증명이 들어 있어서,
  프로젝트만 지우고 남기면 갈 곳 없는 비밀이 된다.
- 0037이 만들지 않았던 경우(서버만 있고 DB는 없는 앱)를 0038이 받는다. 그런 앱에서
  서버를 갈 곳 없이 남기면 아무도 볼 수 없는 서버가 된다.

### P26-2 (2026-08-31) — 모니터링도 프로젝트 안, 수집은 한 번

**요구**: 모니터링도 프로젝트에 포함된 서버+DB만 보여야 한다. 다만 여러 프로젝트에
공통으로 포함된 DB를 여러 개의 커넥션 풀로 나눌 필요는 없다 — 내부적으로 커넥션을
공통으로 관리하되 프로젝트 선택에 따라 포함된 자원만 표시되어야 한다.

**표시 쪽**: 개요·이벤트는 이미 accessibleConnectionIDs를 지나므로 화면이 ?project= 를
붙이는 것만 남아 있었다(대시보드·모니터링·이벤트). 룰 목록은 좁혀지지 않고 있었다 —
특정 DB를 겨냥한 룰은 그 DB가 보이는 사람에게만 보이게 했다. 룰 이름과 임계값에는 그
DB의 사정이 담기고("결제-운영 90% 초과"), 대상이 안 보이는데 룰만 보이면 고칠 수도
없는 줄이 목록에 남는다. 대상이 없는 룰(전체 적용)과 컴퓨터 자신의 이벤트는 그대로 둔다.

**내부 쪽**: 이 앱에는 애초에 오래 사는 커넥션 풀이 없다. 모든 조작이 sql.Open →
사용 → Close 이므로 "프로젝트마다 풀이 갈라지는" 문제는 존재하지 않았다. 실제로
갈라져 있던 것은 **폴러**다. 커넥션 행마다 30초에 한 번 물어보므로, 같은 DB를 두
프로젝트가 각자 등록하면 부하가 두 배가 된다.

그래서 pollAll이 같은 대상을 가리키는 커넥션을 한 묶음으로 묶는다. 열쇠는
(종류·호스트·포트·DB·계정·노드)다. **계정을 넣은 이유**: 같은 서버라도 계정에 따라
보이는 지표가 다르고(권한에 따라 일부 뷰가 막힌다), 한쪽 결과를 다른 쪽에 나눠 주면
자기 계정으로는 볼 수 없는 값을 보게 된다. 수집(네트워크)은 한 번, 저장·룰 평가·
드리프트 판단은 커넥션마다 따로 한다 — 각 프로젝트가 자기 이력과 자기 룰을 갖는다.

결과를 나눠 줄 때는 metric.Set을 **복사**한다. 그대로 주면 첫 커넥션이 누적 카운터를
변화율로 바꾸며 갈아 끼운 값을 다음 커넥션이 다시 변환한다.

**놓칠 뻔한 것**: ListServers의 서명만 바꾸고 WHERE 절을 넣지 않아, 새 프로젝트를
열었는데 남의 팀 서버가 그대로 보였다. 브라우저 확인에서 잡았고 저장 계층 시험을
새로 넣었다(빼면 실패하는 것까지 확인). 목록에서 새는 것은 화면을 열어 보기 전까지
아무도 모른다 — nil(제한 없음)과 빈 슬라이스(하나도 없음)를 함께 시험한 이유다.

### P26-3 (2026-08-31) — 여러 사용자를 같은 권한으로 한 번에

**요구**: 사용자를 생성할 때 여러 사용자를 같은 권한으로 한 번에 추가할 수 있게 한다.

**결정**

- **권한을 이 창에서 새로 정하지 않는다.** 역할만 받고, 나머지는 "이 사람과 같게"
  (권한 원본)로 받는다. 접근 범위·등급·데이터 능력·서버별 예외를 이 창에 다시 그리면
  권한을 정하는 곳이 두 곳이 되고, 두 곳이 어긋나면 어느 쪽이 참인지 화면이 답하지
  못한다. 이 저장소가 사용자 창에서 권한을 빼 둔 이유가 그것이고(users.js의 주석),
  같은 이유가 여기에도 적용된다.
- **참여 프로젝트만 예외로 함께 받는다.** 그것이 나머지 모두보다 앞선 관문이라, 비워
  두면 계정을 만들어 놓고 아무것도 못 보는 상태가 된다.
- **슈퍼 어드민은 권한 원본이 될 수 없다.** 그 권한은 역할에서 나오므로 정책에 적혀
  있는 것이 없다. 복사해 놓고 "같은 권한"이라 하면 아무 권한도 없는 계정이 조용히
  생긴다. 원본을 **계정 생성보다 먼저** 읽는 이유도 같다 — 나중에 거절하면 권한 없는
  계정만 남는다.
- **임시 비밀번호는 계정마다 다르다.** 하나를 나눠 쓰면 그것이 새는 순간 전부 열린다.
  대신 아이디·비밀번호 짝을 한 덩어리로 복사할 수 있게 두었다 — 다섯 번 복사해 다섯 번
  전달하는 과정에서 짝이 어긋나는 것이 실제로 일어나는 사고다.
- 이미 있는 아이디는 건너뛰고 계속 간다(용어 사전 여러 줄 올리기·서버 DB 일괄 등록과
  같은 규칙). 목록의 절반이 이미 있는 것이 보통이고, 거기서 끊으면 사람이 그 줄을
  지우고 다시 붙여넣는 일을 반복하게 된다.
- 한 번에 200명까지. 상한이 없으면 붙여넣기 실수 한 번이 계정 수천 개가 된다.

**확인**: 시험으로 묶은 것 — 정책이 모두에게 같게 들어가는지, 임시 비밀번호가 서로
다른지, 이름·이메일을 쉼표와 탭 양쪽에서 읽는지, 두 번 올리면 건너뛰는지, 슈퍼 어드민
원본을 거절하면서 계정도 남기지 않는지, 어드민은 부를 수 없는지. 브라우저에서도 창을
열어 두 명을 만들고 참여 프로젝트가 둘 다에게 들어간 것을 확인했다.

### P26-4 (2026-08-31) — 사전은 참여자가 함께 쓴다

**요구**: 멤버들이 용어 사전에 용어를 등록할 수 없다.

**무엇이 틀렸었나**: P35에서 사전 쓰기를 커넥션 관리자로 좁혔다("팀의 약속이라 아무나
바꾸면 약속이 아니게 된다"). 그 문장은 그럴듯하지만 실제 쓰임을 뒤집는다 — 사전에
말을 올리는 사람은 **설계하는 사람**이고, 그때마다 관리자를 찾아야 하면 사전은 쓰이지
않는다. 그러면 사전 밖의 약속이 생기고, 그것이 사전이 있는 것보다 나쁘다(P35 자신이
적어 둔 판단 기준이 그것이다).

**결정**: 독립 ERD 초안에 쓴 것과 같은 규칙을 그대로 쓴다.

- **올리기·고치기·여러 줄 올리기: 참여자 누구나.** 관문은 프로젝트 참여뿐이다.
  실제 DB를 건드리지 않는 일이고, 함께 만드는 것이 사전의 성질이다.
- **지우기: 만든 사람과 커넥션 관리자.** 되돌릴 수 없는 동작과 함께 하는 동작을 같은
  문턱에 두면, 함께 쓰게 열어 준 대가로 사고가 따라온다. 자기가 올린 것을 거두는 길은
  열어 둔다 — 잘못 올린 사람이 치울 수 없으면 그동안 틀린 약속이 사전에 남는다.
- 거절할 때 다음 걸음을 말한다: "남이 올린 용어는 관리자만 지울 수 있습니다. 뜻이
  틀렸다면 고치거나, 관리자에게 알려 주세요."
- 응답의 canManage 를 **canWrite 와 canManage 둘로 나눴다.** 하나로 두면 화면이 그
  차이를 그릴 수 없어서, 참여자에게 지우기 단추까지 보이거나 올리기 단추까지 사라진다.
  지우기 단추는 자기가 올린 줄에만 나온다(userId 를 함께 내려보낸다).

## 8. 전 단계 완료 후 남은 것

기능 범위는 P0~P19로 닫혔고, 그 뒤의 P20·P21은 사용 피드백과 운영에서 나온 요청이다.

### 사용 피드백 (2026-08-16 기준)

P19 ~ P19-7로 **모두 반영했다**(로그 메뉴명, 데이터 화면 재작업, SQL 콘솔, 매크로,
ERD 설계 12건, Git 계정 개인화, 모달 배경 클릭 방지, ERD 협업·AI, 되돌리기,
어시스턴트 팝업화, 메뉴얼).

이 밖에 이후 작업이 필요한 지점은 [limitations.md](limitations.md)에 모아두었으며,
그중 설계 결정이 필요한 것은 다음 것들이다.

- **수평 확장**: 세션 저장소와 ERD 허브를 프로세스 밖으로 빼는 결정. 단일 인스턴스로 충분하지
  않다는 근거(동시 편집자 수, 가용성 요구)가 생긴 뒤에 판단하는 것이 맞다.
- **데이터 마스킹**: P11에서 데이터 열람에 별도 권한 축을 만들었지만, 열람을 허용한 뒤의
  **컬럼 단위 가리기**(주민번호·카드번호를 부분 표시)는 넣지 않았다. 어떤 컬럼이 민감한지 판단하는
  규칙(이름 패턴? 태그? 수동 지정?)을 정하는 것이 기능 자체보다 큰 결정이라 근거가 모일 때까지 미뤘다.
  지금은 "볼 수 있는 사람은 원본을 본다"이고, 그 사실이 감사 로그에 남는다.

- ~~**백업 스케줄링**~~ → P14에서 해결. 매크로에 백업 노드가 있고 매크로에 스케줄이 붙었으므로,
  "매일 새벽 3시에 백업" 트리거를 만들면 그대로 정기 백업이 된다.

- ~~**매크로 스케줄링**~~ → P14에서 해결. 답은 **소유자(만든 사람)의 권한**이며, 그 사람의 권한이
  회수되면 자동 실행도 멈춘다(위 P14 기록 참고). "조직마다 답이 다르다"는 것은 사실이지만,
  다른 답을 고르면 앱 전체의 권한 규칙과 어긋난다는 것이 결정의 근거가 되었다.

  남은 것은 **트리거 실패 알림**이다. 지금은 트리거 행과 실행 기록에 남을 뿐이라 아무도 보지 않으면
  모른다(연속 10회 실패하면 스스로 꺼지는 것이 유일한 안전장치다). 이메일이나 웹훅으로 알리려면
  "무엇을 어디로 보낼 것인가"를 정해야 하는데, 그것은 모니터링 이벤트 알림과 같은 문제이므로
  둘을 함께 설계하는 편이 맞다.
