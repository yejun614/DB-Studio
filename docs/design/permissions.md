## 권한 판정

커넥션 권한이 필요한 모든 지점은 `auth.Authorizer.Can(ctx, user, connID, need)`(등급) 또는
`CanCap(...)`(데이터 능력) 한 곳을 통과한다. HTTP 핸들러, WebSocket 허브, AI 툴 실행기,
매크로 엔진이 같은 함수를 쓰므로 우회 경로가 생기지 않는다.

판정 순서: 비활성 계정 → 슈퍼 어드민(항상 migrate + 모든 능력) → 접근 범위(all/allowlist/denylist) →
커넥션별 오버라이드 또는 기본값 → 등급이 `none`이고 능력도 없으면 거부.

## 데이터 권한은 등급의 연장이 아니라 다른 축이다

기존 등급(`none < monitor < erd < migrate`)은 **설계·운영 작업**의 깊이를 나타내는 한 줄짜리
사다리다. 그 사다리에 "데이터 조회"를 끼워 넣을 자리는 없다.

- 스키마를 읽는 것과 그 안의 값을 읽는 것은 위험의 종류가 다르다. **개인정보는 구조가 아니라 값에 있다.**
- "마이그레이션은 할 수 있지만 고객 데이터는 못 본다"와 그 반대가 모두 현실적인 요구다.
  한 줄 사다리로는 둘 중 하나만 표현된다.

그래서 데이터 능력(`data.read` / `data.write` / `sql.run`)은 사다리가 아니라 **독립적인 깃발**이고,
등급과 마찬가지로 커넥션 단위로 부여한다(개발 DB는 마음대로 고쳐도 되지만 운영 DB는 조회만 되어야 하는
것이 보통이다). `TestResolveKeepsLevelAndCapsIndependent`가 이 독립성을 고정한다.

예외는 하나다. **`data.write`에는 `data.read`가 함께 필요하다.** 어떤 행을 고칠지 고르려면 그 행이
보여야 하므로 화면에서 실행 불가능한 상태이고, 그런 설정은 언제나 실수다. 서버가 조용히 `read`를
끼워 넣지 않고 거부하는 이유는, 저장한 것과 다른 값이 남으면 관리자가 무엇을 준 것인지 알 수 없기 때문이다.

반대로 매크로 사용·셸 실행은 커넥션에 매이지 않으므로 **전역 권한**(`users.perms`)이다.
매크로는 여러 커넥션에 걸쳐 동작하고 셸은 애초에 DB와 무관하니, 커넥션별로 부여하면
"어느 커넥션의 권한으로 셸을 실행하는가"라는 답할 수 없는 질문이 생긴다.

저장 위치는 이렇게 다르지만 **부여하는 곳은 권한 설정 화면 한 곳**이다(`PUT /users/:id/access`가
정책과 전역 권한을 함께 받는다). 권한을 사용자 수정 창과 권한 화면에 나눠 두면 회수할 때 두 곳을
모두 확인해야 하고, 한 곳만 보고 "회수했다"고 판단하는 순간이 사고가 된다.

## 권한은 서버로 주고 DB로 뺀다

DB 열 개짜리 서버를 등록하면 체크박스를 열 번 눌러야 하고, DB를 추가할 때마다 모든 사용자의 권한을
다시 챙겨야 한다. 그 부담은 결국 "그냥 모든 DB 접근 가능으로 두자"로 이어진다 — 권한 모델이 있으나
마나 해진다. 그래서 서버 단위 일괄 부여를 얹었다.

판정 순서는 **좁은 쪽이 이긴다**: DB 오버라이드 > 서버 오버라이드 > 기본값. 반대로 두면 예외를 적을
수 없다. 접근 범위(allowlist/denylist)에서는 서버 항목이 그 아래 DB 전부를 뜻하며, 차단은 넓게
걸린다(어느 한쪽이라도 목록에 있으면 막힌다).

한 가지 규칙을 더 두었다. **DB 하나만 등급을 "없음"으로 내리면 서버에서 물려받은 데이터 능력도 함께
지운다.** 그러지 않으면 그 DB는 여전히 조회 가능한 채로 남는데 권한 화면에는 "없음"으로 보인다 —
화면이 거짓말을 하게 된다. 다만 그 DB에 능력을 따로 지정했다면 의도한 것이므로 남긴다.
(이 구멍은 테스트를 쓰다가 발견했다.)

## API 토큰은 세션과 다른 것이다

세션은 브라우저의 것이고 12시간 뒤 사라진다. MCP 클라이언트는 브라우저가 아니고 쿠키를 쓰지
않으며 몇 달 동안 같은 자격증명으로 붙는다. 세션 TTL을 늘려 그 용도를 겸하게 하면
브라우저 세션까지 함께 길어진다.

- **해시만 저장한다**(세션과 같은 규칙). 원문은 발급 순간 한 번만 보여주고 어디에도 남기지
  않는다 — 되찾을 수 있는 토큰은 DB가 유출되면 함께 유출된다.
- **자기 토큰만 만들고 지운다.** 슈퍼 어드민도 남의 토큰을 발급할 수 없다. 그것은 곧 남의
  권한으로 행동할 수단을 주는 것이고, 이 앱에는 그런 개념이 없다. 대신 사용자를 비활성화하면
  그 토큰도 함께 죽는다.
- **폐기는 행을 지우지 않는다.** "이 토큰이 언제까지 살아 있었는가"가 사고 조사에 필요하다.
- 비밀번호 변경이 강제된 사용자의 토큰은 통하지 않는다. 화면에서 막아 둔 사람이 토큰으로는
  통과한다면 그 게이트는 없는 것과 같다.
- 마지막 사용 시각과 IP를 기록한다(5분 간격). 쓰지 않는 토큰을 정리할 때, 그리고 유출을
  의심할 때 첫 단서가 된다.

## 접속 IP는 신뢰할 수 있는 출처에서만 받는다

로그인 시각과 그때의 IP를 사용자 행에 남긴다. 세션 테이블에도 IP가 있지만 세션은 만료되면
사라지므로, "마지막으로 어디서 접속했는가"는 따로 보관해야 한다. 감사 로그에는 모든 로그인이
남고 사용자 행에는 최신 하나만 남는다 — 목록 화면에서 한눈에 보려면 후자가 필요하다.

IP의 출처가 문제다. 기본값에서는 **`X-Forwarded-For`를 무시하고** TCP 원격 주소를 쓴다.
헤더를 무조건 믿으면 앱에 직접 닿을 수 있는 누구나 자기 IP를 위조해 로그인 기록과 감사 로그를
오염시킬 수 있다. 리버스 프록시 뒤에 둘 때만 `-trust-proxy`를 켜고, 그때도 **`-trusted-proxies`에
있는 상대가 보낸 헤더만** 신뢰한다(기본값은 루프백 + 사설망 — 프록시는 거의 항상 거기에 있다).

프록시 체인(`X-Forwarded-For: client, proxy1`)에서는 맨 앞의 클라이언트 IP만 취한다.
검증을 켜지 않으면 헤더 문자열이 그대로 IP 칸에 저장되어 기록이 쓸모없어진다.

## WebSocket의 CSRF 방어는 Origin 검사다

브라우저의 WebSocket API는 커스텀 헤더를 붙일 수 없어 REST에서 쓰는 `X-Requested-With`
검사를 적용할 수 없다. 대신 핸드셰이크에 반드시 실리는 `Origin`을 `Host`와 비교한다.
`Origin`이 아예 없으면 브라우저가 아닌 클라이언트이며, 쿠키 자동 전송이라는 CSRF의 전제가
성립하지 않으므로 허용한다(CLI·테스트 도구).

## Git 토큰 보호

토큰은 DB 비밀번호와 같은 방식(AES-256-GCM)으로 봉인해 저장하고, 구조체 필드에
`json:"-"`를 달아 API 응답에 실릴 수 없게 했다. 화면에는 "설정됨" 여부만 표시한다.
조회 함수가 `withToken` 인자를 요구하므로 목록·표시 경로에서 실수로 복호화할 수 없다.

HTTP 클라이언트는 **리다이렉트를 따르지 않는다** — `Authorization` 헤더가 다른 호스트로
전달되면 자격증명 유출이며, Git 서비스의 정상 API 경로는 리다이렉트를 요구하지 않는다.

self-hosted 주소는 https를 요구하되 **사설망/루프백 주소에만 http를 허용한다**. 사내망
인스턴스에 TLS가 없는 경우는 현실에 있으므로, 그 둘을 구분하면 안전한 기본값과 실용성을
함께 얻는다. 다만 이것이 SSRF를 완전히 막지는 못한다(DNS는 나중에 바뀔 수 있다).
연동 설정은 어드민만 할 수 있고 그들은 이미 DB 자격증명을 다루므로, **이 지점의 신뢰 경계는
"어드민을 신뢰한다"** 이다.
