## AI 어시스턴트는 권한 위에 있지 않다

어시스턴트에 툴을 주는 순간 "누구의 권한으로 실행되는가"가 보안 경계가 된다. 여기서는
**대화 중인 사용자의 권한**이다. 툴이 커넥션에 접근할 때마다 `authz.Can`을 통과하므로,
같은 질문에 사용자마다 다른 답이 나오는 것이 정상이다. 모델이 접근 권한 없는 커넥션
이름을 지정해도 거부되고 그 사실이 감사 로그에 남는다.

**쓰기 툴은 실행하지 않고 제안(pending action)만 만든다.** 실행은 사용자가 승인 버튼을
누른 뒤 별도 요청에서 일어나고, 그 경로는 화면에서 직접 실행할 때와 **같은 함수**
(`migrate.Runner.Apply` 등)를 호출한다. 그래서 검토자 승인 수·사전 검사·운영 DB 확인 문구가
그대로 적용된다 — AI 경로에만 있는 우회로는 없다. 승인은 상태를 먼저 선점한 뒤 실행하므로
두 요청이 동시에 승인해도 한 번만 실행된다.

대화 세션은 **소유자만** 열람할 수 있다. 대화에는 그 사람의 권한으로 조회한 결과가 담기므로,
세션을 공유하면 권한 모델에 구멍이 난다. 실패한 툴 호출도 화면에 남긴다 — 무엇이 시도되고
왜 막혔는지 보이지 않으면 사용자는 모델이 왜 "할 수 없다"고 답하는지 알 수 없다.

프로바이더 어댑터는 두 개(Anthropic 네이티브 / OpenAI 호환)로 유지한다. OpenAI 호환 쪽은
base URL을 사용자가 지정할 수 있어 로컬 LLM과 Google Gemini까지 하나로 덮는다. 채팅은
`EventSource`가 아니라 POST + SSE다: GET만 지원하는 `EventSource`를 쓰면 질문이 URL에 들어가
길이 제한에 걸리고 서버 로그에 대화 내용이 남는다.

## 모델은 관리자가 범위를 정하고 사용자가 그 안에서 고른다

키를 등록하는 사람과 쓰는 사람이 다르고, 모델마다 비용이 열 배씩 차이 난다. 그래서 두 층으로
나눴다: **관리자는 프로바이더마다 허용 모델 목록을 정하고, 사용자는 대화마다 그 안에서 고른다.**

- **빈 목록은 "제한 없음"이다.** 기본값이 "아무것도 못 쓴다"가 되면 이미 돌고 있는 설치가
  업데이트만으로 멈춘다. 제한은 관리자가 명시적으로 고른 결과여야 한다.
- **기본 모델은 반드시 목록 안에 있어야 한다.** 밖에 있으면 아무도 고르지 않은 모델이 모든
  새 대화에서 쓰이고, 그것은 목록을 정한 의미를 없앤다. 목록만 고르고 기본을 비워 두면
  첫 항목이 기본이 된다.
- **판정은 한 함수(`modelAllowed`)를 지난다.** 저장할 때, 세션이 모델을 고를 때, 실제로 호출하기
  직전에 모두 같은 판정을 쓴다. 여러 벌이면 화면에서 고를 수 없는 모델이 API로는 통한다.
- **목록에서 빠진 모델을 쓰던 대화는 조용히 바뀌지 않고 멈춘다.** 다른 모델로 슬쩍 바꿔 부르면
  비용도 답도 달라진 이유를 아무도 모른다. 대신 무엇이 허용되는지 알려주고, 사용자는 대화
  머리에서 모델만 바꾸면 된다.
- 모델 목록은 **저장 전에도 불러올 수 있다**(`POST /ai/providers/models`). 먼저 저장하고 다시
  열어 고르게 하면 그 사이에 기본 모델이 없는 프로바이더가 존재하게 된다. 목록을 주지 않는
  엔드포인트(일부 로컬 LLM)는 오류가 아니라 "직접 입력하라"로 답한다 — 오류로 만들면
  사용자는 키가 틀렸다고 생각한다.

## 툴 호출 조립은 규약을 믿지 않는다

OpenAI 규약은 스트리밍 툴 호출을 이렇게 정한다: 호출은 `index`로 구분되고, `id`와 `name`은
첫 조각에만 오며, `arguments`는 문자열 조각으로 이어 붙는다. 대부분의 서버가 그대로 따른다.

**Gemini의 호환 계층은 `index`를 보내지 않는다.** Go에서 그 필드를 `int`로 받으면 "없음"과
"0번"이 구분되지 않으므로, 한 턴에 툴을 두 개 부른 응답이 전부 0번 슬롯에 겹쳐
`{"connection":"운영"}{"connection":"개발"}` 같은 문자열이 된다. 그래서 `*int`로 받아 존재
여부를 구분하고, 조각을 세 단계로 가른다: **index가 있으면 그것으로, 없으면 `id`로,
둘 다 없으면 직전 슬롯의 이어짐으로.**

어느 방법으로도 갈리지 않는 모양을 위해 마지막 방어선을 하나 더 둔다: **완결된 JSON 값 뒤에
다시 `{`가 오면 그것은 이어지는 인자일 수 없다** — 다음 호출이다. 문법만 보는 규칙이라
어떤 구현에도 통한다. 단, 같은 이름·같은 인자를 통째로 되풀이한 조각은 새 호출로 가르지
않는다(같은 툴이 두 번 실행되고, 변경 툴이면 승인 요청이 두 개 생긴다).

그리고 **툴 인자는 어떤 경로로 나가든 유효한 JSON임을 보장한다**(`NormalizeToolArgs`).
깨진 값을 그냥 흘려보내면 안 되는 이유는 그 값이 저장되기 때문이다 — 대화 이력은 새 질문마다
그대로 다시 실려 나가므로, 한 번 오염되면 그 대화는 지우기 전까지 400을 반복한다.
살릴 수 있으면 첫 번째 완결된 값만 남기고, 아니면 `{}`로 둔다. 후자는 툴이 "필수 인자가 없다"고
답하게 되는데, 그것은 모델이 읽고 고칠 수 있는 오류다.

같은 이유로 이력을 조립할 때 **짝이 맞지 않는 툴 호출과 결과를 걷어낸다.** 프로바이더는
결과 없는 호출도, 호출 없는 결과도 요청 전체를 거부한다("Request contains an invalid
argument"). 예전에 인자가 깨져 assistant 메시지 저장이 실패한 대화에는 결과만 남아 있는데,
읽는 쪽에서 정리하지 않으면 그 대화는 영영 회복되지 않는다.

## 사고 서명은 받은 그대로 돌려준다

Gemini 같은 사고(thinking) 모델은 툴 호출마다 사고 과정의 서명을 붙여 보내고, 다음 요청에
**그것을 그대로 돌려주기를 요구한다.** 돌려주지 않으면 400으로 거부한다:

```
Function call is missing a thought_signature in functionCall parts.
```

증상이 고약하다. 첫 질문은 잘 되고 **툴을 한 번 부른 다음부터** 대화가 죽는다. OpenAI 호환
규약에는 이 칸이 없어서(`tool_calls[].extra_content.google.thought_signature`) 대부분의
클라이언트가 응답을 정규화하며 조용히 버린다.

그래서 이 값을 `ai.ToolCall.Signature`로 들고 다닌다. 우리가 해석할 값이 아니므로 이름도
프로바이더 중립이고, 하는 일은 세 가지뿐이다: 스트림에서 읽고, **대화 이력에 함께 저장하고**,
다음 요청의 같은 자리에 실어 보낸다. 저장이 빠지면 새로고침 뒤에 이어지는 대화만 죽어
원인을 찾기가 더 어려워진다.

서명이 없는 툴 호출에는 `extra_content` 칸 자체를 만들지 않는다 — 이 필드를 모르는 서버
(OpenAI 본체, 로컬 LLM)에 빈 객체를 보내면 거부당할 수 있다.

Google의 호환 엔드포인트는 루트 경로도 다르다(`/v1beta/openai`, 여기에 `/v1`을 덧붙이면 404).
접미사 규칙으로는 가를 수 없어서(Groq은 `/openai/v1`이 루트다) 호스트를 보고 판단한다.

## MCP 서버: 같은 툴, 다른 문

외부 MCP 클라이언트가 쓰는 툴은 앱 안의 AI 어시스턴트가 쓰는 것과 **같은 레지스트리**다
(`internal/api/ai_tools*.go`). 두 벌을 만들면 어느 한쪽에만 있는 툴이 생기고, 더 나쁘게는
권한 검사가 한쪽에만 들어간다. `internal/mcp`는 프로토콜(JSON-RPC 타입과 협상)만 알고
앱을 모른다 — 툴 실행은 `internal/api/mcp_handlers.go`가 기존 경로로 넘긴다.

**전송은 Streamable HTTP만 지원한다.** stdio 모드를 넣지 않은 이유: 그것은 같은 SQLite 파일을
여는 두 번째 프로세스를 뜻하고, 이 앱은 단일 인스턴스를 전제한다. stdio만 받는 클라이언트는
`mcp-remote` 같은 프록시를 쓰면 된다.

**인증은 API 토큰뿐이고 세션 쿠키를 받지 않는다.** 쿠키를 받으면 브라우저가 자동으로 실어
보내므로 다른 사이트가 이 엔드포인트를 부를 수 있게 된다(CSRF). 토큰은 클라이언트가 헤더에
직접 넣어야 하고, 그것이 이 경로의 유일한 문이다. OAuth 2.1을 쓰지 않은 것은 규약이 권하는
방향과 다르지만, 인가 서버·동의 화면·리프레시를 들여올 만한 근거가 아직 없다 —
토큰 하나로 충분한 규모다.

**쓰기는 토큰 범위로 가른다.** 앱 화면에서는 사용자가 승인 버튼을 눌러야 변경 툴이 실행되지만
MCP에는 그 화면이 없다. 대신 두 가지로 그 자리를 채운다.

1. 토큰을 발급할 때 쓰기 허용 여부를 고른다. 읽기 토큰에는 변경 툴이 **목록에도 나오지 않는다** —
   보이는데 부르면 거부되는 툴은 모델이 계속 시도하게 만든다.
2. 툴 주석(`readOnlyHint` / `destructiveHint`)을 붙여 클라이언트가 사람에게 확인을 받게 한다.

그리고 **서버 쪽 게이트는 어느 경로에서든 그대로다.** 능력 판정, 마이그레이션 승인 수,
운영 DB 확인 문구가 전부 살아 있다. 확인 문구가 필요한 동작(운영 DB 복구, 파괴적 마이그레이션
실행)은 MCP로는 아예 실행되지 않는다 — 그 문구는 사람이 직접 타이핑하게 만드는 장치이므로
프로그램 경로에서 통과시키면 존재 이유가 사라진다. 그런 경우 툴은 "웹 화면에서 하라"고 답한다.

**툴 오류는 JSON-RPC 오류가 아니라 `isError`로 돌려준다.** 규약이 그렇게 정한 이유가 있다:
프로토콜 오류로 만들면 클라이언트가 대화를 끊지만, `isError`면 모델이 그 문장을 읽고 스스로
고쳐 다시 부른다. "권한이 없습니다"는 대화를 끊을 일이 아니라 모델이 다른 방법을 찾을 단서다.

## MCP 클라이언트 연결

프로필 화면에서 토큰을 발급한 뒤:

```bash
claude mcp add --transport http dbstudio https://<호스트>/mcp \
  --header "Authorization: Bearer dbs_..."
```

설정 파일을 직접 쓰는 클라이언트:

```json
{
  "mcpServers": {
    "dbstudio": {
      "type": "http",
      "url": "https://<호스트>/mcp",
      "headers": { "Authorization": "Bearer dbs_..." }
    }
  }
}
```

연결되면 `list_connections`부터 부르는 것이 좋다 — 다른 툴에 넘길 커넥션 이름이 거기 있다.

## REST API: 세 번째 문, 같은 관문

MCP가 있는데 REST API를 따로 둔 이유는 하나다: **MCP 클라이언트가 아닌 것들이 있다.**
셸 스크립트, CI 잡, 사내 대시보드, 다른 언어로 쓴 서비스는 JSON-RPC 봉투를 만들고
`initialize`를 협상할 이유가 없다. 그들에게 필요한 것은 `curl` 한 줄이다.

```bash
# 쓸 수 있는 툴과 인자 스키마
curl -H "Authorization: Bearer dbs_..." https://<호스트>/api/tools

# 툴 실행 — 본문이 곧 인자다
curl -X POST https://<호스트>/api/tools/query_data \
  -H "Authorization: Bearer dbs_..." \
  -H "Content-Type: application/json" \
  -d '{"connection":"운영 DB","table":"users","limit":10}'
```

**새로 만든 것은 표현뿐이다.** 인증, 툴 노출 판정, 쓰기 툴 실행 절차는
`internal/api/tokenapi.go`에 한 벌만 있고 MCP와 REST가 그것을 함께 쓴다. 두 문이 각자
판정을 쓰면 언젠가 한쪽에만 검사가 들어가고, 그 사실은 사고가 난 뒤에야 드러난다 —
툴 레지스트리를 어시스턴트와 공유하는 이유와 같은 이야기다. 그래서 여기서 정한 것은
경로·상태 코드·응답 형태 세 가지뿐이다.

**오류는 HTTP 상태 코드로 답한다.** MCP는 툴 오류를 `isError` 텍스트로 돌려준다 —
모델이 그것을 읽고 스스로 고쳐 다시 부르기 때문이다. REST를 부르는 것은 모델이 아니라
프로그램이고, 그것은 `if res.ok`로 분기한다. 200 안에 오류를 숨기면 그 분기가 조용히 틀린다.

| 상태 | 뜻 |
|---|---|
| 401 | 토큰이 없거나 유효하지 않다 (`WWW-Authenticate` 동봉) |
| 403 | 권한이 없다. 읽기 토큰으로 변경 툴을 불렀으면 `read_only_token` |
| 404 | 그런 툴이 없다 (목록 경로를 안내한다) |
| 400 | 본문이 인자 객체가 아니다 |
| 422 | 툴이 거절했다 — 요청 형식은 맞았고 서버도 멀쩡하다 |

`read_only_token`을 `forbidden`과 나눈 이유: 둘을 같은 코드로 답하면 클라이언트는
"토큰을 쓰기 범위로 다시 발급하면 된다"는 사실을 알 수 없다.

**결과는 파싱된 JSON으로 준다.** 툴 결과는 대부분 JSON 문자열이므로 문자열째로 넘기면
클라이언트가 한 번 더 파싱해야 한다. 다만 결과가 상한(24KB)을 넘으면 잘리면서 안내 문장이
붙어 더 이상 JSON이 아니므로, 그때는 `result` 대신 `text`에 원문을 담는다 — 잘린 JSON을
억지로 고쳐 넘기면 클라이언트는 그것이 결과 전부라고 믿는다.

**`/api/v1` 밑에 두지 않았다.** 그 아래는 세션 쿠키 미들웨어가 걸려 있고, 이 경로는
쿠키를 받지 않는다(MCP와 같은 이유 — 쿠키를 받는 순간 다른 사이트가 브라우저를 통해
이 API를 부를 수 있다). 그리고 토큰 미들웨어를 `/api` 전체에 걸지도 않았다: 그러면
그 뒤의 `/api/*` 폴백까지 토큰을 요구하게 되어, 오타 난 프론트엔드 요청이 404 대신
401을 받고 화면은 그것을 세션 만료로 읽어 로그아웃한다.

## Git 연동: 세 서비스의 차이를 인터페이스 뒤로 숨긴다

`vcs.Provider`는 네 가지 동작만 노출한다 — `Verify` / `EnsureBranch` / `PutFiles` / `OpenPR`.
그 뒤에서 각 서비스의 차이를 흡수한다.

**여러 파일을 한 커밋으로 올리는 방법**이 가장 크게 갈린다. GitLab은 커밋 API 하나가 파일
액션 배열을 받고, Bitbucket은 `/src`에 multipart로 보내며(파일 경로가 폼 필드 이름),
GitHub은 Contents API가 파일당 커밋을 만들기 때문에 트리 → 커밋 → ref 갱신을 직접 밟는다
(호출 5회). 그래도 한 커밋으로 묶는 이유는 up.sql과 down.sql이 다른 커밋에 흩어지면
리뷰어가 반쪽만 보고, 되돌릴 때도 커밋 하나로 처리할 수 없기 때문이다.

**브랜치 이름 인코딩은 서비스마다 반대다.** GitLab은 브랜치 이름을 하나의 경로 요소로 보므로
슬래시를 `%2F`로 인코딩해야 하고, GitHub은 `/git/ref/heads/` 뒤 전체를 ref로 해석하므로
슬래시를 그대로 둬야 한다. Bitbucket도 그대로 받는다. 틀리면 404가 나는데 원인을 찾기
어려우므로 `pathEscape`(GitLab)와 `pathKeepSlash`(나머지)로 분리하고 테스트로 고정했다.

**인증 헤더**도 다르다: GitHub `Authorization: Bearer`, GitLab `PRIVATE-TOKEN`,
Bitbucket은 앱 비밀번호면 Basic(사용자 이름 필요)·액세스 토큰이면 Bearer.

## Git 연동은 개인의 것이다

`vcs_integrations`에 담기는 것은 **개인의 Git 계정 토큰**이다. 그것을 여럿이 함께 쓰면
두 가지가 무너진다.

1. **원격 저장소에서 "누가 올렸는가"가 사라진다.** 모든 PR이 토큰 주인의 이름으로 열리므로,
   스키마 변경의 책임자를 Git 쪽 기록만으로는 알 수 없다. 이 앱은 "누구의 권한으로
   실행되는가"를 일관되게 지켜 왔는데(어시스턴트·MCP·매크로·자동 실행) 이 경로만 예외였다.
2. **남의 계정 자격증명을 쥔 사람이 생긴다.** 토큰은 이 앱 밖(저장소·이슈·CI)에서도 쓸 수
   있으므로 그 범위는 DB Studio의 권한 모델을 넘어선다.

그래서 연동에는 주인이 있고, 조회·수정·삭제·연결 확인이 모두 주인으로 좁혀진다.
**슈퍼 어드민도 예외가 아니다** — 남의 Git 계정을 볼 수 있다는 것은 곧 그 사람 명의로
행동할 수 있다는 뜻이고, 그것은 API 토큰을 남이 발급할 수 없게 한 것과 같은 이유다.
없는 것과 남의 것은 똑같이 404로 답한다(존재 여부도 알려줄 이유가 없다).

- **판정은 질의에 넣는다.** "찾은 뒤에 주인을 비교한다"는 호출부마다 반복되고, 한 곳이라도
  빠뜨리면 그것이 곧 통로가 된다. `WHERE ... AND owner_id = ?`로 좁혀 실수할 자리를 없앴다.
- **등록에 별도 권한이 필요 없다.** 등록하는 사람과 쓰는 사람이 언제나 같기 때문이다.
  예전의 "커넥션 관리 권한" 요구는 공유 모델의 잔재였다.
- **계정이 지워지면 함께 지워진다**(`ON DELETE CASCADE`). 주인 없는 토큰이 남을 이유가 없다.
- **이름은 사람마다 따로 센다**(`UNIQUE (owner_id, name)`). 남이 "회사 저장소"를 먼저 썼다고
  내가 다른 이름을 지어야 할 이유는 없다.
- **푸시 이력은 팀의 것이다.** 무엇이 어느 브랜치·PR로 올라갔는지는 마이그레이션에 대한
  사실이고, 커밋과 PR 주소는 이미 팀이 공유하는 산출물이다. 감춰지는 것은 설정과 토큰이다.

기존에 등록된 공유 연동은 이 변경에서 **지웠다**. 공유 연동에는 "이것이 누구의 계정인가"가
기록되어 있지 않다(`created_by`는 등록한 사람일 뿐 토큰 주인이라는 보장이 없다). 잘못된
주인에게 넘기느니 각자 자기 계정으로 다시 등록하는 편이 안전하다.
