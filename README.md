# DB Studio

여러 종류의 데이터베이스(개발/운영)를 등록해 접근 권한을 통제하고, 모니터링·ERD 설계·마이그레이션·
AI 어시스턴트까지 관리하는 웹 앱. **프론트엔드를 포함한 단일 바이너리**로 배포된다.

전체 설계와 단계별 계획은 [`docs/PLAN.md`](docs/PLAN.md) 참고.

## 현재 구현 범위 (P0 ~ P21, 전 단계 완료)

**인증 · 사용자 · 권한**
- 슈퍼 어드민 부트스트랩 (사용자가 없을 때 랜덤 비밀번호 생성 → 터미널 출력)
- 세션 로그인/로그아웃, 첫 로그인 시 비밀번호 변경 강제
- **2단계 인증(TOTP)** — 각 사용자가 자율적으로 켜고, 슈퍼 어드민이 전체 의무화할 수 있다.
  자세한 내용은 아래 [2단계 인증](#2단계-인증-totp) 참고
- 사용자 CRUD, 역할(슈퍼 어드민 / 어드민 / 멤버), 비밀번호 재설정
- 로그인할 때 접속 IP를 기록하고, 사용자 목록에서 **마지막 로그인 시각과 그때의 IP**를 함께 표시
  (프록시 뒤에서는 `-trust-proxy`로 실제 클라이언트 IP를 기록한다)
- 내 프로필 화면: 표시 이름·이메일 수정, **미리 그려둔 라인 아이콘 16개 중에서 프로필 아이콘 선택**
  (직무 8개: DBA·개발자·분석가·운영/SRE·아키텍트·보안·지원·기획 / 사람 8개: 기본·안경·수염·모자·긴 머리·곱슬머리·묶은 머리·웃는 얼굴),
  또는 **이미지 직접 업로드 / 주소(URI)에서 가져오기** (PNG·JPEG·GIF·WebP, 기본 512KB 상한)
- 사용자별 접근 범위(모든 DB / 선택한 DB만 / 특정 DB 제외) × 능력 등급(모니터링 < ERD < 마이그레이션)
- 그와 **독립적인 데이터 능력**(데이터 조회 / 데이터 수정 / SQL 실행)을 부여
- 권한은 **서버 단위로 일괄 부여하고 DB 단위로 예외를 둔다**. 좁은 쪽이 이긴다 —
  "이 서버 전체에 모니터링, 단 billing DB만 접근 불가"가 한 화면에서 표현된다
- 전역 권한(매크로 사용 / 셸 스크립트 실행 / 외부 API 호출)
- 감사 로그 (인증, 사용자, 커넥션, 권한, 스키마 조작, 데이터 조회·수정·SQL 실행, 매크로 실행 및 권한 거부 이력)

**데이터 조회 · 수정 · SQL 실행**
- 테이블 브라우저: 페이지 단위 조회, 컬럼별 조건(=, ≠, 포함, 시작, 대소, NULL 여부), 전체 컬럼 검색,
  컬럼 정렬, 행 추가·수정·삭제 (수정은 **기본키로만** 지정한다)
- **외래키 따라가기**: 행 상세에서 FK 컬럼을 누르면 대상 행이 **오른쪽에 펼쳐지고**,
  거기서 또 따라가면 그 오른쪽으로 이어진다. `user_id = 481`이 누구인지 보려고 표를
  옮겨 다니지 않아도 된다
- MongoDB는 컬렉션 문서 조회·편집(표 + 원본 JSON 양쪽), Redis는 키 접두사 그룹과 값·TTL 조회·편집
- SQL 콘솔: 여러 문장 실행, 읽기 전용 스위치(기본 켜짐), 결과 표, 실행 이력(브라우저에만 저장).
  MongoDB는 `runCommand` JSON, Redis는 명령 한 줄씩
- 편집기에 **줄 번호**가 붙는다. DB가 "3행에서 오류"라고 알려줄 때 그 자리를 바로 찾기 위해서다
- **구문 검사**: 실행하지 않고 문장을 확인한다. 대상 DB의 드라이버로 문장을 *준비만* 해 보므로
  문법뿐 아니라 **테이블·컬럼 이름의 오타까지** 잡히고, 아무것도 실행되지 않는다.
  준비만으로 확인할 수 없는 문장(`USE`, 트랜잭션 제어)은 "오류"가 아니라 "확인 불가"로 구분해 표시한다
- **포맷팅**: 들여쓰기와 예약어 대소문자를 다듬는다. 브라우저에서 처리하며 문자열·주석은 원문 그대로 둔다
- **실행 분석**: 대상 DB의 방식으로 실행 계획을 본다(PostgreSQL `EXPLAIN (ANALYZE, BUFFERS)`,
  MySQL `EXPLAIN ANALYZE`, SQLite `EXPLAIN QUERY PLAN`). ANALYZE는 문장을 실제로 실행하므로
  읽기 전용으로만 돌고, 쓰기 문장은 거부된다 — `EXPLAIN ANALYZE DELETE …`는 행을 지운다

**백업 · 복구**
- **논리 덤프**: 구조(DDL) + 데이터(INSERT)를 담은 텍스트 파일을 만든다. 범위(전체/구조만/데이터만),
  대상 테이블 선택, DROP 문 포함 여부를 고를 수 있고 gzip으로 저장된다
- MongoDB는 줄 단위 확장 JSON, Redis는 줄 단위 명령으로 덤프한다
- **복구**: 저장된 백업을 원래 커넥션 또는 같은 종류의 다른 커넥션에 되돌린다
  (운영 데이터를 개발 DB로 옮겨 재현하는 것이 가장 흔한 용도다)
- 내려받기·내용 미리보기·삭제, 보존 기간이 지난 백업 자동 정리
- 매크로의 "백업 만들기" 노드로 마이그레이션 앞에 백업을 자동으로 남길 수 있다

**스키마 버전 롤백**
- 버전 이력에서 특정 버전을 골라 되돌린다. 현재 구조와의 차이를 보여준 뒤
  **마이그레이션 계획**을 만들고, 기존 흐름(검토 → 승인 → 사전 검사 → 실행)을 그대로 탄다
- 적용이 끝나면 새 버전이 **"롤백" 유형**으로 이력에 등록된다

**구문 강조**
- SQL 콘솔, 매크로의 코드 칸(SQL·Lua·JSON·셸), 마이그레이션 SQL 미리보기, 백업 내용 보기에
  구문 강조가 적용된다. 외부 라이브러리 없이 토크나이저와 규칙 표로 직접 구현했다

**매크로 (노드 에디터 + GopherLua)**
- 노드를 이어 붙여 DB 자동화를 만든다. 내장 노드 19종: 흐름(로그·변수·분기·반복·대기·중단),
  DB(SQL 조회/실행·데이터 조회/수정), DB Studio 조작(스키마 읽기·버전 확정·드리프트 확인·연결 확인·
  백업 만들기·매크로 호출), 스크립트(bash/powershell·Lua)
- **사용자 노드**를 Lua로 작성해 등록할 수 있다. 전역(모든 매크로) 또는 해당 매크로 전용, 버전 관리됨
- 모든 매크로는 **실행 전에 저장**되고 버전이 쌓인다. 롤백은 옛 그래프로 새 버전을 만든다
- 실행 로그는 노드 단위로 남고 SSE로 실시간 스트리밍된다. 결과는 **성공 / 실패 / 취소**로 분류된다
- **매크로는 만든 사람의 것이다.** 기본은 비공개이고, 공유는 셋 중 하나로 넓어진다:
  공개 전환(조회+실행 / 수정 허용 중 선택), 협업자 지정(수정·실행·관리 가능, 삭제는 불가),
  슈퍼어드민(모든 매크로 조회·수정·관리·삭제). 전역 사용자 노드도 같은 규칙을 따르고,
  매크로 전용 노드는 소속 매크로의 권한을 물려받는다
- 접근 권한과는 별개로 **실행 권한은 사람마다 다르며**, 부족하면 화면이 이유를 적고
  실행 버튼을 비활성화한다
- **외부 API 호출**: Lua에서 `http.get/post/request`를 쓰거나 `HTTP 호출` 노드를 놓는다.
  응답이 JSON이면 파싱해서 함께 준다. 별도 권한(`http.call`)이 필요하고, 호출한 주소·상태·소요
  시간이 실행 로그에 남는다. 링크로컬(클라우드 메타데이터) 주소는 항상 막힌다

**매크로 자동 실행 (정기 · 조건)**
- **정기 실행**: 5필드 cron(`분 시 일 월 요일`)과 IANA 시간대. 흔한 주기는 목록에서 고르고,
  저장 전에 **다음 실행 시각 5개를 미리 본다**
- **조건 실행**: 모니터링 이벤트(임계치 위반·접속 실패·스키마 외부 변경·수집 실패)가 **새로 열릴 때**
  실행한다. 종류·심각도·지표·커넥션으로 좁히고, 최소 간격으로 연속 발화를 막는다
- 트리거는 **만든 사람(소유자)의 권한으로** 실행된다. 서비스 계정을 두지 않는 이유는 아래 설계 노트 참고.
  소유자의 권한이 회수되거나 계정이 비활성화되면 그 트리거는 실패하고 **스스로 꺼진다**
- 이벤트로 시작한 실행에는 `trigger` 변수로 어떤 이벤트였는지가 들어온다
- 이전 실행이 끝나지 않았으면 건너뛴다(기본값). 앱이 꺼져 있던 동안 지난 실행은 따라잡지 않는다

**DB 서버와 커넥션**
- **서버 하나에 DB 여러 개.** 접속 정보와 자격증명은 서버가 갖고, 관리 대상 DB가 그 아래에 달린다.
  비밀번호를 한 번 고치면 그 서버의 모든 DB에 반영된다
- 서버를 등록하면 **실제로 접속해 DB 목록을 읽어와** 체크박스로 여러 개를 한 번에 추가한다
  (PostgreSQL·MySQL·MS-SQL·MongoDB·Redis). 시스템 DB와 이미 등록된 DB는 표시만 하고 기본 선택에서 뺀다.
  Oracle(서비스명)과 SQLite(파일 경로)는 대상이 곧 접속 정보라 직접 입력한다
- 같은 서버를 여러 번 등록했다면 **서버 병합**으로 합친다. 겹치는 DB가 있으면 전부 알려주고 아무것도 옮기지 않는다
- 등록/수정/삭제 + 실제 연결 테스트 (MySQL, PostgreSQL, MS-SQL, Oracle, SQLite, MongoDB, Redis)
- DB 종류별 접속 옵션(SSL/TLS, 인증 DB, 레플리카셋 등). MongoDB는 **인증 방식(authMechanism)**을
  목록에서 고르고 방식별 속성(`authMechanismProperties`)을 함께 지정할 수 있다.
  Oracle은 **스키마 소유자(`owner`)**를 지정할 수 있다 — 비우면 접속 계정의 스키마를 보고,
  관리 계정으로 붙어 앱 계정의 테이블을 볼 때 지정한다(구조 화면과 데이터 화면에 함께 적용된다)
- 자격증명 AES-256-GCM 암호화 저장

**스키마**
- 라이브 introspect: 테이블·컬럼·PK·인덱스·FK·체크제약·뷰·enum·주석·통계
- MongoDB는 문서 샘플링으로 필드 구조 추론(필드별 존재 비율 포함), Redis는 키 접두사 그룹 요약
- DB별 타입을 논리 타입으로 정규화 (MySQL `int(11)` = PostgreSQL `integer` = Oracle `NUMBER(10,0)`)
- 두 커넥션 스키마 비교 → 변경 목록(파괴적 변경 표시) + up/down SQL 생성
- 전체 스키마의 CREATE 스크립트 생성, 다른 DB 종류로 타입 변환 출력
- 구조 지문(fingerprint) — 외부 편집 감지의 기반

**모니터링**
- 커넥션별 주기 폴링 → 표준화된 지표 수집 (DB 종류가 달라도 같은 의미면 같은 이름)
- 누적 카운터는 초당 변화율로 변환 (서버 재시작 구간은 건너뜀)
- 임계치 룰 + 지속 시간 조건, 접속 실패 감지, 스키마 외부 변경(드리프트) 감지
- 이벤트 개시/해소/확인, 같은 원인은 발생 횟수로 누적
- 원본 48시간 + 시간 단위 롤업 90일, 범위에 따라 자동 선택
- 상태 그리드, SVG 시계열 차트(의존성 없음), 이벤트 타임라인, 룰 설정 UI

**서버 컴퓨터 감시 (호스트)**
- DB Studio가 도는 컴퓨터 자신의 CPU·메모리·스왑·디스크·네트워크를 같은 주기로 수집
  (외부 라이브러리 없이 리눅스는 `/proc`, 윈도우는 `kernel32`/`iphlpapi`를 직접 읽는다)
- 임계값(경고/심각)과 지속 시간을 화면에서 고친다. 디스크는 지속 시간을 따지지 않는다
- 호스트 재부팅, 앱 시작, **비정상 종료**(강제 종료·전원 차단·크래시),
  시스템 로그의 오류를 이벤트로 남긴다
  (리눅스: syslog 파일 tail / 윈도우: 이벤트 로그 "시스템" 채널)
- 커넥션에 속하지 않는 이벤트이므로 **커넥션 관리 권한**이 있는 계정에게만 보인다
- 읽지 못한 지표는 0으로 채우지 않고 이유를 화면에 남긴다

**알림 (Mattermost · Slack)**
- 이벤트가 생기면 메신저 채널로 보낸다. 들어오는 웹훅(incoming webhook) 하나면 되고,
  봇 토큰·API 권한 관리가 필요 없다
- 두 메신저를 한 설정으로 다룬다: 본문 구조가 같고(Mattermost가 Slack 호환) 다른 것은
  **글자 문법**뿐이다 — Slack의 mrkdwn은 굵게가 별표 하나, 링크가 `<주소|글자>`다.
  그 차이는 함수 두 개(bold·link)에 가둬 두었다
- Slack 앱 웹훅은 채널·보내는 이름 지정을 무시한다(웹훅을 만들 때 고른 채널로 간다).
  화면이 고른 메신저에 맞춰 그 사실을 미리 알려준다
- 웹훅 주소는 **암호화해 저장**하고 화면·감사 로그에는 마스킹해 남긴다
  (그 주소 하나가 곧 그 채널에 글을 쓸 권한이다)
- 무엇을 보낼지 고른다: 최소 심각도, 이벤트 종류, 해소 알림 포함 여부
- 심각도를 **색**으로 먼저 알린다(심각/경고/정보/해소). 값·기준·지속 시간을 함께 싣고,
  앱 주소를 넣어 두면 이벤트 화면 링크를 붙인다
- 전송은 큐를 거쳐 비동기로 나간다(폴러를 막지 않는다). 실패하면 세 번까지 재시도하고,
  마지막 결과는 설정 화면의 **전송 상태**에 남는다
- 링크로컬 주소(클라우드 메타데이터)로는 보내지 않는다. 사설망은 막지 않는다 —
  Mattermost는 사내에 두는 경우가 훨씬 많다

**로그 탐색 · 쿼리 분석**
- 시간순 로그(슬로우 쿼리, 서버 오류, 실행 중 쿼리)와 누적 쿼리 통계를 각각의 탭으로 분리
- MySQL `slow_log`/`performance_schema`, PostgreSQL `pg_stat_statements`/서버 로그,
  MS-SQL `dm_exec_query_stats`/`sp_readerrorlog`, Oracle `v$sql`/알럿 로그,
  MongoDB 프로파일러, Redis `SLOWLOG`
- 소스별 가용성과 활성화 방법을 화면에서 안내 (로그 소스는 DB 설정에 의존한다)
- SQL 정규화 + 다이제스트로 리터럴만 다른 쿼리를 하나로 묶어 Top-N 집계
- 필터: 기간, 소스, 심각도, 최소 소요 시간, 부분 문자열/정규식 검색, 정렬 기준 4종

**구조 (연결된 DB를 ERD로 보기)**
- ERD 설계와 같은 캔버스로 **지금 연결된 DB의 구조**를 본다. 목적이 반대다 —
  저쪽은 만들고 싶은 것을 그리고, 이쪽은 있는 것을 읽는다
- **스키마는 편집할 수 없다.** 바꿀 수 있는 것은 읽는 사람의 정리뿐이다:
  카드 위치, 캔버스 메모, 그룹 묶기
- 그 정리는 **계정별로 저장된다**. 결제를 보는 사람과 배송을 보는 사람은 같은 스키마를 다르게
  늘어놓아야 하고, 한 사람의 정리가 다른 사람의 것을 덮어쓰면 둘 다 못 쓴다
- 최신 상태와 **저장된 스키마 버전** 중에서 시점을 고를 수 있다 ("언제부터 이랬지"에 답하려고
  다른 화면으로 나가지 않는다)
- 스키마에 새 테이블이 생기면 기존 카드와 겹치지 않는 자리에 자동으로 놓는다
- "이 구조로 초안 만들기"로 곧바로 ERD 설계에 넘어간다

**ERD 설계 (동시 편집)**
- SVG 캔버스: 테이블 카드 드래그, 확대/축소·이동, 관계선, 캔버스 메모, 카드 접기
- 편집: 테이블·컬럼·기본키·인덱스·외래키·체크제약·enum (사이드 패널에서 직접)
- **컬럼 타입 고르개**: 대상 DB가 지원하는 모든 타입을 목록에서 고르고, 타입이 요구하는 것만 물어본다
  (길이·자릿수·값 목록·초 정밀도, MySQL의 UNSIGNED, PostgreSQL의 배열). 목록에 없는 타입은
  **직접 입력**으로 그대로 쓸 수 있다. 목록의 출처는 서버(`internal/schema/catalog.go`)다
- **자동 증가(AUTO)**는 타입 창 안에서 켜고 끈다 — 붙일 수 있는 타입을 골랐을 때만 그 칸이
  보인다. 어디까지 되는지는 서버 카탈로그가 타입별로 표시하고(DB마다 다르다: MS-SQL은
  소수 자릿수 0인 DECIMAL에도, SQLite는 INTEGER에만), 정수가 아닌 타입으로 바꾸면 함께 꺼진다.
  생성되는 DDL도 DB마다 다르다(AUTO_INCREMENT / IDENTITY / GENERATED AS IDENTITY /
  INTEGER PRIMARY KEY)
- **도메인(타입 재사용)**: "email = VARCHAR(320)"처럼 이름을 붙여 두고 컬럼에서 골라 쓴다.
  정의를 고치면 그 도메인을 쓰는 컬럼이 함께 바뀌고, 컬럼에서 타입을 직접 고치면 그 컬럼은
  도메인에서 벗어난다. 상단 **도메인** 탭에서 모아 관리한다
- 대상 DB의 현재 스키마를 가져와 초안 시작 (그 시점 스냅샷을 기준으로 기록)
- **대상 DB 없이도** 새 설계도를 그릴 수 있다. DB 문법만 고르면 되고, 결과는 SQL로 내보낸다 —
  설계는 DB를 만들기 전에 시작되는 일이 더 많다.
  이런 초안은 로그인한 사람이면 누구나 함께 편집하고, 삭제·설정 변경은 만든 사람과 어드민만 한다
- **SQL 불러오기**: DDL 스크립트(파일 또는 붙여넣기)를 읽어 초안에 얹는다.
  이름이 같은 테이블은 덮어쓰고(좌표와 색은 유지), `DROP TABLE`은 초안에서도 지우며,
  초안에만 있는 테이블은 그대로 남는다. 적용 전에 **무엇이 바뀌는지 미리 보여준다**
- **SQL 내보내기**: 초안 전체를 만드는 CREATE 스크립트를 복사하거나 파일로 받는다.
  대상 DB 종류를 바꿔 내보낼 수도 있다(타입 변환 경고를 함께 표시)
- 마이그레이션을 만들면 **실행될 SQL을 그 자리에서 보여주고 복사**할 수 있다
- 여러 사용자 동시 편집: 서버 권위 op-log + 필드 단위 LWW, 순번(seq) 기반 정합
- **되돌리기 / 다시실행** (Ctrl+Z, Ctrl+Shift+Z): **내가 한 편집만** 한 칸씩 물러난다.
  남이 그 사이에 같은 대상을 고쳤다면 덮어쓰지 않고 이유를 말하며 멈춘다.
  사람·문서마다 30단계이고, 새로고침해도 30분 동안 남는다.
  AI가 만든 편집도 같은 방법으로 되돌린다 (SQL 불러오기는 제외)
- 프레즌스: 참여자 목록, 커서 위치, 선택 중인 테이블 표시.
  참여자 아이콘을 누르면 **그 사람의 화면을 따라간다** (캔버스를 직접 끌면 풀린다)
- 문서별 채팅 (영속) — 설계 의도를 남겨 리뷰에 쓴다.
  대화 탭을 보고 있지 않으면 새 메시지가 캔버스 위에 카드로 뜬다
- **문서 안의 AI 대화**: 초안을 고치는 툴 8개(테이블·컬럼·기본키·외래키·인덱스 추가/수정)만
  가진 대화를 문서마다 연다. AI가 만든 변경은 초안에 즉시 반영되고 같은 문서를 연 모두에게
  보인다(실제 DB는 바뀌지 않는다). 지우는 툴은 없다 — 되돌리기가 없기 때문이다.
  이 대화는 나만 보며, 쓸 만한 답만 골라 **전체 대화로 공유**한다
- 연결이 끊기면 자동 재연결하고, 확인받지 못한 편집을 다시 전송 (중복 적용 방지)
- 초안 ↔ 대상 DB diff와 적용 SQL 미리보기, 편집 이력 조회

**스키마 버전 · 마이그레이션**
- 버전 이력: 최초 등록 / 마이그레이션 / 외부 편집 / 롤백을 출처별로 구분해 기록
- 앱 밖에서 바뀐 스키마를 드리프트 이벤트에서 한 번에 "외부 편집" 버전으로 확정
- ERD 초안 → 마이그레이션 계획(up/down SQL, 파괴적 변경 표시, 경고)
- 리뷰 요청 → 승인/반려 → 승인됨 상태만 실행 가능 (상태 전이 규칙을 한 곳에서 강제)
- 실행 전 사전 검사: 계획을 만든 시점의 구조 지문과 현재 DB를 비교해 불일치 시 차단
- 운영 DB: 승인 2명(본인 승인 불가), 커넥션 이름 확인 문구, 백업 훅(`-backup-cmd`)
- 문장 단위 실행 기록 — MySQL·Oracle은 DDL이 트랜잭션으로 되돌아가지 않으므로
  "어디까지 적용됐는가"가 복구의 출발점이다
- 롤백: 저장된 down SQL 실행 + 결과를 새 버전으로 등록

**Git 연동 (GitHub · GitLab · Bitbucket)**

**AI 어시스턴트**
- 프로바이더 등록: Anthropic 네이티브, OpenAI 호환(OpenAI 본체·Google Gemini·로컬 LLM·호환 게이트웨이).

- API 키는 암호화 저장·응답에 미노출, 등록 시 모델 목록 조회로 키 유효성 확인
- **허용 모델 목록**: 키를 넣고 모델 목록을 불러와 쓸 수 있는 모델을 고른다.
  비워 두면 제한 없음, 채우면 그 안에서만 고를 수 있다(기본 모델도 그중 하나여야 한다)
- 사용자는 **대화마다 모델을 고르고 도중에 바꾼다** — 조사는 싼 모델로 시작하고
  판단이 필요한 대목에서 좋은 모델로 옮길 수 있다
- **메뉴에서 누르면 떠 있는 팝업으로 뜬다** — 보고 있던 화면(스키마·데이터·ERD)이
  그대로 남는다. 옮기고 크기를 바꿀 수 있고 그 배치를 기억하며, 좁히면 대화 목록이
  위로 눕는다. 팝업 머리의 버튼으로 전체 화면(`/assistant`)으로 옮겨 간다 —
  긴 조사에는 넓은 화면이 낫고, 주소로 공유할 수도 있어야 한다
- 대화 세션(소유자만 열람) + SSE 스트리밍 채팅, 토큰 사용량 집계
- 답변은 **마크다운으로 렌더링한다**(제목·목록·표·코드 블록·링크). 직접 만든 렌더러이며
  innerHTML을 쓰지 않는다 — 모델이 만든 문자열에는 조회한 DB 값이 섞여 있다
- 대화 머리에서 **이름·모델·대상 DB를 바로 바꾼다.** 대상 DB는 시스템 프롬프트에 실려
  나가므로 모델이 "어느 DB를 볼까요?"라고 되묻지 않는다
- 조회 툴 22종: 커넥션·상태·지표·이벤트·로그·스키마·스키마 비교·ERD·마이그레이션·버전,
  데이터 조회·목록·SQL 조회, 백업 목록, 매크로 목록·실행 기록,
  **서버 목록, 서버의 원격 DB 목록, 자동 실행 트리거 목록**
- 변경 툴 16종(ERD 초안 생성, 마이그레이션 생성·리뷰 요청·실행, 버전 확정, Git 푸시,
  데이터 수정, SQL 실행, 백업 생성·복구, 매크로 실행, 버전 롤백,
  **DB 일괄 등록, 자동 실행 트리거 생성·켜기끄기·삭제**):
  **AI는 실행하지 않고 제안만 만들고**, 사용자가 승인해야 실행된다
- **자격증명을 인자로 받는 툴은 없다.** 서버 등록·비밀번호 변경을 툴로 만들지 않은 이유가 이것이다 —
  인자로 받으면 비밀번호가 대화 기록에 남고 AI 프로바이더로 전송된다. 서버 삭제·병합도
  되돌릴 수 없는 폭이 커서 화면에만 둔다
- 툴은 대화 중인 사용자의 권한으로 실행된다 — 권한이 없는 DB는 어시스턴트도 볼 수 없다
- 승인 후에도 기존 안전장치(검토자 승인 수, 사전 검사, 운영 DB 확인 문구)가 그대로 적용된다
- **ERD 화면 안의 대화는 이 목록을 쓰지 않는다.** 초안에 매인 대화에는 문서를 고치는 툴만
  넘어가며(위 "ERD 설계"), 그쪽은 실제 DB에 닿지 않으므로 승인 단계도 없다

**MCP 서버 (외부 AI 클라이언트 연동)**
- Claude Code·Claude Desktop 같은 MCP 클라이언트가 `POST /mcp`로 붙어 위 툴 38종을 그대로 쓴다
  (앱 안의 어시스턴트와 **같은 툴 레지스트리**를 공유한다)
- 전송은 Streamable HTTP + JSON-RPC 2.0. 프로토콜 판 `2025-06-18`·`2025-03-26`·`2024-11-05` 협상
- 인증은 **API 토큰**(`Authorization: Bearer …`). 토큰은 발급한 사용자의 권한을 그대로 쓴다
- 토큰 범위는 읽기/쓰기 둘 중 하나다. 읽기 토큰에는 변경 툴이 **목록에도 보이지 않는다**
- 토큰은 프로필 화면에서 발급·폐기하며, 원문은 발급 순간 한 번만 표시된다(해시만 저장)

**REST API (스크립트·CI·외부 서비스 연동)**
- MCP 클라이언트가 아닌 것들을 위한 두 번째 문. 같은 토큰, 같은 툴 38종, 같은 권한 판정을
  JSON-RPC 봉투 없이 `curl` 한 줄로 쓴다
- `GET /api/tools` 목록(인자 스키마 포함) · `GET /api/tools/{name}` 스키마 하나 ·
  `POST /api/tools/{name}` 실행(본문이 곧 인자) · `GET /api/me` 토큰 주인과 범위
- 결과는 파싱된 JSON으로 온다. 오류는 상태 코드로 갈린다 —
  401 자격증명 · 403 권한/범위 · 404 없는 툴 · 400 잘못된 본문 · 422 툴이 거절
- 모든 호출이 감사 로그에 남는다(`api.tool.call`, `api.tool.denied`, `api.auth.denied`)

**MongoDB · Redis 전용 탐색**
- MongoDB: 컬렉션별 문서 수·저장 크기·평균 문서 크기, 인덱스 크기와 속성(unique/sparse/TTL/partial),
  **서버 재시작 이후 사용 횟수**(쓰이지 않는 인덱스는 삭제 후보로 별도 표시), 뷰/시계열 구분,
  필드별 존재 비율과 혼합 타입 표시
- Redis: 메모리 사용량·상한·정책·단편화, 지속성 상태(AOF/RDB·마지막 저장), 적중률·축출·만료,
  DB별 키 수와 TTL 설정 비율, 키 접두사 그룹(ID 세그먼트를 `*`로 묶음)의 타입 분포와 TTL 비율,
  메모리를 많이 쓰는 큰 키, 명령별 호출·평균 소요 시간
- 구조와 통계만 보여주며 **문서 내용이나 키 값은 반환하지 않는다** (데이터 접근은 권한 모델에 없다)
- 어시스턴트도 같은 정보를 `explore_nosql` 툴로 조회한다 (권한은 동일하게 적용)

**메뉴얼 (`/manual`)**
- 앱 안에 들어 있는 사용 설명서. 사이드바에서 **새 탭으로** 연다 —
  읽으려고 하던 일을 접어야 하면 결국 읽지 않는다
- 화면별 사용법, 권한 모델, 매크로와 **Lua 레퍼런스**(샌드박스 범위, `db`·`http`·`sh`·
  `json`·`log`·`macro` API, 반환값과 포트)
- 매크로 노드 목록은 **서버에서 받아 그린다** — 손으로 적은 목록은 노드가 늘어난 다음에
  틀린 목록이 된다

**배포**
- 단일 바이너리 · 크로스 컴파일 릴리스 스크립트(체크섬 포함), 버전 스탬핑, `/api/v1/health`에 빌드 정보

## 로그인

- **아이디 저장**: 체크해 두면 다음 로그인 때 아이디가 채워지고 커서가 비밀번호 칸에서
  시작한다. **비밀번호는 저장하지 않는다** — 그 일은 브라우저의 비밀번호 관리자가
  안전하게 하도록 만들어진 물건이고, 앱이 흉내 내면 저장소를 읽을 수 있는 누구에게나
  자격증명을 넘겨주는 셈이 된다. 저장 위치는 이 브라우저(localStorage)이며,
  체크를 끄고 로그인하면 지워진다
- 저장은 **로그인에 성공한 뒤**에 한다. 오타를 기억해 두면 다음에도 그 오타로 시작한다

## 2단계 인증 (TOTP)

비밀번호 하나가 새면 이 앱이 열어 주는 모든 것 — 운영 DB의 데이터, 마이그레이션 실행,
백업 복구 — 이 함께 샌다. 그래서 두 번째 자물쇠를 붙였다. SMS나 이메일이 아니라 TOTP인
이유는 이 앱이 **외부망 없이 도는 곳에도 설치되기 때문**이다. 나가는 통신 없이 동작하는
두 번째 요소는 사실상 이것뿐이다.

### 쓰는 법

- **개인**: 프로필 화면 → `2단계 인증 켜기` → QR을 인증 앱으로 찍고 코드 6자리 입력.
  등록을 마치면 **복구 코드 10개**가 한 번만 표시된다.
  Google Authenticator, Microsoft Authenticator, 1Password, Authy 등 표준 TOTP 앱이면 모두 동작한다.
- **슈퍼 어드민**: 보안 설정 화면 → `모든 사용자에게 의무화`.
  기본값은 **자율**이며, 켜면 미등록 사용자는 로그인 후 등록 화면에서 멈춘다(API 토큰도 함께 막힌다).
  의무화하려면 **본인이 먼저 켜 두어야 한다** — 되돌릴 수 있는 사람이 스스로 잠기는 상태를 막기 위해서다.
- **인증 앱을 잃었을 때**: 로그인 2단계 화면에서 `복구 코드 사용`.
  복구 코드도 없으면 슈퍼 어드민이 사용자 화면에서 초기화해 준다(감사 로그에 남는다).

### 설계

- **1단계에서 세션을 만들지 않는다.** 비밀번호가 맞으면 세션 대신 5분짜리 챌린지를 발급하고
  HttpOnly 쿠키로 내려보낸다. "비밀번호는 통과했다"는 상태를 세션으로 표현하면 세션을 읽는
  모든 코드가 그 예외를 알아야 하고, 하나라도 모르면 그것이 우회로가 된다.
- **공유 비밀은 봉인해서 저장한다**(DB 자격증명과 같은 AES-GCM). 코드 검증에 원문이 필요하므로
  해시할 수는 없지만, 메타 DB만 새어 나가서는 남의 코드를 만들 수 없어야 한다.
- **한 코드는 한 번만 쓰인다.** 마지막으로 성공한 시간 스텝을 기록해 같거나 이른 코드를 거부한다.
- 실패가 누적되면 계정 단위로 5분 잠긴다. 챌린지를 새로 만들어 시도 횟수를 초기화하는 우회도 막힌다.
- 복구 코드는 해시만 저장하고, 소비는 `UPDATE … WHERE used_at IS NULL` 한 문장으로 처리한다
  (조회 후 갱신으로 나누면 같은 코드로 두 세션을 얻을 수 있다).

### 서버 시계가 틀려도 동작한다

TOTP는 서버와 인증 앱이 같은 시각을 본다는 가정 위에 있는데, 이 앱이 놓이는 자리(사내망 서버,
노트북, 컨테이너)의 시계는 자주 틀린다. NTP가 막혀 있거나, VM이 정지·재개되며 몇 분씩 밀리거나,
누군가 시각을 손으로 맞춰 놓는다. 그 상태에서 TOTP를 붙이면 증상은 "인증 앱이 고장 났다"로
나타나고 사용자는 원인을 알 방법이 없다. 그래서 **DB Studio는 자체 시계를 관리한다**
(`internal/clock`).

1. **단조 시계에 고정한다.** 시작할 때 벽시계를 한 번 읽어 기준으로 삼고, 그 뒤로는 경과 시간을
   단조 시계로 잰다. 실행 중에 시스템 시각이 튀어도(NTP 도약, 수동 변경, VM 재개) 내부 시각은
   그만큼 튀지 않는다. `time.Now()`를 그대로 쓰면 그 순간 모든 사용자의 코드가 한꺼번에 틀린다.
2. **인증 앱에게서 배운다.** 시각이 맞는 장치와 대조하는 것 말고는 우리 시계가 틀렸음을 알 방법이
   없고, 사용자의 휴대폰이 바로 그 장치다. 등록할 때는 ±15분을 훑어 몇 칸 어긋났는지를 재고,
   그 값을 그 사용자의 보정값으로 확정한다. 외부 시각 서버에 나가지 않고 시계를 맞추는 셈이다.
3. **전역 보정값을 학습한다.** 관측을 지수 평활로 조금씩 반영해, 다음 사용자는 처음부터 맞은
   자리에서 등록을 시작한다. 한 사람의 틀린 휴대폰이 전체를 끌고 가지 않도록 가중치로 눌린다.
   이 값은 재시작 후에도 이어진다.
4. **이미 등록한 사람은 흔들리지 않는다.** 사용자별 보정값은 전역 보정값이 아니라 움직이지 않는
   기준 시각에 매달려 있다. 남이 로그인했다는 이유로 내 코드가 틀리게 되면 안 된다.
5. **시계가 크게 어긋나면 스스로 재동기화한다.** 로그인 검증은 ±30초만 받아들이지만, 거기서
   실패한 코드를 ±15분 범위로 한 번 더 훑어본다. 거기서 맞으면 **로그인은 거절하되 보정값만
   고치고** "다음 코드를 입력하세요"라고 안내한다. 그 코드로 통과시켜 주면 인증에 쓰이는 창이
   몇십 분으로 넓어져, 어깨너머로 본 코드가 그동안 살아 있게 되기 때문이다.

보안 설정 화면에서 내부 시각·시스템 시각·학습된 보정값·이 브라우저와의 차이를 한 번에 볼 수 있다.
"왜 코드가 안 맞는가"에 답하는 화면이다.

## 빌드 & 실행

CGO가 필요 없으므로 크로스 컴파일이 그대로 동작한다.

```bash
CGO_ENABLED=0 go build -o bin/dbstudio ./cmd/dbstudio
./bin/dbstudio -addr :8080 -data ./data
```

Windows:

```powershell
$env:CGO_ENABLED="0"; go build -o bin/dbstudio.exe ./cmd/dbstudio
.\bin\dbstudio.exe -addr :8080 -data .\data
```

최초 실행 시 슈퍼 어드민 계정과 랜덤 비밀번호가 터미널에 출력된다. 이 값은 다시 표시되지 않는다.

> 참고: Windows 콘솔이 UTF-8이 아니면 한글 출력이 깨질 수 있다. `chcp 65001` 후 실행하거나
> Windows Terminal을 사용하면 정상 표시된다.

### 릴리스 빌드

```bash
scripts/release.sh v1.0.0        # 버전을 생략하면 git describe → dev
```

```powershell
.\scripts\release.ps1 -Version v1.0.0
```

`dist/`에 5개 플랫폼(linux amd64·arm64, darwin amd64·arm64, windows amd64) 바이너리와
`SHA256SUMS`가 만들어진다. `-trimpath -ldflags "-s -w"`로 빌드해 개발 경로가 남지 않고
크기도 줄어든다(약 50~53MB). 버전은 바이너리에 심어지므로 실행 없이도 확인할 수 있다.

빌드 시각을 심기 때문에 같은 소스라도 실행마다 해시가 달라진다. 해시를 고정해야 한다면
`SOURCE_DATE_EPOCH`로 시각을 지정한다(`SOURCE_DATE_EPOCH=1700000000 scripts/release.sh v1.0.0`).

```bash
./dbstudio -version                       # dbstudio v1.0.0 linux/amd64 go1.26.5
curl -s localhost:8080/api/v1/health      # 로그인 없이 빌드 정보 확인 (배포 검증용)
```

### CI와 릴리스 자동화 (GitHub Actions)

`.github/workflows/`에 둘이 있다.

| 워크플로 | 언제 | 하는 일 |
|---|---|---|
| `ci.yml` | main 푸시 · PR | gofmt 확인, `go vet`, `go test ./...`(우분투·윈도우), 5개 플랫폼 크로스 빌드 |
| `release.yml` | `v*` 태그 푸시 | 시험 → `scripts/release.sh` 빌드 → 릴리스 노트 작성 → GitHub 릴리스 생성 |

```bash
git tag v1.0.0 && git push origin v1.0.0
```

- **빌드 명령은 `scripts/release.sh` 하나뿐이다.** 워크플로가 `go build`를 다시 적으면
  ldflags가 두 곳에 생기고, 손으로 만든 빌드와 CI 빌드가 조용히 달라진다.
- 릴리스 빌드는 태그가 가리키는 커밋 시각을 `SOURCE_DATE_EPOCH`로 심는다. 같은 태그를
  다시 빌드하면 바이너리 해시가 같다.
- 하이픈이 있는 태그(`v1.0.0-rc.1`)는 사전 배포로 올라간다.
- **시험이 실패하면 릴리스를 만들지 않는다.** 태그를 되돌리는 것보다 거기서 멈추는 편이 싸다.
- CI가 윈도우에서도 시험을 돌리는 이유: 호스트 감시와 OS 로그 읽기는 플랫폼마다 구현이
  다르다(`internal/hostmon/*_windows.go`). 한쪽에서만 돌리면 다른 쪽 코드는 아무도 실행하지 않는다.
- 크로스 빌드를 따로 두는 이유: OS별로 갈라지는 파일이 있어 리눅스 시험이 통과해도 macOS
  빌드가 깨질 수 있고, 그 사실은 릴리스를 만드는 순간에야 드러난다.
- 통합 시험(실제 DB 접속)은 `-integration` 플래그나 `DBSTUDIO_INTEGRATION`이 있을 때만 도므로
  CI에서는 자동으로 건너뛴다. 돌리려면 `docker/compose.test.yaml`을 먼저 띄워야 한다.

| `-macro-http-max-kb` | `DBSTUDIO_MACRO_HTTP_MAX_KB` | `1024` | 외부 응답 본문의 상한. 넘으면 자르고 `truncated`로 알린다 |

| `-backup-dir` | `DBSTUDIO_BACKUP_DIR` | `<data>/backups` | 논리 덤프 파일을 두는 디렉터리 |
| `-backup-max-mb` | `DBSTUDIO_BACKUP_MAX_MB` | `2048` | 이 크기를 넘는 덤프는 **실패로 끝낸다** (압축 전 기준) |
| `-backup-retention` | `DBSTUDIO_BACKUP_RETENTION` | `720h` (30일) | 이보다 오래된 백업을 자동 삭제. `0`이면 보관 |
| `-avatar-max-kb` | `DBSTUDIO_AVATAR_MAX_KB` | `512` | 프로필 이미지 최대 크기 |
| `-avatar-allow-private-uri` | `DBSTUDIO_AVATAR_ALLOW_PRIVATE_URI` | `false` | 사설망·루프백 주소에서 프로필 이미지 가져오기 허용 |
| — | `DBSTUDIO_MASTER_KEY` | (자동 생성) | base64 32바이트 암호화 키 |

> **`-allow-shell`은 의식적으로 켜는 스위치다.** 이 플래그가 없으면 사용자에게 어떤 권한을 줘도
> 셸 노드는 실행되지 않는다. 권한 설정은 화면에서 몇 번의 클릭으로 바뀌지만, 이 기능이 켜지는
> 순간 앱은 원격 셸이 된다 — 그런 성격의 변경은 프로세스를 띄우는 사람이 정해야 한다.

### 로그 — 서버가 멈췄을 때 먼저 볼 곳

로그는 stderr와 **파일에 동시에** 기록된다. 터미널을 닫거나 서비스로 띄우면 stderr는
사라지므로, 파일이 없으면 "왜 멈췄는지"를 확인할 방법이 없어진다.

| 파일 | 내용 |
|---|---|
| `<data>/dbstudio.log` | 앱 로그. 20MB를 넘으면 `.1`로 밀려나고 새로 시작한다 |
| `<data>/dbstudio.log.1` | 직전 로그 한 개만 보관한다 |
| `<data>/dbstudio.log.crash` | Go 런타임 크래시 리포트. 여기 내용이 있으면 패닉으로 죽은 것이다 |
| `<data>/dbstudio.running` | 실행 중 표식. 1분마다 갱신하고 정상 종료 시 지운다 |

**종료 원인 읽는 법.** 정상 종료는 세 줄을 남긴다.

```
level=INFO msg="종료 신호 수신" signal=interrupt note="터미널을 닫거나 Ctrl+C를 누르면 이 신호가 옵니다"
level=INFO msg="정리 시작" trigger=interrupt timeout=10s
level=INFO msg="정리 완료"
level=INFO msg="프로세스 종료" pid=49420 uptime=3h12m0s
```

| 로그의 마지막 모습 | 의미 |
|---|---|
| `종료 신호 수신` → `프로세스 종료` | 정상 종료. **터미널을 닫거나 Ctrl+C를 눌렀을 때도 이 경로다** |
| `서버가 오류로 종료합니다` + `hint=...` | 시작 실패(포트 충돌, 키 문제, 데이터 디렉터리 권한). hint가 다음 할 일을 알려준다 |
| `프로세스 종료` 줄이 아예 없음 | 강제 종료(`kill -9`, 작업 관리자, 다른 프로세스의 종료 명령, 전원 차단) 또는 런타임 크래시 |
| `.crash` 파일에 스택 | 패닉으로 죽음. 스택의 첫 줄이 원인이다 |
| `패닉을 복구했습니다` | 백그라운드 작업 하나만 중단됐고 서버는 살아 있다 |

**강제 종료는 다음 시작 때 스스로 알려준다.** 종료 기록을 남길 기회조차 없었던 실행은
`dbstudio.running` 표식이 남으므로, 다음 시작이 그것을 읽어 보고한다.

```
level=WARN msg="이전 실행이 종료 기록을 남기지 않았습니다"
  이전실행="pid=58548 version=v1.0.0 addr=:18008 시작=…T02:05:36+09:00 마지막 생존=…T02:24:12+09:00"
  원인="강제 종료로 보입니다 (작업 관리자·kill -9·다른 프로세스의 종료 명령·전원 차단). 크래시 리포트는 비어 있습니다"
```

표식을 1분마다 갱신하기 때문에 **"몇 시까지 살아 있었는지"** 를 말할 수 있다. 이것이 없으면
DB 파일의 수정 시각 같은 간접 증거를 뒤져야 한다. 표식의 주인이 아직 살아 있으면
(같은 데이터 디렉터리를 두 인스턴스가 쓰는 경우) 크래시로 오해하지 않고 그 사실을 알려주며,
살아 있는 쪽의 표식을 건드리지 않는다.

같은 로그 파일에 여러 인스턴스가 쓸 수 있으므로 모든 줄에 `pid`가 있는 시작·종료 줄을
기준으로 구분한다. 포트 충돌로 죽은 인스턴스가 있으면 그 사실이 그대로 남는다.

**요청 로그.** 기본값에서는 문제 있는 요청만 남긴다 — 5xx 응답(`요청 실패`)과
5초를 넘긴 요청(`느린 요청`). 정적 자산과 폴링까지 남기면 정작 필요한 줄을 찾을 수 없다.
전부 보려면 `-log-level debug`로 올린다.

```bash
./dbstudio -log-level debug              # 모든 API 요청 기록
./dbstudio -log-format json              # 수집기(Loki, CloudWatch 등)에 넣을 때
./dbstudio -log-file /var/log/dbstudio.log
./dbstudio -log-file ""                  # 파일 없이 stderr만 (컨테이너에서 유용)
```

### 백업 훅

운영 DB에 마이그레이션을 적용하기 전에 실행할 외부 명령을 지정한다. 실패하면 마이그레이션을
중단한다.

```bash
./bin/dbstudio -backup-cmd "/opt/scripts/backup.sh {kind} {host} {port} {database} {id}"
```

인자에 쓸 수 있는 치환값: `{name}` `{kind}` `{host}` `{port}` `{database}` `{env}` `{id}`.

앱이 DB별 백업을 직접 구현하지 않는 이유는 도구와 정책이 조직마다 다르고(pg_dump, mysqldump,
볼륨 스냅샷) 잘못 만든 백업은 없는 것보다 위험하기 때문이다. 명령은 **실행 플래그로만**
지정할 수 있다 — API로 지정하게 하면 이 앱이 임의 명령 실행 통로가 된다. 셸을 거치지 않고
실행하므로 커넥션 이름 같은 사용자 지정 값이 명령으로 해석되지 않는다. 자격증명은 넘기지
않으며, 백업 도구의 인증은 환경변수나 설정 파일로 준비해야 한다.

### 마스터 암호화 키

DB 접속 비밀번호는 AES-256-GCM으로 암호화되어 저장된다. 키는 `DBSTUDIO_MASTER_KEY`(base64 32바이트)를
쓰거나, 없으면 `<data>/master.key`에 자동 생성된다.

**이 키를 잃으면 저장된 모든 DB 자격증명을 복호화할 수 없다.** 운영 환경에서는 환경변수로 주입하고
시크릿 관리 시스템에 보관할 것.

## 개발

프론트엔드는 번들러나 빌드 스텝이 없다. 네이티브 ES Module과 직접 작성한 CSS를 `go:embed`로 포함한다.

```bash
go run ./cmd/dbstudio -dev          # web/ 을 디스크에서 서빙
go test ./...                       # 단위 테스트 (DB 컨테이너 불필요)
```

단위 테스트는 `store`(시간 형식·이벤트 중복 억제·롤업 멱등성·ERD 스냅샷 재생),
`monitor`(룰 판정·지속 시간 게이트·카운터 변화율), `dblog`(SQL 정규화·다이제스트 안정성),
`erd`(op 패치 의미·식별자 검증·참조 무결성), `erdhub`(동시 편집의 seq 유일성·거부 격리·
재전송 멱등성·프레즌스), `migrate`(상태 전이 규칙·승인 수 규칙),
`vcs`(3사 API의 경로·헤더·본문 형식과 호출 순서)를 다룬다.

`erdhub` 테스트는 WebSocket 없이 허브를 직접 구동하므로 동시성 문제를 브라우저 없이
재현할 수 있다. `vcs` 테스트는 `httptest`로 각 서비스를 흉내내 "내가 이해한 API 계약"을
코드로 고정한다 — 실제 서비스와의 차이는 문서를 다시 읽어 그 테스트를 고치는 방식으로
반영한다.

### 통합 테스트

컨테이너가 떠 있으면 introspect 정확성과 DDL 왕복을 실제 DB에 대해 검증한다.
컨테이너가 없으면 각 케이스는 스킵된다.

```bash
go test ./internal/dbx/ -integration -v
DBSTUDIO_INTEGRATION=1 go test ./...    # 전체 (환경변수로도 켤 수 있다)
```

검증 내용:
- **구조 정확성** — PK/FK/인덱스/체크제약/주석/타입 정규화를 알려진 스키마와 대조
- **읽기 안정성** — 같은 DB를 두 번 읽은 결과의 diff가 빈 집합이어야 한다.
  이게 깨지면 변경이 없는데도 마이그레이션이 생성되어 앱을 신뢰할 수 없다.
- **변경 감지** — 인위적 변경을 넣고 의도한 변경만 정확히 잡히는지
- **DDL 왕복** — 생성한 DDL을 빈 스키마에 실제로 실행하고 다시 읽어 원본과 비교.
  diff가 비어야 생성기가 원본 구조를 재현했다고 말할 수 있다.
- **드리프트 감지** — 드라이버로 직접 DDL을 실행해 앱 외부 변경을 재현하고,
  기준선 저장 → 무변경 무시 → 추가 변경(경고) → 파괴적 변경(심각 승격)을 확인
- **마이그레이션 왕복** — 실제 DB에 적용 → 구조 확인 → 롤백 → 지문이 원본과 일치.
  더불어 프리체크의 드리프트 차단, 승인 게이트, dialect별 실패 동작(트랜잭션 DB는 전부
  되돌아가고 비트랜잭션 DB는 부분 적용이 기록됨)을 검증한다.
- **MongoDB·Redis 특화 조회** — 컬렉션 저장 통계, 인덱스 속성(unique/sparse/TTL)과 크기,
  복합 인덱스의 키 순서·방향, 뷰 구분, 필드 존재 비율, Redis INFO 파싱과 접두사 그룹의
  타입·TTL 집계, 큰 키 정렬

각 테스트는 전용 데이터베이스를 만들어 쓴다. 스키마 지문은 DB 내 모든 테이블을
포함하므로, DB를 공유하면 한 테스트의 테이블 생성이 다른 테스트에게 "외부 변경"으로
보이고, `go test`가 패키지를 병렬 실행하기 때문에 결과가 실행 조합에 따라 달라진다.

| DB | 포트 | 계정 |
|---|---|---|
| MySQL 8.4 | 13306 | `root` / `rootpw123`, db `appdb` |
| PostgreSQL 17 | 15432 | `postgres` / `rootpw123`, db `appdb` (sslmode=disable) |
| MS-SQL 2022 | 11433 | `sa` / `RootPw123!`, db `master` |
| Oracle Free 23 | 11521 | `appuser` / `RootPw123`, service `FREEPDB1` |
| MongoDB 8 | 27018 | `root` / `rootpw123`, db `appdb` (auth_source=admin) |
| Redis 7 | 16379 | 비밀번호 `rootpw123`, db `0` |

```
cmd/dbstudio/        엔트리포인트, 부트스트랩, graceful shutdown
embed.go             web/ 정적 자산 embed (루트에 있어야 web/ 참조 가능)
internal/
  config/            플래그·환경변수 설정
  crypto/            argon2id 비밀번호 해싱, AES-GCM 시크릿 봉인, 랜덤 생성
  store/             메타 SQLite: 마이그레이션 러너 + 리포지토리
                     servers.go = DB 서버(접속 정보·자격증명), connections.go = 그 아래 DB
    migrations/      embed된 스키마 SQL
  model/             엔티티와 열거형 (역할, 접근 모드, 능력 등급, DB 종류)
                     perm.go = 데이터 능력·전역 권한 (등급과 독립적인 두 번째 축)
  auth/              세션 서비스 + RBAC 판정(Authorizer.Can / CanCap)
                     totp.go = 2단계 인증(로그인 2단계·등록·복구 코드·시계 재동기화)
  totp/              RFC 4226/6238 구현과 QR 인코더 (외부 의존성 없음)
  clock/             앱이 스스로 관리하는 시계. 단조 시계에 고정하고 인증 앱에게서 보정값을 배운다
  api/               Fiber 라우팅, 미들웨어, 핸들러
                     ai_tools*.go = 툴 레지스트리(어시스턴트·MCP·REST API가 함께 쓴다),
                     tokenapi.go = 토큰 경로의 공통 관문(인증·툴 노출 판정·실행),
                     mcp_handlers.go / rest_handlers.go = 그 위에 프로토콜만 입힌 두 문
  schema/            스키마 IR(ir.go) + 타입 정규화(types.go) + diff(diff.go) + DDL 생성(ddl.go)
  metric/            지표 타입 전용 (dbx와 monitor의 순환 의존을 끊기 위해 분리)
  dblog/             로그 타입 + SQL 정규화/다이제스트 (같은 이유로 dbx와 분리)
  dbx/               대상 DB 어댑터 (DSN 생성, Ping, introspect_*.go, metrics_*.go, logs_*.go,
                     explore_*.go = Mongo/Redis 특화 조회,
                     data*.go = 값 조회/수정/문장 실행 + 방언 차이(data_dialect.go),
                     listdb.go = 서버의 DB 목록 조회(일괄 등록용))
  macro/             매크로 엔진: 그래프(graph.go), 실행기(engine.go), 내장 노드(nodes.go),
                     Lua 샌드박스와 호스트 API(lua.go), 셸 실행(shell.go), 외부 HTTP(http.go),
                     cron 해석(cron.go), 자동 실행 스케줄러와 권한 판정(trigger.go)
  backup/            논리 덤프 생성(dump*.go)과 복구(restore.go), 작업 관리(backup.go)
  monitor/           폴러(poller.go) + 룰 엔진(rules.go) + 드리프트 감지(drift.go)
  erd/               ERD 문서 모델 + 편집 op 정의/적용/검증 (전송·저장 계층을 모른다)
  erdhub/            문서별 실시간 편집 중개: seq 부여, 브로드캐스트, 프레즌스, 채팅
  migrate/           마이그레이션 사전 검사와 실행 (프리체크·백업 훅·문장별 기록·롤백)
  vcs/               GitHub/GitLab/Bitbucket 공통 인터페이스와 3사 REST 구현
```

### 접속 IP는 신뢰할 수 있는 출처에서만 받는다

로그인 시각과 그때의 IP를 사용자 행에 남긴다. 세션 테이블에도 IP가 있지만 세션은 만료되면
사라지므로, "마지막으로 어디서 접속했는가"는 따로 보관해야 한다. 감사 로그에는 모든 로그인이
남고 사용자 행에는 최신 하나만 남는다 — 목록 화면에서 한눈에 보려면 후자가 필요하다.

IP의 출처가 문제다. 기본값에서는 **`X-Forwarded-For`를 무시하고** TCP 원격 주소를 쓴다.
헤더를 무조건 믿으면 앱에 직접 닿을 수 있는 누구나 자기 IP를 위조해 로그인 기록과 감사 로그를
오염시킬 수 있다. 리버스 프록시 뒤에 둘 때만 `-trust-proxy`를 켜고, 그때도 **`-trusted-proxies`에
있는 상대가 보낸 헤더만** 신뢰한다(기본값은 루프백 + 사설망 — 프록시는 거의 항상 거기에 있다).

프록시 체인(`X-Forwarded-For: client, proxy1`)에서는 맨 앞의 클라이언트 IP만 취한다.
검증을 켜지 않으면 헤더 문자열이 그대로 IP 칸에 저장되어 기록이 쓸모없어진다.

### 로그는 "이유 없이 꺼졌다"를 없애기 위해 있다

프로세스가 사라진 뒤에 남는 것은 파일뿐이다. 그래서 세 가지를 설계에 넣었다.

1. **파일에도 항상 쓴다.** stderr만 쓰면 터미널을 닫는 순간 기록이 사라진다.
   파일을 열지 못해도 서버는 뜬다 — 로그를 못 쓴다고 서비스가 안 되면 그게 더 큰 장애다.
2. **종료 경로는 반드시 한 줄을 남긴다.** 어떤 신호를 받았는지(`signal=interrupt`),
   정리가 끝났는지(`정리 완료`), 얼마나 살아 있었는지(`uptime=`)를 적는다.
   그래서 **줄이 없는 것 자체가 정보가 된다** — 강제 종료나 런타임 크래시라는 뜻이다.
3. **강제 종료는 다음 시작이 보고한다.** 실행 중 표식(`dbstudio.running`)을 두고 1분마다
   갱신하다가 정상 종료 시 지운다. 표식이 남아 있다는 것은 그 프로세스가 종료 처리를 할
   기회조차 얻지 못했다는 뜻이고, 마지막 갱신 시각이 "몇 시까지 살아 있었는가"를 말해 준다.
   로그의 부재를 증거로 바꾸는 장치다.
4. **런타임 크래시는 별도 파일로 받는다.** `debug.SetCrashOutput`으로 패닉 스택을
   `dbstudio.log.crash`에 남긴다. 어떤 recover로도 잡을 수 없는 goroutine 패닉은
   이 파일이 유일한 증거다. 로그 파일과 분리한 이유는 (1) 런타임이 그 파일 핸들을 쥐고 있어
   같은 파일을 로테이션할 수 없고(Windows에서 실패한다) (2) 흔치 않은 결정적 증거가
   평상시 로그에 밀려 사라지면 안 되기 때문이다.

**패닉으로 죽는 경로를 막았다.** Fiber의 recover 미들웨어는 HTTP 핸들러만 감싼다.
그 밖에서 도는 goroutine — 모니터 폴러, WebSocket 읽기/쓰기 펌프, SSE 스트림 라이터
(핸들러가 반환한 뒤에 실행된다) — 에서 패닉이 나면 프로세스 전체가 죽는다.
이들을 `applog.Recover`로 감싸 해당 작업만 중단되고 스택이 로그에 남게 했다.
패닉 미들웨어에도 스택 로깅을 붙였다. 기본 설정은 조용히 500을 돌려주므로
서버는 살아 있는데 무엇이 깨졌는지 아무도 모르는 상태가 된다.

### 파비콘은 그려서 넣는다 (이모지가 아니라)

처음에는 `data:` URI 안에 🗄️ 이모지를 넣어 두었다. 이모지는 OS마다 다른 그림이 나오고,
플랫폼에 따라 흑백 글리프로 떨어지며, 앱의 사이드바 아이콘과도 닮지 않는다.
그래서 브랜드 아이콘과 같은 원통형 DB 형태를 직접 그렸다.

- **선이 아니라 면으로 그린다**: 16px에서 1.8px 선은 뭉개져 형태가 사라진다.
  구분선은 배경색으로 덧그려 "잘라낸" 음영으로 만든다(원통의 원근을 따르는 곡선).
- **SVG를 주 아이콘으로 두고 `.ico`를 폴백으로 둔다**: 링크에서 SVG를 뒤에 선언하면
  지원 브라우저는 SVG를, 나머지는 `.ico`를 고른다. `.ico`에는 16/32/48을 함께 담는다 —
  브라우저는 탭·즐겨찾기·작업 표시줄에서 다른 크기를 쓴다.
- **SVG는 `prefers-color-scheme`으로 반전한다**: 어두운 탭 바에서도 또렷하게 남는다.
- **apple-touch-icon은 직각 모서리**: iOS가 스스로 둥근 마스크를 씌우므로
  여기서 둥글게 만들면 두 번 잘려 모서리에 틈이 생긴다.

**`/favicon.ico`가 HTML을 돌려주던 문제도 함께 고쳤다.** 브라우저는 링크가 없어도
`/favicon.ico`를 자동으로 요청하는데, SPA 폴백이 그 요청에 `index.html`을 200으로
응답하고 있었다. 자산처럼 보이는 경로(`.js` `.css` `.ico` `.png` …)는 파일이 없으면
404로 답한다 — 없는 `.js`에 HTML을 돌려주면 브라우저는 "HTML에서 문법 오류"라고
보고해 원인을 찾기 어려워진다.

### 화면은 shadcn/ui 규약을 따른다

프레임워크가 없으므로 shadcn/ui 컴포넌트를 가져올 수는 없다. 대신 그 **규약**을 CSS로 옮겼다.

- **색은 HSL 3요소로 저장한다**: `--h-primary: 240 5.9% 10%` 로 두고 `hsl(var(--h-primary) / 0.1)`
  처럼 조합한다. hover·선택·비활성처럼 배경 위에 얹는 상태를 색을 새로 정의하지 않고 만들 수 있다.
- **컨트롤은 무채색, 색은 의미가 있을 때만**: 버튼·입력·탭은 회색 계열이고, 색은 파괴적 동작·
  상태(정상/경고/오류)·차트에만 쓴다. 관리 도구는 한 화면에 요소가 많아 색을 장식으로 쓰면
  정작 위험한 동작이 눈에 띄지 않는다.
- **변형을 이름으로 고정한다**: 기본 버튼은 테두리(outline), 주 동작은 검은 solid,
  파괴적 동작은 대화상자에서 solid·목록에서 ghost. 목록에서 카드마다 solid 버튼이 반복되면
  "지금 눌러야 하는 것"이 사라진다.

테마는 `<html data-theme>` 하나로 결정된다. 기본값은 OS 설정을 따르고 사용자가 고른 값이
그것을 덮는다(시스템 → 라이트 → 다크 순환, 사이드바 하단·로그인 화면 우상단).
첫 페인트가 반대 팔레트로 깜빡이지 않도록 `js/theme-init.js`를 `<head>`에서 동기로 읽어
스타일시트 적용 전에 속성을 정한다. 인라인 스크립트가 아닌 이유는 CSP가 `script-src 'self'`이기
때문이다 — `unsafe-inline`을 열면 XSS 방어가 무력해지고, 해시를 쓰면 파일을 고칠 때마다
서버 헤더를 함께 고쳐야 한다. 모듈이 아닌 이유는 `type="module"`이 defer와 같아서
문서 파싱 후에 실행되고, 그때는 이미 한 번 그려져 있기 때문이다.

### 값이 정해진 접속 옵션은 고르게 한다

접속 옵션은 대부분 자유 입력이다(`search_path`, 추가 파라미터처럼 값이 열려 있다).
그런데 MongoDB의 인증 방식처럼 **드라이버가 아는 값이 정해져 있는** 옵션은 다르다.
자유 입력으로 두면 오타가 접속 시점에야 드러나고, 그때의 메시지
("auth mechanism ... not supported")는 어디를 고쳐야 하는지 알려주지 않는다.

그래서 `OptionHint`에 `Choices`를 두고, 값이 있으면 화면이 선택 목록을 그린다.
목록(`dbx.MongoAuthMechanisms`)과 저장 시 검증이 같은 배열을 본다 — 화면에서 고른 값을
저장이 거부하는 상황은 테스트로 막아 두었다(`TestMongoAuthMechanismHintMatchesValidation`).

- 첫 항목은 항상 빈 값("기본값")이다. MongoDB는 고르지 않으면 서버가 정한 방식(대개
  SCRAM-SHA-256)으로 협상하며, 빈 값을 `authMechanism=`으로 내보내면 드라이버가 거부하므로
  쿼리에서 아예 뺀다.
- 저장된 값이 목록에 없으면(서버 쪽 목록이 바뀐 경우) 그 값을 "(알 수 없음)" 항목으로 덧붙여
  보여준다. 화면을 열었다는 이유만으로 기존 설정이 조용히 지워지면 안 된다.
- 대소문자만 다른 입력(`scram-sha-256`)은 고쳐서 받는다. 옮겨 적는 값이고, 대문자 여부는
  사용자가 판단할 수 있는 종류의 문제가 아니다.
- GSSAPI·MONGODB-AWS·OIDC는 속성이 있어야 실제로 쓸 수 있으므로 `authMechanismProperties`
  입력을 함께 둔다.

전체 URI를 입력한 경우에는 이 옵션들이 붙지 않는다 — 화면의 도움말이 그렇게 약속하고 있고,
사용자가 적은 URI를 도구가 고쳐 쓰면 결과를 예측할 수 없다.

### 프로필 아이콘은 고르는 것이 기본이고, 이미지는 DB에 담는다

기본은 **미리 그려둔 라인 아이콘 중 하나를 고르는 것이다.** DB에 저장되는 것은 `role-dba` 같은
키 문자열 하나뿐이다.

여기에 더해 **이미지 업로드와 주소(URI) 가져오기**를 받는다. 처음에는 받지 않았고, 그때의 이유
("저장 위치·용량 제한·디코딩·삭제 정책이 전부 딸려 온다")는 지금도 사실이다. 달라진 것은
그 비용을 어디에 두느냐다.

- **바이트는 메타 DB에 넣는다**(`user_avatars`). 파일로 떨어뜨리면 단일 바이너리 원칙이 깨지지만,
  BLOB 한 행은 백업·삭제(FK CASCADE)·권한이 나머지 데이터와 같은 규칙을 따른다.
  사용자당 한 장이고 상한이 있으므로(기본 512KB) 비용이 작다.
- **형식은 바이트를 디코딩해 확인한다.** 확장자와 Content-Type은 믿지 않는다 —
  `.png`로 올린 실행 파일은 png가 아니다. 크기 상한(`-avatar-max-kb`)과 화면 크기 상한(2048px)도 함께 건다.
- **SVG는 받지 않는다.** SVG는 스크립트를 품을 수 있는 문서 형식이라 이미지가 아니라 실행 가능한
  마크업이고, 그것을 사용자 입력으로 받아 다른 사람에게 보여주는 것은 저장형 XSS와 같은 말이다.
  리사이즈도 하지 않는다 — 그 순간 이미지 처리 라이브러리와 그 취약점을 떠안게 된다. 거부하는 편이 정직하다.
- **URI는 서버가 한 번 내려받아 저장한다.** URL을 그대로 두고 브라우저가 불러오게 하면
  CSP(`img-src 'self' data:`)를 외부 출처까지 열어야 하고, 링크가 깨지거나 외부망이 없으면
  아바타가 사라진다. 대신 SSRF를 막기 위해 **사설망·루프백 주소를 기본으로 차단하고**
  리다이렉트 대상도 같은 검사를 거친다(`-avatar-allow-private-uri`로 풀 수 있다).
  아바타는 모든 사용자가 쓰는 기능이라(커넥션 등록은 어드민 전용이다) 특히 넓게 열려 있는 통로다.
- 이미지 주소에는 버전 번호가 붙는다(`?v=3`). 경로가 그대로면 사진을 바꿔도 브라우저가
  캐시된 옛 이미지를 계속 보여준다.
- `avatar='upload'`는 업로드 API만 설정할 수 있다. 프로필 수정 API로 그 값을 넣을 수 있으면
  이미지 없이 "업로드 사용" 상태가 되어 화면이 깨진 이미지를 그린다
  (`TestValidAvatarRejectsUploadSentinel`).

- **키는 서버, 획은 화면.** 목록(`internal/model/avatar.go`)은 서버가 갖고 `/meta`로 내보내며,
  저장할 때 그 목록으로 검증한다. 그림(`web/js/core/avatars.js`)은 화면이 갖는다.
  목록을 화면이 정하면 서버가 검증할 수 없고, 그림을 서버가 갖게 되면 SVG 문자열이 API를
  타고 흐른다 — 신뢰할 수 없는 마크업을 화면에 넣는 습관은 이런 데서 시작한다.
- 두 곳이 갈라지는 경우(서버에 키가 있는데 획이 없는 경우)에는 선택지에서 아예 빼고
  이니셜로 떨어진다. 고를 수는 있는데 아무것도 안 보이는 항목은 고장으로 보인다.
  `scratchpad/profile_check.mjs`가 "선택지 수 == 서버 목록 + 1(이니셜)"을 확인해 이 갈라짐을 잡는다.
- 아이콘은 두 축으로 나눠 놓았다. **직무**(무슨 일을 하는지)는 같은 상반신에 배지만 바꿔
  실루엣을 공유하고, **사람**(누구인지)은 얼굴 특징으로 구분한다. 20개가 넘어가면 고르는 일이
  일이 되므로 각 8개로 묶었다.
- "이니셜"이 목록의 첫 항목이다. 고르지 않을 자유가 없으면 되돌릴 방법도 없다.

프로필 수정 API(`PATCH /auth/profile`)는 사용자 관리 API와 분리했다. 바꿀 수 있는 것은
표시 이름·이메일·아이콘 세 개뿐이며, 역할·상태 필드는 무시되는 것이 아니라 요청 구조체에
자리가 없다 — 있으면 언젠가 연결된다. 이 성질은 테스트로 고정해 두었다
(`TestProfileRequestIgnoresPrivilegeFields`).

사이드바의 사용자 칩이 프로필 화면 입구다. 메뉴에 항목을 더하지 않은 이유는 사람들이
자기 이름을 먼저 누르기 때문이고, 좁은 화면에서 칩을 숨기지 않는 이유는 그러면 프로필에
갈 방법이 사라지기 때문이다(이름만 접는다). 칩은 상태를 구독해 스스로 다시 그린다 —
저장했는데 사이드바가 옛 이름을 계속 보여주면 저장이 안 된 것으로 보인다.

ERD 편집 화면의 참가자 표시는 아이콘을 쓰지 않는다. 그곳의 원은 **커서 색과 짝지은 신원
표시**라서, 색 대신 아이콘을 넣으면 화면 위 커서와 사람을 연결할 수 없다.

### 사이드바: 데스크톱에서는 폭을 조절하고, 좁은 화면에서는 서랍이 된다

**폭 조절**(`web/js/core/sidebar.js`). 셸 그리드가 `var(--sidebar-w)`를 읽고, 오른쪽
경계선 위의 손잡이가 그 변수를 바꾼다. 값은 `localStorage`에 남고 190~420px로 제한된다.

- 손잡이는 보이는 경계선(1px)보다 넓게(7px) 잡는다. 1px짜리 목표는 마우스로 정확히
  잡을 수 없다.
- 포인터 이벤트 + `setPointerCapture`를 쓴다. 마우스·터치·펜이 한 코드로 처리되고,
  커서가 창 밖으로 나가도 드래그가 끊기지 않는다.
- 저장은 손을 뗄 때 한 번만 한다. 드래그 중 저장은 낭비다.
- 키보드로도 조절한다(`role="separator"` + 화살표/Home/End, 더블클릭이나 Enter로 기본값).
  마우스로만 되는 조절은 조절이 아니라 장식이다.

**좁은 화면(≤900px)에서는 서랍**. 이전에는 사이드바가 가로로 스크롤되는 띠였고, 메뉴가
14개라 화면에는 두어 개만 보였다 — 있는 줄도 모르는 메뉴가 대부분이었다. 지금은 상단
막대의 햄버거 버튼으로 열고 닫는다.

- 닫혀 있을 때는 `transform`으로 밀어낼 뿐 아니라 `visibility: hidden`으로 초점 순서에서도
  빼낸다. 밀어내기만 하면 탭 키가 보이지 않는 메뉴 14개를 훑고 지나간다.
- 단 **visibility는 전환하지 않는다**(`0s`). 전환 중인 값은 스타일을 강제로 계산해도 아직
  `hidden`이라, 서랍을 열면서 첫 메뉴에 초점을 주는 코드가 조용히 무시된다. 닫을 때만
  미끄러지는 시간만큼 숨김을 미뤄 애니메이션을 지킨다.
- 닫는 방법을 셋 준다: 배경 누르기, Escape, 메뉴 고르기(이동하면서 닫힌다).
  화면이 바뀌었는데 서랍이 그 위에 남아 있으면 결과를 볼 수 없다.
- 넓은 화면으로 돌아가면 `matchMedia` 변화로 열림 상태를 정리한다. 남겨 두면 본문 위에
  막이 덮인 채로 유지된다.

프로필 입구인 사용자 칩은 서랍 안에 그대로 있다. 좁은 화면에서 칩을 숨기면 프로필에 갈
방법이 사라진다.

### 표 안의 버튼 줄은 텍스트 스타일에 얹지 않는다

이벤트 표의 "외부 편집으로 버전 등록 / 버전 이력"처럼 셀 안에 버튼이 여러 개 들어가는
자리가 있다. 이것을 보조 텍스트 스타일(`.cell-sub`, 12px/18px)에 담으면 버튼이 글줄 위의
인라인 요소가 되어 baseline에 걸리고, 아이콘이 있는 버튼만 아래로 밀린다. 버튼 줄은
텍스트가 아니라 배치의 문제이므로 `.cell-actions`(flex, `align-items: center`, gap, wrap)로
따로 둔다.

### 대시보드 카드는 카드 전체가 링크다

이름만 링크였을 때는 눌러야 할 곳이 카드 안의 작은 글씨 하나뿐이었다. 카드를 눌러 볼
것이라고 기대하는 편이 자연스럽다. 대신 **카드 안에 다른 링크·버튼을 두지 않는다** —
링크 안의 링크는 키보드와 스크린리더에서 깨진다. 상태 점·배지·지표·스파크라인은 모두
표시 요소이므로 이 제약이 문제가 되지 않는다.

### 화면은 브라우저 폭을 그대로 쓴다

본문에 `max-width`를 두지 않는다. 이 도구의 화면은 대부분 표(커넥션·이벤트·감사 로그·
스키마 컬럼)이고, 표는 폭이 남으면 열을 더 편하게 읽을 수 있다. 읽기 편한 글줄 길이를
지키려고 폭을 묶는 것은 문서에 맞는 규칙이지, 한 행에 여러 값을 나란히 놓고 비교하는
관리 화면에 맞는 규칙이 아니다.

폭을 풀면 대신 그리드가 문제가 된다. 셸은 `grid-template-columns: 240px minmax(0, 1fr)`
이어야 한다. `1fr`의 최소 크기는 기본이 `auto`(=내용의 min-content)여서, 넓은 표가
하나라도 있으면 본문 트랙이 뷰포트보다 커지고 **페이지 전체가 가로로 밀린다**. 좁은 화면
(480px)에서 실제로 7px씩 밀렸다. 최소를 0으로 고정하면 본문은 항상 남은 폭에 맞고,
넘치는 표는 `.card { overflow-x: auto }` 덕분에 카드 안에서만 스크롤한다.

### 대시보드는 "지금 문제가 있는가"에 먼저 답한다

첫 화면의 순서는 그대로 판단 순서다.

1. **요약 타일 6개** — 전체 커넥션·운영 DB·응답 없음·열린 심각·열린 경고·24시간 이벤트.
   모두 링크이고, 심각/경고 타일은 `/events`를 해당 필터가 적용된 상태로 연다.
   숫자를 보고 다음에 할 일이 링크 한 번이어야 한다.
2. **확인이 필요한 항목** — 열린 이벤트를 심각도·커넥션·시각과 함께 최대 6건. 하나도
   없으면 비워 두지 않고 "이상 없음"을 문장으로 말한다. 빈 자리는 "확인했고 문제 없음"과
   "수집하지 않음"을 구분해 주지 못한다.
3. **데이터베이스 상태 카드** — 커넥션마다 상태 점, 환경, 열린 이벤트 수,
   세션 사용률 막대(`connections.total/max`), 핵심 지표(응답·쿼리·캐시),
   이상 신호 칩, 6시간 부하 스파크라인.

카드의 이상 신호 칩은 **0이 아닐 때만** 나타난다(느린 쿼리·데드락·중단된 연결·키 축출·
복제 지연·차단된 클라이언트). 항상 0인 칸이 여섯 개 있으면 0이 아닌 하나가 눈에 띄지
않는다. 대신 모두 정상일 때는 "이상 신호 없음 (N개 지표)"로 **무엇을 몇 개 확인했는지**
밝힌다. 같은 이유로 세션 사용률은 막대에만 두고 지표 칸에서는 뺐다 — 같은 수치를 두 번
적으면 서로 다른 지표를 읽는 데 방해가 된다.

부하 그래프는 `query.rate`가 있으면 그것을, 없으면 `connections.total`, 그다음 응답 시간을
쓴다. 재시작 직후에는 비율 지표에 표본이 두 개 필요해서 세션·응답으로 그려지고,
한 번 더 폴링하면 쿼리로 바뀐다. 축 이름에 무엇을 그렸는지 항상 적는 이유다.

30초마다 갱신하며, 화면을 벗어나면 타이머를 정리한다. 모니터링 API가 실패해도 커넥션
목록과 기능 입구는 그대로 보여준다 — 화면 전체가 한 요청의 실패에 묶이면 안 된다.

### 스키마 IR이 중심인 이유

`internal/schema`의 중간 표현이 introspect(실제 DB 읽기), ERD 편집, diff, 마이그레이션
SQL 생성, 버전 저장에 모두 쓰인다. 덕분에 "ERD로 그린 것"과 "DB에 실제로 있는 것"을
같은 방식으로 비교할 수 있고, 드리프트 감지도 같은 경로를 재사용한다.

타입은 DB별 원본 문자열(`RawType`)과 정규화된 논리 타입(`LogicalType`)을 함께 보관한다.
원본만 비교하면 DB를 옮겼을 때 모든 컬럼이 변경으로 잡히고, 논리 타입만 보관하면
같은 dialect로 되돌릴 때 정보가 손실된다.

이름 변경(rename)은 의도적으로 추론하지 않는다. 스키마 두 장만 보고 rename을 추측하면
잘못 짚었을 때 데이터가 사라지므로, 삭제 + 생성으로 표현하고 실제 rename은
ERD 편집 이력(P6~P7)에서 명시적 op로 전달한다.

### 시간은 고정 폭 문자열로 저장한다

`internal/store`의 `timeLayout`은 소수점 9자리를 항상 채운다.
`time.RFC3339Nano`는 소수점 뒤 0을 제거해 자리수가 가변인데, SQLite는 시간을 문자열로
비교하므로 정확히 정초인 값(`"…:40Z"`)과 소수부가 있는 값(`"…:40.5Z"`)의 비교가
뒤집힌다(`'Z'` 0x5A > `'.'` 0x2E). 그러면 모든 시간 범위 조건과 `ORDER BY`가
조용히 틀린 결과를 낸다. `internal/store/time_test.go`가 이 성질을 검증한다.

### 쿼리를 정규화한 뒤에 센다

`internal/dblog/normalize.go`는 리터럴을 `?`로 바꾸고 `IN (?,?,?)`을 `IN (?)`으로 접은
뒤 SHA-256 앞 8바이트를 다이제스트로 쓴다. 이 과정 없이 세면 값만 다른 같은 쿼리가
전부 별개로 잡혀 "가장 비용이 큰 쿼리" 목록이 무의미해진다.

두 가지는 일부러 건드리지 않는다. **단일 인용부호만 문자열 리터럴로 본다** — 백틱(MySQL)과
이중 인용부호(표준/PostgreSQL)는 식별자이므로 치환하면 `SELECT "user_id"`가 `SELECT ?`가
된다. **대문자화는 키워드에만 적용한다** — PostgreSQL은 인용된 식별자의 대소문자를 구분하므로
식별자를 대문자로 바꾸면 다른 테이블을 가리키게 된다.

MySQL의 `performance_schema`, MS-SQL의 `query_hash`, Oracle의 `sql_id`처럼 DB가 이미
정규화된 형태와 식별자를 제공하면 그것을 그대로 쓴다. 직접 정규화하면 DB 내부 집계와
어긋난다.

### 호스트 지표는 외부 라이브러리 없이, OS가 주는 값만 읽는다

`internal/hostmon`은 리눅스에서 `/proc/stat`·`/proc/meminfo`·`/proc/net/dev`·`statfs`를,
윈도우에서 `GetSystemTimes`·`GlobalMemoryStatusEx`·`GetDiskFreeSpaceEx`·`GetIfTable`을
직접 읽는다. 고른 함수는 모두 오래되고 안 바뀌는 것들이다 — 최신 API(`MIB_IF_ROW2` 등)는
구조체에 열거형과 비트필드가 섞여 있어 Go 구조체로 옮기다 한 칸만 어긋나면 **그럴듯한
숫자**가 나오고, 그런 오류는 화면에서 알아볼 수 없다.

**읽지 못한 값은 저장하지 않는다.** 차트에서 "0%"와 "모름"은 전혀 다른 뜻인데, 0으로
채우면 둘을 영원히 구분할 수 없다. 첫 표본의 CPU 사용률도 없다(두 표본의 차이로 구하므로).
못 읽은 이유는 스냅샷의 `notes`로 화면에 그대로 나간다.

**윈도우의 인터페이스 표는 같은 트래픽을 여러 번 센다.** 필터 드라이버마다 한 줄씩
나오고(WFP Native MAC Layer, QoS Packet Scheduler …) 이름만 조금씩 다르다. 누적값이 같은
줄은 하나로 합치고 그중 짧은 이름(어댑터 본래 이름)을 남긴다. 한 바이트도 오간 적 없는
가상 어댑터는 버린다 — 남기면 목록이 수십 개가 되어 진짜 랜카드를 찾을 수 없다.

**호스트 이벤트에는 커넥션이 없다.** 이벤트 조회 범위는 지금까지 "볼 수 있는 커넥션 목록"
하나였는데, 목록에 넣을 ID가 없다고 조건을 비우면 전체 공개가 된다. `EventFilter`에
`IncludeSystem`을 따로 두고 **커넥션 관리 권한**에게만 켠다. 목록과 요약 배지는 같은
조건 생성 함수를 쓴다 — 둘이 어긋나면 배지에는 숫자가 있는데 목록은 비어 있는 화면이 되고,
그때 사람들은 알림 자체를 믿지 않게 된다.

### ERD 동시 편집: 서버가 순서를 정하고, 클라이언트는 적용 로직을 갖지 않는다

편집은 op(연산)로 전달된다. 서버가 검증하고 순번(seq)을 붙여 저장한 뒤 모든 구독자에게
브로드캐스트한다. 같은 문서의 op는 서버에서 완전히 직렬화되므로 순서가 하나뿐이고,
그 순서대로 적용하면 모든 참여자가 같은 상태에 도달한다. 브로드캐스트는 보낸 사람에게도
가므로 "내 편집"을 특별 취급하는 경로가 없다.

갱신 op는 **패치**다. 없는 필드는 "변경하지 않음", 빈 문자열은 "제거"를 뜻한다.
전체 교체 방식이면 두 사람이 같은 컬럼의 다른 속성을 동시에 고칠 때 나중 op가 앞의
편집을 되돌린다.

구조를 바꾼 op는 브로드캐스트에 적용 결과(문서 전체)를 함께 담는다. 그렇게 하지 않으면
클라이언트가 검증·제약 정리·이름 변경 전파를 JavaScript로 다시 구현해야 하고, 두 구현이
어긋나는 순간 사용자마다 다른 스키마를 본다. 구조 편집은 사람의 속도로 일어나므로 문서를
다시 보내는 비용이 싸다. 반대로 좌표 이동은 초당 수십 번 발생하지만 대입이 곧 적용이므로
op만 보내고 클라이언트가 반영한다.

거부된 편집에는 최신 상태를 함께 보낸다. 낙관적으로 적용한 클라이언트는 그 순간 틀린
상태를 보고 있고, op별 역연산은 종류마다 필요하고 틀리기 쉽다.

캔버스 좌표와 메모는 스키마 IR이 아니라 문서에 따로 담는다. IR의 지문이 드리프트 감지와
버전 비교의 기준이므로, 좌표가 IR에 들어가면 테이블을 옮기기만 해도 스키마가 바뀐 것이 된다.

### 되돌리기: 역연산을 손으로 쓰지 않는다

op가 24종이고 그중 몇은 단순하지 않다. 테이블 삭제는 컬럼·인덱스·외래키·제약을 함께
지우고 **다른 테이블의 외래키까지** 정리한다. 그 규칙을 역방향으로 한 벌 더 쓰면 구현이
둘이 되고, 언젠가 한쪽만 고쳐진다 — 증상은 "되돌렸는데 뭔가 사라져 있다"이다.

그래서 적용 **전후를 비교해** 되돌리는 op(`doc.restore`)를 만든다. 규칙은 `Apply` 한
곳에만 남고, 그 op를 다시 비교에 넣으면 다시실행이 나온다. 되돌리기 스택은 (문서,
사용자)마다 하나다 — 문서 단위로 잡으면 내 Ctrl+Z가 남이 방금 한 일을 지운다. 되돌리는
op는 새 편집으로 기록된다. op-log에서 과거를 지우면 그 사이에 남이 쌓은 편집의 기준이
흔들린다.

복원은 대상을 통째로 교체하므로, 남이 그 사이에 같은 것을 고쳤다면 그 편집이 조용히
사라진다. 그래서 복원 payload에 "지금 이 모습이어야 한다"는 지문을 함께 싣고 다르면
거절한다. 좌표에는 걸지 않는다 — 남이 카드를 조금 옮겼다고 되돌리기를 막으면 쓸 수 없다.

### 마이그레이션 안전성은 DDL 트랜잭션 지원 여부에서 갈린다

| DB | DDL 트랜잭션 | 중간에 실패하면 |
|---|---|---|
| PostgreSQL · MS-SQL · SQLite | 지원 | 전부 되돌아간다 (부분 적용 없음) |
| MySQL · Oracle | 미지원 (암묵적 커밋) | 앞의 문장은 적용된 채 남는다 |

그래서 실행 기록을 **문장 단위**로 남긴다. MySQL에서 중간에 실패하면 "어디까지 적용됐는가"가
복구의 유일한 출발점이다. 자동 복구는 하지 않는다 — up 문장과 down 문장이 1:1로 대응하지
않으므로(되돌릴 수 없는 변경은 down이 없다) 기계적으로 짝지어 되돌리는 것은 틀리기 쉽다.
대신 적용된 문장을 정확히 보여주고, "오류를 무시하고 계속" 옵션이 있는 롤백으로 정리하게 한다.

**사전 검사(프리체크)** 는 계획을 만든 시점의 구조 지문과 실행 직전의 대상 DB를 비교한다.
다르면 차단하고 무엇이 달라졌는지 보여준다. 이 검사가 없으면 남이 먼저 바꾼 스키마 위에
낡은 계획을 실행해 그 변경을 덮어쓴다.

**버전은 의도가 아니라 관측된 실제 스키마를 기록한다.** 실행 후 다시 introspect한 결과를
등록하고 목표와의 차이가 남으면 경고한다. 목표(초안)를 등록하면 DDL 생성기의 미묘한 차이가
이력에 영원히 숨는다.

### Git 연동: 세 서비스의 차이를 인터페이스 뒤로 숨긴다

`vcs.Provider`는 네 가지 동작만 노출한다 — `Verify` / `EnsureBranch` / `PutFiles` / `OpenPR`.
그 뒤에서 각 서비스의 차이를 흡수한다.

**여러 파일을 한 커밋으로 올리는 방법**이 가장 크게 갈린다. GitLab은 커밋 API 하나가 파일
액션 배열을 받고, Bitbucket은 `/src`에 multipart로 보내며(파일 경로가 폼 필드 이름),
GitHub은 Contents API가 파일당 커밋을 만들기 때문에 트리 → 커밋 → ref 갱신을 직접 밟는다
(호출 5회). 그래도 한 커밋으로 묶는 이유는 up.sql과 down.sql이 다른 커밋에 흩어지면
리뷰어가 반쪽만 보고, 되돌릴 때도 커밋 하나로 처리할 수 없기 때문이다.

**브랜치 이름 인코딩은 서비스마다 반대다.** GitLab은 브랜치 이름을 하나의 경로 요소로 보므로
슬래시를 `%2F`로 인코딩해야 하고, GitHub은 `/git/ref/heads/` 뒤 전체를 ref로 해석하므로
슬래시를 그대로 둬야 한다. Bitbucket도 그대로 받는다. 틀리면 404가 나는데 원인을 찾기
어려우므로 `pathEscape`(GitLab)와 `pathKeepSlash`(나머지)로 분리하고 테스트로 고정했다.

**인증 헤더**도 다르다: GitHub `Authorization: Bearer`, GitLab `PRIVATE-TOKEN`,
Bitbucket은 앱 비밀번호면 Basic(사용자 이름 필요)·액세스 토큰이면 Bearer.

### Git 연동은 개인의 것이다

`vcs_integrations`에 담기는 것은 **개인의 Git 계정 토큰**이다. 그것을 여럿이 함께 쓰면
두 가지가 무너진다.

1. **원격 저장소에서 "누가 올렸는가"가 사라진다.** 모든 PR이 토큰 주인의 이름으로 열리므로,
   스키마 변경의 책임자를 Git 쪽 기록만으로는 알 수 없다. 이 앱은 "누구의 권한으로
   실행되는가"를 일관되게 지켜 왔는데(어시스턴트·MCP·매크로·자동 실행) 이 경로만 예외였다.
2. **남의 계정 자격증명을 쥔 사람이 생긴다.** 토큰은 이 앱 밖(저장소·이슈·CI)에서도 쓸 수
   있으므로 그 범위는 DB Studio의 권한 모델을 넘어선다.

그래서 연동에는 주인이 있고, 조회·수정·삭제·연결 확인이 모두 주인으로 좁혀진다.
**슈퍼 어드민도 예외가 아니다** — 남의 Git 계정을 볼 수 있다는 것은 곧 그 사람 명의로
행동할 수 있다는 뜻이고, 그것은 API 토큰을 남이 발급할 수 없게 한 것과 같은 이유다.
없는 것과 남의 것은 똑같이 404로 답한다(존재 여부도 알려줄 이유가 없다).

- **판정은 질의에 넣는다.** "찾은 뒤에 주인을 비교한다"는 호출부마다 반복되고, 한 곳이라도
  빠뜨리면 그것이 곧 통로가 된다. `WHERE ... AND owner_id = ?`로 좁혀 실수할 자리를 없앴다.
- **등록에 별도 권한이 필요 없다.** 등록하는 사람과 쓰는 사람이 언제나 같기 때문이다.
  예전의 "커넥션 관리 권한" 요구는 공유 모델의 잔재였다.
- **계정이 지워지면 함께 지워진다**(`ON DELETE CASCADE`). 주인 없는 토큰이 남을 이유가 없다.
- **이름은 사람마다 따로 센다**(`UNIQUE (owner_id, name)`). 남이 "회사 저장소"를 먼저 썼다고
  내가 다른 이름을 지어야 할 이유는 없다.
- **푸시 이력은 팀의 것이다.** 무엇이 어느 브랜치·PR로 올라갔는지는 마이그레이션에 대한
  사실이고, 커밋과 PR 주소는 이미 팀이 공유하는 산출물이다. 감춰지는 것은 설정과 토큰이다.

기존에 등록된 공유 연동은 이 변경에서 **지웠다**. 공유 연동에는 "이것이 누구의 계정인가"가
기록되어 있지 않다(`created_by`는 등록한 사람일 뿐 토큰 주인이라는 보장이 없다). 잘못된
주인에게 넘기느니 각자 자기 계정으로 다시 등록하는 편이 안전하다.

### Git 토큰 보호

토큰은 DB 비밀번호와 같은 방식(AES-256-GCM)으로 봉인해 저장하고, 구조체 필드에
`json:"-"`를 달아 API 응답에 실릴 수 없게 했다. 화면에는 "설정됨" 여부만 표시한다.
조회 함수가 `withToken` 인자를 요구하므로 목록·표시 경로에서 실수로 복호화할 수 없다.

HTTP 클라이언트는 **리다이렉트를 따르지 않는다** — `Authorization` 헤더가 다른 호스트로
전달되면 자격증명 유출이며, Git 서비스의 정상 API 경로는 리다이렉트를 요구하지 않는다.

self-hosted 주소는 https를 요구하되 **사설망/루프백 주소에만 http를 허용한다**. 사내망
인스턴스에 TLS가 없는 경우는 현실에 있으므로, 그 둘을 구분하면 안전한 기본값과 실용성을
함께 얻는다. 다만 이것이 SSRF를 완전히 막지는 못한다(DNS는 나중에 바뀔 수 있다).
연동 설정은 어드민만 할 수 있고 그들은 이미 DB 자격증명을 다루므로, **이 지점의 신뢰 경계는
"어드민을 신뢰한다"** 이다.

### WebSocket의 CSRF 방어는 Origin 검사다

브라우저의 WebSocket API는 커스텀 헤더를 붙일 수 없어 REST에서 쓰는 `X-Requested-With`
검사를 적용할 수 없다. 대신 핸드셰이크에 반드시 실리는 `Origin`을 `Host`와 비교한다.
`Origin`이 아예 없으면 브라우저가 아닌 클라이언트이며, 쿠키 자동 전송이라는 CSRF의 전제가
성립하지 않으므로 허용한다(CLI·테스트 도구).

### PostgreSQL 확장 소유 객체는 스키마에서 제외한다

`pg_stat_statements` 같은 확장을 설치하면 그 뷰가 `public` 스키마에 들어온다. 이를
사용자 객체로 취급하면 ERD가 무관한 객체로 어지러워지고, 생성한 `CREATE VIEW`가
확장 전용 C 함수를 참조해 다른 스키마/DB에서 실행되지 않는다. `pg_depend.deptype='e'`로
걸러내며(MS-SQL의 `is_ms_shipped=0`과 같은 이유), 조용히 빠지면 오해하므로 제외 사실을
스키마 노트로 남긴다.

### MongoDB·Redis는 별도 화면을 갖는다

두 DB도 스키마 IR로 읽는다(컬렉션→테이블, 필드→컬럼, 키 접두사 그룹→테이블). 그래야 다른
DB와 같은 화면에서 나란히 볼 수 있다. 하지만 **운영에 필요한 정보는 그 표현에 들어가지 않는다**:
컬렉션별 저장 크기, 인덱스가 실제로 쓰이는지, 메모리 정책, TTL이 없는 키, 큰 키.
테이블·컬럼 모델에 억지로 밀어넣으면 양쪽 다 읽기 어려워지므로 전용 화면(`/nosql`)을 따로 뒀다.

어댑터 인터페이스는 키우지 않았다. `DocumentExplorer`/`KeyspaceExplorer`를 선택적 인터페이스로
두고 `Capabilities.explore`로 지원 여부를 알린다. 관계형 어댑터 5종은 이 코드를 알 필요가 없고,
화면과 AI 툴은 같은 플래그를 보고 판단한다.

**구조와 통계만 반환한다.** 문서 내용이나 키 값은 응답에 담지 않는다 — 이 앱의 권한 모델은
"모니터링 / ERD / 마이그레이션"이고 데이터 열람은 그 안에 없는 개념이다. 감사 로그에도 규모만
남기고 키 이름·필드 이름은 남기지 않는다.

전체 키를 훑지 않는다. Redis는 `SCAN` 표본(최대 2만 개)만 보고, 타입·TTL·메모리는 그중
앞쪽 2천 개만 파이프라인으로 조사한다. `KEYS`는 서버를 멈추고, 키마다 3번 왕복하면
1천 개에 3천 번이 된다. 화면에는 표본 크기와 상한 도달 여부를 함께 보여준다 —
근사값을 정확한 값처럼 보여주면 잘못된 판단을 만든다.

MongoDB의 `system.*` 컬렉션은 제외한다. 프로파일러 기록(`system.profile`)은 문서마다 형태가
달라 필드가 수백 개로 추론되고, 뷰 정의(`system.views`)는 접근 권한이 없는 경우가 많다.
제외했다는 사실은 화면에 남긴다.

### MCP 서버: 같은 툴, 다른 문

외부 MCP 클라이언트가 쓰는 툴은 앱 안의 AI 어시스턴트가 쓰는 것과 **같은 레지스트리**다
(`internal/api/ai_tools*.go`). 두 벌을 만들면 어느 한쪽에만 있는 툴이 생기고, 더 나쁘게는
권한 검사가 한쪽에만 들어간다. `internal/mcp`는 프로토콜(JSON-RPC 타입과 협상)만 알고
앱을 모른다 — 툴 실행은 `internal/api/mcp_handlers.go`가 기존 경로로 넘긴다.

**전송은 Streamable HTTP만 지원한다.** stdio 모드를 넣지 않은 이유: 그것은 같은 SQLite 파일을
여는 두 번째 프로세스를 뜻하고, 이 앱은 단일 인스턴스를 전제한다. stdio만 받는 클라이언트는
`mcp-remote` 같은 프록시를 쓰면 된다.

**인증은 API 토큰뿐이고 세션 쿠키를 받지 않는다.** 쿠키를 받으면 브라우저가 자동으로 실어
보내므로 다른 사이트가 이 엔드포인트를 부를 수 있게 된다(CSRF). 토큰은 클라이언트가 헤더에
직접 넣어야 하고, 그것이 이 경로의 유일한 문이다. OAuth 2.1을 쓰지 않은 것은 규약이 권하는
방향과 다르지만, 인가 서버·동의 화면·리프레시를 들여올 만한 근거가 아직 없다 —
토큰 하나로 충분한 규모다.

**쓰기는 토큰 범위로 가른다.** 앱 화면에서는 사용자가 승인 버튼을 눌러야 변경 툴이 실행되지만
MCP에는 그 화면이 없다. 대신 두 가지로 그 자리를 채운다.

1. 토큰을 발급할 때 쓰기 허용 여부를 고른다. 읽기 토큰에는 변경 툴이 **목록에도 나오지 않는다** —
   보이는데 부르면 거부되는 툴은 모델이 계속 시도하게 만든다.
2. 툴 주석(`readOnlyHint` / `destructiveHint`)을 붙여 클라이언트가 사람에게 확인을 받게 한다.

그리고 **서버 쪽 게이트는 어느 경로에서든 그대로다.** 능력 판정, 마이그레이션 승인 수,
운영 DB 확인 문구가 전부 살아 있다. 확인 문구가 필요한 동작(운영 DB 복구, 파괴적 마이그레이션
실행)은 MCP로는 아예 실행되지 않는다 — 그 문구는 사람이 직접 타이핑하게 만드는 장치이므로
프로그램 경로에서 통과시키면 존재 이유가 사라진다. 그런 경우 툴은 "웹 화면에서 하라"고 답한다.

**툴 오류는 JSON-RPC 오류가 아니라 `isError`로 돌려준다.** 규약이 그렇게 정한 이유가 있다:
프로토콜 오류로 만들면 클라이언트가 대화를 끊지만, `isError`면 모델이 그 문장을 읽고 스스로
고쳐 다시 부른다. "권한이 없습니다"는 대화를 끊을 일이 아니라 모델이 다른 방법을 찾을 단서다.

### API 토큰은 세션과 다른 것이다

세션은 브라우저의 것이고 12시간 뒤 사라진다. MCP 클라이언트는 브라우저가 아니고 쿠키를 쓰지
않으며 몇 달 동안 같은 자격증명으로 붙는다. 세션 TTL을 늘려 그 용도를 겸하게 하면
브라우저 세션까지 함께 길어진다.

- **해시만 저장한다**(세션과 같은 규칙). 원문은 발급 순간 한 번만 보여주고 어디에도 남기지
  않는다 — 되찾을 수 있는 토큰은 DB가 유출되면 함께 유출된다.
- **자기 토큰만 만들고 지운다.** 슈퍼 어드민도 남의 토큰을 발급할 수 없다. 그것은 곧 남의
  권한으로 행동할 수단을 주는 것이고, 이 앱에는 그런 개념이 없다. 대신 사용자를 비활성화하면
  그 토큰도 함께 죽는다.
- **폐기는 행을 지우지 않는다.** "이 토큰이 언제까지 살아 있었는가"가 사고 조사에 필요하다.
- 비밀번호 변경이 강제된 사용자의 토큰은 통하지 않는다. 화면에서 막아 둔 사람이 토큰으로는
  통과한다면 그 게이트는 없는 것과 같다.
- 마지막 사용 시각과 IP를 기록한다(5분 간격). 쓰지 않는 토큰을 정리할 때, 그리고 유출을
  의심할 때 첫 단서가 된다.

### MCP 클라이언트 연결

프로필 화면에서 토큰을 발급한 뒤:

```bash
claude mcp add --transport http dbstudio https://<호스트>/mcp \
  --header "Authorization: Bearer dbs_..."
```

설정 파일을 직접 쓰는 클라이언트:

```json
{
  "mcpServers": {
    "dbstudio": {
      "type": "http",
      "url": "https://<호스트>/mcp",
      "headers": { "Authorization": "Bearer dbs_..." }
    }
  }
}
```

연결되면 `list_connections`부터 부르는 것이 좋다 — 다른 툴에 넘길 커넥션 이름이 거기 있다.

### REST API: 세 번째 문, 같은 관문

MCP가 있는데 REST API를 따로 둔 이유는 하나다: **MCP 클라이언트가 아닌 것들이 있다.**
셸 스크립트, CI 잡, 사내 대시보드, 다른 언어로 쓴 서비스는 JSON-RPC 봉투를 만들고
`initialize`를 협상할 이유가 없다. 그들에게 필요한 것은 `curl` 한 줄이다.

```bash
# 쓸 수 있는 툴과 인자 스키마
curl -H "Authorization: Bearer dbs_..." https://<호스트>/api/tools

# 툴 실행 — 본문이 곧 인자다
curl -X POST https://<호스트>/api/tools/query_data \
  -H "Authorization: Bearer dbs_..." \
  -H "Content-Type: application/json" \
  -d '{"connection":"운영 DB","table":"users","limit":10}'
```

**새로 만든 것은 표현뿐이다.** 인증, 툴 노출 판정, 쓰기 툴 실행 절차는
`internal/api/tokenapi.go`에 한 벌만 있고 MCP와 REST가 그것을 함께 쓴다. 두 문이 각자
판정을 쓰면 언젠가 한쪽에만 검사가 들어가고, 그 사실은 사고가 난 뒤에야 드러난다 —
툴 레지스트리를 어시스턴트와 공유하는 이유와 같은 이야기다. 그래서 여기서 정한 것은
경로·상태 코드·응답 형태 세 가지뿐이다.

**오류는 HTTP 상태 코드로 답한다.** MCP는 툴 오류를 `isError` 텍스트로 돌려준다 —
모델이 그것을 읽고 스스로 고쳐 다시 부르기 때문이다. REST를 부르는 것은 모델이 아니라
프로그램이고, 그것은 `if res.ok`로 분기한다. 200 안에 오류를 숨기면 그 분기가 조용히 틀린다.

| 상태 | 뜻 |
|---|---|
| 401 | 토큰이 없거나 유효하지 않다 (`WWW-Authenticate` 동봉) |
| 403 | 권한이 없다. 읽기 토큰으로 변경 툴을 불렀으면 `read_only_token` |
| 404 | 그런 툴이 없다 (목록 경로를 안내한다) |
| 400 | 본문이 인자 객체가 아니다 |
| 422 | 툴이 거절했다 — 요청 형식은 맞았고 서버도 멀쩡하다 |

`read_only_token`을 `forbidden`과 나눈 이유: 둘을 같은 코드로 답하면 클라이언트는
"토큰을 쓰기 범위로 다시 발급하면 된다"는 사실을 알 수 없다.

**결과는 파싱된 JSON으로 준다.** 툴 결과는 대부분 JSON 문자열이므로 문자열째로 넘기면
클라이언트가 한 번 더 파싱해야 한다. 다만 결과가 상한(24KB)을 넘으면 잘리면서 안내 문장이
붙어 더 이상 JSON이 아니므로, 그때는 `result` 대신 `text`에 원문을 담는다 — 잘린 JSON을
억지로 고쳐 넘기면 클라이언트는 그것이 결과 전부라고 믿는다.

**`/api/v1` 밑에 두지 않았다.** 그 아래는 세션 쿠키 미들웨어가 걸려 있고, 이 경로는
쿠키를 받지 않는다(MCP와 같은 이유 — 쿠키를 받는 순간 다른 사이트가 브라우저를 통해
이 API를 부를 수 있다). 그리고 토큰 미들웨어를 `/api` 전체에 걸지도 않았다: 그러면
그 뒤의 `/api/*` 폴백까지 토큰을 요구하게 되어, 오타 난 프론트엔드 요청이 404 대신
401을 받고 화면은 그것을 세션 만료로 읽어 로그아웃한다.

### AI 어시스턴트는 권한 위에 있지 않다

어시스턴트에 툴을 주는 순간 "누구의 권한으로 실행되는가"가 보안 경계가 된다. 여기서는
**대화 중인 사용자의 권한**이다. 툴이 커넥션에 접근할 때마다 `authz.Can`을 통과하므로,
같은 질문에 사용자마다 다른 답이 나오는 것이 정상이다. 모델이 접근 권한 없는 커넥션
이름을 지정해도 거부되고 그 사실이 감사 로그에 남는다.

**쓰기 툴은 실행하지 않고 제안(pending action)만 만든다.** 실행은 사용자가 승인 버튼을
누른 뒤 별도 요청에서 일어나고, 그 경로는 화면에서 직접 실행할 때와 **같은 함수**
(`migrate.Runner.Apply` 등)를 호출한다. 그래서 검토자 승인 수·사전 검사·운영 DB 확인 문구가
그대로 적용된다 — AI 경로에만 있는 우회로는 없다. 승인은 상태를 먼저 선점한 뒤 실행하므로
두 요청이 동시에 승인해도 한 번만 실행된다.

대화 세션은 **소유자만** 열람할 수 있다. 대화에는 그 사람의 권한으로 조회한 결과가 담기므로,
세션을 공유하면 권한 모델에 구멍이 난다. 실패한 툴 호출도 화면에 남긴다 — 무엇이 시도되고
왜 막혔는지 보이지 않으면 사용자는 모델이 왜 "할 수 없다"고 답하는지 알 수 없다.

프로바이더 어댑터는 두 개(Anthropic 네이티브 / OpenAI 호환)로 유지한다. OpenAI 호환 쪽은
base URL을 사용자가 지정할 수 있어 로컬 LLM과 Google Gemini까지 하나로 덮는다. 채팅은
`EventSource`가 아니라 POST + SSE다: GET만 지원하는 `EventSource`를 쓰면 질문이 URL에 들어가
길이 제한에 걸리고 서버 로그에 대화 내용이 남는다.

### 모델은 관리자가 범위를 정하고 사용자가 그 안에서 고른다

키를 등록하는 사람과 쓰는 사람이 다르고, 모델마다 비용이 열 배씩 차이 난다. 그래서 두 층으로
나눴다: **관리자는 프로바이더마다 허용 모델 목록을 정하고, 사용자는 대화마다 그 안에서 고른다.**

- **빈 목록은 "제한 없음"이다.** 기본값이 "아무것도 못 쓴다"가 되면 이미 돌고 있는 설치가
  업데이트만으로 멈춘다. 제한은 관리자가 명시적으로 고른 결과여야 한다.
- **기본 모델은 반드시 목록 안에 있어야 한다.** 밖에 있으면 아무도 고르지 않은 모델이 모든
  새 대화에서 쓰이고, 그것은 목록을 정한 의미를 없앤다. 목록만 고르고 기본을 비워 두면
  첫 항목이 기본이 된다.
- **판정은 한 함수(`modelAllowed`)를 지난다.** 저장할 때, 세션이 모델을 고를 때, 실제로 호출하기
  직전에 모두 같은 판정을 쓴다. 여러 벌이면 화면에서 고를 수 없는 모델이 API로는 통한다.
- **목록에서 빠진 모델을 쓰던 대화는 조용히 바뀌지 않고 멈춘다.** 다른 모델로 슬쩍 바꿔 부르면
  비용도 답도 달라진 이유를 아무도 모른다. 대신 무엇이 허용되는지 알려주고, 사용자는 대화
  머리에서 모델만 바꾸면 된다.
- 모델 목록은 **저장 전에도 불러올 수 있다**(`POST /ai/providers/models`). 먼저 저장하고 다시
  열어 고르게 하면 그 사이에 기본 모델이 없는 프로바이더가 존재하게 된다. 목록을 주지 않는
  엔드포인트(일부 로컬 LLM)는 오류가 아니라 "직접 입력하라"로 답한다 — 오류로 만들면
  사용자는 키가 틀렸다고 생각한다.

### 툴 호출 조립은 규약을 믿지 않는다

OpenAI 규약은 스트리밍 툴 호출을 이렇게 정한다: 호출은 `index`로 구분되고, `id`와 `name`은
첫 조각에만 오며, `arguments`는 문자열 조각으로 이어 붙는다. 대부분의 서버가 그대로 따른다.

**Gemini의 호환 계층은 `index`를 보내지 않는다.** Go에서 그 필드를 `int`로 받으면 "없음"과
"0번"이 구분되지 않으므로, 한 턴에 툴을 두 개 부른 응답이 전부 0번 슬롯에 겹쳐
`{"connection":"운영"}{"connection":"개발"}` 같은 문자열이 된다. 그래서 `*int`로 받아 존재
여부를 구분하고, 조각을 세 단계로 가른다: **index가 있으면 그것으로, 없으면 `id`로,
둘 다 없으면 직전 슬롯의 이어짐으로.**

어느 방법으로도 갈리지 않는 모양을 위해 마지막 방어선을 하나 더 둔다: **완결된 JSON 값 뒤에
다시 `{`가 오면 그것은 이어지는 인자일 수 없다** — 다음 호출이다. 문법만 보는 규칙이라
어떤 구현에도 통한다. 단, 같은 이름·같은 인자를 통째로 되풀이한 조각은 새 호출로 가르지
않는다(같은 툴이 두 번 실행되고, 변경 툴이면 승인 요청이 두 개 생긴다).

그리고 **툴 인자는 어떤 경로로 나가든 유효한 JSON임을 보장한다**(`NormalizeToolArgs`).
깨진 값을 그냥 흘려보내면 안 되는 이유는 그 값이 저장되기 때문이다 — 대화 이력은 새 질문마다
그대로 다시 실려 나가므로, 한 번 오염되면 그 대화는 지우기 전까지 400을 반복한다.
살릴 수 있으면 첫 번째 완결된 값만 남기고, 아니면 `{}`로 둔다. 후자는 툴이 "필수 인자가 없다"고
답하게 되는데, 그것은 모델이 읽고 고칠 수 있는 오류다.

같은 이유로 이력을 조립할 때 **짝이 맞지 않는 툴 호출과 결과를 걷어낸다.** 프로바이더는
결과 없는 호출도, 호출 없는 결과도 요청 전체를 거부한다("Request contains an invalid
argument"). 예전에 인자가 깨져 assistant 메시지 저장이 실패한 대화에는 결과만 남아 있는데,
읽는 쪽에서 정리하지 않으면 그 대화는 영영 회복되지 않는다.

### 사고 서명은 받은 그대로 돌려준다

Gemini 같은 사고(thinking) 모델은 툴 호출마다 사고 과정의 서명을 붙여 보내고, 다음 요청에
**그것을 그대로 돌려주기를 요구한다.** 돌려주지 않으면 400으로 거부한다:

```
Function call is missing a thought_signature in functionCall parts.
```

증상이 고약하다. 첫 질문은 잘 되고 **툴을 한 번 부른 다음부터** 대화가 죽는다. OpenAI 호환
규약에는 이 칸이 없어서(`tool_calls[].extra_content.google.thought_signature`) 대부분의
클라이언트가 응답을 정규화하며 조용히 버린다.

그래서 이 값을 `ai.ToolCall.Signature`로 들고 다닌다. 우리가 해석할 값이 아니므로 이름도
프로바이더 중립이고, 하는 일은 세 가지뿐이다: 스트림에서 읽고, **대화 이력에 함께 저장하고**,
다음 요청의 같은 자리에 실어 보낸다. 저장이 빠지면 새로고침 뒤에 이어지는 대화만 죽어
원인을 찾기가 더 어려워진다.

서명이 없는 툴 호출에는 `extra_content` 칸 자체를 만들지 않는다 — 이 필드를 모르는 서버
(OpenAI 본체, 로컬 LLM)에 빈 객체를 보내면 거부당할 수 있다.

Google의 호환 엔드포인트는 루트 경로도 다르다(`/v1beta/openai`, 여기에 `/v1`을 덧붙이면 404).
접미사 규칙으로는 가를 수 없어서(Groq은 `/openai/v1`이 루트다) 호스트를 보고 판단한다.

### 권한 판정

커넥션 권한이 필요한 모든 지점은 `auth.Authorizer.Can(ctx, user, connID, need)`(등급) 또는
`CanCap(...)`(데이터 능력) 한 곳을 통과한다. HTTP 핸들러, WebSocket 허브, AI 툴 실행기,
매크로 엔진이 같은 함수를 쓰므로 우회 경로가 생기지 않는다.

판정 순서: 비활성 계정 → 슈퍼 어드민(항상 migrate + 모든 능력) → 접근 범위(all/allowlist/denylist) →
커넥션별 오버라이드 또는 기본값 → 등급이 `none`이고 능력도 없으면 거부.

### 데이터 권한은 등급의 연장이 아니라 다른 축이다

기존 등급(`none < monitor < erd < migrate`)은 **설계·운영 작업**의 깊이를 나타내는 한 줄짜리
사다리다. 그 사다리에 "데이터 조회"를 끼워 넣을 자리는 없다.

- 스키마를 읽는 것과 그 안의 값을 읽는 것은 위험의 종류가 다르다. **개인정보는 구조가 아니라 값에 있다.**
- "마이그레이션은 할 수 있지만 고객 데이터는 못 본다"와 그 반대가 모두 현실적인 요구다.
  한 줄 사다리로는 둘 중 하나만 표현된다.

그래서 데이터 능력(`data.read` / `data.write` / `sql.run`)은 사다리가 아니라 **독립적인 깃발**이고,
등급과 마찬가지로 커넥션 단위로 부여한다(개발 DB는 마음대로 고쳐도 되지만 운영 DB는 조회만 되어야 하는
것이 보통이다). `TestResolveKeepsLevelAndCapsIndependent`가 이 독립성을 고정한다.

예외는 하나다. **`data.write`에는 `data.read`가 함께 필요하다.** 어떤 행을 고칠지 고르려면 그 행이
보여야 하므로 화면에서 실행 불가능한 상태이고, 그런 설정은 언제나 실수다. 서버가 조용히 `read`를
끼워 넣지 않고 거부하는 이유는, 저장한 것과 다른 값이 남으면 관리자가 무엇을 준 것인지 알 수 없기 때문이다.

반대로 매크로 사용·셸 실행은 커넥션에 매이지 않으므로 **전역 권한**(`users.perms`)이다.
매크로는 여러 커넥션에 걸쳐 동작하고 셸은 애초에 DB와 무관하니, 커넥션별로 부여하면
"어느 커넥션의 권한으로 셸을 실행하는가"라는 답할 수 없는 질문이 생긴다.

저장 위치는 이렇게 다르지만 **부여하는 곳은 권한 설정 화면 한 곳**이다(`PUT /users/:id/access`가
정책과 전역 권한을 함께 받는다). 권한을 사용자 수정 창과 권한 화면에 나눠 두면 회수할 때 두 곳을
모두 확인해야 하고, 한 곳만 보고 "회수했다"고 판단하는 순간이 사고가 된다.

### 데이터 수정은 모아 두었다가 한 번에 적용한다

화면에서 고친 값을 바로 DB로 보내지 않는다. 적용 대기에 쌓아 두었다가 "적용하기"에서
**실행될 문장을 확인한 뒤** 한 번에 나간다. 한 줄씩 저장하면 "지금 무엇을 바꾸고 있는지"를
전체로 볼 기회가 없는데, 데이터 수정은 되돌릴 수 없다.

이 흐름이 값어치를 가지려면 두 가지가 지켜져야 한다.

- **미리보기가 실제와 같아야 한다.** 화면에서 SQL을 조립해 보여주면 그것은 추측이고,
  방언과 인용 규칙이 다른 순간 미리보기와 실행이 갈라진다. 서버에 `dryRun`으로 물어
  **실제 적용과 같은 코드**가 만든 문장을 받아 온다(`buildMutation` 하나를 두 경로가 공유한다).
- **전부 되거나 전부 안 되어야 한다.** 묶음은 한 트랜잭션으로 돈다. 하나라도 실패하면 전부
  취소하고 몇 번째에서 멈췄는지 알린다. 절반만 반영되면 사용자는 무엇이 남았는지 알 수 없다.

트랜잭션이 없는 종류(MongoDB·Redis)에서는 이 흐름을 켜지 않고 지금처럼 바로 반영한다.
`DataCapabilities.Preview`가 그 갈림길이며, 보여줄 문장이 없는데 확인 단계만 늘리면
번거롭기만 하다. 한 번에 보낼 수 있는 변경은 100건까지다 — 그보다 큰 일괄 수정은 이 화면이
아니라 SQL 콘솔이 할 일이다.

행을 고르는 방식도 함께 바꿨다. 행 왼쪽의 아이콘 세 개는 어느 표에서나 폭을 먹고 값을
오른쪽으로 밀어서, **행 자체를 상세의 입구**로 삼고 그 자리에는 체크박스만 남겼다.
여러 행을 골라 한 컬럼을 같은 값으로 맞추거나 한꺼번에 삭제 대기에 넣을 수 있다.
컬럼 설명(스키마의 주석)은 값 위에 머무를 때 popover로 뜬다 — 브라우저 기본 툴팁은 뜨기까지
1초 가까이 걸리고, 그 자리는 이미 "잘리지 않은 전체 값"이 쓰고 있다.

### 데이터 수정은 기본키로만 한다

행 수정·삭제는 사용자가 WHERE 절을 쓰지 않는다. 화면이 보낸 기본키 값으로 서버가 조건을 만들고,
**기본키가 없는 테이블은 편집 불가로 표시한다.** WHERE를 사용자가 쓰게 하면 한 줄을 고치려다
테이블을 비우는 사고가 나고, 복합키의 일부만 받으면 한 행을 고치려던 UPDATE가 여러 행을 바꾼다.

식별자(테이블·컬럼·정렬 기준)는 요청에 담겨 오지만 쿼리에 넣기 전에 **DB에서 읽은 실제 목록과
대조해 그 목록에 있는 문자열로 치환한다.** 값은 파라미터로만 보낸다. 이 둘을 지키면 SQL 주입은
구조적으로 불가능해진다 — 인용만으로 막으려 하면 언젠가 인용을 빠뜨린 경로가 생긴다.
(스모크 테스트: `{"column":"name; DROP TABLE people"}` → `존재하지 않는 컬럼입니다`)

컬럼 메타데이터는 `information_schema`를 다시 조회하는 대신 `SELECT * FROM t WHERE 1=0`의 결과
메타데이터에서 얻는다. 방언마다 다른 카탈로그 쿼리를 다섯 벌 쓰지 않아도 되고, 무엇보다
**실제로 그 쿼리가 돌려줄 컬럼**을 알려주므로 뷰나 권한에 따라 컬럼이 숨겨진 경우에도 틀리지 않는다.

정렬은 사용자가 고른 컬럼이 없으면 기본키로 한다. 뷰나 기본키 없는 테이블처럼 **정렬할 것이
없으면 정렬 없이 페이지를 나누고, 순서가 보장되지 않는다는 note를 결과에 붙인다**(화면이 그것을
경고로 보여준다). 예전에는 이 경우를 에러로 막았는데, MS-SQL·Oracle의 `OFFSET/FETCH`가 정렬을
요구한다는 이유였다. 그 결과 두 방언에서만 뷰를 아예 열 수 없었다 — 순서가 흔들릴 수 있다는 것과
보지 못하는 것은 다른 문제다. 방언 차이는 MS-SQL에만 `ORDER BY (SELECT NULL)`을 넣는 것으로
흡수한다(Oracle 12c+의 행 제한 절은 정렬이 없어도 된다).

목록의 셀 값은 표시용으로 잘라서 보내고 잘렸다고 표시한다. 편집은 그 값을 쓰지 않고
**서버에서 그 행을 다시 통째로 읽는다** — 잘린 값을 저장하면 데이터가 잘린 채로 덮인다.

### 백업은 논리 덤프다 (물리 백업이 아니다)

이 앱이 만드는 백업은 **구조를 만드는 문장과 값을 넣는 문장이 담긴 텍스트 파일**이다.
mysqldump·pg_dump가 만드는 것과 같은 성격이며, 다른 서버에 그대로 다시 세울 수 있다.

파일 수준 스냅숏이나 시점 복구(PITR)는 하지 않는다. DB마다 도구와 절차가 다르고,
**잘못 만든 물리 백업은 없는 것보다 위험하다**(복구할 수 있다고 믿게 만든다).
그 자리에는 이미 `-backup-cmd` 훅이 있다 — 조직이 쓰는 도구를 그대로 부르는 것이 정직하다.
두 기능은 경쟁하지 않고 층이 다르다: 훅은 마이그레이션 직전의 안전망이고,
논리 덤프는 옮기고 재현하기 위한 것이다.

- **파일은 디스크에, 기록은 메타 DB에.** 덤프는 GB 단위가 될 수 있고 그것을 SQLite에 넣으면
  백업 한 번이 앱 전체를 느리게 만든다(프로필 이미지를 DB에 넣은 것과 반대의 판단인데,
  근거는 같다 — 크기). 행이 사라지면 파일도 함께 지운다.
- **상한을 넘으면 자르지 않고 실패한다.** 잘린 백업은 복구할 수 있다고 믿게 만들므로
  없는 백업보다 위험하다. 상한은 압축 전 크기로 잰다 — 압축률은 데이터에 따라 열 배씩
  달라져서 압축 후 크기로 재면 사용자가 예측할 수 없다.
- **항상 gzip.** 덤프는 반복이 많은 텍스트라 5~10배로 줄고, 제약이 되는 것은 CPU가 아니라
  디스크다. 내려받기도 `.gz` 그대로 준다(`zcat dump.sql.gz | psql …`).
- **덤프는 표시용 값을 쓰지 않는다.** 데이터 화면은 보여주기 위해 값을 가공한다 —
  바이너리를 16진 문자열로 바꾸고 긴 문자열을 자른다. 그 값으로 덤프를 만들면 복구했을 때
  다른 데이터가 들어간다. 그래서 덤프는 드라이버가 준 원본 값을 받아 방언별 리터럴로 직접 쓴다
  (`dbx.SQLLiteral`). 이 함수가 이 기능에서 가장 조용히 틀릴 수 있는 자리라 테스트가 가장 두껍다.
- **커서 하나로 읽는다.** 페이지(LIMIT/OFFSET)로 읽으면 뒤로 갈수록 앞의 행을 다시 세므로
  큰 테이블에서 전체 시간이 행 수의 제곱에 가까워진다.
- **뷰는 데이터를 담지 않는다.** 뷰의 내용은 원본에서 다시 계산되며, 뷰에 INSERT하는
  복구 스크립트는 대부분 실패한다.

**복구는 이 앱이 만든 백업만 받는다.** 외부 .sql 파일을 올려 실행하는 경로는 두지 않았다.
그것은 결국 "임의의 SQL을 파일로 실행하는 기능"이고, 그 통로는 이미 SQL 콘솔에 있으며
거기에는 `sql.run` 권한이 붙어 있다. 두 경로가 같은 능력을 가리키면 어느 쪽이 진짜 관문인지
흐려진다. 백업을 내려받아 보관할 수 있으므로 외부 파일을 되돌릴 방법이 없는 것도 아니다.

복구 권한은 **`migrate` 등급 + `data.write`** 둘 다다. 복구는 구조를 바꾸면서 데이터를
덮어쓰는 동작이므로, 어느 한쪽만 가진 사람에게 허용하면 그 권한 하나로는 못 하는 일을 하게 된다.
전체를 한 트랜잭션으로 감싸지는 않는다 — MySQL·Oracle은 DDL이 암묵적 커밋이라 애초에 성립하지
않고, 수십만 문장을 메모리에 들고 있을 수도 없다. 대신 **어느 문장에서 멈췄는지**를 남긴다
(마이그레이션 실행 기록과 같은 판단이다).

### 버전 롤백은 마이그레이션이 된다

"v3으로 되돌린다"는 결국 **현재 구조에서 v3 구조로 가는 마이그레이션**이다. 그래서 전용 실행
경로를 만들지 않고 기존 워크플로(리뷰 → 승인 → 사전 검사 → 실행)를 그대로 탄다.

전용 경로를 만들면 승인 없이 구조를 바꾸는 길이 하나 더 생긴다. 그것이 이 앱이 P7부터
막으려는 바로 그 상황이고, "되돌리기니까 안전하다"는 직관은 틀렸다 — **그 버전 이후에 만들어진
테이블은 되돌리면 삭제되고 그 안의 데이터는 복구되지 않는다.** 그래서 되돌리기 대화상자는
누르기 전에 변경 목록·파괴적 변경 수·실행될 SQL을 먼저 보여준다.

적용이 끝나면 등록되는 버전의 출처가 `migration`이 아니라 `rollback`이 된다
(`migrations.rollback_to_version`이 그 표시다). 이력에서 "되돌린 지점"이 보여야 나중에
무슨 일이 있었는지 읽을 수 있다.

### 구문 강조는 직접 만든다

라이브러리를 쓰지 않는다. 번들러가 없고 CSP가 `script-src 'self'`라 CDN은 애초에 불가능하며,
highlight.js 계열을 통째로 넣으면 바이너리에 수백 KB가 붙는다. 필요한 것은 네 언어(SQL·Lua·
JSON·셸)의 토큰을 색으로 나누는 것뿐이고, 그것은 스캐너 하나와 규칙 표로 끝난다.

- **innerHTML을 쓰지 않는다.** 강조 대상은 사용자가 쓴 SQL과 스크립트, 즉 신뢰할 수 없는
  문자열이다. 문자열을 이어 붙여 innerHTML에 넣는 순간 이스케이프를 한 번만 빠뜨려도
  저장형 XSS가 된다. `createTextNode`로 만들면 그런 실수를 할 자리가 없다.
- **토큰을 다시 이으면 원본과 같아야 한다.** 규칙에 걸리지 않는 문자는 한 글자씩 평문으로
  흘리므로 어떤 입력에도 무한 루프나 누락이 없다 — 강조기가 사용자의 편집을 막는 일은 없어야 한다.
  잘린 문자열·닫히지 않은 주석에서도 성립하는지 확인했다.
- **편집기는 투명한 textarea를 강조된 pre 위에 겹친다.** contenteditable을 쓰면 커서 위치·
  되돌리기·IME·붙여넣기를 전부 직접 다뤄야 하고, 그중 하나만 틀려도 한글 입력이 깨진다.
  textarea는 그 모든 것을 브라우저가 이미 올바르게 처리하며, 우리는 색만 뒤에 깐다.
  두 요소의 글꼴·크기·행간·여백·줄바꿈 규칙이 하나라도 다르면 글자가 어긋나므로 CSS에서
  두 선택자에 값을 한 번에 준다(`.code-editor` 절을 따로 손대지 말 것).
- **24,000자를 넘으면 강조를 포기한다.** 토큰 하나가 span 하나이므로 큰 덤프를 강조하면
  수만 개의 노드가 생겨 브라우저가 멈춘다. 색이 없는 것보다 화면이 멈추는 것이 훨씬 나쁘다.
- 파괴적인 SQL 낱말(DROP·DELETE·TRUNCATE·ALTER·REVOKE)은 다른 색으로 칠한다.
  실행 버튼을 누르기 전에 눈에 들어와야 하는 것들이며, 마이그레이션 계획이 이미 같은 구분을 쓴다.

### 마크다운도 직접 만든다 (`web/js/core/markdown.js`)

모델은 제목·목록·표·코드 블록을 섞어 답한다. 그것을 글자 그대로 보여주면 `**테이블 수**: 3개`
같은 줄이 그대로 남고 표는 형태를 잃는다. 라이브러리를 쓰지 않은 이유는 강조기와 같다:
번들러가 없고 CSP가 외부 스크립트를 막으므로 통째로 벤더링해야 하는데, 필요한 문법은
모델이 실제로 쓰는 것 정도라 그만큼만 만드는 편이 낫다.

- **innerHTML을 쓰지 않는다.** 여기 들어오는 문자열은 LLM이 만든 것이고 그 안에는 사용자가
  조회한 DB 값이 섞여 있다 — 즉 신뢰할 수 없는 입력이다. 처음부터 끝까지 DOM 노드만 만들어서
  "이스케이프를 빠뜨렸다"는 실수가 나올 자리를 없앴다.
- **링크는 스킴을 허용 목록으로 막는다.** `javascript:`를 href에 넣으면 모델이 만든 문자열이
  코드가 된다. 막힌 주소는 지우지 않고 글자로 남긴다 — 조용히 지우면 원문에 무엇이 있었는지
  알 수 없다.
- **밑줄 강조는 낱말 안에서 무시한다.** 컬럼 이름은 대개 snake_case이고, `app_order_item`의
  가운데를 기울임으로 바꾸면 이름이 달라 보인다. 반대로 별표에는 같은 검사를 하지 않는다 —
  `*중요*합니다` 처럼 조사가 바로 붙는 것이 한국어에서는 정상이다.
- **표는 구분선이 있어야 표로 본다.** 값에 `|`가 들어 있는 한 줄을 표로 오인하면 그 줄이
  통째로 사라진 것처럼 보인다.
- **스트리밍 중에도 마크다운으로 그리되 프레임당 한 번만 그린다.** 토큰은 화면 갱신보다 훨씬
  빠르게 오므로, 조각마다 다시 그리면 같은 화면을 수십 번 만든다.

사용자가 쓴 메시지에는 적용하지 않는다. 사람이 친 `*`는 강조가 아니라 그냥 별표다.

### 프론트엔드에는 컴파일러가 없으므로 시험이 대신한다

번들러도 타입 검사기도 없다는 결정에는 대가가 있다: **부르는데 어디에도 없는 이름**이
조용히 남는다. 그 코드가 실제로 도는 순간에만 `ReferenceError`가 나고, 그 자리에서 렌더가
멈춘다 — 화면에는 아무 일도 일어나지 않은 것처럼 보인다. ERD 인스펙터가 그랬다: 테이블을
눌러도 오른쪽 패널이 그대로였고, 원인은 `truncate`를 import하지 않은 한 줄이었다.

그 한 줄을 잡자고 node 도구 사슬을 들여오지는 않았다. 대신 필요한 검사만 Go 시험으로
한다(`assets_test.go`): **모듈이 부르는 이름이 그 모듈 안에 있거나 import되어 있는가.**
`go test ./...` 에 얹히므로 따로 기억할 것이 없다.

- **주석·문자열·정규식 리터럴을 먼저 지운다.** 정규식 한 방으로는 안 된다 — 문자열 안에
  `//`가 들어 있고(`'https?://…'`) 주석 안에 따옴표가 들어 있어서, 어느 쪽을 먼저 지워도
  나머지가 망가진다. 한 글자씩 훑으며 지금 어디에 있는지 알고 지운다.
- **스코프는 따지지 않는다.** 모듈 단위로만 본다. 넓게 잡아 거짓 경보를 내느니 놓치는 쪽을
  택했다 — 경보가 일상이 되면 아무도 읽지 않는다.
- `this.x()`·`this.#x()`처럼 앞에 `.`이나 `#`이 붙은 호출은 이 검사의 대상이 아니다.

### 대화 화면은 한 화면에 가둔다

어시스턴트 화면만 뷰포트 높이를 고정해 쓴다(`height: calc(100vh - 본문 여백)`). 다른 화면과
달리 여기서는 아래 여백이 손해이기 때문이다 — 남긴 만큼 대화가 보이는 창이 좁아지고, 답변
하나가 화면을 넘겨 매번 스크롤하게 된다. 대화 로그만 안에서 스크롤하고 입력창은 항상 제자리에
있다(`flex: 1` + `min-height: 0`; 후자를 빠뜨리면 flex 항목이 내용보다 작아지지 않아 입력창이
화면 밖으로 밀려난다). 본문 여백은 CSS 변수로 두어 두 곳에 같은 숫자를 적지 않는다.

### 매크로: 저장된 것만, 실행자의 권한으로

세 가지가 이 기능의 뼈대다.

1. **저장된 것만 실행한다.** `Engine.Start`는 그래프를 인자로 받지 않고 매크로 ID와 버전을 받는다.
   편집 중인 내용을 그대로 실행할 방법이 없어야 "무엇이 실행됐는지"가 언제나 버전 하나로 특정된다.
2. **실행자의 권한으로 실행한다.** 매크로를 만든 사람의 권한이 아니다. 그러지 않으면 권한 높은
   사람이 만든 매크로가 권한 상승 통로가 된다. AI 어시스턴트가 툴을 호출자 권한으로 실행하는 것과 같은 규칙이다.
3. **끝은 성공·실패·취소 셋 중 하나다.** 어느 쪽이든 반드시 기록된다. 앱이 실행 도중 죽어
   `running`으로 남은 기록은 부팅 시 실패로 정리한다 — 그 실행이 이어지지 않았음을 아는 유일한 시점이다.

**접근과 실행은 다른 축이다.** 두 판정을 모두 통과해야 매크로가 돈다.

*접근*은 매크로마다 정해진다. 기본은 비공개(만든 사람만)이고, 소유자가 공개로 열거나
협업자를 지정해 넓힌다. 판정은 포함 관계를 가지는 한 줄 사다리 하나로 끝난다
(`model.ResolveMacroAccess`):

| 등급 | 할 수 있는 것 | 누가 |
| --- | --- | --- |
| `view` | 조회, 실행, 실행 이력 열람 | 공개(조회) 매크로의 모든 매크로 권한자 |
| `edit` | + 새 버전 저장, 되돌리기, 이름·설명 변경 | 공개(수정 허용) 매크로의 모든 매크로 권한자 |
| `manage` | + 공개 설정, 협업자, 자동 실행 트리거 | 협업자 |
| `owner` | + 삭제 | 만든 사람, 슈퍼어드민 |

사다리를 하나로 둔 이유는 판정이 필요한 자리가 많아서다 — 조합으로 따지면 어딘가는
반드시 빠뜨린다. 여러 자격이 겹치면 가장 높은 것을 준다. 삭제만 협업자에게 열지 않는데,
이 기능에서 유일하게 되돌릴 수 없는 동작이기 때문이다(버전이 전부 함께 사라진다).

권한 없는 매크로에 대한 응답은 403이 아니라 **404**다. 403은 "그런 이름의 매크로가
있다"는 사실을 알려주고, 비공개 매크로에서는 그 사실 자체가 새어 나가면 안 된다.

*실행 권한*은 사람마다 다르므로, 매크로를 열 때 서버가 노드별 요구 권한을 훑어
"이 사람이 실행할 수 있는가"를 계산해 함께 내려보낸다. 화면은 그 결과로 이유를 적고 버튼을 막으며,
실행 시점에 엔진이 노드마다 다시 확인한다 — 화면을 조작해도 실행은 막힌다.

접근 판정은 HTTP 핸들러에만 있지 않다. `Engine.load`가 실행자 기준으로 다시 확인하는데,
자동 실행과 "다른 매크로 호출" 노드는 핸들러를 거치지 않기 때문이다. 이것이 없으면
공개 매크로 하나가 남의 비공개 매크로를 부르는 통로가 되고, 소유자가 매크로를 비공개로
되돌려도 남이 걸어 둔 트리거는 계속 돈다. 반대로 **노드 정의의 공개 설정은 실행에 관여하지
않는다.** 그러지 않으면 남의 비공개 전역 노드를 하나 쓰는 공개 매크로가 만든 사람 외에는
아무에게도 돌지 않는다 — 공개 설정은 팔레트에서 보이고 고칠 수 있는가를 정할 뿐이다.

**실행 모델은 제어 흐름 + 변수 가방이다.** 노드를 잇는 선은 "다음에 무엇을 실행하는가"만 나타내고
데이터는 변수로 오간다. 데이터 포트를 선으로 잇는 진짜 데이터플로우를 쓰지 않은 이유는,
DB 자동화에서 노드가 만드는 것은 대개 "행 목록" 하나인데 그것을 쓰는 쪽은 세 노드 뒤의 조건식이거나
Lua 스크립트 안이기 때문이다. 선으로 표현하면 화면이 선으로 뒤덮이고 정작 알고 싶은
"무엇이 어떤 순서로 실행되는가"가 묻힌다.

반복은 되돌아오는 간선이 아니라 **반복 노드가 몸통을 소유하는** 방식이다(`body` / `done` 포트).
되돌아오는 간선은 종료 조건이 어디에 있는지 보이지 않는다.

### Lua 샌드박스는 화이트리스트다

열어 주는 표준 라이브러리는 `base` · `table` · `string` · `math` 넷뿐이다. `io` · `os` · `package` ·
`debug`는 열지 않고, `base`에 딸려 온 `dofile` · `loadfile` · `load` · `loadstring` · `require`도 지운다.

전부 열고 위험한 것을 지우는 방식(블랙리스트)은 언젠가 하나를 빠뜨리고, 빠뜨렸다는 사실은
사고가 난 뒤에 알게 된다. `TestSandboxHasNoEscapeHatches`가 이 목록을 고정한다.

파일을 읽거나 명령을 실행하는 유일한 길은 호스트 함수(`sh.run`)이고, 그 함수는 서버 설정과
실행자 권한을 모두 확인한다. DB 접근(`db.query` / `db.exec` / `db.rows` / `db.mutate`)도 마찬가지로
`auth.Authorizer`를 통과한다 — 스크립트를 고쳐 우회할 수 있는 경로가 없다.

무한 루프는 **컨텍스트로 멈춘다**(`-macro-lua-timeout`). GopherLua에는 명령 수를 세는 훅이 없고,
있더라도 "몇 개의 명령이 정상인가"는 아무도 답할 수 없다. 반면 "한 노드가 1분 넘게 돌면 무언가
잘못됐다"는 판단은 할 수 있다.

### 셸 실행은 이중 게이트 뒤에 있다

`-allow-shell`(서버) **그리고** `script.run`(사용자) 둘 다 필요하다. 권한 설정은 화면에서 몇 번의
클릭으로 바뀌지만, 이 기능이 켜지는 순간 앱은 원격 셸이 된다. 그런 성격의 변경은 프로세스를 띄우는
사람이 정해야 한다(`-backup-cmd`를 플래그로만 받는 것과 같은 판단이다).

게이트를 통과한 뒤에는 명령을 걸러 내려 하지 않는다. 셸에서 무언가를 금지하는 것은 원리적으로
불가능하고(파이프, 인코딩, 인터프리터 호출), 반쯤 막힌 것을 안전하다고 부르는 편이 아무것도
막지 않는 것보다 위험하다. 여기서 할 수 있는 정직한 일은 **실행되는 것을 전부 기록하는 것**이다.

스크립트는 `-c "..."`가 아니라 임시 파일로 넘긴다. 인자 길이 제한과 플랫폼별 따옴표 처리 차이 때문에
조용히 다른 스크립트가 실행되는 일을 없애기 위해서다.

### 서버를 위로 뽑았지, 커넥션을 쪼개지 않았다

"커넥션 하나로 여러 DB를 관리한다"는 요구에는 두 가지 구현이 있다. 커넥션이 DB 목록을 직접
갖고 화면마다 DB 선택기를 두는 방법과, 접속 정보를 **서버**로 뽑아 그 아래에 DB를 다는 방법이다.
후자를 골랐다.

이유는 `connection_id`가 이 앱에서 **18개 테이블의 기준 단위**라는 데 있다 — 접근 권한·능력 등급·
지표·이벤트·드리프트·ERD 문서·스키마 버전·마이그레이션·백업·트리거가 전부 커넥션을 가리킨다.
커넥션 하나가 DB 여러 개를 품게 하려면 그 18개 전부에 database 차원을 더해야 하고, 무엇보다
**권한이 조용히 넓어진다**: 권한은 커넥션 단위이므로, 한 커넥션이 DB 열 개를 뜻하게 되는 순간
"이 DB만 허용"을 표현할 방법이 사라진다.

서버를 위에 두면 다운스트림은 그대로다. `model.Connection`은 접속 정보를 서버에서 조인해 채우므로
그것을 쓰는 코드는 서버가 생긴 것을 모른다. 권한은 DB 단위 정밀도를 유지한 채 서버 단위 일괄
부여만 얹으면 된다.

**환경(운영/개발)만은 DB에 남겼다.** 서버 속성처럼 보이지만 이 값이 실제로 뜻하는 것은
"이 대상을 얼마나 조심히 다룰 것인가"다(운영이면 승인 수와 확인 문구가 붙는다). 한 서버에 실운영
DB와 임시 DB가 함께 사는 일은 흔하고, 그때 둘을 같게 취급하면 안전장치가 필요 없는 쪽에 붙거나
필요한 쪽에서 빠진다. 서버는 "새 DB를 추가할 때의 기본값"만 갖는다.

**기존 커넥션은 자동으로 묶지 않는다.** 이관은 커넥션 하나당 서버 하나를 만든다.
`(종류, 호스트, 포트)`가 같으면 같은 서버처럼 보이지만 자격증명이 다를 수 있고, 비밀번호는 매번
다른 nonce로 봉인되어 있어 SQL로는 같은지 비교할 수조차 없다. 잘못 묶으면 한쪽 자격증명이 조용히
사라지고 그 사실은 다음 접속 실패로만 드러난다. 합치는 일은 값을 확인할 수 있는 사람이 화면에서
명시적으로 한다(서버 병합).

### 권한은 서버로 주고 DB로 뺀다

DB 열 개짜리 서버를 등록하면 체크박스를 열 번 눌러야 하고, DB를 추가할 때마다 모든 사용자의 권한을
다시 챙겨야 한다. 그 부담은 결국 "그냥 모든 DB 접근 가능으로 두자"로 이어진다 — 권한 모델이 있으나
마나 해진다. 그래서 서버 단위 일괄 부여를 얹었다.

판정 순서는 **좁은 쪽이 이긴다**: DB 오버라이드 > 서버 오버라이드 > 기본값. 반대로 두면 예외를 적을
수 없다. 접근 범위(allowlist/denylist)에서는 서버 항목이 그 아래 DB 전부를 뜻하며, 차단은 넓게
걸린다(어느 한쪽이라도 목록에 있으면 막힌다).

한 가지 규칙을 더 두었다. **DB 하나만 등급을 "없음"으로 내리면 서버에서 물려받은 데이터 능력도 함께
지운다.** 그러지 않으면 그 DB는 여전히 조회 가능한 채로 남는데 권한 화면에는 "없음"으로 보인다 —
화면이 거짓말을 하게 된다. 다만 그 DB에 능력을 따로 지정했다면 의도한 것이므로 남긴다.
(이 구멍은 테스트를 쓰다가 발견했다.)

### 자동 실행은 소유자의 권한으로 돈다

정기·조건 실행에서 답해야 하는 질문은 하나다: **누구의 권한으로 도는가.**

서비스 계정을 만들어 그 권한으로 돌리는 방법이 흔하지만 쓰지 않았다. 그러면 "툴은 호출자의
권한으로 실행된다"는 앱 전체의 규칙(어시스턴트·MCP·수동 실행이 모두 이 규칙을 따른다)이
자동 실행에서만 무너지고, 트리거를 만들 수 있는 사람은 누구나 서비스 계정의 권한을 빌려 쓸 수 있게 된다.

그래서 트리거는 **만든 사람**을 소유자로 고정하고(수정으로도 바뀌지 않는다), 발화할 때마다
소유자를 다시 읽어 그 사람의 권한으로 판정한다. 판정에는 화면·MCP와 **같은 함수**(`macro.Engine.Blockers`)를
쓴다 — 세 곳이 각자 계산하면 언젠가 답이 갈라지고, 갈라진 쪽이 자동 실행이면 아무도 알아채지 못한다.

대가는 명확하다. 소유자의 권한이 회수되거나 계정이 비활성화되면 그 트리거는 실패한다.
그것이 옳은 동작이다 — 사람이 못 하게 된 일을 그 사람이 만든 자동화가 계속하고 있으면 안 된다.
실패는 트리거 행에 이유와 함께 남고, 연속 실패가 쌓이거나 소유자가 사라지면 트리거는 스스로 꺼진다.

### 놓친 실행은 따라잡지 않는다

앱이 꺼져 있던 동안 지나간 실행은 건너뛴다(유예 1시간). 새벽 3시 정리 작업을 오전 9시에 실행하는 것은
대개 틀린 일이고, 밤새 꺼져 있었다면 여덟 번을 몰아 실행하게 된다. 재시작하면 다음 시각을 다시 잡고,
건너뛴 사실을 로그와 트리거 상태에 남긴다.

같은 이유로 이벤트 트리거의 디바운스 상태는 메모리에만 둔다. 재시작 뒤 첫 이벤트는 억제하지 않는 편이
안전하다 — 억제해서 잃는 것(대응이 늦는다)이 중복 실행보다 크다.

cron 해석은 라이브러리를 쓰지 않고 직접 구현했다(`internal/macro/cron.go`). 필요한 것은 표준 5필드이고
그것은 표 다섯 개와 "다음 시각 찾기" 한 함수로 끝난다. 반면 라이브러리를 들이면 자체 스케줄러 고루틴처럼
우리 실행 모델(소유자 권한·중복 방지·놓친 실행)과 어긋나는 것들이 함께 들어온다.
시간대 데이터(`time/tzdata`)는 바이너리에 넣는다 — Windows나 최소 컨테이너에는 시스템 tzdata가 없고,
"매일 새벽 3시(한국 시간)"가 배포 환경에 따라 다른 시각에 도는 것은 스케줄러로서 치명적이다.

### 외부 HTTP는 셸과 다른 게이트를 쓴다

`http.call`은 셸과 달리 **서버 플래그를 요구하지 않는다.** 셸은 켜지는 순간 앱이 원격 셸이 되지만,
HTTP는 이 앱이 이미 하고 있는 일(Git 연동, AI 프로바이더, 프로필 이미지 가져오기)과 같은 종류의
동작이다. 게이트를 하나 더 두면 실제로 막는 것 없이 설정만 늘어난다.

그래도 권한을 따로 둔 이유는 이것이 **데이터 반출 통로**이기 때문이다. 조회 권한과 결합하면
DB에서 읽은 값을 임의의 주소로 보낼 수 있다. "매크로를 쓸 수 있다"와 "외부로 내보낼 수 있다"는
따로 판단해야 한다.

**링크로컬 주소는 허용 목록에 적어도 막는다.** `169.254.169.254`(클라우드 메타데이터)는 인스턴스
자격증명을 그대로 내주며, 정상적인 매크로가 그곳을 부를 이유가 없다. 나머지 사설망은 기본 허용이다 —
사내 웹훅을 부르는 것이 이 기능의 주 용도인데 막아 두면 쓸 수 없다. 더 좁혀야 하면 `-macro-http-allow`로
목록을 정한다. 리다이렉트는 매 홉마다 다시 검사한다(공개 주소로 시작해 내부로 보내는 것이 SSRF의 전형이다).

### 분산 스토리지: DB가 아닌 것을 커넥션으로 다루는 이유 (`internal/storage`)

하둡(HDFS·YARN)과 Ceph를 커넥션으로 등록해 상태를 보고 관리한다.

**왜 커넥션인가.** 이들은 데이터베이스가 아니다. 그런데 접근 권한·자격증명 보관·지표 수집·
임계값·이벤트·알림은 전부 커넥션 단위로 이미 돌아간다. 스토리지만 따로 두면 그 여섯 가지를
한 벌 더 만들어야 하고, 사용자는 "권한을 어디서 주는가"를 대상마다 다시 배워야 한다. 대신
어댑터의 능력(Capabilities)에서 스키마·SQL·마이그레이션·ERD를 전부 끄고 `storage`만 켠다 —
화면은 그 값을 보고 메뉴를 감추므로 "테이블 목록이 비어 있는 하둡" 같은 상태가 생기지 않는다.

**REST만 쓴다.** HDFS RPC는 하둡 클라이언트 라이브러리를, librados는 C 라이브러리를 요구한다.
둘 다 단일 바이너리 원칙과 충돌한다. 관리 화면에 필요한 것(용량·목록·조작)은 WebHDFS·
NameNode JMX·YARN REST·Ceph 대시보드 API로 전부 된다.

**지표 이름은 종류를 넘어 공유한다.** 하둡의 데이터노드와 Ceph의 OSD는 둘 다 "데이터를 들고
있는 구성원"이므로 `storage.nodes.up/down` 하나로 본다. 상태도 마찬가지다 — Ceph의 HEALTH_*와
HDFS의 손실 블록·세이프모드를 `storage.health`(0 정상 / 1 주의 / 2 위험)라는 같은 눈금에 올린다.
그래야 임계값 룰을 종류마다 따로 만들지 않아도 되고, 기본 룰 다섯 개가 두 종류에 함께 걸린다.

**쓰기는 하둡만, 그것도 세어 보여준 뒤에.** HDFS의 디렉터리 만들기·이름 바꾸기·삭제는 지원한다
(data.write 능력 + 감사 로그). 재귀 삭제는 무엇이 사라지는지 먼저 세어 확인 대화상자에 보여준다 —
휴지통이 꺼져 있으면 되돌릴 방법이 없다. 루트(/)는 어떤 경우에도 지우지 않는다.
**Ceph는 조회 전용이다**: 풀 삭제·OSD out·CRUSH 변경은 되돌릴 수 없고 클러스터 전체의 데이터
배치를 바꾼다. 그 판단을 버튼 하나로 옮겨 놓는 것은 위험을 옮기는 것일 뿐이다.

### 클러스터: 쓰기를 한 곳으로 모은다 (`internal/cluster`)

여러 서버에서 DB Studio를 띄우고 하나처럼 다룬다. 구조는 **마스터-리플리카**다.

**왜 마스터가 하나인가.** 이 앱의 상태는 SQLite 파일 하나다. 여러 노드가 각자 쓰면 같은 행을 서로
다르게 고칠 수 있고, SQLite에는 그 충돌을 풀 방법이 없다. 쓰기를 한 곳으로 모으면 충돌이 **생기지
않는다** — "누가 이겼는가"를 나중에 사람이 조사하는 일이 없어진다. 대신 마스터가 멈추면 그동안
쓰기를 못 한다. 그때 리플리카는 읽기 전용으로 계속 동작하고(화면이 열리고 지표·이력이 보인다),
쓰기만 분명한 이유와 함께 거절된다.

**자동 승격은 하지 않는다.** 노드가 서로를 못 보는 동안 각자 자신을 마스터로 올리면 진실이 둘이 되고,
그 둘을 나중에 합칠 방법이 없다. 잠깐의 정지가 낫다. 승격은 운영자가 역할을 바꿔 재시작해서 한다.

**복제는 행 단위(논리 복제)다.** 마스터의 모든 표에 트리거를 달아 변경을 `repl_log`에 적고, 리플리카가
그 로그를 순서대로 적용한다. SQL 문장을 재실행하지 않는 이유는 `now()`·`random()`이 노드마다 다른
값을 만들기 때문이다 — 결과(행)를 나르면 그런 여지가 없다. 로그가 잘려 따라잡을 수 없거나 새 노드가
처음 붙을 때는 스냅샷(`VACUUM INTO`)을 받아 통째로 맞춘 뒤 그 지점부터 이어 간다.

**행을 맞출 때 REPLACE를 쓰지 않는다.** SQLite의 `INSERT OR REPLACE`는 충돌 행을 지우고 다시 넣는데,
그 삭제가 `ON DELETE CASCADE`를 깨운다. 사용자 행 하나가 복제될 때마다 그 사람의 세션이 통째로
사라졌고(증상은 "그 노드에서만 로그아웃된다"), 오류도 경고도 남지 않았다. 그래서 있으면 고치고
없으면 넣는다.

**쓰기 전달과 읽기 일관성.** 리플리카는 상태를 바꾸는 요청을 마스터로 넘기고(세션 쿠키를 그대로
싣는다 — 권한 판정은 언제나 마스터에서 그 사람의 자격으로 이뤄진다), 마스터가 응답에 실어 준 복제
지점까지 따라잡은 뒤에 답한다. 그러지 않으면 저장 직후 목록을 다시 읽을 때 방금 만든 것이 없다.

**담당 노드.** 사설망 안에 있어 특정 서버에서만 닿는 DB가 있다. 커넥션에 담당 노드를 지정하면 그
DB에 접속하는 요청(조회·질의·데이터 수정)은 어느 노드로 들어오든 그 노드에서 실행된다. 넘기는
경로는 허용 목록으로 관리한다 — 기본값이 "넘긴다"이면 메타 DB에 쓰는 새 경로가 리플리카에서
실행되어 그 기록이 조용히 사라진다.

**리플리카가 하지 않는 것**: 지표 폴링, 매크로 자동 실행, 호스트 지표 저장. 모두 메타 DB에 쓰는
일이고, 리플리카가 쓰면 다음 복제에서 사라진다. 대신 호스트 상태는 하트비트에 실려 마스터의 노드
목록에 남는다 — 각 서버의 CPU·메모리·디스크를 클러스터 화면 한 곳에서 본다.

### 알려진 제약

- **H2 미지원**: Pure Go 드라이버가 존재하지 않는다(자체 TCP 프로토콜/JDBC 전용). 지원하려면 JVM
  사이드카가 필요해 단일 바이너리 원칙과 충돌하므로, `kind` 목록에서 아예 제거했다 — 고를 수 없는
  항목을 목록에 남겨두는 것보다 없는 편이 낫다.
- **하둡의 Kerberos(SPNEGO)는 지원하지 않는다**: 의사(pseudo) 인증의 `user.name`과 프록시
  (Knox 등)의 기본 인증만 쓴다. 티켓 캐시와 keytab 관리가 필요해 단일 바이너리 범위를 넘는다.
- **Ceph는 대시보드(Manager) API가 켜져 있어야 한다**: 그 모듈이 없으면 상태를 읽을 수 없다.
  RGW가 없으면 버킷 목록은 비고, 그 사유를 화면에 적는다.
- **클러스터는 마스터-리플리카다**: 쓰기는 마스터 한 곳에서만 처리된다. 자동 승격이 없으므로
  마스터가 멈추면 그동안 **조회만** 가능하다(승격은 역할을 바꿔 다시 띄우는 운영 작업이다).
  ERD 실시간 편집은 리플리카가 마스터로 소켓을 중계해 방 하나로 모은다.
- **ERD 문서의 대상은 관계형 DB만**: MongoDB/Redis는 스키마 개념이 없어 초안 생성이 거부된다.
  대상 DB 없는 초안도 DB 문법은 관계형 종류 중에서 골라야 한다.
- **SQL 불러오기는 완전한 파서가 아니다**(`internal/sqlimport`): `CREATE/ALTER/DROP TABLE`,
  `CREATE INDEX`, `COMMENT ON` 만 읽는다. 뷰·함수·트리거·`INSERT` 같은 문장은 ERD에 담을 것이
  없어 건너뛴다. **건너뛴 문장은 화면에 그대로 나열한다** — 조용히 넘기면 사용자는 불러오기가
  끝난 뒤에야 빠진 것을 발견한다. 정의가 스크립트에 없는 테이블을 `ALTER` 하는 문장도
  같은 이유로 반영하지 않고 알린다(빈 테이블을 만들어 붙이면 초안의 기존 테이블이 덮어써진다).
- **구조 화면의 개인 배치는 커넥션 단위다**: 버전을 바꿔 봐도 배치는 하나를 공유한다.
  버전마다 따로 두면 시점을 옮길 때마다 정리를 다시 해야 한다.
- **구문 검사로 확인할 수 없는 문장이 있다**: `USE`·트랜잭션 제어처럼 준비만으로는 효과가
  나타나지 않는 문장, MySQL이 프리페어드 프로토콜에서 지원하지 않는 일부 문장이 그렇다.
  그런 문장은 "오류"가 아니라 **"확인 불가"** 로 구분해 표시한다 — 둘을 같은 색으로 보여주면
  사람은 멀쩡한 문장을 고치기 시작한다.
- **떠난 참여자 감지**: 정상 경로(페이지 이동·탭 닫기)는 즉시 정리되지만, 네트워크가 조용히
  끊긴 경우는 핑/퐁 타임아웃(60초)까지 프레즌스 목록에 남는다.
- **MongoDB / Redis**: 스키마 개념이 없어 ERD·마이그레이션 대상이 아니다(`Capabilities`로 표시).
  스키마 조회는 지원하지만 결과는 "정의"가 아니라 "관찰된 구조"다.
- **SQLite 마이그레이션 제약**: SQLite의 `ALTER TABLE`은 컬럼 추가/이름변경/삭제만 지원한다.
  컬럼 타입·제약 변경과 기존 테이블의 FK/체크제약 추가는 테이블 재작성이 필요하며,
  자동 생성 시 인덱스·트리거 복원까지 책임져야 해 위험하므로 DDL을 생성하지 않고
  계획에 경고로 남긴다. 테이블/컬럼 주석도 저장할 곳이 없어 ERD에서 주석을 달면
  그 차이는 수렴하지 않는다(계획 단계에서 경고한다).
- **롤백은 구조만 되돌린다**: 저장된 down SQL로 구조는 복구되지만 삭제된 데이터는 복구되지
  않는다. 되돌릴 수 없는 변경은 계획에 `irreversible`로 표시하고 실행·롤백 대화상자에서
  경고한다.
- **부분 적용 자동 복구 없음**: MySQL·Oracle에서 중간에 실패하면 적용된 문장을 정확히
  보여주되 자동으로 되돌리지는 않는다. 사람이 확인한 뒤 롤백하거나 직접 정리해야 한다.
- **Git 연동은 Bitbucket Cloud만 지원**: Bitbucket Server(Data Center)는 API가 다르다.
  Bitbucket은 저장소 응답에 권한 정보를 주지 않아 연결 확인에서 쓰기 권한을 미리 알 수 없다
  (실제 푸시에서 드러난다).
- **Git 푸시는 PR을 만들 뿐 병합하지 않는다**: 병합과 브랜치 삭제는 저장소 쪽 정책과
  CI에 맡긴다. 앱이 병합까지 하면 저장소의 보호 규칙을 우회하게 된다.
- **Oracle**: `ON UPDATE` 참조 동작을 지원하지 않아 DDL 생성 시 생략된다.
- **호스트 감시는 리눅스·윈도우만 온전하다**: macOS·BSD에서는 디스크와 부팅 시각만 읽고
  CPU·메모리·네트워크는 읽지 않는다(sysctl 이름과 구조체가 플랫폼마다 달라, 손으로 옮기다
  틀리면 그럴듯한 숫자가 나와 더 나쁘다). 못 읽는다는 사실은 화면에 남는다.
- **시스템 로그 감시의 범위**: 리눅스는 평문 syslog 파일(`/var/log/syslog`,
  `/var/log/messages`)을 읽는다. journald만 쓰는 시스템에서는 파일이 없어 감시가 꺼지며,
  `-host-syslog`로 경로를 지정할 수 있다(외부 명령 `journalctl`을 부르지 않는 이유는
  최소 이미지·컨테이너에서 그 명령이 없을 때의 실패가 조용하기 때문이다).
  윈도우는 이벤트 로그의 "시스템" 채널만 보며, 메시지 원문(소스 DLL로 포맷하는 문장)
  대신 **소스 이름 + 이벤트 ID + 삽입 문자열**을 보여준다.
- **호스트 지표는 롤업하지 않는다**: 호스트는 하나뿐이라 보존기간(기본 48시간) 안의 원본만
  둔다. 장기 추세는 이 앱이 답할 질문이 아니다 — 인프라 모니터링 도구의 몫이다.
- **AI 툴 루프 상한 8회**: 한 질문에 툴을 8번까지만 부른다. 상한에 걸리면 그 사실을
  화면에 알린다. 더 필요한 질문은 나눠 물어야 한다.
- **AI 대화는 프로바이더에 전송된다**: 툴 결과(스키마 구조, 지표, 로그 쿼리 텍스트)가
  프롬프트에 담겨 외부 API로 나간다. 자체 호스팅 LLM을 OpenAI 호환 주소로 등록하면
  데이터를 내보내지 않고 쓸 수 있다.
- **AI 제안은 새 질문에 만료된다**: 승인하지 않은 제안은 다음 사용자 메시지에서 만료된다.
  문맥을 잃은 승인 버튼이 한참 뒤에 눌리는 것이 더 위험하다.
- **모델별 비용·한도를 앱이 알지 못한다**: 허용 목록으로 "어떤 모델을 쓸 수 있는가"는 정하지만
  "얼마까지 쓸 수 있는가"는 정하지 못한다. 세션별 토큰 사용량은 집계하되 상한은 없다.
  모델 가격표를 앱에 넣으면 그것부터 낡기 시작하고, 틀린 금액은 없느니만 못하다.
- **사고 서명은 툴 호출에만 붙여 보관한다**: 텍스트 응답에 붙어 오는 서명은 저장하지 않는다.
  400을 내는 것은 함수 호출 쪽이고, 이력에 남길 자리를 늘리려면 메시지 표에 열이 하나 더
  필요하다 — 실제로 그것을 요구하는 사례를 만나면 그때 넣는 것이 맞다.
- **MCP는 HTTP 전송만**: stdio 모드가 없다. 그것은 같은 SQLite 파일을 여는 두 번째 프로세스를
  뜻하고 단일 인스턴스 전제와 어긋난다. stdio만 받는 클라이언트는 `mcp-remote` 등의 프록시가 필요하다.
- **MCP 인증은 Bearer 토큰**: OAuth 2.1(규약 권장)은 구현하지 않았다. 인가 서버·동의 화면·
  리프레시를 들여올 근거가 아직 없다. 토큰은 사용자별이며 발급자의 권한을 그대로 쓴다.
- **MCP에는 리소스·프롬프트가 없다**: `resources/list`와 `prompts/list`는 빈 목록을 돌려준다
  (메서드를 모른다고 답하면 일부 클라이언트가 연결 자체를 실패로 처리한다).
- **확인 문구가 필요한 동작은 MCP·REST API로 실행되지 않는다**: 운영 DB 복구, 파괴적 마이그레이션
  실행 등. 그 문구는 사람이 직접 타이핑하게 만드는 장치이므로 프로그램 경로에서 통과시킬 수 없다.
- **REST API는 툴 단위다**: 화면이 쓰는 `/api/v1/*`(커넥션 CRUD, 사용자 관리 등)을 토큰으로 열지
  않았다. 그쪽은 화면의 필요에 맞춰 바뀌는 내부 계약이고, 토큰으로 열면 화면을 고칠 때마다
  외부 스크립트가 깨진다. 툴 레지스트리는 그 반대다 — 이름과 스키마가 계약이고, 어시스턴트·MCP가
  이미 그 계약에 의존하고 있어 함부로 바뀌지 않는다.
- **REST API에 스트리밍이 없다**: 툴 하나를 부르면 끝날 때까지 기다린다(상한 6분, MCP와 같다).
  백업처럼 원래 배경에서 도는 작업은 툴이 작업 ID를 돌려주므로 상태를 다시 물어 확인하지만,
  마이그레이션 실행은 응답이 올 때까지 그 요청이 열려 있다.
- **REST API에 요청 수 제한이 없다**: 토큰은 발급자의 권한을 그대로 쓰고 모든 호출이 감사 로그에
  남지만, 초당 호출 수를 세지는 않는다. 필요하면 앞단 프록시에서 거는 것이 맞다.
- **데이터 마스킹 없음**: 데이터 조회 권한을 가진 사람은 값을 원본 그대로 본다. 컬럼 단위 가리기를
  넣으려면 "어떤 컬럼이 민감한가"를 정하는 규칙(이름 패턴? 태그? 수동 지정?)이 먼저 필요하고,
  그 결정이 기능 자체보다 크다. 지금은 조회 사실이 감사 로그에 남는 것으로 대신한다
  (테이블·조건 개수·검색 여부는 남기고 **조회된 값은 남기지 않는다** — 감사 로그가 유출 경로가 되면 안 된다).
- **전체 행 수는 요청해야 센다**: 페이지를 넘길 때마다 `count(*)`를 돌리면 큰 테이블에서 가장 비싼
  동작이 된다. 기본은 "다음 페이지가 있는가"만 알려주고(한 행 더 읽기), 전체 개수는 버튼을 눌러 센다.
- **백업은 논리 덤프만**: 파일 수준 스냅숏·시점 복구(PITR)는 하지 않는다. 그 자리에는
  `-backup-cmd` 훅이 있고, 조직이 쓰는 도구를 그대로 부르는 것이 맞다.
- **복구는 이 앱이 만든 백업만**: 외부 .sql 파일 업로드 복구는 없다. 그 통로는 SQL 콘솔
  (`sql.run` 권한)에 이미 있으며, 두 경로가 같은 능력을 가리키면 관문이 흐려진다.
- **복구는 트랜잭션 하나가 아니다**: MySQL·Oracle은 DDL이 암묵적 커밋이라 성립하지 않고,
  큰 덤프의 모든 문장을 메모리에 들고 있을 수도 없다. 대신 어느 문장에서 멈췄는지 기록한다.
- **Redis 컬렉션 타입 덤프는 근사값**: 해시·리스트·셋의 원소를 표시용 문자열(`", "`로 이은 것)에서
  되돌리므로, 값 안에 `", "`가 들어 있으면 원본과 다르게 복구된다. 문자열 키만 정확히 보장한다.
  Redis의 `DUMP`/`RESTORE` 바이너리 형식을 쓰지 않은 이유는 그것이 서버 버전에 묶여 있어
  다른 버전으로 복구하면 거부되기 때문이다(백업의 목적은 이식이다).
- **Oracle의 큰 바이너리는 덤프되지 않는다**: `HEXTORAW` 리터럴이 2000바이트로 제한된다.
  넘는 값은 NULL과 함께 그 사실을 주석으로 남긴다.
- **MongoDB 인덱스는 덤프에 없다**: 인덱스 생성은 서버 명령이라 문서 줄 형식에 담기 어렵다.
  담을 수 없는 것을 담은 척하지 않는다 — 복구 후 인덱스는 다시 만들어야 한다.
- **버전 롤백은 즉시 실행되지 않는다**: 마이그레이션 계획을 만들고 기존 승인 흐름을 탄다.
  운영 DB나 파괴적 변경이면 2명의 승인이 필요하다. 급할 때 답답하지만, 되돌리기라고 해서
  안전한 것이 아니다(그 버전 이후에 만들어진 테이블은 삭제된다).
- **구문 강조는 24,000자까지**: 그보다 긴 코드는 평문으로 그린다. 토큰마다 DOM 노드가
  생기므로 큰 덤프에서 브라우저가 멈추는 것을 막는다.
- **자동 실행은 분 단위**: cron의 최소 단위가 1분이고 스케줄러는 30초마다 확인한다. 초 단위 주기나
  "정확히 그 순간"은 표현할 수 없다. 조건 실행도 모니터링 폴링 주기(`-monitor-interval`)만큼 늦게 반응한다.
  모니터링을 끄면(`-monitor=false`) 이벤트가 생기지 않으므로 조건 트리거는 동작하지 않는다(화면이 알려준다).
- **매크로 반복 상한**: 반복 노드는 기본 1000회에서 멈추고, 한 실행의 노드 처리 횟수는 1만 회가 상한이다.
  반복이 있는 그래프는 정지 여부를 정적으로 알 수 없으므로 상한이 필요하다. 걸리면 로그에 남는다.
- **셸 노드는 앱이 도는 기계에서 실행된다**: 컨테이너 안이면 컨테이너 안이고, 격리(별도 사용자·
  자원 제한)는 앱이 아니라 배포가 책임진다. 기본은 꺼져 있다(`-allow-shell`).
- **Redis 표 편집은 문자열 키만**: 해시의 필드 하나, 리스트의 n번째 원소를 고치는 것은 각각 다른
  명령이고 화면도 달라야 한다. 표 한 칸을 고치는 UI로 그것을 표현하면 무엇을 바꾸는지 알 수 없으므로,
  컬렉션 타입은 명령 콘솔에서 다룬다.
- **Redis 탐색 결과는 표본 기반**: `SCAN` 표본이므로 그룹별 키 수와 크기는 근사값이다.
  타입·TTL·메모리는 표본 앞쪽 2천 개만 조사하며, 그 사실을 화면에 표시한다.
- **MongoDB 인덱스 사용 횟수는 서버 재시작 시 초기화**: `$indexStats`는 마지막 재시작 이후의
  누적치다. 가동 시간이 짧으면 "사용되지 않음"이 판단 근거가 되지 못하므로 화면에 함께 안내한다.
  `$indexStats` 권한이 없으면 0회가 아니라 "확인 불가"로 표시한다.
- **MEMORY USAGE가 막힌 Redis**: 관리형 서비스에서 이 명령이 비활성일 수 있다. 그 경우
  타입·TTL은 그대로 보여주고 크기·큰 키 목록만 비워진다.
  `TIME` 타입이 없어 `INTERVAL DAY TO SECOND`로 근사한다.
- **로그 소스는 DB 설정에 의존한다**: MySQL 슬로우 로그는 `slow_query_log=ON` +
  `log_output=TABLE`, PostgreSQL 통계는 `pg_stat_statements` 확장, MongoDB 프로파일러는
  `db.setProfilingLevel()`이 각각 필요하다. 앱은 이를 대신 켜지 않고(운영 DB 설정을
  임의로 바꾸는 것은 위험하다) 소스별 가용성과 활성화 방법만 화면에 표시한다.
  파일로만 기록되는 서버 로그는 SQL로 읽을 수 없어 조회되지 않는 경우가 있다.
- **SQLite는 로그 소스가 없다**: 서버 프로세스가 없으므로 슬로우 쿼리·세션 개념이 없다.
  `Capabilities().Logs = false`이며 로그 조회 요청은 400으로 거부된다.
- **로그 조회 권한은 모니터링 등급 기준**: 로그에는 실행된 쿼리 원문이 포함되고 그 안에
  리터럴 값(개인정보 등)이 들어갈 수 있다. 화면에서 이 사실을 사용자에게 알린다.
